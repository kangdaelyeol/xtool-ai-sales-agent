# PoC 측정 기록

브라우저 PoC(본 개발 전에 부품을 붙여 "되는지"를 확인한 단계)에서 잰 값을 날짜순으로 쌓는 기록입니다. 학습서와 다른 문서가 인용하는 지연·정확도 숫자의 원본이므로, 숫자가 어떤 조건에서 나왔는지 확인할 때 읽습니다. 부품이나 설정을 바꾸면 같은 방법으로 다시 재서 새 절을 더합니다. 무엇을 확인할지는 [3-poc-setup.md 4장](3-poc-setup.md#4-poc에서-확인할-것)에, 재는 순서는 [4-setup-checklist.md 5장](4-setup-checklist.md#5-검증-순서)에 있습니다.

> 측정 환경: 맥(M1 Pro, 서울) → 해외 API. 서버를 GCP 서울에 두면 값이 달라질 수 있습니다.

## 이 기록을 읽는 법 (2026-11-08 추가)

**공통 조건.** 아래 절은 모두 같은 맥(M1 Pro)에서 서울의 인터넷으로 해외 API를 부르며 쟀습니다. 음성을 거친 측정은 워커도 그 맥에서 개발 모드로 돌렸으므로, 턴 감지 모델은 클라우드 `v1`이었고 적응형 끼어들기도 켜져 있었습니다. 직접 운영(`start`)으로 띄우면 기본이 로컬 `v1-mini`와 적응형 끼어들기 꺼짐으로 바뀌므로 값이 달라질 수 있습니다([학습서 4-5절](1-study/04-worker-runtime.md#중요-개발과-운영에서-기본-모델이-다르다)). LiveKit 패키지는 모든 측정에서 `@livekit/agents`와 플러그인 1.9.5입니다(그때의 `pnpm-lock.yaml` 기준). 날짜는 절 제목에 있습니다.

**재는 방법.** 절마다 아래 넷 중 하나를 썼습니다.

| 방법 | 무엇을 거치나 | 쓴 곳 |
|---|---|---|
| `pnpm check:llm` ([scripts/check-llm.ts](../scripts/check-llm.ts)) | LLM만 거칩니다. 같은 요청을 되풀이해 첫 토큰까지의 시간과 출력 토큰 수를 셉니다 | 첫 측정의 "LLM 단독" |
| `lk agent debugger --audio` | 디버거가 고객 대사를 LiveKit Inference TTS로 읽어 에이전트 마이크에 넣습니다. STT·VAD·턴 감지·LLM·TTS를 모두 거칩니다. 고객 목소리가 합성음이고 전화 음질(8kHz)도 아닙니다 | 첫 측정의 "음성 전체 경로", STT 비교, Soniox 말 끝 판단 |
| 텍스트 디버거·텍스트 시뮬레이션 (`lk agent debugger`, `lk agent simulate text`) | STT·VAD·TTS를 건너뛰고 글로 대화합니다. 말 끝 판단과 TTS 지연이 없습니다 | 대화 품질, 답 길이, LLM 비교, 시나리오 시뮬레이션 |
| 두 경로를 번갈아 부르기 | 같은 요청을 Anthropic API와 Bedrock에 번갈아 보내 첫 토큰을 비교합니다. 다시 잴 때는 `pnpm compare:llm`([scripts/compare-llm.ts](../scripts/compare-llm.ts))을 씁니다 | Bedrock 도쿄 A/B |

**지연 지표.** 표에 나오는 세 구간은 SDK 메트릭과 이렇게 대응합니다([학습서 13-3절](1-study/13-latency.md#13-3-무엇을-재는가-livekit-메트릭의-정확한-의미)).

| 이 문서의 말 | SDK 메트릭 | 재는 구간 |
|---|---|---|
| 말 끝 판단 | EOU 메트릭의 `endOfUtteranceDelayMs` | 고객의 마지막 말소리 → 워커가 턴을 확정한 때. VAD가 무음을 확인하는 256ms와 STT 확정(FINAL 도착)이 이 안에 들어 있습니다 |
| LLM 첫 토큰 | LLM 메트릭의 `ttftMs` | LLM에 요청을 보냄 → 첫 토큰이 옴 |
| TTS 첫 음성 | TTS 메트릭의 `ttfbMs` | 글을 TTS 공급사에 보내기 직전 → 플러그인이 첫 오디오 프레임을 내놓음. 문장을 모으는 시간과 방까지 가는 길은 빠집니다([학습서 10-2절](1-study/10-tts.md#ttfb)) |

- **합계는 구간마다 따로 잰 값을 더한 것입니다.** 문장 모으기와 양 끝의 네트워크·재생이 빠져 있어, 고객이 실제로 기다리는 시간보다 짧습니다([학습서 1-3절](1-study/01-big-picture.md#지연은-어디서-오나-구성식에-poc-숫자-넣기-2026-11-05-추가)).
- **"목표" 칸은 잰 값이 아닙니다.** [2-tech-stack.md 8장](2-tech-stack.md#8-응답-지연-예산)이 정한 구간별 목표입니다.
- **"0.38∼0.54초" 같은 범위는 잰 턴들의 최솟값∼최댓값입니다.** 표본이 작아 평균 대신 범위를 적었습니다. 평균만 보면 가끔 느린 턴(꼬리)이 가려집니다([학습서 13-6절](1-study/13-latency.md#13-6-평균이-아니라-꼬리를-본다)).
- 대부분 한두 번 돌린 결과라 표본이 작습니다. 뒤에 밝혀진 사실과 어긋나는 해석에는 단서를 달았습니다(문단에는 "(2026-11-08 추가)" 표시). 잰 값은 그대로 두었습니다.

### 대화 품질 (텍스트, 판정 흐름 한 통화)

- 첫 멘트(고정 문장, AI·녹음 고지)부터 판정 질문 8개, 마무리 요약까지 끝까지 진행됐습니다.

| 고객이 한 말 | STT 결과 |
|---|---|

- 텍스트 디버거와 텍스트 시뮬레이션은 STT를 거치지 않아 이 보정도 타지 않습니다. 단위 테스트로 확인합니다.
- **Soniox(`stt-rt-v5` + context.terms)와 같은 문장으로 비교해야 합니다.** STT 선택의 핵심 지표입니다.

### 턴 감지

- 고객이 두 문장을 말하며 사이에 쉬면, 첫 문장("…하려고요.")에서 턴이 끝났다고 보고 AI가 답을 시작했다가 끊기는 경우가 있었습니다.
- 문법적으로 끝난 문장이라 턴 감지 판단 자체는 이상하지 않습니다. 실제 마이크 통화(`lk agent console`)에서 자주 나오면 `turnHandling.endpointing.minDelay`(기본 0.5초)를 늘려 봅니다.
  - (2026-11-08 추가) 이 구성에서는 minDelay 기본값이 0.5초가 아니라 0.3초입니다. 오디오 턴 감지 모델을 쓰면 SDK가 기본을 minDelay 300ms·maxDelay 2,500ms로 바꿉니다(`voice/turn_config/endpointing.ts`). 또 이 프로젝트에서는 턴 확정 시각을 대개 Soniox의 확정 글(FINAL) 도착이 정합니다(실제 확정은 말 끝 뒤 약 0.38∼0.64초). 그래서 minDelay를 올려도 FINAL이 오는 시각보다 작으면 효과가 없습니다([학습서 7-4절](1-study/07-turn-taking.md#끝점-지연endpointing-delay)).
- 로그에 `VAD inference is slower than realtime` 경고가 두 번 나왔습니다. 맥에서 디버거 TTS와 같이 돌 때 생긴 것으로 보이며, 서버에서 다시 확인합니다. 이 경고는 VAD가 창 하나(32ms 분량의 소리)를 처리하는 데 200ms 넘게 걸렸다는 뜻입니다(`inference/vad.ts`의 `SLOW_INFERENCE_THRESHOLD_MS`, [학습서 5장](1-study/05-vad.md)).

## 2026-11-03 STT 비교 1차 (같은 문장 5개, `lk agent debugger --audio`)

문장은 디버거가 LiveKit Inference TTS로 읽어 에이전트 마이크에 넣습니다. 사람 목소리·전화 음질(8kHz)은 아니므로 실제 녹음 비교는 따로 해야 합니다. 전화 음질에서 무엇이 빠지는지는 [학습서 2장](1-study/02-audio.md#4khz-위가-비어-있다는-말의-뜻-2026-11-08-추가)에 있습니다.

표의 Deepgram 칸은 보정 전 원문입니다. 칸 안의 `/`는 서로 다른 두 결과를 나란히 적은 것이고, "정확"은 말한 문장과 글자가 같다는 뜻입니다.

| 말한 문장 | Deepgram `nova-3` 원문 | Soniox `stt-rt-v5` |
|---|---|---|
| 에프투 울트라로 가죽 지갑에 각인하려고요. | F two 울트라로 가죽 지갑에 각인하려고요. | F2 울트라로 가죽 지갑에 각인하려고요. |
| 메탈팹이랑 피쓰리도 같이 보고 있어요. | 메탈 팩이랑 P 3도 / Mecharpack이랑 P 3 | 메탈팹이랑 P3도 같이 보고 있어요. |
| 엑스툴 제품 중에 엠투나 오원도 괜찮나요? | 제품 중에 M two나 O one도 (엑스툴 빠짐) | 엑스툴 제품 중에 M2나 O1도 괜찮나요? |
| 예산은 이백구십만 원 정도고, 할부로 하고 싶어요. | 예산은 이 백 구 십 만 원 정도고 로 하고 싶어요. (**할부 빠짐**) | 예산은 2,900,000원 정도고, 할부로 하고 싶어요. |
| 다음 주 토요일 오후 세 시쯤 방문할게요. | 정확 | 다음 주 토요일 오후 3시쯤 방문할게요. |

- Deepgram 지연: 말 끝 판단 0.38∼0.41초(첫 턴 1.13초). LLM 첫 토큰 0.86∼1.86초.
- 보정표(`MISHEARD_TERMS`)에 P3·M2·O1의 영문 표기를 추가했습니다. "할부"처럼 **통째로 빠진 단어는 보정으로 살릴 수 없어** STT 선택으로 해결해야 합니다.
- 고친 버그: Soniox 플러그인도 import 시점에 `SONIOX_API_KEY`를 읽어 두어 키를 못 찾았습니다. 생성할 때 직접 넘기도록 고쳤습니다(`src/models/index.ts`).

- **Soniox는 5문장 모두 정확**했습니다. 제품명은 보정 전 원문부터 맞았습니다(`context.terms` 효과로 보임). 숫자는 아라비아 숫자로 적습니다.
- 대신 Soniox의 말 끝 판단이 더 느립니다: 0.57∼1.42초 (Deepgram 0.38∼0.41초). LLM 첫 토큰은 0.76∼1.63초.
- **판단: 기본 STT는 Soniox로 유지.** 다음 과제는 Soniox 끝점 설정(`maxEndpointDelayMs`, `endpointLatencyAdjustmentLevel`) 조정으로 말 끝 판단을 0.5초 안팎으로 줄이는 것입니다.

## 2026-11-03 Soniox 말 끝 판단 줄이기

| 단계 | 말 끝 판단 (5턴) | 비고 |
|---|---|---|
| 기본 설정 | 0.57∼1.42초 | |
| + `endpointLatencyAdjustmentLevel: 3`, 언어 자동 감지 끔 | 0.40초 ×3, 1.26·1.29초 ×2 | 느린 턴은 Soniox가 최종 결과를 늦게 보낸 것 (받아쓰기 확정 지연 1.26초) |
| **+ 말이 끝나면 수동 확정(`finalize`)** | **0.38∼0.54초 (10턴 모두)** | 1초 넘는 턴이 사라짐 |

- 원인: LiveKit 코어는 VAD가 말 끝을 감지해도 STT에 알리지 않고, Soniox 플러그인은 flush 신호를 무시합니다(자세한 분석은 [학습서 6-5절](1-study/06-stt.md#6-5-사례-연구-13초-늦던-턴을-05초로수동-확정-패치)).
- 해결:
  - 고객 상태가 speaking → listening으로 바뀌면 STT 스트림에 flush를 보냅니다 (`src/models/soniox.ts`, `src/main.ts`).
  - 플러그인 패치로 flush를 Soniox `{"type":"finalize"}` 요청으로 바꿉니다 (`patches/@livekit__agents-plugin-soniox@1.9.5.patch`).
- 정확도는 그대로였습니다. 10턴 중 1번 "피쓰리"를 `F3`로 적은 경우가 있어 지켜봅니다.
- **이제 병목은 LLM 첫 토큰입니다** (같은 측정에서 0.99∼1.69초). 다음 과제입니다.

## 2026-11-03 즉시 반응 ("네네")

- 고객 말이 끝나자마자(`onUserTurnCompleted`) "네네." / "네." / "아, 네."를 돌아가며 먼저 말하고, 그동안 LLM이 본 답을 만듭니다 (`src/ack.ts`, `src/agent.ts`).
- 즉시 반응은 대화 기록에 넣지 않습니다. LLM이 따라 하지 않게 하고 프롬프트 캐시도 유지하려는 것입니다.
- 프롬프트로 "답을 '네'로 시작하지 말라"고 해도 3/3회 "감사합니다", "아,", "네,"로 시작해서 "네네. 네, …"처럼 겹쳤습니다. 그래서 LLM 출력 첫머리의 맞장구를 코드로 뗍니다 (`llmNode` 훅). 적용 후 4/4회 깨끗했습니다.
  - (2026-11-08 추가) 지금 구현([src/ack.ts](../src/ack.ts))은 첫머리 맞장구를 최대 두 개까지 떼고, 맞장구인지 판단할 수 있을 때까지만 첫머리를 모아 둡니다([학습서 11-7절](1-study/11-session-pipeline.md#11-7-llmnode-재정의-첫머리-맞장구-떼기)).

| 경우 | 고객 말이 끝나고 첫소리까지 |
|---|---|
| 이전 (본 답만) | 약 1.4∼1.6초 |
| **즉시 반응 적용** | **약 0.6∼0.8초** (말 끝 판단 0.41∼0.64초 + TTS 0.17초) |
| 본 답 시작 | 약 1.4초 (즉시 반응 뒤에 이어짐) |

(2026-11-08 추가) 이때는 즉시 반응도 그때그때 TTS로 합성했으므로 "TTS 0.17초"가 들어 있습니다. 같은 날 즉시 반응을 미리 합성하도록 바꿔(아래 "개선 묶음") 이 몫은 빠질 것으로 보지만, 실제 통화로는 아직 재지 않았습니다([학습서 13-5절](1-study/13-latency.md#즉시-반응-미리-합성-2026-11-03-갱신-구현됨)).

- 남은 점:
  - 본 답이 다시 길어지는 경향이 있습니다. "∼하시는군요"로 고객 말을 되풀이한 뒤 질문을 두 개 붙입니다.
  - 즉시 반응과 본 답 사이의 틈은 사람 목소리로 들어 봐야 합니다(`lk agent console`). 어색하면 즉시 반응 음성을 미리 합성해 두거나, 반응 종류를 늘립니다(미리 합성은 같은 날 붙였습니다. 아래 "개선 묶음").

### Bedrock 도쿄 A/B (2026-11-05, 맥에서 측정)

|---|---|---|---|
| Anthropic API | 0.77초 | 0.87초 | 0.74초 |

(2026-11-08 추가, 확인 필요) **Haiku 4.5의 `jp.` 프로필.** 표의 Bedrock 줄은 `jp.`(도쿄) 추론 프로필로 기록돼 있습니다. 그런데 Anthropic의 예전 Bedrock 연동 문서(Opus 4.6 이하를 다루는 페이지, 2026-11-08 확인)의 추론 프로필 표에서 Haiku 4.5 행은 `global`·`us`·`eu`만 "Yes"이고 `jp`는 "No"입니다. 그날 실제로 부른 모델 ID를 남기지 않아, 요청이 정말 일본 안에서 처리됐는지는 확인이 필요합니다. 도쿄 리전에서 `aws bedrock list-inference-profiles --region ap-northeast-1`을 보내 Haiku 4.5의 `jp.` 프로필이 있는지 보면 가릴 수 있습니다. 표의 값은 그대로 둡니다. 어느 프로필이었든 서울에서 도쿄 끝점(`bedrock-runtime.ap-northeast-1`)에 붙어 잰 값이라는 점은 같습니다(학습서 13-5절).

- 프롬프트 캐시는 효과가 없었습니다(약 3,300토큰, 캐시 있음·없음 차이가 측정 오차 안). "hi" 한 단어 요청도 0.7초라, 첫 토큰의 대부분은 네트워크와 서버 대기입니다.
  - (2026-11-08 추가) Haiku 4.5가 캐시하는 최소 길이는 4,096토큰입니다(Anthropic 문서). 약 3,300토큰이던 이 요청은 캐시 항목이 아예 생기지 않았을 가능성이 큽니다(그날 usage를 남기지 않아 확인 못 함). 그러니 "캐시가 소용없다"가 아니라 "캐시가 돌지 않은 비교"로 읽습니다. 운영 모델 Haiku 5.5의 최소는 512토큰이라 이 지시문이면 캐시가 돕니다([학습서 8-4절](1-study/08-llm.md#요청-사이의-프롬프트-캐시)).
- **판단:** 도쿄로 옮기면 턴마다 약 0.1초 줄어듭니다. Haiku 5.5가 열리면 `LLM_PROVIDER=bedrock`으로 바꾸고 `pnpm compare:llm`으로 다시 확인합니다.
  - (2026-11-08 추가) 바꾸기 전에 볼 것이 하나 더 있습니다. 이 레포의 Bedrock 경로(`AnthropicBedrock`, InvokeModel)는 Anthropic 문서가 "예전 연동"으로 나누는 길입니다. 그 문서는 이 연동이 지원하지 않는 기능으로 최상위 `cache_control`, 곧 이 레포가 쓰는 자동 캐시를 적습니다. 400으로 거절되는지, 캐시 없이 조용히 도는지는 아직 모릅니다. 그래서 먼저 400이 나는지, 2회차의 `cached tokens`가 0인지 봅니다. `pnpm check:llm`은 `LLM_PROVIDER`를 읽지 않고 늘 Anthropic API로 재므로(`scripts/check-llm.ts`) 이 확인에 쓸 수 없습니다([학습서 8-8절](1-study/08-llm.md#응용-연결만-바꿔-끼우기-bedrock-클라이언트-2026-11-05-추가)). 캐시가 돌지 않으면 매 턴 지시문 전체를 다시 처리하므로 첫 토큰이 수십 ms(추정) 늘고 입력 요금도 늘어, 위 0.1초 이득의 일부를 잃습니다.
- 계정 설정에서 겪은 것(자세한 경과와 이론은 [학습서 16장](1-study/16-cloud-accounts-iam.md)):
  - 무료 플랜은 리전 하나만 열려 있어 업그레이드가 필요했습니다.
  - 조직 정책(SCP)이 Bedrock API 키(bearer)와 멤버 계정의 사용 목적 제출을 막았습니다. 그래서 IAM 액세스 키를 쓰고, 사용 목적은 관리 계정에서 냈습니다.
  - Mantle(Anthropic API 호환 주소)의 도쿄에는 Haiku 5.5가 없어서 bedrock-runtime 경로를 씁니다.
