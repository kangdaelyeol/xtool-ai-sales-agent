STT가 고객 말을 글로 바꾸면, LLM이 그 글과 지금까지의 대화를 읽고 다음에 할 말을 만듭니다. 이 프로젝트는 Anthropic의 **Claude Haiku 5.5**(`claude-haiku-5-5`)를 씁니다. 이 장은 LLM이 글을 만드는 원리에서 시작해, **왜 생각 모드를 껐는지, 왜 프롬프트 캐시를 켰는지, 왜 temperature를 보내지 않는지**를 원리로 설명합니다. 마지막으로 플러그인을 감싸 필요한 옵션을 넣는 기법([src/models/anthropic.ts](../../src/models/anthropic.ts))을 해부합니다.

(2026-11-06 추가) 이번 판에서는 절마다 "깊이 보기"를 붙여 숫자와 바이트 수준까지 내려갑니다. 로짓을 확률로 손 계산하고(8-2), 프리필과 디코드가 왜 서로 다른 자원에 막히는지와 첫 토큰 지연의 구간을 따지고(8-3), 어텐션과 KV 캐시 메모리를 손으로 풀고 프롬프트 캐시가 어디에 쓰이고 어디서 읽히며 얼마인지 계산합니다(8-4). 가짜 서버로 플러그인이 실제로 보내는 요청과 받는 SSE를 바이트로 찍고(8-6), 오류마다 재시도가 되는지와 최악의 침묵을 계산합니다(8-7). 실습 스크립트 4개는 모두 키와 외부 네트워크 없이 돌아갑니다. 주장마다 **코드로 확인**, **실측**, **추정**, **문서 기준**을 구분해 적었습니다. ## 8-1. LLM은 "다음 토큰"을 맞히는 기계다

### 토큰

LLM은 글자를 그대로 다루지 않고 **토큰**이라는 조각으로 자른 뒤 각 조각을 번호로 바꿉니다. 자주 나오는 문자열은 하나의 토큰이 되고, 드문 문자열은 여러 토큰으로 쪼개집니다(BPE 같은 하위 단어 분할 방식).

```text
"안녕하세요, 고객님."  →  [안녕] [하세요] [,] [ 고객] [님] [.]   (분할 예시일 뿐, 실제 경계는 모델마다 다름)
```

- 영어는 대략 단어 하나가 토큰 1~1.5개입니다. **한국어는 같은 의미를 담는 데 토큰이 더 많이 드는 경향**이 있습니다. 학습 데이터에 영어가 많아 영어 조각이 더 큰 단위로 묶여 있기 때문입니다.
- 비용, 속도, 길이 제한이 모두 토큰 단위로 계산됩니다. "오십 자 안팎으로 말하라"는 지시(9장)가 비용과 속도에도 직결되는 이유입니다.

(2026-11-06 추가) **BPE가 한국어를 자르는 방식(일반 원리).** 흔한 바이트 단위 BPE는 글을 먼저 UTF-8 바이트로 바꾸고, 256개 바이트에서 출발해 학습 글에서 **가장 자주 붙어 나오는 두 조각을 하나로 합치는** 일을 수만 번 되풀이해 어휘를 만듭니다. 한글 한 글자는 UTF-8로 3바이트입니다("안" = `EC 95 88`, "녕" = `EB 85 95`). 자주 나오는 글자는 3바이트가 합쳐져 토큰 하나가 되고, "안녕하세요"처럼 아주 흔한 말은 여러 글자가 한 토큰이 되기도 하며, 드문 글자는 바이트 조각 2~3개로 남습니다. 학습 글에 영어가 많으면 영어 조각이 더 길게 합쳐지므로, 같은 뜻에 한국어 토큰이 더 많이 듭니다. Claude의 토크나이저가 정확히 이 방식인지와 어휘는 공개되지 않았습니다.

(2026-11-06 추가) **이 프로젝트의 숫자.**

- 지금 지시문(`buildInstructions(SAMPLE_CALL)`, 지식 파일은 비어 있어 빠짐)은 **3,004자, UTF-8로 6,886바이트**입니다. 한글 1,936자가 3바이트씩(5,808B), 영문·숫자·기호·공백·줄바꿈 1,061자가 1바이트씩, 나머지 7자(`·` 넷은 2바이트, `→` 셋은 3바이트, 합 17B)입니다(실측: 직접 셈). (2026-11-06 갱신) 17-2 #34에서 말하는 방식 예시의 "아, "(한글 1자 + 쉼표·공백)를 빼서 3,007자·6,891바이트에서 3자·5바이트 줄었습니다.
- [5-poc-results.md](../5-poc-results.md)의 "2회차부터 2,384토큰 캐시 적중"은 지금 지시문의 값이 아닙니다. 측정 기록이 처음 들어간 커밋(`5cb4046`)의 **요청 전체**를 되풀이해 잰 값입니다. 그때 요청은 도구 없이 지시문 2,291자(5,257B) + `(empty)` 7자 + 첫 멘트 109자 + 고객 말 48자, 모두 2,455자였습니다(당시 코드를 꺼내 같은 가상 고객으로 다시 만들어 셈).
- 나누면 **글자당 약 0.97토큰**입니다(추정: 측정이 한 번이고 메시지 틀의 토큰이 섞임). 영어는 글자당 약 0.25토큰이니, 같은 글자 수면 한국어가 약 4배 듭니다. 이 비율로 지금 지시문은 약 2,900토큰입니다(추정).
- 정확한 값은 `count_tokens` API(`POST /v1/messages/count_tokens`)로 잽니다. 요청과 같은 모양(system, tools, messages)을 받아 입력 토큰 수만 돌려주고, **무료**지만 분당 요청 수 제한이 있고 API 키가 필요합니다. 돌려주는 값은 추정치이며, 토크나이저가 모델마다 달라 `model`을 `claude-haiku-5-5`로 줘야 합니다(문서 기준). 절별로 누적해 재는 스크립트 스케치는 [9-2절 깊이 보기](09-prompt-design.md#깊이-보기-토큰은-글자-수로-정해지지-않는다--count_tokens로-재기-2026-11-06-추가)에 있습니다(제안, 키가 필요해 재지 않음).

### 자기회귀 생성

LLM이 하는 일은 단 하나입니다. **지금까지의 토큰을 보고, 다음 토큰의 확률 분포를 계산합니다.** 그중 하나를 뽑아 뒤에 붙이고, 다시 전체를 보고 다음 토큰을 계산합니다. 이것을 반복합니다.

```text
입력: [system 지시문 …] [user: 가격 얼마예요?] [assistant:]
 1단계 → 다음 토큰 후보: "정확" 41%, "가격" 22%, "죄송" 9% …  → "정확" 선택
 2단계 → [... assistant: 정확]  → "한" 88% …                    → "한" 선택
 3단계 → [... assistant: 정확한] → " 금액" 63% …               → " 금액" 선택
 … "담당 상담사가 안내드릴게요." 까지 반복, 끝 토큰이 나오면 멈춤
```

이 방식을 **자기회귀(autoregressive)** 생성이라고 합니다. 두 가지 결과가 따라옵니다.

1. **답은 앞에서부터 한 토큰씩 나옵니다.** 그래서 다 만들기 전에 앞부분을 먼저 TTS로 보낼 수 있습니다(스트리밍). 음성 에이전트의 지연을 줄이는 핵심 성질입니다.
2. **답이 길수록 오래 걸립니다.** 토큰 하나에 일정 시간이 드니, 길이에 비례합니다.

### 트랜스포머와 어텐션 (아주 짧게)

현대 LLM은 **트랜스포머**라는 신경망 구조입니다. 핵심 부품인 **어텐션**은 "지금 다음 토큰을 정할 때, 앞의 어떤 토큰들을 얼마나 참고할지"를 계산합니다. 예를 들어 "F2 울트라 맞으시죠?"를 만들 때 어텐션은 지시문의 "문의 기기: F2 울트라" 부분에 크게 주목합니다. 대화 기록 전체가 매번 입력으로 들어가야 하는 이유가 이것입니다. LLM에는 별도의 기억 장치가 없고, **입력 창(컨텍스트) 안에 있는 것만** 참고할 수 있습니다.

## 8-2. 샘플링과 temperature, 그리고 Haiku 5.5의 제약

"확률 분포에서 하나를 뽑는" 방법을 **샘플링**이라고 합니다.

| 파라미터 | 뜻 |
| --- | --- |
| `temperature` | 분포를 뾰족하게(낮을수록 항상 1등만) 또는 평평하게(높을수록 다양하게) 만듭니다 |
| `top_p` | 누적 확률 p 안에 드는 후보들 중에서만 뽑습니다 |
| `top_k` | 상위 k개 후보 중에서만 뽑습니다 |

예전에는 "정확한 답이 필요하면 temperature를 0으로"가 흔한 요령이었습니다. 그런데 **Claude Haiku 5.5는 기본값이 아닌 sampling 값을 보내면 400 오류로 거절합니다.** 그래서 [src/models/anthropic.ts](../../src/models/anthropic.ts)는 `temperature`를 아예 보내지 않고, 테스트가 이를 확인합니다.

```ts
// src/models/anthropic.test.ts
expect(lastBody).not.toHaveProperty('temperature');
```

출력의 일관성은 샘플링 파라미터 대신 **지시문과 예시**(9장), 그리고 **코드 후처리**(`withoutLeadingAck`, 12장)로 확보합니다.

(2026-11-06 추가) 문서는 Haiku 5.5가 API 버전 `2023-06-01`에서는 기본값이 아닌 sampling 값을, 최신 버전 `2026-10-21`에서는 값이 무엇이든 거절한다고 적습니다(문서 기준). 플러그인의 SDK 0.33은 `anthropic-version: 2023-06-01` 머리글을 보냅니다(8-6절 실습, 실측).

#### 깊이 보기: 로짓에서 확률까지 손으로 (2026-11-06 추가)

모델의 마지막 층은 어휘의 모든 토큰마다 실수 하나를 냅니다. 이것이 **로짓(logit)**입니다. "얼마나 그럴듯한가"의 점수라 음수도 되고 합이 1도 아닙니다. 5장의 로짓 ln(p/(1−p))은 후보가 둘일 때의 같은 개념이고, 후보가 수만 개일 때는 **소프트맥스(softmax)**로 확률로 바꿉니다.

```text
p_i = e^(z_i / T) / Σ_j e^(z_j / T)        z: 로짓, T: temperature
```

8-1절 그림의 첫 단계에서 후보 셋만 남았다고 하고 로짓을 (3.0, 2.5, 1.5)로 둡니다(지어낸 숫자).

| | 정확 | 가격 | 죄송 | 합 |
| --- | --- | --- | --- | --- |
| T = 1: e^z | 20.09 | 12.18 | 4.48 | 36.75 |
| T = 1: 확률 | **0.547** | 0.331 | 0.122 | 1 |
| T = 0.5: e^(z/0.5) | 403.43 | 148.41 | 20.09 | 571.93 |
| T = 0.5: 확률 | **0.705** | 0.259 | 0.035 | 1 |
| T = 2: 확률 | 0.444 | 0.346 | 0.210 | 1 |

- 1등과 2등의 확률 비는 e^(Δz/T)입니다. Δz = 0.5이므로 T = 1이면 1.65배, T = 0.5면 e ≈ 2.72배, T = 2면 1.28배입니다. T를 낮추면 차이가 벌어지고(뾰족), 높이면 좁혀집니다(평평). T → 0이면 1등만 남는 **탐욕 디코딩**이 됩니다(T = 0.05면 1.0000 / 0.0000 / 0.0000).
- 로짓 전체에 같은 수 c를 더해도 확률은 그대로입니다. e^(z+c) = e^c·e^z이고 e^c는 분모·분자에서 약분됩니다. 그래서 구현은 **최댓값을 뺀 뒤** 지수를 취해 넘침을 막습니다. 로짓 + 1000을 그대로 지수로 바꾸면 float64에서도 무한대가 되어 NaN이 나옵니다(실습).

**top-p 0.9**는 확률이 큰 순으로 더해 0.9 이상이 되는 가장 작은 집합만 남기고, 남은 것끼리 다시 나눕니다.

- T = 1: 0.547 → 누적 0.878(아직 0.9 미만) → 0.122를 더해 1.0. **셋 다 남습니다.** 이 분포에서 top-p 0.9는 아무것도 자르지 않습니다.
- T = 0.5: 0.705 → 누적 0.965(0.9 이상). **"죄송"이 잘리고**, 둘을 다시 나누면 0.705 ÷ 0.965 = 0.731, 0.269입니다.
- top-k 2(T = 1)는 개수로 자릅니다. 20.09 ÷ (20.09 + 12.18) = 0.622, 0.378입니다.

같은 top-p라도 temperature에 따라 자르는 양이 달라집니다. 흔한 구현은 temperature를 먼저 적용하고 top-p·top-k를 겁니다. Claude가 내부에서 어떤 순서와 기본값으로 뽑는지는 공개되지 않았습니다.

**뽑기와 문장의 확률.** 0~1 사이 난수 r을 누적표 [0, 0.547) → 정확, [0.547, 0.878) → 가격, [0.878, 1) → 죄송에 떨어뜨려 고릅니다(역변환 뽑기). 시드를 고정해 1만 번 뽑으면 T = 1에서 54.8%, 32.8%, 12.4%가 나와 확률과 맞습니다(실습). 문장의 확률은 단계별 확률의 곱입니다. 8-1절 그림의 세 단계(0.41, 0.88, 0.63)를 곱하면 0.227이고, 토큰 60개가 모두 0.9여도 0.9^60 ≈ 0.0018입니다. 그래서 모델과 디코더는 확률 대신 로그 확률을 더합니다(6장 CTC와 같은 이유).

이 프로젝트와의 연결: Haiku 5.5에서는 sampling 값을 바꿀 수 없으므로, 우리가 바꿀 수 있는 것은 **로짓을 만드는 입력**, 곧 지시문과 대화 기록뿐입니다. 거꾸로 구조화 출력(8-11절)은 허용되지 않는 토큰의 로짓을 −∞로 만들어 확률을 정확히 0으로 만드는 방법입니다.

직접 돌려 보기: [lab/08-softmax.mjs](lab/08-softmax.mjs) (순수 계산, 1초 안).

## 8-3. 추론의 두 단계: 프리필과 디코드

LLM 서버가 요청 하나를 처리하는 과정은 두 단계로 나뉩니다. 이 구분을 알아야 "첫 토큰 지연(TTFT)"을 이해할 수 있습니다.

```text
요청 도착
  │
  ├─ [대기열] 서버가 바쁘면 차례를 기다림
  │
  ├─ [프리필 prefill]  입력 토큰 전체(도구·지시문·첫 멘트 약 3,500개 + 대화 기록)를 한꺼번에 처리
  │                     → 병렬 계산이라 빠르지만, 입력이 길수록 오래 걸림
  │                     → 이 단계에서 각 토큰의 "KV" 값을 계산해 둠 (8-4절)
  │
  ├─ (생각 모드라면) [생각 토큰 생성]  보이지 않는 추론 토큰을 수백 개 만듦  ← 8-5절
  │
  ├─ 첫 번째 답 토큰 출력   ◀── 여기까지가 TTFT (Time To First Token)
  │
  └─ [디코드 decode]   토큰을 하나씩 생성 (초당 수십~수백 개, TPS)
                        → 앞 토큰이 나와야 다음을 계산하므로 순차적
```

| 지표 | 뜻 | 음성 에이전트에서의 중요도 |
| --- | --- | --- |
| **TTFT** | 요청부터 첫 답 토큰까지 | **가장 중요.** 첫 토큰이 나와야 TTS가 시작할 수 있음 |
| **TPS** | 디코드 속도(초당 토큰) | 중요도 중간. 답이 짧고(50자), TTS가 말하는 속도가 더 느리므로 대개 따라잡음 |
| 전체 시간 | TTFT + 출력 토큰 수 / TPS | 채팅에선 중요하지만 음성에선 덜 중요 |

음성에서는 TTS가 사람 말 속도(초당 몇 글자)로 재생하므로, LLM이 그보다 빨리 토큰을 만들기만 하면 뒤쪽 생성 시간은 재생에 가려집니다. 그래서 **음성 에이전트의 LLM 선택 기준 1순위는 TTFT**입니다.

PoC 측정에서 한 턴 지연(약 1.4~1.6초) 중 LLM 첫 토큰이 약 0.8~1.0초로 가장 큰 몫이었습니다([5-poc-results.md](../5-poc-results.md)). 서울↔미국 왕복 네트워크 시간도 여기에 들어 있습니다.

(2026-11-06 갱신) 그림의 "약 3,500개"는 도구 사용 system 프롬프트(문서 값 286토큰)와 `end_call` 정의, 지시문, 첫 멘트를 8-1절의 비율로 어림한 값입니다(추정, 8-4절 깊이 보기). 처음 판의 "지시문 2천여 개"는 예전 지시문으로 잰 2,384토큰에서 나온 말이었습니다.

(2026-11-06 추가) **"프리필"의 두 뜻.** 이 절의 프리필은 서버가 입력 토큰을 한꺼번에 계산하는 **추론 단계**입니다. 8-6절의 "prefill 금지"는 전혀 다른 뜻으로, `messages`를 assistant 메시지로 끝내 "답을 이 글로 시작하라"고 **답의 앞머리를 미리 채워 주는 API 기법**(assistant prefill)입니다. 영어도 같은 단어를 씁니다. 이 장에서는 앞의 것을 "프리필", 뒤의 것을 "assistant prefill"로 부릅니다.

#### 깊이 보기: 프리필은 계산이, 디코드는 메모리 읽기가 막는다 (2026-11-06 추가)

트랜스포머가 토큰 하나를 한 층 통과시키는 일은 대부분 "가중치 행렬 × 그 토큰의 벡터"입니다. 파라미터 하나마다 곱셈 한 번과 덧셈 한 번이 들어, 토큰 하나에 **약 2 × 파라미터 수**의 연산(FLOP)이 듭니다. 차이는 가중치를 메모리에서 읽어 오는 횟수에서 납니다.

- **프리필**은 입력 n개를 한꺼번에 넣습니다. 가중치를 한 번 읽어 n개 토큰에 다 쓰므로(행렬 × 행렬), 읽기보다 계산이 오래 걸립니다. 이것을 **계산 한계(compute-bound)**라고 합니다.
- **디코드**는 한 번에 토큰 하나입니다. 토큰 하나를 만들 때마다 가중치 **전부**를 읽어 단 한 번씩만 씁니다(행렬 × 벡터). 계산기는 놀고 메모리 읽기를 기다립니다. 이것을 **메모리 대역폭 한계(memory-bound)**라고 합니다.

예시로 손 계산합니다. 파라미터 80억 개를 16비트로 둔 모델(가중치 16GB)과, 공개 사양 하나(16비트 연산 초당 989조 회, 메모리 대역폭 초당 3.35TB)를 씁니다. Claude의 크기와 서빙 하드웨어는 공개되지 않았으므로 **자릿수 감각용 예시**입니다.

| | 프리필 3,300토큰 | 디코드 1토큰 |
| --- | --- | --- |
| 계산 | 2 × 8×10⁹ × 3,300 = 52.8조 회 → **53ms** | 160억 회 → 0.016ms |
| 메모리 읽기 | 가중치 16GB 한 번 → 4.8ms | 가중치 16GB + KV 0.43GB(8-4절) → **4.9ms** |
| 막는 것 | 계산 | 읽기 |

- **산술 강도**(읽은 바이트당 연산)로 보면 디코드는 약 1, 프리필은 약 3,300이고, 이 GPU가 둘을 맞추는 균형점은 989조 ÷ 3.35조 ≈ 295입니다. 디코드는 균형점보다 한참 아래라 계산기 대부분이 놉니다.
- 그래서 사용자 하나만 처리하면 디코드는 초당 약 200토큰이 상한입니다. 서버는 여러 사용자의 디코드를 **묶어서(배치)** 한 번 읽은 가중치를 나눠 씁니다. 서버가 붐비면 묶음이 커져 각자의 속도와 대기가 흔들립니다.
- 프리필 시간은 입력 길이에 비례합니다. 프롬프트 캐시(8-4절)가 줄이는 것이 이 몫입니다. 이 예시로는 3,300토큰이 수십 ms이니, 첫 토큰 0.8초 가운데 프리필은 작은 몫일 것으로 봅니다(추정). 2026-11-05 A/B에서 "hi" 한 단어 요청이 0.7초, 지시문 전체 요청이 p50 0.77초였던 것(Haiku 4.5, 13-5절)도 같은 방향입니다. 두 값은 다른 측정이고, 그날은 캐시가 아예 돌지 않았을 가능성이 커서(8-4절) 거친 비교입니다.

직접 돌려 보기: [lab/08-kv-cache.mjs](lab/08-kv-cache.mjs) 4번 (순수 계산).

## 8-4. KV 캐시와 프롬프트 캐시

### 요청 안에서의 KV 캐시

어텐션 계산에는 앞 토큰마다 계산한 **키(K)와 값(V)** 벡터가 필요합니다. 디코드 단계에서 토큰을 하나 만들 때마다 앞의 모든 K, V를 다시 계산하면 낭비이므로, 한 번 계산한 것을 메모리에 저장해 둡니다. 이것이 **KV 캐시**입니다. 모든 LLM 서버가 요청 하나 안에서 당연히 씁니다.

#### 깊이 보기: 어텐션 식, 인과 마스크, KV 메모리 (2026-11-06 추가)

**Q, K, V.** 층마다 각 토큰의 입력 벡터 x에 학습된 행렬 셋을 곱해 벡터 셋을 만듭니다. **Q**(query, 질의) = W_Q·x는 "지금 내가 찾는 것", **K**(key, 열쇠) = W_K·x는 "내가 가진 것의 표지", **V**(value, 값) = W_V·x는 "실제로 건넬 내용"입니다. 어텐션은 이렇게 계산합니다.

```text
Attention(Q, K, V) = softmax( Q·Kᵀ / √d + M ) · V
```

- Q·Kᵀ는 각 토큰의 q와 모든 토큰의 k의 내적, 곧 "누가 누구를 얼마나 볼지"의 점수표입니다. √d(벡터 차원의 제곱근)로 나누는 이유는, 차원이 크면 내적 값이 커져 소프트맥스(8-2절)가 한 칸으로 쏠리기 때문입니다.
- M은 **인과 마스크(causal mask)**입니다. i번째 토큰이 자기보다 뒤(j > i)를 보지 못하게 그 칸에 −∞를 더합니다. e^−∞ = 0이라 가중치가 정확히 0이 됩니다. 8-2절의 소프트맥스, 8-11절 구조화 출력의 마스크와 같은 수법입니다.
- 결과는 가중치로 V를 섞은 벡터이고, 다음 층의 입력이 됩니다.

**왜 과거의 K·V를 저장해도 되나.** k_j = W_K·x_j, v_j = W_V·x_j는 토큰 j 자신의 입력만으로 정해집니다. 그리고 인과 마스크 때문에 토큰 j의 출력은 j와 그 앞 토큰에만 기댑니다. 그러면 뒤에 토큰을 덧붙여도 j의 출력, 곧 다음 층의 입력 x_j가 그대로이고, 다음 층의 k_j·v_j도 그대로입니다. 층마다 같은 논리가 이어지므로 **과거 토큰의 K·V는 모든 층에서 바뀌지 않습니다.** 새 토큰 하나를 만들 때는 그 토큰의 q 하나로 저장된 K·V를 읽기만 하면 됩니다.

장난감 한 층(차원 4, 지어낸 숫자)으로 확인합니다([lab/08-kv-cache.mjs](lab/08-kv-cache.mjs) 1·2번).

```text
토큰 "정확", "한", " 금액"에서 " 금액"의 점수 q·k/√4 = [0.50  0.00  1.00]
  소프트맥스 가중치 = [0.31  0.19  0.51] → 출력 = Σ w·V
"은"을 덧붙여 다시 계산: 앞 세 토큰의 K·V 같음, 출력 같음 (인과 마스크)
마스크를 빼면: "정확"의 출력이 [0.57 0.51 0.43 −0.07] → [0.34 0.40 0.34 0.16]으로 바뀜
```

마스크가 없는 모델(문장 전체를 양쪽으로 보는 인코더)은 뒤에 한 글자만 붙어도 앞 토큰의 결과가 바뀌어 이런 캐시를 쓸 수 없습니다. 프롬프트 캐시가 "앞부분이 같으면 재사용"이라는 규칙을 갖는 것도 같은 성질에서 나옵니다. 앞부분의 계산은 뒤에 무엇이 오든 같기 때문입니다.

**메모리 손 계산.** 토큰 하나의 KV 캐시 = 층 수 × KV 헤드 수 × 헤드 차원 × 2(K와 V) × 숫자 하나의 바이트입니다.

| 예시 모델 | 계산 | 토큰당 | 3,300토큰 | 1만 토큰 |
| --- | --- | --- | --- | --- |
| A: 32층, KV 헤드 8, 128차원, 16비트 | 32 × 8 × 128 × 2 × 2 | 128KiB | 412.5MiB | 1.22GiB |
| B: A를 KV 헤드 32개로 | 32 × 32 × 128 × 2 × 2 | 512KiB | 1.6GiB | 4.88GiB |
| C: A를 8비트로 저장 | 32 × 8 × 128 × 2 × 1 | 64KiB | 206MiB | 0.61GiB |

- 예시 A는 Llama 3 8B 같은 공개 모델의 설정과 같은 모양입니다. **Claude의 층 수·헤드 수는 공개되지 않았으므로** 자릿수 감각용입니다.
- B와 A의 차이가 GQA(grouped-query attention)입니다. 질의 헤드 여러 개가 K·V 헤드 하나를 같이 써서 KV 메모리를 줄입니다.
- 이 정도 크기라서, 요청 사이에 KV를 남겨 두는 프롬프트 캐시에는 보관 시간과 최소 길이, 따로 매긴 값이 붙습니다. 서버가 이것을 GPU 메모리에 두는지 더 느린 저장소로 옮기는지는 공개되지 않았습니다(추정의 영역).

### 요청 사이의 프롬프트 캐시

음성 통화에서는 매 턴 요청을 새로 보냅니다. 그런데 입력의 앞부분(지시문 + 이전 대화)은 직전 턴과 똑같습니다. 그렇다면 **이전 요청에서 계산한 KV를 다음 요청이 재사용**할 수 있지 않을까요? 이것이 **프롬프트 캐시**입니다.

```text
렌더 순서: tools → system → messages                         ▼ = 자동 캐시의 브레이크포인트(마지막 블록)
턴 1 요청: [도구][지시문 + 고객 정보][(empty)][첫 멘트][user1▼]
           └────────────── 캐시에 씀(write) ──────────────┘
턴 2 요청: [도구][지시문 + 고객 정보][(empty)][첫 멘트][user1][assistant1][user2▼]
           └────────────── 캐시에서 읽음(read) ───────────┘└─── 씀 ────┘
```

(2026-11-06 갱신) 처음 판의 그림은 맨 앞을 "[지시문 2,384토큰]"으로 그렸습니다. 실제로 모델 입력의 맨 앞은 `end_call` **도구 정의**이고, 2,384토큰은 예전 요청 **전체**의 값이었습니다(8-1절).

- **접두사(prefix) 일치**: 앞에서부터 **바이트 하나까지 같은 부분**만 재사용됩니다. 중간에 한 글자라도 다르면 그 뒤는 전부 새로 계산합니다. 9장에서 고객 정보를 지시문 맨 뒤에 둔 이유입니다. (2026-11-06 추가) 다만 "같은 부분"을 아무 데서나 끊어 읽지는 않습니다. **앞선 요청이 브레이크포인트를 둔 블록 경계**에서만 읽습니다(아래 깊이 보기). 렌더 순서의 맨 앞은 도구라서, 도구를 더하거나 설명을 고치면 그 뒤가 전부 새로 계산됩니다.
- **효과**: 프리필 계산을 건너뛰므로 TTFT가 줄고, 캐시에서 읽은 입력 토큰은 기본 입력 단가의 약 **0.1배**만 냅니다. 처음 쓸 때(write)는 약 1.25배를 냅니다(5분 보관 기준). 두 번째 요청부터 이득입니다. (2026-11-06 추가) Haiku 5.5 단가로는 백만 토큰당 입력 $0.10, 캐시 쓰기 $0.125, 캐시 읽기 $0.01, 출력 $0.50입니다(문서 기준, 프롬프트 10만 토큰 이하).
- **보관 시간(TTL)**: 기본 5분이고, 읽을 때마다 타이머가 다시 시작됩니다. 통화 중에는 턴이 몇 초 간격으로 이어지니 계속 살아 있습니다. (2026-11-06 갱신) 5분은 그 항목을 쓰거나 읽은 **요청이 시작한 때**부터 잽니다(문서 기준). 처음 판은 "통화와 통화 사이도 5분 안에 다음 통화가 시작되면 지시문 부분을 공유한다"고 썼는데, **지금 구조에서는 통화 사이에 지시문 앞부분 캐시를 나눠 쓰지 않을 가능성이 큽니다.** 캐시 항목은 브레이크포인트 자리에만 생기는데, 지금은 그 자리가 늘 대화의 마지막 블록이고 그 앞의 지시문은 고객 정보까지 한 블록이기 때문입니다. 문서 규칙에서 끌어낸 결론이고 실측으로 확인하지는 않았습니다. 이유는 아래 깊이 보기, 이 지시문에 대 본 결과와 두 블록 제안은 [9-3절 깊이 보기](09-prompt-design.md#깊이-보기-캐시-경계를-이-지시문에-대-보기-2026-11-06-추가)에 있습니다.
- **최소 길이**: 모델마다 캐시 가능한 최소 길이가 있고, Haiku 5.5는 512토큰입니다. 그보다 짧으면 오류 없이 **조용히 캐시되지 않습니다.** 이 프로젝트의 지시문은 그보다 충분히 깁니다. (2026-11-06 추가) 최소 길이는 세대가 바뀐다고 줄기만 하지 않습니다. **Haiku 4.5는 4,096토큰**입니다(문서 기준). 2026-11-05 Bedrock A/B(Haiku 4.5)에서 "캐시 있음·없음 차이가 측정 오차 안"이었던 것은([5-poc-results.md](../5-poc-results.md)), 약 3,300토큰이던 그 요청이 이 최소에 못 미쳐 **캐시 항목이 아예 생기지 않았기 때문일 가능성이 큽니다**(문서 기준 추론, 그날 usage를 남기지 않아 확인 못 함).
- (2026-11-06 추가) **범위**: 캐시는 Claude API에서는 워크스페이스마다, Bedrock에서는 조직마다 따로이고, 모델마다 따로입니다. 생각 모드나 effort를 요청마다 바꾸면 messages 쪽 캐시가 깨지므로(문서 기준), `LLM_THINKING`·`LLM_EFFORT`는 통화 중에 바뀌지 않는 지금처럼 둡니다.

### 이 프로젝트의 설정: 자동 캐시

Anthropic API에는 캐시 지점을 블록마다 지정하는 방식과, **요청 최상위에 `cache_control` 하나만 두면 마지막 블록까지 자동으로 캐시하는 방식**이 있습니다. 이 프로젝트는 후자를 씁니다.

```ts
// src/models/anthropic.ts (요청 본문에 추가되는 값)
cache_control: { type: 'ephemeral' },
```

자동 캐시는 대화가 길어질 때마다 캐시 지점을 마지막 블록으로 옮겨 줍니다. 그래서 턴 N의 요청은 턴 N-1까지의 대화 전체를 캐시에서 읽습니다.

(2026-11-06 갱신) 더 정확히는 이렇습니다. 캐시 지점을 **브레이크포인트(breakpoint)**라고 부르고, 블록에 `cache_control`을 달면 그 블록이 브레이크포인트가 됩니다. 최상위 `cache_control`(자동 캐시)은 서버가 **마지막 캐시 가능 블록에 브레이크포인트 하나를** 대신 두는 것입니다(그 블록이 대상이 될 수 없으면 가장 가까운 앞 블록으로). 그래서 턴 N의 요청은 **턴 N−1 요청 전체**(user N−1까지)를 읽고, 그 뒤에 붙은 assistant N−1과 user N만 새로 씁니다. `ephemeral`(잠깐 머무는)은 캐시 종류의 이름으로 지금은 이것 하나뿐이고, 기본 5분, `ttl: "1h"`를 주면 1시간(쓰기 2배)입니다. 브레이크포인트는 요청 하나에 최대 4개이고 자동 캐시도 하나를 씁니다(문서 기준).

#### 깊이 보기: 캐시 항목은 어디에 생기고 어떻게 찾나 (2026-11-06 추가)

**규칙 (문서 기준).**

1. 모델 입력은 **tools → system → messages** 순서로 렌더됩니다. 요청 JSON의 칸 순서(플러그인은 model, messages, system, tools, …)와는 상관없습니다.
2. 브레이크포인트 하나는 **"맨 앞부터 그 블록까지"의 해시로 항목 하나**를 씁니다. 그보다 앞 자리에는 항목을 쓰지 않습니다.
3. 읽을 때는 각 브레이크포인트에서 거꾸로 **최대 20자리**(자기 포함)까지, 앞선 요청이 써 둔 항목을 찾습니다. 찾으면 거기까지 읽고, 가장 높이 적중한 곳 뒤의 차이만 씁니다.
4. 항목은 그것을 쓴 요청의 응답이 **스트리밍을 시작한 뒤**에야 읽을 수 있습니다. 같은 앞부분의 요청을 동시에 여럿 보내면 서로 읽지 못합니다.

여기서 "자리"는 블록입니다(도구 하나, system 글 블록 하나, 메시지 안의 내용 블록 하나). 8-6절 실습의 1턴 요청을 렌더 순서로 펼치면 이렇습니다(실측, 크기는 요청 JSON 조각의 바이트로 견줄 거리일 뿐이고 토큰화는 비공개).

| 자리 | 블록 | 크기 |
| --- | --- | --- |
| 1 | tools: `end_call` | 722B |
| 2 | system[0]: 지시문 + 고객 정보 | 7,024B |
| 3 | messages[0] user `(empty)` | 46B |
| 4 | messages[1] assistant 블록 0: 고지 | 264B |
| 5 | messages[1] assistant 블록 1: 질문 | 88B |
| 6 | messages[2] user: 고객 말 | 155B ← 자동 브레이크포인트 |

(2026-11-06 갱신) 위 표와 아래 표의 바이트는 17-2 #34 뒤 다시 돌린 값입니다(지시문이 5바이트 줄어 자리 2와 그 뒤 누적이 5바이트씩 작아짐).

도구를 쓰면 이와 별도로 API가 넣는 **도구 사용 system 프롬프트**(Haiku 5.5, `tool_choice: auto`일 때 286토큰)도 입력에 더해집니다(문서 기준, 가격 문서).

실습은 위 규칙 2·3을 흉내 낸 장난감 캐시(자리마다 "앞부분 해시")에 요청을 차례로 넣어 봅니다. 통화 B는 신청서 칸이 모두 빈 가상 통화입니다.

| 요청 | 브레이크포인트 | 읽은 자리 | 새로 쓴 몫 |
| --- | --- | --- | --- |
| 통화 A 1턴 | 6 | 없음 | 전부 (8,299B) |
| 통화 A 2턴 | 8 | 1~6 (A 1턴이 6에 쓴 항목) | 7~8 (263B) |
| 통화 B 1턴 | 6 | **없음** | 전부 (8,205B) |

- A 2턴의 앞 6자리는 A 1턴과 바이트까지 같고, A 1턴이 자리 6에 항목을 써 두었으며, 자리 8에서 6까지는 2칸이라 20칸 안입니다. 그래서 읽힙니다. 한 턴이 더하는 자리는 보통 2개(assistant, user)라 통화 안에서는 20칸 한도에 걸릴 일이 없습니다. 도구 호출이 있는 턴도 연속된 tool_use·tool_result는 각각 한 자리로 칩니다(문서 기준).
- B 1턴은 지시문의 2,922번째 글자("- 호칭: " 뒤, 6,708바이트째)에서 A와 갈라집니다. 앞 2,922자가 같아도, 그 경계는 system 블록 **안**이라 항목이 생길 수 있는 자리가 아닙니다. 고객 정보보다 앞에 있는 블록 경계는 "도구 끝"(자리 1) 하나뿐인데 거기에는 브레이크포인트가 없습니다. 그래서 B는 아무것도 읽지 못합니다. 문서의 비용 최적화 안내도 "자동 캐시는 한 대화 안에서만 이득을 나눈다"고 적습니다.
- **제안(코드는 고치지 않음).** 지시문을 "공통 지시"와 "고객 정보" 두 system 블록으로 나누고 앞 블록에 `cache_control`을 달면, 같은 장난감 모델에서 B 1턴이 자리 1~2(7,518B)를 읽고 712B만 씁니다. 문서가 권하는 "정적인 앞부분에 명시 브레이크포인트 하나 + 자라는 대화에는 자동 캐시" 조합입니다. 조건은 같은 모델·같은 워크스페이스(Bedrock은 조직), 도구와 공통 지시가 바이트까지 같고, 앞 통화가 그 항목을 쓰거나 읽은 지 5분 안이라는 것입니다. 구현 방법과 실측 계획은 [9-3절 깊이 보기](09-prompt-design.md#깊이-보기-캐시-경계를-이-지시문에-대-보기-2026-11-06-추가)에 있습니다. 돈으로는 통화당 0.04센트 안팎이라(아래 손 계산) 목적은 지연입니다.

#### 깊이 보기: 턴별 읽기·쓰기와 비용 손 계산 (2026-11-06 추가)

**가정 (추정).** 앞부분(도구 사용 system 프롬프트 286 + `end_call` 정의 약 180 + 지시문 약 2,920 + `(empty)`와 첫 멘트 약 110) ≈ **3,500토큰**, 고객 말 한 번 30토큰, AI 답 한 번 70토큰(출력이자 다음 요청의 입력), 8턴. 앞부분 어림은 8-1절의 글자당 0.97토큰을 썼고, 영어 위주인 도구 설명은 글자당 0.25토큰으로 셌습니다.

요청 n의 입력은 R_n = 3,500 + 100(n − 1) + 30입니다. 자동 캐시에서 n턴은 **직전 요청 전체 R_(n−1)을 읽고**, 나머지 R_n − R_(n−1) = 100을 씁니다. 1턴은 전부 씁니다.

| 턴 | 입력 R_n | 읽기 (×$0.01/M) | 쓰기 (×$0.125/M) | 출력 (×$0.50/M) | 이 턴 비용 | 캐시 없을 때 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 3,530 | 0 | 3,530 | 70 | $0.000476 | $0.000388 |
| 2 | 3,630 | 3,530 | 100 | 70 | $0.000083 | $0.000398 |
| 3 | 3,730 | 3,630 | 100 | 70 | $0.000084 | $0.000408 |
| … | | | | | | |
| 8 | 4,230 | 4,130 | 100 | 70 | $0.000089 | $0.000458 |
| 합 | 31,040 | 26,810 | 4,230 | 560 | **$0.001077** | $0.003384 |

- 1턴: 3,530 × 0.125 + 70 × 0.5 = 441 + 35 = 476 (단위 백만분의 1달러). 캐시가 없으면 3,530 × 0.1 + 35 = 388이라 **1턴만 보면 캐시가 손해**입니다(쓰기 1.25배).
- 2턴: 3,530 × 0.01 + 100 × 0.125 + 35 = 35.3 + 12.5 + 35 = 82.8. 캐시가 없으면 398입니다.
- 입력만 합치면 캐시 없음 31,040 × 0.1 = $0.003104, 자동 캐시 26,810 × 0.01 + 4,230 × 0.125 = $0.000797로 **74% 줄어듭니다.** 출력까지 통화 하나 약 $0.0011, 1달러 1,400원으로 치면 약 1.5원입니다.
- 손익분기는 "같은 앞부분을 두 번 쓰는 순간"입니다. 1.25 + 0.1 = 1.35 < 2(캐시 없이 두 번)이기 때문입니다(문서 기준).
- 응답의 usage로 보면 1턴은 `cache_creation_input_tokens` ≈ 3,530, `cache_read_input_tokens` = 0이고, n턴은 읽기 ≈ R_(n−1), 쓰기 ≈ 100입니다. `input_tokens`는 마지막 브레이크포인트 뒤의 꼬리뿐이라(문서 기준) 자동 캐시에서는 아주 작을 것입니다(추정). LiveKit 지표에서는 `promptTokens` = 세 값의 합, `promptCachedTokens` = 읽기, `cacheCreationTokens` = 쓰기입니다(`plugin/llm.ts` 443~455, 8-6절 실습).
- (2026-11-06 갱신) 선제 생성(11장)이 턴 확정 전에 보낸 요청이 버려져도 **요청은 끝까지 갑니다.** 플러그인이 취소 신호(`signal`)를 HTTP에 넘기지 않아 모델이 답을 다 만들기 때문입니다(11-4절 깊이 보기, 12-8절, 17-2 #41). 그래서 버린 시도 하나의 비용은 "끝부분 쓰기 조금"이 아니라 대략 **한 턴의 비용**(입력 읽기·쓰기 + 출력)입니다.
- 위 제안(지시문 두 블록)으로 통화 B의 1턴이 공통 앞부분 약 3,280토큰을 읽으면 아끼는 돈은 3,280 × (0.125 − 0.01) ≈ $0.00038입니다.

#### 깊이 보기: 첫 턴은 늘 쓰기다 — 고지 동안 미리 써 두기 (제안) (2026-11-06 추가)

위 표처럼 통화의 첫 LLM 요청은 읽을 항목이 없어 앞부분 전체를 프리필하고 씁니다. 얼마나 느린지는 기록이 없습니다. PoC는 2·3회차만 적었고, 1회차에는 연결 비용도 섞입니다. 8-3절의 예시 계산으로는 수천 토큰의 프리필이 수십 ms 규모라 차이가 크지 않을 수도 있습니다(추정). 그래서 **먼저 잽니다.** `pnpm check:llm`의 1회차와 2회차 첫 토큰 차이를, 연결을 한 번 데운 뒤 비교합니다(과금).

차이가 의미 있다면, 문서가 정확히 이 용도로 적어 둔 방법이 있습니다(문서 기준).

- **`max_tokens: 0` 요청**을 보내면 서버가 프리필만 하고 브레이크포인트에 캐시를 쓴 뒤 곧바로 `content: []`, `stop_reason: "max_tokens"`로 돌아옵니다. 출력 토큰 값은 없고 캐시 쓰기 값만 냅니다.
- `stream: true`, `thinking.type: "enabled"`, `output_config.format`, 강제 `tool_choice`(`any`·`tool`)와 함께 쓰면 거절됩니다.
- 브레이크포인트는 **실제 요청과 같은 마지막 블록**(여기서는 system 블록)에 명시적으로 답니다. 최상위 자동 캐시를 쓰면 자리표시용 user 메시지에 항목이 생겨 실제 요청이 읽지 못합니다.
- 생각 모드와 effort도 실제 요청과 같게 보냅니다. 렌더에 들어가기 때문입니다.

이 프로젝트에 대 보면 (제안, 코드 수정 안 함):

- 플러그인은 늘 `stream: true`로 보내므로(`plugin/llm.ts` 299) 이 요청은 플러그인으로 할 수 없고, 세션을 시작할 때 SDK로 따로 보내야 합니다. 본문은 같은 `model`, `tools`, `tool_choice`, `thinking: {type: "disabled"}`, `output_config: {effort: "low"}`, `system: [{type: "text", text: 지시문, cache_control: {type: "ephemeral"}}]`, `messages: [{role: "user", content: "(empty)"}]`, `max_tokens: 0`, `stream` 없음입니다.
- 실제 1턴 요청의 자동 브레이크포인트(자리 6)에서 거꾸로 네 칸만 가면 system 끝(자리 2)에 이 항목이 있으므로, 1턴은 도구와 지시문을 읽고 메시지만 씁니다.
- 고지와 질문이 재생되고 고객이 답하는 몇 초가 있으므로 시간은 넉넉합니다. 쓰기 총량은 같고, 더 드는 것은 1턴의 읽기 약 3,400 × $0.01/M ≈ $0.00003입니다(추정).
- 미리 쓰기 요청이 연 연결은 4초 유휴 종료(8-8절) 때문에 1턴까지 남지 않을 가능성이 큽니다. 연결 데우기와는 따로 생각합니다.
- 확인할 것: Bedrock 경로가 `max_tokens: 0`을 받는지(확인 필요), 그리고 효과(1턴 첫 토큰이 실제로 줄어드는지). 9-3절의 두 블록 제안과 함께 쓰면 최근 5분 안에 다른 통화가 있었을 때는 미리 쓰기가 필요 없습니다.

### 캐시가 동작하는지 확인하는 법

응답의 사용량(usage)에 캐시 정보가 옵니다.

| 필드 (Anthropic API) | 뜻 |
| --- | --- |
| `cache_creation_input_tokens` | 이번에 캐시에 쓴 토큰 |
| `cache_read_input_tokens` | 이번에 캐시에서 읽은 토큰 |
| `input_tokens` | 캐시를 안 거친 입력 토큰 |

LiveKit은 이를 `ChatChunk.usage.promptCachedTokens` 같은 이름으로 옮겨 줍니다. [scripts/check-llm.ts](../../scripts/check-llm.ts)가 `cached tokens` 열에 찍는 값이 이것입니다. PoC에서 2회차부터 2,384토큰이 캐시 적중했습니다. **같은 요청을 반복했는데 이 값이 0이면** 앞부분 어딘가가 매번 바뀌고 있다는 뜻입니다(현재 시각, 무작위 id 등).

(2026-11-06 갱신) 2,384토큰은 **같은 요청을 되풀이**해서 요청 전체가 읽힌 값이고, 그때 요청은 지금보다 짧은 지시문(2,291자, 지금 3,004자)에 도구가 없었습니다(8-1절). "지시문의 토큰 수"나 "통화 사이에 나눠 쓴 몫"이 아닙니다. 지금 요청으로 다시 재면 도구와 긴 지시문 때문에 더 클 것입니다(앞 손 계산은 약 3,500으로 어림). 0이 나올 때 이유는 하나 더 있습니다. 앞부분이 그 모델의 최소 길이에 못 미치는 경우입니다(Haiku 4.5는 4,096토큰). `check-llm`을 다른 모델로 돌릴 때 기억해 둡니다.

## 8-5. 생각 모드와 effort: 왜 껐는가

### 생각(추론) 모드란

최신 LLM은 답을 바로 쓰지 않고, 먼저 **보이지 않는 추론 토큰**을 생성한 뒤 답을 쓸 수 있습니다. 어려운 수학이나 코딩에서 정확도를 크게 올립니다. Claude에서는 이를 `thinking` 설정으로 제어합니다.

- `thinking: { type: 'adaptive' }`: 모델이 문제 난이도를 보고 얼마나 생각할지 스스로 정합니다.
- `thinking: { type: 'disabled' }`: 생각하지 않고 바로 답합니다.
- `output_config: { effort: 'low' | 'medium' | 'high' | … }`: 생각의 깊이와 전체 토큰 사용량의 수준을 조절합니다.

**Claude Haiku 5.5의 기본값은 "생각 켬(adaptive), effort medium"**입니다. 그리고 생각을 끄는 `disabled`는 effort가 `high` 이하일 때만 허용됩니다. 그 위의 effort와 같이 보내면 400입니다.

### 생각 토큰은 TTFT에 그대로 더해진다

8-3절의 그림에서 생각 토큰은 **첫 답 토큰보다 먼저** 생성됩니다. 생각 토큰이 400개면, 디코드 속도가 초당 200토큰이라 해도 첫 답 토큰이 2초 늦어집니다. PoC 측정이 정확히 이것을 보여 줍니다.

| 설정 | 첫 토큰 (캐시 후) | 출력 토큰 | 해석 |
| --- | --- | --- | --- |
| **생각 끔 / low** | **0.78~0.84초** | 220개 안팎 | 답 토큰만 |
| 생각 켬 / low | 2.5~3.0초 | 440~540개 | 생각 토큰 200~300개가 앞에 붙음 |
| 생각 켬 / medium | 2.1~3.0초 | 410~530개 | 위와 같음 |

(2026-11-06 추가) **"220개 안팎"을 읽는 법.** 생각을 끈 설정의 출력 220토큰이 답 길이(77~119자)에 비해 많아 보인다는 지적이 있었습니다. 확인해 보니 두 숫자는 **서로 다른 측정**입니다.

- 220토큰은 2026-11-03 첫 측정의 `check-llm`(조합마다 3회)입니다. 그때 지시문은 init 커밋(`5cb4046`)의 판으로 길이 규칙이 "한 번에 한두 문장"뿐이었고, 고객 대사("가죽 말고 스테인리스 텀블러에도 각인돼요? 가격은 얼마예요?")에는 **질문이 둘**입니다. 그 답의 글자 수는 남아 있지 않습니다. 스크립트는 `chars` 열을 찍지만 5-poc-results.md에 옮기지 않았습니다.
- 77자·119자는 같은 날의 다른 측정(같은 고객 대사 6턴의 평균 답 길이, 지시문에 "오십 자 안팎"을 넣기 전후, 9-2절)입니다.
- 8-1절의 비율(글자당 약 0.97토큰)로 보면 220토큰은 약 225자 답입니다. 두 질문에 답하고 상담사 연결을 안내하는 답이 "한두 문장" 규칙 아래 그 정도였다면 생각 토큰 없이도 설명됩니다(추정). 생각을 켰을 때 늘어난 220~320개가 생각 토큰이라는 아래 해석은 그대로입니다.
- 확인하려면 `pnpm check:llm`을 다시 돌려 같은 줄의 `output tokens`와 `chars`를 나란히 봅니다(과금, 키 필요). 생각을 끈 줄에서 출력 토큰 ÷ 글자 수가 1 안팎이면 답 토큰뿐이고, 2를 넘으면 다른 것이 섞였다고 봅니다.

출력 토큰이 두 배가 된 것이 "보이지 않는 생각 토큰"의 흔적입니다. 그리고 **답 품질은 세 설정이 거의 같았습니다.** 상담 첫 통화의 대화는 깊은 추론이 필요한 문제가 아니기 때문입니다. 그래서 기본값을 **생각 끔 + effort low**로 정했습니다([src/config.ts](../../src/config.ts)의 `LLM_THINKING=off`, `LLM_EFFORT=low`).

### 끄는 것의 대가

Anthropic은 일반적으로 "생각을 끄기보다 effort를 낮추라"고 권합니다. 생각을 끈 모델에서 알려진 문제 두 가지가 있습니다.

1. **도구 호출을 말로 흘리는 경우.** 도구 호출 블록 대신 본문에 도구 호출 같은 글을 써서, 실제로는 호출이 안 되고 오류도 나지 않는 경우가 있습니다. [src/agent.ts](../../src/agent.ts) 주석이 이를 대비한 지시문 문장을 미리 적어 두었습니다(9-6절).
2. **생각 블록과 대화 기록.** 생각을 켜면 응답에 생각 블록이 붙는데, LiveKit 플러그인은 대화 기록을 만들 때 이 블록을 버립니다. 도구를 쓰는 대화에서는 이전 생각 블록을 그대로 돌려줘야 하는 경우가 있어, 생각을 켠 채 도구를 붙이면 동작을 보장하기 어렵습니다. 그래서 [src/models/anthropic.ts](../../src/models/anthropic.ts) 주석이 "도구를 붙이면 `off`가 안전하다"고 적어 둔 것입니다.

결론: **지금은 지연 때문에 끄고, 도구를 붙일 때 다시 측정해서 정합니다.** 설정이 환경변수로 열려 있어(`LLM_THINKING`, `LLM_EFFORT`) 코드 수정 없이 비교할 수 있습니다.

(2026-11-03 갱신) 코드에 첫 도구 `end_call`이 붙었고, 생각 모드는 끈 채로 갑니다. 위 1번 문제에 대비한 문장을 지시문 "통화 끝내기" 절에 넣었습니다(9-6절). 도구가 있으면 Anthropic 플러그인이 답 글 속의 `<thinking>…</thinking>` 표기를 걸러 내는 처리도 켜집니다. 생각 모드를 켠 비교 측정은 아직 남아 있습니다.

## 8-6. Messages API의 모양

Anthropic의 대화 API는 대략 이렇게 생겼습니다. (2026-11-06 갱신) 아래는 이 프로젝트의 플러그인이 1턴에 실제로 보내는 본문을 줄인 것입니다(8-6절 깊이 보기의 실측). 처음 판의 예시는 `system`이 문자열이고 `(empty)` 턴, 첫 멘트 병합, 도구가 빠진 개념 모양이었습니다.

```json
{
  "model": "claude-haiku-5-5",
  "messages": [
    { "role": "user", "content": "(empty)" },
    { "role": "assistant", "content": [
      { "type": "text", "text": "안녕하세요, 김민수 고객님. 오리지널스 AI 상담사입니다. … 녹음됩니다." },
      { "type": "text", "text": "이삼 분 정도 통화 괜찮으실까요?" }
    ] },
    { "role": "user", "content": "네, 괜찮아요. 근데 이거 가죽 말고 스테인리스 텀블러에도 각인돼요? …" }
  ],
  "system": [{ "type": "text", "text": "당신은 주식회사 오리지널스의 AI 상담사입니다. … - 문의 내용: …" }],
  "tools": [{ "name": "end_call", "description": "…", "input_schema": { "type": "object", "properties": {} } }],
  "stream": true,
  "max_tokens": 2048,
  "thinking": { "type": "disabled" },
  "output_config": { "effort": "low" },
  "cache_control": { "type": "ephemeral" },
  "tool_choice": { "type": "auto", "disable_parallel_tool_use": false }
}
```

- **system은 따로**: 지시문은 `messages` 안이 아니라 최상위 `system` 필드에 들어갑니다. LiveKit의 대화 기록(`ChatContext`)에는 지시문이 `system` 역할 메시지로 들어 있고, 플러그인이 이를 꺼내 최상위로 옮깁니다. 대화 중간에 있던 system 메시지도 위치와 상관없이 모두 최상위로 올라갑니다. (2026-11-06 추가) 플러그인은 system 메시지 하나마다 `{type: "text", text}` 블록 하나를 만들어 **배열**로 보냅니다(`plugin/llm.ts` 133~134). API는 문자열도 받지만, 블록이어야 블록마다 `cache_control`을 달 수 있습니다(8-4절 제안).
- **user와 assistant**: 고객 말은 `user`, 에이전트 말은 `assistant`입니다.
- **`max_tokens: 2048`**: 응답 길이 상한입니다. 답은 50자 안팎이라 한참 남지만, 생각 모드를 켜면 생각 토큰도 여기에 포함되므로 여유를 둡니다([src/models/index.ts](../../src/models/index.ts) 주석).

### prefill 금지와 "." 턴

예전 Claude는 `messages`가 `assistant`로 끝나면 "답을 이 문장으로 시작하라"는 뜻(**prefill**)으로 받아 이어 썼습니다. **Haiku 5.5는 prefill을 지원하지 않아 400을 돌려줍니다.**

(2026-11-06 추가) 여기의 prefill(assistant prefill)은 8-3절의 "프리필"(서버가 입력을 계산하는 단계)과 다른 뜻입니다. 이름만 같습니다.

음성 에이전트에서는 대화가 assistant로 끝나는 상황이 생길 수 있습니다. 예를 들어 에이전트가 말한 직후 코드가 다시 답을 생성하라고 요청하는 경우입니다. LiveKit Anthropic 플러그인은 이때 끝에 `"."`만 담은 user 턴을 붙여 prefill이 되지 않게 합니다. 프로젝트 테스트가 이 동작을 고정합니다.

```ts
// src/models/anthropic.test.ts
it('대화가 assistant로 끝나도 prefill이 되지 않게 user 턴으로 끝난다', async () => {
  // system + assistant만 있는 대화로 요청
  const messages = lastBody.messages as { role: string }[];
  expect(messages.at(-1)?.role).toBe('user');
});
```

### 플러그인이 실제로 만드는 요청의 모양

플러그인 코드(`agents-plugin-anthropic/src/llm.ts`)를 따라가면, 이 프로젝트의 요청은 위 예시와 조금 다릅니다.

| 플러그인 동작 | 이 프로젝트에서 일어나는 일 |
| --- | --- |
| 첫 메시지가 user가 아니면 맨 앞에 `{role: 'user', content: '(empty)'}`를 넣음 | 첫 멘트(`session.say`)가 assistant로 먼저 기록되므로 **매 요청이 `(empty)` user 턴으로 시작**합니다 |
| 같은 역할이 연속되면 하나로 합침 | 첫 멘트 두 문장(고지 + 질문)이 assistant 메시지 하나로 합쳐집니다 |
| 마지막이 assistant면 `"."` user 턴을 붙임 | prefill 400 방지 |
| user·assistant 메시지는 글(`rawTextContent`)만 씀 | 이미지·오디오 내용은 조용히 버려집니다 (이 프로젝트는 글만 쓰므로 영향 없음) |
| 도구 호출은 `tool_use`, 도구 결과는 `tool_result` 블록으로 변환 | 도구를 붙이면 쓰입니다 |
| 최종 본문 = `{model, messages, system, tools, stream: true, max_tokens, ...extraKwargs}` | **extraKwargs가 맨 마지막에 펼쳐져서** `thinking`·`output_config`·`cache_control`이 그대로 들어갑니다. 반대로 말하면 extraKwargs로 `model`이나 `max_tokens`까지 덮어쓸 수 있으니 조심해야 합니다 |
| (2026-11-06 추가) system 메시지마다 `{type: "text"}` 블록 하나, 배열로 (133~134) | 지시문 하나라 블록 하나(3,004자, 2026-11-06 갱신). 블록 자체에는 `cache_control`이 없음 |
| (2026-11-06 추가) 도구는 이름순 정렬(`agents/llm/tool_context.ts` 267~274), 설명과 JSON 스키마로 (231~244) | `end_call` 하나. 모양과 뜻은 [9-1절 깊이 보기](09-prompt-design.md#깊이-보기-모델이-실제로-받는-요청-2026-11-06-추가) |
| (2026-11-06 추가) 도구가 있고 `parallelToolCalls`(기본 true, 49)가 정해져 있으면 `tool_choice: {type: "auto", disable_parallel_tool_use: false}`를 extras **맨 뒤에** 더함 (247~291). `toolChoice: 'none'`이면 도구를 통째로 뺌 (256~259) | 늘 붙습니다. 그래서 정확한 순서는 `{…, max_tokens, ...extraKwargs, tool_choice}`입니다(294~302). 도구가 빠지는 드문 경로에서는 렌더 맨 앞이 바뀌어 캐시가 처음부터 깨집니다 |
| (2026-11-06 추가) user·assistant의 `content`는 글이면 문자열, 합쳐진 메시지는 블록 배열. 끝에 붙이는 `"."` 턴은 배열 (195) | `(empty)`와 고객 말은 문자열, 첫 멘트는 블록 둘의 배열 |

`(empty)` 턴은 이상해 보이지만 대화 기록 맨 앞에 고정되어 매번 같으므로, 프롬프트 캐시를 깨지는 않습니다.

### 스트리밍 응답: SSE 이벤트

`stream: true`면 응답이 한 번에 오지 않고 **SSE(Server-Sent Events)**로 조각조각 옵니다. SSE는 HTTP 응답을 끊지 않고 `event:`/`data:` 줄을 계속 흘려보내는 단순한 형식입니다.

```text
event: message_start          ← 메시지 시작, 입력 토큰 사용량
event: content_block_start    ← 블록 시작 (thinking 또는 text 또는 tool_use)
event: content_block_delta    ← 조각: text_delta / thinking_delta / signature_delta / input_json_delta
event: content_block_delta
…
event: content_block_stop
event: message_delta          ← stop_reason(end_turn 등), 출력 토큰 사용량
event: message_stop
```

플러그인은 이 이벤트를 다음과 같이 LiveKit의 `ChatChunk`로 바꿉니다.

| 이벤트 | 플러그인 처리 |
| --- | --- |
| `message_start` | 입력 토큰, 캐시 쓰기·읽기 토큰을 기억 |
| `text_delta` | `{ delta: { role: 'assistant', content } }` 청크로 내보냄 → TTS로 흘러감 |
| `content_block_start(tool_use)` + `input_json_delta` | JSON 조각을 모았다가 블록이 끝나면 도구 호출 청크 하나로 내보냄 |
| 생각 블록(`thinking_delta`, `signature_delta`) | **어느 분기에도 걸리지 않아 버려짐.** 내보내지도, 대화 기록에 저장하지도 않음 |
| 스트림 끝 | 사용량 청크 하나: `promptTokens = 입력 + 캐시 쓰기 + 캐시 읽기`, `promptCachedTokens = 캐시 읽기`, `completionTokens = 출력(생각 토큰 포함)` |
| (2026-11-06 추가) `message_delta` | 출력 토큰 수만 읽음(368~369). `stop_reason`은 보지 않음 |
| (2026-11-06 추가) `ping` | 플러그인까지 오지 않음. SDK가 건너뜀(`sdk/streaming.ts` 64~66) |
| (2026-11-06 추가) `error` | SDK가 예외로 던짐(`sdk/streaming.ts` 68~75). 재시도 여부는 8-7절 |

생각 블록이 버려진다는 사실이 8-5절의 "도구를 붙이면 생각 끔이 안전하다"는 판단의 코드상 근거입니다.

[src/models/anthropic.test.ts](../../src/models/anthropic.test.ts)는 이 이벤트들을 **직접 만들어 돌려주는 가짜 서버**를 띄웁니다. 생각 블록(thinking + signature) 다음에 텍스트 블록이 오는 응답을 흉내 내고, 플러그인이 **텍스트만 꺼내 "네, 좋아요."를 돌려주는지** 확인합니다. 생각 내용이 음성으로 새어 나가지 않는다는 보장입니다. 이 테스트 기법은 14장에서 다시 다룹니다.

(2026-11-06 추가) **`signature_delta`란.** 생각 모드에서 생각 블록 끝에 오는 조각으로, 그 생각 블록에 대한 **암호 서명**입니다. 다음 요청에서 생각 블록을 그대로 돌려줄 때 서버가 "우리가 만든 블록이 맞고 고쳐지지 않았다"를 확인하는 데 씁니다. Haiku 5.5는 생각의 글을 기본으로 생략하므로(문서 기준) 서명만 의미 있는 경우가 많습니다. 이 플러그인은 생각 블록과 서명을 모두 버리므로, 도구를 쓰는 대화에서 생각 블록을 돌려줘야 할 때 돌려줄 것이 없습니다. 8-5절의 "도구를 붙이면 생각 끔이 안전하다"의 다른 면입니다.

```text
event: error
data: {"type": "error", "error": {"type": "overloaded_error", "message": "Overloaded"}}
```

**한 칸 늦은 해석 (코드로 확인, 실측).** 위 표에서 서버는 첫 글을 164ms에 썼는데 플러그인의 첫 청크는 208ms였습니다. 원인은 SDK 0.33.1의 SSE 해석에 있습니다. SDK는 받은 바이트를 버퍼에 이어 붙이고, 빈 줄(`\n\n`)을 찾을 때마다 이벤트 하나를 잘라 냅니다(`sdk/streaming.ts` 233~261). 빈 줄을 찾는 함수가 이렇습니다.

```ts
// sdk/streaming.ts 263~ (findDoubleNewlineIndex, @anthropic-ai/sdk 0.33.1)
for (let i = 0; i < buffer.length - 2; i++) {
  if (buffer[i] === newline && buffer[i + 1] === newline) return i + 2;   // \n\n
  …
}
```

`i`는 `buffer.length − 3`까지만 갑니다. 버퍼 맨 끝 두 바이트가 `\n\n`이면(i = length − 2) 검사하지 않고 지나갑니다. 서버가 이벤트 하나를 보내고 다음을 아직 보내지 않았다면 버퍼는 정확히 `…\n\n`로 끝나므로, **그 이벤트는 다음 바이트가 올 때까지 버퍼에 남습니다**(스트림이 끝나면 남은 것을 내보냄, 258). `@anthropic-ai/sdk` 1.4.0(Bedrock SDK 밑에 깔린 판)은 같은 함수가 `i < buffer.length - 1`이라 이 문제가 없습니다(`src/internal/decoders/line.ts` 113).

실습은 서버가 이벤트 하나를 쓰고 300ms 쉰 뒤 다음을 쓰게 해서 두 SDK를 비교합니다(실측, 가짜 서버).

```text
SDK 0.33.1 (Anthropic 플러그인)  서버가 쓴 시각: message_start 0, message_stop 300 → 받은 시각: message_start 304, message_stop 304
SDK 1.4.0 (Bedrock SDK 밑)       서버가 쓴 시각: message_start 0, message_stop 300 → 받은 시각: message_start 5, message_stop 305
```

- 영향: Anthropic 경로에서 첫 `text_delta`는 **그다음 이벤트가 도착할 때까지** 늦게 나옵니다. 실제 서버에서 첫 글 조각과 다음 조각 사이가 얼마인지는 재지 않았습니다. 토큰이 초당 수십~수백 개씩 나오는 중이라면 수~수십 ms일 것입니다(추정). 네트워크가 여러 이벤트를 한 덩어리로 실어 오면 그 덩어리의 마지막 이벤트만 늦습니다.
- 확인 방법(제안): 실제 API에 같은 요청을 두 SDK로 번갈아 보내, 첫 `text_delta`가 나온 시각을 비교합니다(과금). 플러그인을 고치는 것은 이 레포의 일이 아니므로 LiveKit에 알릴 거리입니다.

## 8-7. LiveKit의 LLM 추상화

LiveKit Agents는 공급사마다 다른 API를 하나의 인터페이스로 감쌉니다.

```text
llm.LLM (추상 클래스)
 ├─ chat({ chatCtx, toolCtx, extraKwargs, … }) → LLMStream
 │
 ├─ @livekit/agents-plugin-anthropic 의 LLM   ← Anthropic Messages API
 ├─ inference.LLM                              ← LiveKit Inference (GPT-6 Luna 등)
 └─ … (OpenAI, Google 등 플러그인)

LLMStream = AsyncIterable<ChatChunk>
ChatChunk = {
  id,
  delta?: { role, content?: string, toolCalls?: FunctionCall[] },   ← 글 조각 / 도구 호출
  usage?: { promptTokens, completionTokens, promptCachedTokens, … } ← 사용량
}
```

- **`ChatContext`**: 대화 기록입니다. `ChatMessage`(role, content 배열), 도구 호출, 도구 결과 같은 항목의 목록입니다.
- **`LLMStream`**: `for await`로 순회하는 비동기 스트림입니다(12장). 한 조각씩 받아서 바로 TTS 쪽으로 넘깁니다.
- 공급사를 바꿔도 에이전트 코드는 그대로입니다. [src/models/index.ts](../../src/models/index.ts)의 `createLLM()`이 환경변수에 따라 Anthropic 플러그인 또는 LiveKit Inference를 고를 뿐입니다(15장).

| 층 | 하는 일 | 위치 |
| --- | --- | --- |
| 세션 | LLM 연결 옵션을 넘김. 이 레포는 바꾸지 않아 기본값 `{maxRetry: 3, retryIntervalMs: 2000, timeoutMs: 10000}` | `agents/voice/agent.ts` 559, `agents/voice/agent_session.ts` 747, `agents/types.ts` 63~67 |
| LiveKit `LLMStream` | 최대 maxRetry + 1 = **4번** 시도. 오류가 `APIError`이고 `retryable`이면 기다렸다 다시. 기다림은 첫 재시도 **100ms**, 그 뒤 **2,000ms** | `agents/llm/llm.ts` 308~360, `agents/types.ts` 69~82 |
| 플러그인 | 오류를 `retryable` 플래그가 붙은 LiveKit 오류로 바꿈 | `plugin/llm.ts` 456~477 |
| SDK | 스스로는 재시도하지 않음(`maxRetries: 0`). 시간 제한 `timeoutMs`를 받아 씀 | `plugin/llm.ts` 80·358~360 |

플러그인의 판정은 이렇습니다.

1. `retryable`은 `true`로 시작해서, 글 조각이나 도구 호출을 **하나라도 내보내면** `false`가 됩니다(346, 390·415·439). 고객 귀에 이미 간 말을 다시 만들 수 없기 때문입니다.
2. SDK의 `Anthropic.APIError`이면: 상태 408은 `APITimeoutError`, 나머지는 `APIStatusError`로 바꾸고 `retryable = retryable && (상태 === 429 || 상태 >= 500)`입니다.
3. 그 밖의 오류는 `APIConnectionError`(retryable 그대로)입니다.

그런데 SDK 0.33에서 연결 실패, 시간 초과, 스트림 중간 `error` 이벤트는 모두 `APIError`의 하위 클래스이면서 **상태 코드가 없습니다**(`sdk/error.ts` 104~117, `sdk/core.ts` 467~479). 그래서 2번으로 가고, `undefined === 429 || undefined >= 500`은 거짓이라 **재시도하지 않습니다.** LiveKit 쪽 상태 코드는 −1로 찍힙니다(`agents/_exceptions.ts` 92).

시간 제한도 생각과 다릅니다. SDK는 `fetch`를 부를 때 타이머를 걸고 **`fetch`가 풀리는 순간**, 곧 응답 머리글이 오면 타이머를 지웁니다(`sdk/core.ts` 548~564). 10초는 "머리글이 올 때까지"이고, 그 뒤 본문 스트림에는 시간 제한이 없습니다.

가짜 서버로 경우마다 확인했습니다([lab/08-request-dump.mjs](lab/08-request-dump.mjs) 5번, 실측, 시간 제한 실험만 0.5초로 줄임).

| 경우 | 서버가 받은 요청 (ms) | LiveKit이 받은 오류 | 다시 보냈나 |
| --- | --- | --- | --- |
| HTTP 529 (스트림 전) | 4개: 4, 111, 2,117, 4,123 | `APIStatusError` 529, retryable | **예, 3번.** 4.1초 뒤 실패 |
| HTTP 400 | 1개 | `APIStatusError` 400 | 아니요 (맞음) |
| 200 + `error` 이벤트, 글 전 | 1개 | `APIStatusError` −1, retryable=false | **아니요** (같은 과부하인데 529와 다름) |
| 200 + `error` 이벤트, 글 뒤 | 1개 | 같음 | 아니요 (맞음). "스테인리스 텀블러도"는 이미 나감 |
| 머리글이 1.5초 늦음 | 1개 | `APIStatusError` −1 "Request timed out." | **아니요** |
| 머리글 뒤 1.5초 멈춤 | 1개 | 없음 | 시간 제한이 걸리지 않고 1.5초 뒤 글이 나옴 |
| 연결 거부 | 0개 | `APIStatusError` −1 "Connection error." | **아니요** |
| Bedrock 클라이언트 + HTTP 400 | 4개: 7, 116, 2,136, 4,162 | `APIConnectionError`, retryable | **예, 3번** (400인데도) |

- **연결 오류, 시간 초과, 스트림 중간 오류는 재시도되지 않습니다.** 플러그인 옵션 설명("framework owns retries", `plugin/llm.ts` 35)의 의도와 다른 결과입니다. 순간적인 연결 끊김 한 번이 그 턴의 답을 통째로 없앱니다.
- **Bedrock 경로는 거꾸로입니다.** Bedrock 클라이언트는 SDK 1.4 위에 있어 그 오류는 플러그인이 가진 SDK 0.33의 `Anthropic.APIError` 클래스가 아닙니다(같은 이름의 다른 클래스). `instanceof`가 거짓이라 3번으로 가서, 400·403처럼 다시 보내도 소용없는 오류까지 세 번 다시 보내고 상태 코드도 잃습니다. 8-8절 "타입 강제 변환의 대가"의 또 다른 예입니다.

**최악의 침묵 손 계산.** 고객 말이 끝나면 "네네"(즉시 반응, 11장)가 먼저 나가고, 그 뒤부터 첫 답 글까지가 침묵입니다. 모든 시도가 실패하면 답이 없고, 에이전트가 듣기 상태로 돌아간 뒤 고객과 에이전트가 함께 10초 조용하면 "여보세요? 제 목소리 잘 들리세요?"가 나갑니다([src/call-guard.ts](../../src/call-guard.ts), `userAwayTimeout` 타이머는 둘 다 듣기 상태일 때만 돎, `agents/voice/agent_session.ts` 1917).

| 상황 | 실패까지 | "여보세요?"까지 |
| --- | --- | --- |
| 529가 바로 돌아옴(왕복 r = 0.3초로 가정) | 4r + 0.1 + 2 + 2 = 4.1 + 1.2 = **5.3초** | 약 15.3초 |
| 매 시도가 10초 가까이 끌다 5xx | 4 × 10 + 4.1 = **44.1초** (계산상 최대) | 약 54초 |
| 머리글이 오지 않음 | **10초** (재시도 없음) | 약 20초 |
| 머리글 뒤 멈춤 (`ping`만 옴) | 클라이언트 쪽 한도 없음. 서버가 끝내거나 고객이 말해 끊을 때까지 | — |
| Bedrock 403 (모델 자격 없음, 16장) | 4r + 4.1 = 약 5.3초 | 약 15.3초 |

- 복구할 수 없는 LLM 오류가 연달아 4번째가 되면 세션이 오류로 닫히지만(`maxUnrecoverableErrors` 3, `agents/types.ts` 114, `agent_session.ts` 1819~1846), 에이전트가 말을 시작하면 그 수가 0으로 돌아가므로(1880) "여보세요?"를 하는 이 레포에서는 잘 일어나지 않습니다(코드로 추론).
- 대응 후보(제안): 재시도 판정을 LiveKit에 알리기(상태 코드 없는 SDK 연결 오류를 연결 오류로 분류), 시간 제한을 음성에 맞게 줄이되 지금은 시간 초과가 재시도되지 않으므로 줄이기만 하면 "더 빨리 포기"가 될 뿐이라는 점을 함께 보기, 긴 대기 중 짧은 안내 멘트. 모두 측정과 함께 결정할 일입니다.

## 8-8. 기법: 플러그인이 지원하지 않는 옵션을 넣는 법

### 문제

Anthropic 플러그인 1.9.5의 생성자에는 `thinking`, `effort`, 자동 캐시 옵션이 없습니다. 그런데 Haiku 5.5를 음성용으로 쓰려면 셋 다 필요합니다.

### 발견

플러그인 코드를 읽어 보니, `chat()`이 받는 `extraKwargs`를 **요청 본문에 그대로 펼쳐 넣습니다.** 원래는 공급사별 추가 옵션을 넘기라고 열어 둔 통로입니다.

### 해결: 상속으로 감싸기

```ts
// src/models/anthropic.ts
export class VoiceAnthropicLLM extends anthropic.LLM {
  #extra: Record<string, unknown>;

  constructor({ effort, thinking, ...opts }: VoiceAnthropicOptions) {
    const apiKey = opts.apiKey ?? process.env.ANTHROPIC_API_KEY;
    super({ ...opts, ...(apiKey ? { apiKey } : {}) });
    this.#extra = {
      thinking: thinking === 'off' ? { type: 'disabled' } : { type: 'adaptive' },
      output_config: { effort },
      cache_control: { type: 'ephemeral' },
    };
  }

  override chat(args: Parameters<anthropic.LLM['chat']>[0]) {
    return super.chat({ ...args, extraKwargs: { ...this.#extra, ...args.extraKwargs } });
  }
}
```

한 줄씩 보면 배울 것이 많습니다.

| 코드 | 의미 |
| --- | --- |
| `extends anthropic.LLM` | 플러그인을 고치지 않고 **바깥에서** 동작을 덧붙입니다. 플러그인을 업그레이드해도 이 클래스는 그대로입니다 |
| `{ effort, thinking, ...opts }` | 우리만 쓰는 옵션 둘을 떼고 나머지는 부모에게 그대로 넘깁니다 |
| `#extra` | JavaScript의 **진짜 private 필드**입니다(`private` 키워드와 달리 런타임에도 밖에서 접근 불가). 부모 클래스의 필드 이름과 충돌할 걱정도 없습니다 |
| `override chat(...)` | tsconfig의 `noImplicitOverride` 때문에 `override`를 명시해야 합니다. 부모 메서드 이름이 바뀌면 컴파일 오류로 알려 줍니다 |
| `Parameters<anthropic.LLM['chat']>[0]` | 부모 `chat`의 첫 인자 타입을 **그대로 가져옵니다.** 타입을 직접 다시 쓰지 않아 플러그인이 바뀌어도 따라갑니다 |
| `{ ...this.#extra, ...args.extraKwargs }` | 순서가 중요합니다. 호출하는 쪽이 같은 키를 주면 **호출자가 이깁니다.** 기본값은 우리가, 예외는 호출자가 정하는 구조입니다 |

이 클래스는 LiveKit의 `llm.LLM` 인터페이스를 그대로 만족하므로, 세션 입장에서는 일반 Anthropic LLM과 구분되지 않습니다. 그리고 **정말로 요청 본문에 값이 들어가는지**는 가짜 서버 테스트(8-6절)로 확인합니다. 문서를 믿지 않고 실제 바이트를 검사하는 것이 핵심입니다.

### 함정: import 시점에 읽는 환경변수

생성자의 이 줄에 주목하세요.

```ts
// 플러그인은 import 시점에 ANTHROPIC_API_KEY를 읽어 두므로, dotenv 이후 값으로 다시 넘깁니다.
const apiKey = opts.apiKey ?? process.env.ANTHROPIC_API_KEY;
```

왜 이런 문제가 생길까요? **ES 모듈의 평가 순서** 때문입니다.

```ts
// src/main.ts
import ... from '@livekit/agents';          // ← 1. import된 모듈이 먼저 전부 평가됨
import { createLLM, ... } from './models/index.ts';   //    (플러그인 모듈의 최상위 코드도 이때 실행)
import dotenv from 'dotenv';

dotenv.config({ path: '.env.local' });      // ← 2. 그다음에야 본문 실행: .env.local을 읽음
```

`import` 문은 파일 어디에 쓰든 **본문 코드보다 먼저** 처리됩니다(호이스팅). (2026-11-06 추가) 호이스팅(hoisting, 끌어올림)은 선언이 코드의 어디에 있든 실행 전에 맨 위로 끌어올린 것처럼 동작하는 성질입니다. ES 모듈은 실행 전에 `import`를 모두 읽어 모듈 그래프를 만들고, 의존하는 모듈을 먼저 평가한 다음에야 이 파일의 본문을 실행합니다. 그래서 플러그인 모듈이 최상위에서 `process.env.ANTHROPIC_API_KEY`를 읽어 기본값으로 저장해 두면, 그 시점에는 아직 `.env.local`이 읽히지 않아 값이 비어 있습니다. 해결은 **값이 채워진 뒤(생성자 호출 시점)에 다시 읽어서 명시적으로 넘기는 것**입니다. Soniox 플러그인도 같은 문제가 있어 같은 방법으로 고쳤습니다([5-poc-results.md](../5-poc-results.md) "고친 버그", [src/models/index.ts](../../src/models/index.ts)). [src/config.ts](../../src/config.ts)의 `loadConfig()`가 "dotenv를 읽은 뒤에 호출합니다"라고 주석을 단 것도 같은 이유입니다.

### 응용: 연결만 바꿔 끼우기, Bedrock 클라이언트 (2026-11-05 추가)

LLM을 일본에서 처리하려고 Amazon Bedrock을 붙일 때(13-5절, 16장) 같은 생각을 한 번 더 썼습니다. 계정·권한 쪽은 16장에 있고, 여기서는 코드만 봅니다.

**문제.** LiveKit의 AWS 플러그인은 Node SDK를 지원하지 않습니다. 다른 플러그인을 새로 쓰면 위의 `VoiceAnthropicLLM`(생각 모드·effort·자동 캐시)도 다시 만들어야 합니다.

**발견.** Anthropic 플러그인 옵션에는 `client`(미리 만든 Anthropic SDK 클라이언트)가 있습니다. 플러그인 코드(`dist/llm.js`)를 보면 그 클라이언트로 하는 일은 셋뿐입니다.

| 플러그인이 쓰는 것 | 언제 | Bedrock 클라이언트(`AnthropicBedrock`)에서 |
| --- | --- | --- |
| `client.messages.create({ …, stream: true })` | 매 턴의 요청 | 있음. SDK가 Bedrock 모양으로 다시 씀(16-6절) |
| `client.models.list({ limit: 1 })` | `_prewarmImpl`: 세션이 시작될 때 미리 연결 | **없음.** TypeError가 나지만 SDK의 `prewarm()`이 조용히 삼킴 (17-2 #27, 아래 "미리 연결 대신 하기"에서 고침) |
| `client.baseURL` | `provider` 이름(지표 라벨) | `bedrock-runtime.ap-northeast-1.amazonaws.com` |

**해결.** 플러그인도, 감싸는 클래스도 그대로 두고 클라이언트만 바꿉니다([src/models/index.ts](../../src/models/index.ts)).

```ts
case 'bedrock': {
  const client = createBedrockClient();
  return new VoiceAnthropicLLM({
    model: config.model, // 기본 jp.anthropic.claude-haiku-5-5
    effort: config.effort,
    thinking: config.thinking,
    maxTokens: 2048,
    // 플러그인은 @anthropic-ai/sdk 0.33 타입을 기대하지만, 쓰는 것은 messages.create 스트림뿐입니다.
    client: client as unknown as NonNullable<anthropic.LLMOptions['client']>,
    prewarmUrl: client.baseURL,
  });
}

export function createBedrockClient(): AnthropicBedrock {
  return new AnthropicBedrock({
    awsRegion: process.env.AWS_REGION || 'ap-northeast-1',
    apiKey: null,
    maxRetries: 0,
  });
}
```

- `maxRetries: 0`은 플러그인의 기본값과 같습니다. 재시도는 LiveKit이 연결 옵션으로 하므로, SDK까지 재시도하면 실패한 턴이 겉으로 드러나지 않은 채 몇 배로 늦어집니다.
- (2026-11-05 갱신) 인증 키는 생성자에 넣지 않고 환경변수의 IAM 키를 찾게 둡니다. 다만 `apiKey: null`로 Bedrock API 키 환경변수만은 읽지 않게 막습니다. 처음 코드에는 이 줄이 없어서, 남아 있던 API 키가 IAM 키보다 먼저 쓰였습니다(17-2 #26, 16-4절).
- `prewarmUrl`은 아래 "미리 연결 대신 하기"에서 다룹니다.

**타입 강제 변환의 대가.** `@anthropic-ai/bedrock-sdk` 1.1.1은 `@anthropic-ai/sdk` 1.x 위에 만들어졌고, 플러그인의 타입은 0.33의 `Anthropic` 클래스를 가리킵니다. TypeScript는 모양(구조)으로 타입을 비교하는데, 두 버전의 클래스는 멤버가 달라 서로 대입되지 않습니다. 그래서 `as unknown as …`로 **"이 경계에서는 검사하지 마라"**고 컴파일러에 알립니다. 관련 없는 두 타입 사이의 직접 변환은 TypeScript가 거부하므로 `unknown`을 한 번 거칩니다. `NonNullable<anthropic.LLMOptions['client']>`는 0.33 SDK를 따로 import하지 않고 플러그인이 선언한 타입을 그대로 꺼내 쓰는 방법입니다.

대가는 바로 위 표에 있습니다. 플러그인이 `messages` 말고 다른 것을 쓰면 컴파일러가 알려 주지 않습니다. 실제로 `models.list`가 그랬고, 오류마저 삼켜져 아무 표시 없이 미리 연결만 빠졌습니다. 강제 변환은 **검사를 사람에게 넘기는 것**이라, 그 경계를 지키는 장치가 따로 있어야 합니다. 예를 들어 플러그인을 올릴 때마다 Bedrock으로 한 턴을 돌려 보거나, 플러그인이 부르는 메서드가 Bedrock 클라이언트에 있는지 확인하는 테스트(14장)를 둡니다.

(2026-11-06 추가) 메서드만이 아니라 **오류 클래스**도 경계를 넘습니다. 플러그인은 `e instanceof Anthropic.APIError`로 오류를 가르는데(`plugin/llm.ts` 457), 이 `Anthropic`은 0.33이고 Bedrock 클라이언트가 던지는 오류는 1.4의 클래스입니다. 그래서 Bedrock의 400·403이 모두 "재시도 가능한 연결 오류"로 바뀌어 세 번 더 보내집니다. 가짜 서버로 재현했습니다(8-7절 깊이 보기).

**옵션은 그대로 흘러간다.** `VoiceAnthropicLLM`이 넣는 `thinking`, `output_config.effort`, 맨 위 `cache_control`(8-4절의 자동 캐시)은 요청 본문에 실립니다. Bedrock SDK는 본문에서 `model`·`stream`만 빼서 경로로 옮기고 `anthropic_version`을 더하므로(16-6절. (2026-11-06 갱신) 이 SDK판이 넣는 값은 `"2026-10-21"`이고, AWS 문서가 적는 `bedrock-2023-05-31`과 달라 17-2 #54에 남김), 나머지는 그대로 Bedrock에 갑니다. **Bedrock이 이 셋을 Haiku 5.5에서 받아 주는지는 아직 확인되지 않았습니다.** 2026-11-05의 A/B(13-5절)는 Haiku 5.5가 이 계정에 열리지 않아, 이 옵션이 없는 기본 플러그인과 Haiku 4.5로 쟀기 때문입니다. 특히 자동 캐시는 Anthropic API 기능이라 Bedrock이 모르는 필드로 보고 400을 낼 수도 있습니다. Haiku 5.5가 열리면 `LLM_PROVIDER=bedrock pnpm check:llm`으로 운영 경로를 한 번 돌려 봅니다(2026-11-05 확인: 아직 모델 사용 자격 403). `check:llm`은 400 설정 거절을 바로 보여 주도록 만들어져 있습니다(8-9절).

(2026-11-06 갱신) Anthropic 문서의 플랫폼별 기능 표는 자동 캐시(최상위 `cache_control`)를 Bedrock에서도 지원한다고 적고, 거절하는 것은 Opus 4.6 이하용 예전 Bedrock 연동뿐이라고 합니다(문서 기준). 그래서 400 가능성은 낮아 보이지만, 이 계정의 Haiku 5.5로 확인한 것은 아닙니다. Bedrock에서는 캐시가 워크스페이스가 아니라 조직 단위로 나뉩니다(8-4절).

#### 미리 연결 대신 하기 (2026-11-05 추가)

미리 연결(prewarm)은 첫 요청 전에 **DNS 조회, TCP 연결, TLS 핸드셰이크**를 끝내 두는 기법입니다. 서울에서 도쿄까지 왕복이 수십 ms이므로, 새 연결 하나는 왕복 두세 번, 곧 0.1초 안팎입니다. LiveKit은 `AgentSession`을 만들 때 `llm.prewarm()`을 부르고, 플러그인은 그 안에서 `models.list`를 부릅니다. 응답 내용은 버리고 연결만 남기려는 요청입니다.

Bedrock 클라이언트에는 이 메서드가 없으므로, [src/models/anthropic.ts](../../src/models/anthropic.ts)의 `VoiceAnthropicLLM`이 `_prewarmImpl`을 덮어씁니다. `prewarmUrl`이 있으면 그 주소로 서명 없는 HEAD를 보냅니다.

```ts
protected override async _prewarmImpl(signal: AbortSignal): Promise<void> {
  if (!this.#prewarmUrl) return super._prewarmImpl(signal);
  await fetch(this.#prewarmUrl, { method: 'HEAD', signal });
}
```

가짜 키로 거절 응답만 받으며 잰 결과(2026-11-05, 맥 서울)가 이 결정의 근거입니다.

| 실험 | 결과 |
| --- | --- |
| Bedrock 주소에 HEAD | 404와 `connection: close`. **서버가 이 연결은 닫습니다** |
| HEAD 뒤 6초 쉬고 첫 요청 vs 미리 연결 없이 첫 요청 | 6쌍 모두 HEAD 쪽이 빠름. 중앙값 약 0.165초 vs 0.21초 |
| 서명한 요청 뒤 0·3초 쉬고 다음 요청 | 연결 재사용 (새 연결 0) |
| 서명한 요청 뒤 5·10초 쉬고 다음 요청 | 새 연결 1 |
| Anthropic 경로(SDK 0.33) 같은 실험 | 0·3초는 재사용, 6초는 새 연결 |

- 연결이 닫혀도 빨라지는 이유는 **DNS 결과와 TLS 세션**이 남기 때문입니다. TLS 1.3은 전에 받은 세션 티켓으로 다시 맺을 수 있습니다(세션 재개). (2026-11-06 갱신) 0-RTT를 쓰지 않으면 왕복 수는 그대로이고, 줄어드는 것은 인증서를 주고받고 검증하는 몫입니다(13-2절 깊이 보기). SDK도 같은 전역 `fetch`를 써서 세션 캐시를 같이 씁니다.
- 연결 자체는 4초 넘게 쉬면 **클라이언트 쪽에서** 닫습니다. Node 내장 fetch(undici)와 SDK 0.33의 `agentkeepalive` 모두 쉬는 연결을 4초 뒤 닫는 것이 기본값이고, AWS는 더 오래 두라는 `Keep-Alive` 머리글을 보내지 않습니다. 통화에서는 세션을 만들고 고지 멘트가 끝난 뒤에야 첫 LLM 요청이 가므로, Anthropic 경로의 미리 연결도 실제로는 DNS·TLS 세션 정도만 남깁니다. 그래서 HEAD 방식으로 두 경로가 같은 수준이 됩니다.
- 이 실험이 더 큰 질문을 남겼습니다. 턴 사이(AI가 말하고 고객이 답하는 시간)가 4초를 넘으면 **매 턴이 연결을 다시 맺습니다**(17-2 #28). 실제 통화에서 얼마인지는 아직 재지 않았습니다(13-5절).

## 8-9. 측정 도구: check-llm

[scripts/check-llm.ts](../../scripts/check-llm.ts)는 LLM 하나만 떼어 지연을 잽니다. 음성 전체를 돌리지 않고 LLM만 재는 이유는 **변수를 하나로 줄이기 위해서**입니다.

- 실제 지시문(`buildInstructions(SAMPLE_CALL)`)과 첫 멘트, 가격을 묻는 고객 대사로 대화를 만듭니다.
- 생각 모드·effort 조합 세 가지를 각각 N번 돌립니다.
- 측정 항목: 첫 토큰 시간, 전체 시간, 출력 토큰 수, 캐시 토큰 수, 답 길이.
- 첫 회는 캐시를 쓰는(write) 회차라 느리고, 2회차부터가 실제 통화 중 상황에 가깝습니다.
- API 오류는 스트림이 아니라 `error` 이벤트로 오기 때문에 `model.on('error', …)`로 잡아 바로 종료합니다. 400(설정 거절)을 놓치지 않기 위해서입니다.

`performance.now()`로 시간을 재고 `??=`(값이 없을 때만 대입)로 첫 토큰 시각을 한 번만 기록하는 패턴도 눈여겨볼 만합니다.

```ts
if (chunk.delta?.content) {
  firstToken ??= performance.now() - started;
  text += chunk.delta.content;
}
```

### A/B 도구: compare-llm (2026-11-05 추가)

[scripts/compare-llm.ts](../../scripts/compare-llm.ts)(`pnpm compare:llm`)는 같은 대화를 Anthropic API와 Bedrock `jp.`에 **번갈아** 보내 첫 토큰 시간을 비교합니다.

- **번갈아 부르는 이유.** 서버 혼잡은 시간에 따라 바뀝니다. A를 10번 다 부르고 B를 10번 부르면 "공급자 차이"와 "시간대 차이"가 섞여 가를 수 없습니다. A, B, A, B…로 엮으면 시간에 따른 흔들림이 양쪽에 고르게 들어갑니다. 실험 설계에서 교란 변수를 막는 기본 기법입니다.
- **세 숫자.** 중앙값(p50)은 튀는 값에 강하고, p90은 꼬리(13-6절)를, 최소는 "모든 것이 잘 맞았을 때"의 바닥을 보여 줍니다. 최소의 차이는 거리(네트워크) 몫에 가깝고, 중앙값의 차이는 거기에 서버 대기까지 합친 몫입니다.
- **표본이 작습니다.** (2026-11-06 갱신) 이 스크립트의 백분위 식(`sorted[floor(n·p)]`)으로는 12회면 p90이 두 번째로 느린 값이고, **10회(기본값)면 최댓값**입니다(13-6절 깊이 보기 "백분위를 손으로"). 0.1초 안쪽 차이는 다시 재서 같은 방향이 나오는지 봐야 합니다.
- **운영과 같은 경로.** 이 스크립트는 운영과 같은 `createLLM`을 써서, 인증도 운영과 같은 순서로 찾습니다. 2026-11-05의 실제 측정은 #26이 남아 있어 Bedrock API 키 변수를 지운 임시 스크립트로 했습니다. #26을 고친 지금은 그대로 돌려도 됩니다.
- **재사용된 연결로 잰 값.** 두 경로를 쉬지 않고 번갈아 부르므로, 한쪽이 쉬는 시간은 다른 쪽 호출 하나(1~2초)뿐이라 4초 유휴 종료(17-2 #28)에 걸리지 않습니다. 실제 통화는 턴 사이가 더 길어 두 경로 모두 연결을 다시 맺는 몫이 더해질 수 있습니다.

## 8-11. 통화 후 판정 코드 읽기: 구조화 출력 (2026-11-04 추가)

> originalshq `functions-xtool/src/voice-call/analyze.ts`(커밋 `d57c577`)를 바탕으로 썼습니다. 이 레포 밖의 코드지만, 이 프로젝트에서 LLM을 **말하는 데가 아니라 칸을 채우는 데** 쓰는 유일한 곳이라 따로 봅니다. 저장과 트리거 쪽은 15-6절에서 다룹니다.

### 요청의 모양

```ts
const response = await client.beta.messages.parse({
  model: 'claude-opus-5-5',
  max_tokens: 16000,
  betas: ['server-side-fallback-2026-07-01'],        // 거절되면 서버가 다른 모델로 다시 돌림
  fallbacks: 'default',
  output_config: {
    effort: 'low',                                    // Opus 5.5 기본은 medium
    format: betaZodOutputFormat(CallJudgmentSchema),  // 이 모양의 JSON만 내게
  },
  system: SYSTEM,
  messages: [{ role: 'user', content: renderTranscript(record) }],
});
if (response.stop_reason === 'refusal') throw new Error(`판정 모델이 거절했습니다: ...`);
if (!response.parsed_output) throw new Error(`판정 결과를 읽지 못했습니다 ...`);
return response.parsed_output;                       // 타입이 CallJudgment
```

통화 중 요청(8-6절)과 비교하면 세 가지가 다릅니다.

- **스트리밍이 아닙니다.** 기다리는 사람이 없으니 첫 토큰을 서두를 이유가 없고, 한 번에 받아 검사합니다.
- **출력이 말이 아니라 JSON입니다.** 코드가 바로 Firestore에 저장하고 화면이 칸별로 보여 줍니다.
- **타입까지 받습니다.** `parse()`가 응답 JSON을 zod 스키마로 읽어 `parsed_output`에 담으므로, TypeScript에서 `result.budget`이 정해진 값 중 하나라는 것까지 압니다. `betas`를 쓰는 베타 경로라 도우미도 베타용(`betaZodOutputFormat`)을 씁니다.

### 구조화 출력: "JSON으로 답해 줘"와 무엇이 다른가

LLM에게 정해진 모양의 답을 받는 방법은 대략 이렇게 발전했습니다.

| 방법 | 보장 | 실패 모습 |
| --- | --- | --- |
| 지시문에 "JSON으로만 답하라" | 없음. 확률적으로 잘 지킴 | 앞에 설명 문장, 닫는 괄호 누락, 없는 값 이름 |
| 도구 호출 형식 빌리기 (가짜 도구의 입력으로 받기) | 대체로 모양을 지킴 | 드물게 필드 누락·타입 틀림 |
| **구조화 출력** (`output_config.format`) | **스키마에 맞는 JSON** | 거절·토큰 한도 같은 예외만 |

원리는 **제약 디코딩(constrained decoding)**입니다. 8-1절에서 본 것처럼 LLM은 매 단계 다음 토큰의 확률 분포를 내고 그중 하나를 고릅니다. 제약 디코딩은 고르기 전에 **스키마(문법)를 어기게 되는 토큰을 후보에서 지웁니다.** 예를 들어 `"budget": "` 다음에는 `~300만`, `300~700만`, `700만~`, `미정`, `미확인` 중 하나로 이어질 수 있는 토큰만 남습니다. 그래서 모양은 "잘 지키는" 것이 아니라 **어길 수 없습니다.** 6-8절의 정규식이 다 만들어진 글을 고치는 장치라면, 이것은 글이 만들어지는 순간에 문법을 강제하는 장치입니다.

(2026-11-06 추가) **어떻게 지우나(일반적인 구현).** 스키마를 문법으로 바꾸고, 그 문법을 **유한 상태 기계(FSM, finite-state machine)**로 만들어 둡니다. 상태는 "지금 JSON의 어디까지 썼나"(예: `"budget": "` 바로 뒤)이고, 상태마다 다음에 올 수 있는 토큰 집합이 정해져 있습니다. 매 단계 허용되지 않는 토큰의 로짓에 −∞를 더하면 소프트맥스(8-2절)에서 확률이 정확히 0이 되고, 남은 후보끼리 다시 나눠 뽑습니다. 8-4절 인과 마스크와 같은 수법입니다. 토큰 하나가 여러 글자를 담고 있어(8-1절) 실제 구현은 "이 토큰의 글자들을 이어 받아도 문법 안에 있나"를 토큰마다 미리 계산해 둡니다. Anthropic이 내부에서 이렇게 구현하는지는 공개되지 않았습니다.

단, 보장하는 것은 **모양**이지 **내용이 사실인지**가 아닙니다. 예산을 말한 적 없는 고객의 `budget`에 그럴듯한 값을 넣는 것은 스키마가 막지 못합니다. 그래서 스키마를 어떻게 짜느냐가 중요합니다.

### 스키마도 지시문이다

```ts
const unknownOr = (values) => z.enum([...values, '미확인']);

budget: unknownOr(['~300만', '300~700만', '700만~', '미정']),
visitTime: z.string().describe('방문체험 희망 일시(고객이 말한 그대로). 없으면 빈 문자열.'),
interest: z.enum(['높음', '보통', '낮음']),
interestReason: z.string().describe('관심도 판정 근거 한 줄.'),
```

| 설계 | 효과 |
| --- | --- |
| 값 이름을 업무 문서(README 6-2) 표와 똑같이 | 결과를 Monday 칸·통계로 그대로 옮길 수 있음. 자유 글이면 "300만 원 이하", "삼백 이하"처럼 흩어짐 |
| 사실 칸마다 **`'미확인'` 선택지** | **강제 선택(forced choice)을 피함.** 고를 값이 넷뿐이면 모델은 넷 중 하나를 고를 수밖에 없음. "모름"을 표현할 출구가 있어야 지어내지 않음. 지시문의 "추측으로 칸을 채우지 말고 미확인"과 짝 |
| `'미정'`과 `'미확인'`을 구분 | "고객이 아직 안 정했다"(사실)와 "통화에서 확인 못 했다"(정보 없음)는 다른 정보. 상담사가 다음 통화에서 물을 것이 달라짐 |
| `interest`, `outcome`에는 `'미확인'` 없음 | 사실이 아니라 **판단**이라 항상 내리게 함. 대신 `interestReason`으로 근거 한 줄을 받아 사람이 검증할 수 있게 |
| `.describe()` | JSON Schema의 `description`이 되어 모델에게 전달됨. 칸마다 붙는 작은 지시문. "고객이 말한 그대로"처럼 멋대로 정규화하지 말라는 지시도 여기 |
| 자유 글 칸은 "없으면 빈 문자열" | 없는 값의 표기를 하나로 고정 (`null`, "없음", "-"가 섞이지 않게) |

9장에서 지시문을 "모델에게 주는 설계 문서"로 봤다면, 구조화 출력에서는 **스키마가 그 설계 문서의 일부**입니다. 칸 이름, 허용 값, 설명이 모두 모델이 읽는 지시입니다.

(2026-11-06 추가) 여기서 **JSON Schema**는 JSON 데이터의 모양(칸 이름, 타입, 필수 여부, 허용 값 `enum`, 설명 `description`)을 다시 JSON으로 적는 표준 형식입니다. zod 스키마는 요청을 보낼 때 이 형식으로 바뀌어 `output_config.format`에 실립니다. 통화 중 `end_call` 도구의 `input_schema`도 같은 형식입니다(8-6절 덤프의 `"$schema": "http://json-schema.org/draft-07/schema#"`).

### 잡음 섞인 입력 다루기

대화록의 고객 말은 STT 결과입니다(6장). 시스템 지시문은 판매 기기 목록을 주고 "제품명이 조금 틀리게 적혀 있을 수 있으니 맥락으로 바로잡아 읽으라"고 합니다. 6장의 문맥 편향(STT에 단어 목록, 6-6절)과 코드 보정(`correctTranscript`, 6-8절의 "마지막 방어선")은 통화 중에 빠르게 고치는 장치입니다. 이것은 **통화가 끝난 뒤의 방어선**으로, 큰 모델이 문맥 전체를 보고 고칩니다. AI 말에 발음 변환된 글("에프투 울트라")이 남는 경우(17-2 #10)에도 이 목록이 도움이 될 수 있습니다.

### effort와 생각 모드

Opus 5.5는 생각 모드가 항상 켜져 있고 끌 수 없습니다(`thinking: disabled`를 보내면 400). 깊이는 `effort`로만 조절하며 기본은 medium입니다. 정해진 칸을 채우는 일은 긴 추론보다 꼼꼼한 읽기라 low로 낮췄습니다. 통화 중 Haiku 5.5에서 생각을 끈 이유는 지연(8-5절)이었지만, 여기서 낮춘 이유는 비용입니다. 생각 토큰도 `max_tokens` 안에서 쓰이므로, 한도는 출력 JSON보다 넉넉하게(16,000) 잡았습니다.

### 거절과 대체 모델

최신 대형 모델에는 안전 분류기가 있어 요청을 거절할 수 있습니다. 거절은 **HTTP 오류가 아니라** 정상 응답(200)에 `stop_reason: 'refusal'`과 `stop_details.category`로 옵니다. 그래서 응답 내용을 읽기 전에 `stop_reason`부터 봐야 합니다. 영업 통화 요약이 거절될 일은 드물겠지만, 대화록은 고객이 한 말이라 내용을 통제할 수 없습니다.

`fallbacks: 'default'`는 거절되면 **API 서버가 같은 요청을 거절 사유별 기본 대체 모델로 다시 돌려**, 한 번의 호출 안에서 답을 받게 합니다. 베타 헤더와 형식이 짝으로 정해져 있습니다. `'default'` 형식은 `server-side-fallback-2026-07-01`과 짝이고, 모델을 배열로 적는 형식은 다른 날짜의 헤더를 쓰며, 섞으면 400입니다. 대체 모델까지 거절하면 최종 응답이 `refusal`이므로 위의 검사가 여전히 필요합니다.

방어가 층으로 쌓여 있습니다.

```text
거절 → 서버가 대체 모델로 재시도 (fallbacks)
  └ 그래도 거절 → stop_reason 검사 → 예외
모양을 못 맞춤 (토큰 한도 등) → parsed_output이 null → 예외
예외 → 트리거가 status: 'analysis_failed'와 이유를 저장 (15-6절)
```

### 모델에 무엇을 주나

```text

- 이름: 김민수
- 문의 기기: F2 울트라
```

신청서를 함께 주는 것은 "신청서 기기와 다르면 바뀐 기기"처럼 **비교해야 하는 판단**이 있어서입니다. 종료 사유는 `outcome`의 단서입니다(예: 고객이 거의 말하지 않고 무응답으로 끝났으면 "부재"). 지연 기록은 판정과 상관없어 넣지 않습니다.

(다) Bedrock 클라이언트의 오류는 SDK 1.4의 클래스라 플러그인의 `instanceof Anthropic.APIError`(0.33)가 거짓이 되고, 마지막 분기에서 재시도 가능한 `APIConnectionError`가 되어 **400인데도 세 번 더 보냅니다**(약 4.1초 + 왕복 4번 뒤 실패).
