## 7-1. 사람의 턴 테이킹: 대화 분석의 발견

### 턴과 전환 지점

사회학자 Sacks, Schegloff, Jefferson의 1974년 논문 「대화의 턴 테이킹 조직에 관한 가장 단순한 체계」는 대화를 이렇게 설명했습니다.

- 말은 **턴 구성 단위(TCU)**로 이루어집니다. 문장, 구, 단어 하나("네")도 단위가 될 수 있습니다.
- 각 단위가 끝날 수 있는 지점이 **전환 적합 지점(TRP, Transition-Relevance Place)**입니다. 여기서 다른 사람이 말을 이어받을 수 있습니다.
- 듣는 사람은 TRP를 **미리 예측**합니다. 문장이 어떻게 끝날지 문법과 의미로 짐작하기 때문입니다.

### 사람의 공백은 약 0.2초

Stivers 등(2009, PNAS)은 한국어를 포함한 10개 언어의 대화에서 질문과 대답 사이 공백을 쟀습니다. 언어마다 평균은 조금씩 달랐지만(일본어가 가장 짧고 덴마크어가 가장 긴 편), **모든 언어에서 가장 흔한 공백은 0~200ms 근처**였습니다. 턴 테이킹의 타이밍은 문화를 넘어 거의 보편적이라는 뜻입니다.

그런데 사람이 단어 하나를 말하려고 계획해서 입을 떼기까지는 600ms 이상 걸린다고 알려져 있습니다. 200ms 공백이 어떻게 가능할까요? Levinson과 Torreira(2015)의 설명은 이렇습니다. **듣는 사람은 상대가 말하는 도중에 이미 대답을 준비하기 시작하고**, 상대 말이 끝날 신호가 오면 준비된 대답을 내보냅니다.

이것이 11장의 **선제 생성(preemptive generation)**과 정확히 같은 전략입니다. 고객 말이 확정되기 전에 LLM을 미리 돌려 두는 것입니다.

### 말이 끝났다는 신호들

| 신호 | 예 |
| --- | --- |
| 문법·의미 | 문장이 완결됨. 한국어는 "-요", "-다", "-까" 같은 종결 어미 |
| 운율 | 문장 끝 음높이가 내려감(평서) 또는 올라감(질문), 마지막 음절이 길어짐 |
| 숨·멈춤 | 숨을 들이쉼, 말을 멈춤 |
| 시선·몸짓 | 상대를 쳐다봄 (전화에는 없음) |

(2026-11-06 추가) **운율(prosody)**은 말의 내용이 아니라 소리에 실린 정보입니다. 음높이(기본 주파수 F0, 2-1절)의 오르내림, 음절의 길이, 세기, 쉼이 여기에 듭니다. 같은 "네"도 끝을 내리면 대답이고, 끌면서 올리면 "그래서요?"에 가까워집니다. 7-3절의 오디오 턴 감지 모델이 글만 보는 모델보다 문장 중간 쉼에 강한 이유가 이 운율을 듣기 때문입니다.

전화는 시선 신호가 없어서 **소리 신호(말소리 유무, 운율)와 말의 내용**에만 의존해야 합니다.

### 한국어의 특성

- **동사가 문장 끝에 옵니다(SOV).** 종결 어미가 와야 문장이 끝나므로 문법적 끝이 비교적 분명합니다.
- 그런데 문법적으로 끝난 문장 뒤에 **이어 말하는 일이 흔합니다.** PoC에서 고객이 "…하려고요." 하고 잠깐 쉬었다가 다음 문장을 말했는데, AI가 첫 문장에서 답을 시작했다가 끊긴 일이 있었습니다([5-poc-results.md](../5-poc-results.md)). 문법만 보면 끝났으니 판단이 틀렸다고 하기도 어렵습니다.
- **맞장구가 매우 잦습니다.** "네", "예", "음", "아", "그렇죠". 그리고 같은 "네"가 **맞장구일 수도, 질문에 대한 대답일 수도** 있습니다. "이삼 분 통화 괜찮으세요?" 뒤의 "네"는 대답이지만, AI가 길게 설명하는 중의 "네"는 맞장구입니다.

## 7-2. 음성 에이전트의 두 가지 결정

에이전트는 매 순간 두 가지를 결정합니다.

| 결정 | 질문 | 틀리면 |
| --- | --- | --- |
| **말 끝 판단** (end-of-turn) | 고객 말이 끝났나? 이제 대답해도 되나? | 너무 빠르면: 말을 자름 / 너무 느리면: 굼뜨다고 느낌 |
| **끼어들기 판단** (barge-in) | 내가 말하는 중에 고객이 말했다. 멈춰야 하나? | 너무 민감하면: 맞장구에도 멈춤 / 너무 둔하면: "잠깐만요"에도 계속 떠듦 |

두 결정 모두 **두 종류의 오류 사이의 교환**입니다. 하나를 줄이면 다른 하나가 늘어납니다. 튜닝은 "어느 오류가 우리 업무에 더 아픈가"를 정하는 일입니다. 영업 첫 통화에서는 고객 말을 자르는 것이 굼뜬 것보다 더 큰 실례이므로, 약간 느려도 자르지 않는 쪽이 낫다고 볼 수 있습니다.

## 7-3. 말 끝 판단 방법들

| 방법 | 원리 | 장단점 |
| --- | --- | --- |
| 무음 시간 (VAD만) | 무음이 N초 이어지면 끝 | 가장 단순·빠름. 생각하며 쉬는 사람을 자름 |
| STT 끝점 | STT가 알려 주는 끝점 사용 | STT마다 품질이 다름 |
| 텍스트 턴 감지 모델 | 받아 적은 글을 작은 언어 모델에 넣어 "문장이 완결됐나" 판단 | 의미는 보지만 억양을 못 봄. STT가 늦으면 같이 늦음 |
| **오디오 턴 감지 모델** | 소리 자체를 모델에 넣어 의미와 운율을 함께 봄 | 글을 기다리지 않음. 이 프로젝트가 쓰는 방식 |

LiveKit 문서는 텍스트 모델이 문장 중간 쉼("항공권 예약하고 싶은데요… 더블린에서 뉴욕으로… 이번 금요일")에 속아 세 번 턴을 끊는 동안, 오디오 모델은 진짜 끝에서 한 번만 끊는 예를 보여 줍니다. 오디오 모델은 "아직 할 말이 남은 억양"을 듣기 때문입니다. LiveKit의 텍스트 턴 감지 모델은 지금 지원 중단(deprecated) 예정입니다.

## 7-4. 이 프로젝트의 말 끝 판단: 한 턴의 타임라인

설정은 이것뿐입니다.

```ts
// src/main.ts
turnHandling: {
  turnDetection: new inference.TurnDetector(),
  preemptiveGeneration: { enabled: true },
  interruption: { minDuration: 200, discardAudioIfUninterruptible: false },
},
```

### 오디오 턴 감지 모델 (`inference.TurnDetector`)

- **입력은 고객 오디오(16kHz)뿐**입니다. 대화 기록이나 글은 쓰지 않습니다.
- 출력은 "지금 턴이 끝났을 확률" p입니다.
- 두 버전이 있습니다(4장). 클라우드 `v1`은 통화 내내 고객 오디오를 LiveKit Inference로 계속 보내고, 예측이 필요할 때 요청합니다. 로컬 `v1-mini`는 최근 1.2초 오디오를 잘라 공유 추론 프로세스에 보냅니다.
- 한국어를 포함한 14개 언어를 지원합니다.

(2026-11-06 추가) 이름 정리: **`v1`**은 LiveKit Inference(클라우드)에서 도는 전체 모델(`turn-detector-v1`), **`v1-mini`**는 워커의 추론 프로세스에서 도는 작은 모델(`turn-detector-v1-mini`)입니다. 버전을 정하지 않으면 SDK가 고릅니다. LiveKit Cloud 호스팅이나 개발 모드(`dev` 등, 4-5절)면 `v1`, 그 밖(직접 운영 `start`)이면 `v1-mini`입니다(`agents/inference/eot/detector.ts` 76~80). `v1`을 골랐는데 키가 없으면, 자동 선택일 때만 경고하고 `v1-mini`로 내려갑니다(95~111). "14개 언어"는 `v1-mini`의 기준값 표에 든 언어 수입니다(`agents/inference/eot/languages.ts` 21~36).

#### 깊이 보기: 턴 감지 모델의 입력과 출력 (2026-11-06 추가)

두 버전은 같은 스트림 겉모양(`agents/inference/eot/base.ts`)을 쓰고, 안쪽의 **전송(transport)**만 다릅니다(`transports.ts`). 세션은 방에서 온 소리를 VAD·STT로 나누기 **전에** 턴 감지 스트림에 한 프레임씩 넣습니다(`agents/voice/audio_recognition.ts` 552~575). 그래서 고지 중이나 AEC 워밍업 때 STT에 무음이 들어가도(7-6절) 턴 감지와 VAD는 진짜 소리를 받습니다(코드).

**공통 입구 (코드).** 24kHz 프레임을 `QUICK` 리샘플러로 16kHz로 바꿉니다(`base.ts` 332~363, 2-2절). 예측은 `predict()` 하나로 요청합니다. 요청마다 ID(`turn_request_…`)를 새로 만들고 앞 요청을 밀어내며, 결과는 Future(나중에 값이 채워지는 약속 객체)로 돌려줍니다(251~268).

**`v1-mini` (코드).**

| 단계 | 일 | 코드 |
| --- | --- | --- |
| 쌓기 | 16kHz 샘플을 **고리 버퍼**(크기가 고정이라 가득 차면 가장 오래된 것부터 덮어쓰는 버퍼)에 넣음. 크기 19,200샘플 = 1.2초 | `transports.ts` 85~133·221~223 |
| 요청 | 그 순간 버퍼의 스냅숏(최대 19,200샘플 = 38,400B)을 base64(51,200자)로 바꿔 `executor.doInference('lk_eot_audio', { pcm })` | 170~219 |
| 건너가기 | 잡 → 워커 → 추론 프로세스, [IPC](17-glossary-and-next.md#17-1-용어집)(Node 기본 JSON 한 줄) 두 구간 | [4-5절 깊이 보기](04-worker-runtime.md#4-5-추론-프로세스와-턴-감지-모델의-위치) |
| 계산 | base64 → `Int16Array` → `@livekit/local-inference`의 `predict()`. libuv 스레드 풀에서 돌아 메인 스레드를 막지 않음 | `runner.ts` 55~71, 4-4절 |

| 턴 경계 | 턴이 확정되면 버퍼를 비움(flush). 그래서 다음 턴의 첫 예측은 1.2초보다 짧은 소리로 할 수 있음 | `transports.ts` 225~229, `audio_recognition.ts` 1965~1969 |

[lab/07-eot-curve.mjs](lab/07-eot-curve.mjs) 0·5·6번에서 모델의 계약, SDK 경로, 시간을 직접 확인했습니다(실측. 4번은 아래 깊이 보기 "쉼 동안의 확률…").

```text

```

- **입력 길이.** 선언 파일(`index.d.ts`) 주석은 "1.2초보다 짧으면 앞을 무음으로 채우고, 길면 오른쪽에 맞춰 자른다"고 적지만, 40,000샘플을 넣으면 자르지 않고 `RangeError`를 던졌습니다. SDK는 고리 버퍼가 19,200샘플을 넘지 않으므로 이 길을 밟지 않습니다. 짧은 입력은 주석대로 앞을 0으로 채운 것과 같은 값이 나왔습니다.
- **상태가 없습니다.** VAD(5-3절)는 핸들마다 LSTM 상태를 들고 다니지만, 턴 감지는 같은 입력에 늘 같은 값을 냅니다. 판단 근거는 그 1.2초 안의 소리뿐이고, 그보다 앞의 말(긴 문장의 앞부분)은 보지 않습니다.
- **"무음"에도 모양이 있습니다.** 완전한 0(디지털 무음) 1.2초에는 0.30을 내지만, 방의 무음을 SDK처럼 리샘플한 것에는 0.57~0.64(실행마다 다름)를 냅니다. rtc-node 리샘플러가 16비트로 내보낼 때 샘플의 약 4분의 1에 ±1을 섞기 때문입니다. 이렇게 일부러 섞는 아주 작은 무작위 잡음을 **디더(dither)**라고 합니다. 정수로 반올림할 때 생기는 규칙적인 오차를 흩어 없애려는 것입니다. 2-2절에서 "실행마다 1~2 LSB 다르다, 디더 때문으로 보인다(추정)"고 적은 현상을, 0을 넣어도 ±1이 나오고 두 번 돌리면 약 8,100~8,200샘플이 달라지는 것으로 다시 확인했습니다(실측). 리샘플러가 libsoxr로 계산한다는 것은 2-2절에서 봤고, 디더를 섞는 곳이 soxr 안인지 rtc-node 안인지는 소스로 확인하지 않았습니다. 실제 통화는 회선 잡음이 ±1보다 훨씬 크므로, 모델이 실제로 보는 "쉼"은 0.30 쪽이 아니라 0.6 쪽에 가까울 것입니다(추정).
- **크기 표기가 셋입니다.** SDK 주석은 "약 138MB"(`runner.ts` 7·48, `transports.ts` 139), 네이티브 패키지 선언 파일은 `initEot()`에 "~108MB"라고 적고, `initEot()` 전후 RSS 증가는 233~243MB(다섯 번 실행)였습니다. 디스크의 네이티브 파일(`local-inference.darwin-arm64.node`)은 모델을 넣고도 35MB입니다. RSS에는 추론 런타임의 작업 메모리까지 들어가므로, 컨테이너 메모리는 주석이 아니라 RSS 실측(4-4절: 빈 프로세스에서 약 290MB)으로 잡는 편이 안전합니다.
- **시간.** 선언 파일 주석은 "~10ms"인데, 이 실습의 예측 246번(실제 녹음 창)의 중앙값은 27.3~27.7ms(최소 26.6ms, 최대 41.6~66.6ms, 세 번 실행)였습니다. 4-4절 실습(사인파 20번)은 약 34ms였습니다. 둘 다 주석의 3배 안팎입니다(이 맥 Apple M1 Pro 기준). 예측 대기 한도 1초(`DEFAULT_PREDICTION_TIMEOUT_MS`, `base.ts` 24)에 비하면 여유가 큽니다.

**취소 (코드).** 고객이 다시 말하면(START, 또는 말하는 중의 말소리 창) 세션은 `cancelInference()`를 부릅니다(`audio_recognition.ts` 2158~2162·2182~2188). 이 함수는 **워커 안에서만** 요청을 지웁니다. 기다리던 Future를 p = 0.0으로 채우고 요청 ID를 비울 뿐, 클라우드에 취소 메시지를 보내지 않습니다(`base.ts` 272~287). 늦게 온 답은 요청 ID가 달라 버려집니다(400~402). `v1-mini`의 IPC 요청도 취소할 수 없어 끝까지 계산된 뒤 버려집니다(`transports.ts` 231~238). 0.0이 판정에 쓰이지 않는 것은 같은 순간 판정 대기 작업도 취소되기 때문입니다(`audio_recognition.ts` 2169·1716).

### 끝점 지연(endpointing delay)

(2026-11-06 추가) **끝점 지연**은 "마지막 말소리 뒤 얼마나 기다렸다가 턴을 확정할까"입니다. 17-1절의 [끝점 검출(endpointing)](17-glossary-and-next.md#17-1-용어집) 가운데 세션이 맡는 몫입니다. SDK는 이 판단을 **EOU**(end of utterance, 말 끝)라고 부르며, 함수 `runEOUDetection`과 메트릭 `EOUMetrics`(13장)에 이 이름이 나옵니다.

턴 감지 모델을 쓰면 기본 대기 시간이 바뀝니다(`voice/turn_config/endpointing.ts`).

| | 기본 (모델 없을 때) | **오디오 턴 감지 모델과 함께 (이 프로젝트)** |
| --- | --- | --- |
| `minDelay` | 500ms | **300ms** |
| `maxDelay` | 3,000ms | **2,500ms** |

모델이 "끝났다"고 자신 있게 말해 주니 기본 대기를 줄인 것입니다. [5-poc-results.md](../5-poc-results.md)의 "`minDelay`(기본 0.5초)를 늘려 본다"는 메모는, 이 조합에서는 실제 기본값이 0.3초라는 점을 감안해 읽어야 합니다. (2026-11-06 추가) 또 이 프로젝트에서는 FINAL 글이 대개 300ms보다 늦게 와서 minDelay가 거의 묶이지 않습니다. minDelay를 올려도 "256ms + Soniox 왕복"보다 작으면 효과가 없습니다(아래 깊이 보기 "한 턴을 ms로").

### 판정 규칙: 확률에 비례하지 않고 둘 중 하나

코드(`voice/audio_recognition.ts`의 `runEOUDetection`)의 핵심은 단 한 줄입니다.

```ts
if (endOfTurnProbability < unlikelyThreshold) endpointingDelay = this.endpointing.maxDelay;
// 그 외(확률이 기준 이상, 예측 없음, 시간 초과)는 모두 minDelay
```

- 확률이 언어별 기준(`unlikelyThreshold`)보다 **낮으면** → "아직 말할 게 남았다" → **2.5초** 기다림
- 그 밖에는 → **0.3초** 기다림

확률이 0.9든 0.45든 기준만 넘으면 같은 0.3초입니다. 로컬 `v1-mini`의 한국어 기준값은 **0.4**입니다(`inference/eot/languages.ts`, 영어는 0.36). 클라우드 `v1`은 서버가 기준값을 알려 줍니다.

(2026-11-06 추가) `unlikelyThreshold`는 이름 그대로 "이보다 낮으면 턴이 끝났을 **가능성이 낮다(unlikely)**"고 보는 경계입니다. 기준값은 STT가 알려 준 언어로 찾고, 언어가 없으면 `en`으로 찾습니다(`agents/inference/eot/languages.ts` 173~178). [lab/07-turn-rules.mjs](lab/07-turn-rules.mjs) 1번은 SDK의 `ThresholdOptions`를 그대로 불러 본 것입니다(실측).

```text
1) 턴 감지 기준값 (unlikelyThreshold) — inference.ThresholdOptions
   v1-mini: ko=0.4  ko-KR=0.4  Korean=0.4  (없음)=0.36  ''=0.36  xx=0.36  en=0.36  ja=0.295
   v1(클라우드) 서버 기준값을 받기 전: ko=undefined, 지원 여부=true (서버가 SessionCreated로 보내면 채워짐)
   사용자 지정 숫자 0.5: ko=0.5, 언어 모름=0.5 / 언어별 {ko: 0.5}: ko=0.5, 언어 모름=0.36
```

- `v1-mini`에서 0.4는 `ko`, 0.36은 "언어 모름 또는 영어"입니다. 표에 없는 언어(`xx`)도 0.36이라, 언어 때문에 판정을 건너뛰는 일은 없습니다.
- 클라우드 `v1`은 연결 직후 서버가 보내는 `sessionCreated`로 기준값을 채웁니다. 채워지기 전에 판정하면 기준값이 없어 확률과 상관없이 minDelay를 씁니다(`audio_recognition.ts` 1746~1752). 연결은 통화 시작 때 하므로 보통 첫 턴 전에 끝날 것입니다(추정).
- 숫자 하나로 지정하면 모든 언어가 그 값이 되고, 언어별로 지정하면 나머지는 기본값을 씁니다. 지정하면 SDK가 "서버가 보정한 기본값을 바꾸면 나빠질 수 있다"는 경고를 남깁니다(`agents/inference/eot/detector.ts` 202~219).

**운영에서 남기기.** 운영(`start`)은 기본 로그 수준이 info라 위 디버그 줄이 꺼져 있습니다(`agents/cli.ts` 173). 대신 세션 이벤트 `EotPrediction`을 받을 수 있습니다(`agents/voice/events.ts` 295~331, `agents/voice/agent_activity.ts` 2436~2438). 이 레포에는 아직 리스너가 없습니다. 예를 들면 이렇게 남길 수 있습니다(제안, 적용하지 않음).

```ts
session.on(voice.AgentSessionEventTypes.EotPrediction, (ev) => {
  log().info(
    {
      probability: Number(ev.probability.toFixed(2)),
      threshold: ev.threshold,
      waitMs: ev.probability < ev.threshold ? 2500 : 300, // 이 프로젝트의 maxDelay / minDelay
      delayMs: Math.round(ev.delayMs),
    },

  );
});
```

| --- | --- |
| `probability`, `threshold` | p와 쓴 기준값. 언어 칸은 없으므로 `v1-mini`에서는 기준값으로 언어를 가늠 |

| `createdAt` | 이벤트 시각 |

예측 요청 하나에 한 번만 옵니다. 같은 예측을 두 판정(말 끝, FINAL)이 읽어도 한 번이고(1799~1812), 시간 초과면 오지 않습니다.

### 판정이 취소되는 경우

대기 중에 다음이 오면 판정을 취소하고 처음부터 다시 합니다.

- VAD `START_OF_SPEECH` (고객이 다시 말함)
- 말소리가 섞인 VAD 추론 결과 (미리 받은 예측도 취소)
- 새 FINAL 글

(2026-11-06 추가) 셋 모두 판정 대기 작업을 처음부터 다시 시작하게 합니다(위 "bounce 태스크"). 예측 취소는 워커 안에서만 일어나고 서버나 추론 프로세스의 계산은 멈추지 않습니다(위 깊이 보기 "턴 감지 모델의 입력과 출력"의 **취소**). 새 예측은 다음 쉼에서 무음이 다시 8창 쌓이면 나갑니다.

### 알아 둘 함정들

| 함정 | 내용 |

Soniox 서버 동작이라 코드로는 확정할 수 없습니다. 로그·트레이스의 턴 감지 언어 속성으로 **확인이 필요**합니다. (2026-11-06 갱신) 판정 방법: `eot prediction` 디버그 줄의 `language` 칸이 빠졌거나, `v1-mini`에서 `unlikelyThreshold`가 0.36이면 영어 기준이 쓰인 것입니다(위 깊이 보기 "로그와 이벤트로…") |

| 개발과 운영의 차이 | 개발 모드는 `v1`, 직접 운영 `start`는 `v1-mini`가 기본입니다(4장, `agents/inference/eot/detector.ts` 76~80). 같은 결과를 원하면 `new inference.TurnDetector({ version: 'v1' })`처럼 명시합니다 |

### 조정할 수 있는 손잡이

| 손잡이 | 효과 |
| --- | --- |

#### 깊이 보기: dynamic 모드의 EMA (2026-11-06 추가)

**EMA(지수 이동 평균, exponential moving average)**는 새 값이 올 때마다 지금까지의 평균을 조금씩 끌어당기는 평균입니다. 과거 값을 저장하지 않고 숫자 하나로 계산하며, 오래된 값의 무게가 한 번에 α배씩 줄어듭니다.

```text
v ← α·v + (1 − α)·x      α = 0.9, x = 이번에 배운 쉼, v의 처음 값 = minDelay      (agents/utils.ts 373~389)
v는 [minDelay, maxDelay] = [300, 2,500] 안으로 잘림                                (agents/voice/turn_config/endpointing.ts 122~127)
dynamic 모드의 minDelay = min(v, maxDelay), maxDelay는 고정                         (130~132)
```

손 계산: 300에서 쉼 700을 배우면 0.9 × 300 + 0.1 × 700 = 340, 이어서 800을 배우면 0.9 × 340 + 0.1 × 800 = **386**입니다. 바닥 아래로는 내려가지 않습니다. 300에서 쉼 260을 배우면 296이 되지만 300으로 잘립니다.

**무엇을 쉼으로 배우나 (코드).** 쉼 x는 앞 발화의 말 끝(VAD가 거꾸로 맞춘 시각)부터 다음 발화의 말 시작까지입니다(`betweenUtteranceDelay`, 134~139). 배우는 순간은 다음 발화가 끝날 때이고, 두 경우에만 배웁니다(192~244).

| 경우 | 조건 | 뜻 |
| --- | --- | --- |
| 고객 혼자 이어 말함 | 쉼 앞뒤로 에이전트 말이 없었음 (226~233) | 고객의 평소 말 리듬 |
| 에이전트가 막 시작했는데 고객이 이어 말함 | 에이전트 시작과 고객 재개의 차가 minDelay 이하이고, 고객 말이 끝날 때 에이전트가 아직 말하는 중 (212~225) | 앞의 쉼은 사실 같은 턴이었다. 다음에는 덜 자르게 |

맞장구로 판정된 겹침(`interruption === false`)은 배우지 않고 지웁니다(193~205). VAD 말 끝은 무음 8창(256ms)이 있어야 나므로, 배우는 쉼은 늘 약 256ms 이상입니다. [lab/07-turn-rules.mjs](lab/07-turn-rules.mjs) 3번은 SDK의 `voice.DynamicEndpointing` 클래스에 사건을 직접 넣은 결과입니다(실측).

```text
3) endpointing.mode 'dynamic' — voice.DynamicEndpointing (minDelay 300, maxDelay 2500, alpha 0.9)
   고객 말 0~2,000ms                                        minDelay 300.0
   700ms 쉬고 이어 말함 (2,700~4,000)                       minDelay 340.0
   800ms 쉬고 이어 말함 (4,800~6,000)                       minDelay 386.0
   에이전트가 답한 뒤 고객이 말함 (쉼 사이에 에이전트 말)   minDelay 386.0
   260ms 쉬고 이어 말함 (0.9 × 386 + 0.1 × 260)             minDelay 373.4
   에이전트 시작 100ms 뒤 이어 말함, 에이전트 계속 말함     minDelay 340.0
   같은 상황, 끼어들기로 에이전트가 먼저 멈춤               minDelay 300.0
   2,000ms 쉼을 12번 배우면: 470 → 623 → 761 → 885 → 996 → 1097 → 1187 → 1268 → 1341 → 1407 → 1467 → 1520
```

- 에이전트가 답한 뒤의 쉼은 배우지 않습니다(386 그대로). 턴 사이의 쉼은 고객의 말 리듬이 아니기 때문입니다.
- 끼어들기로 에이전트가 먼저 멈추면 둘째 경우의 조건이 깨져 배우지 않습니다. SDK 안에서 일시정지는 "에이전트 말 끝"으로 처리되기 때문입니다(`agents/voice/agent_activity.ts` 2303~2311). VAD 방식에서는 고객 말이 224ms를 넘으면 에이전트가 멈추므로, 둘째 경우는 그보다 짧게 이어 말했거나 AEC 워밍업처럼 끼어들기가 막힌 때에 주로 해당합니다(코드에서 따라간 추론).
- 2초씩 쉬는 고객이면 12번 만에 1,520ms가 됩니다. 확신할 때의 대기가 1.5초가 되는 셈이라, 자르지 않는 대신 굼떠집니다. 위 "한 턴을 ms로"에서 본 것처럼 이 값이 "256ms + Soniox 왕복"을 넘어서야 체감이 바뀝니다.
- 배운 값은 에이전트 활동이 시작될 때 새로 만드는 객체에 있으므로(`agent_activity.ts` 1037), 통화를 넘어 남지 않습니다(코드).

## 7-5. 끼어들기: 에이전트가 말하는 중에 고객이 말하면

### 두 가지 방식

| 방식 | 판단 근거 | 언제 켜지나 |
| --- | --- | --- |
| **VAD 방식** | 고객 말소리가 `minDuration`(지금 200ms) 이상 이어지면 끼어들기 | 기본 대체 경로 |
| **적응형(adaptive)** | 겹친 구간의 소리를 모델에 보내 "진짜 끼어들기인가, 맞장구인가" 판정 | **LiveKit Cloud 배포 또는 dev 모드에서만 자동**. 직접 운영 `start`에서는 `interruption.mode: 'adaptive'`를 명시해야 켜짐 |

[src/main.ts](../../src/main.ts)의 주석이 바로 이 조건을 설명합니다. 지금 설정에는 `mode`가 없으므로 **PoC(dev)에서는 적응형, GKE `start`에서는 VAD 방식**이 됩니다. 운영에서 적응형을 쓰려면 한 줄을 추가해야 합니다.

### VAD 방식의 흐름

```text
에이전트 말하는 중
  고객 말소리 ≥ minDuration (200ms)
    → 에이전트 발화 "일시정지" (멈추되 버리지 않음), 에이전트 상태 'listening'
    → 고객 말이 끝나면 2초 타이머 (falseInterruptionTimeout)
        ├ 2초 안에 FINAL 글이 없음 → "거짓 끼어들기" → 멈췄던 곳부터 다시 재생 (resumeFalseInterruption)
        └ FINAL 글이 옴 / 턴 확정 → 진짜로 중단 (interrupt)
```

기침이나 잡음으로 멈췄다가 아무 말이 없으면 이어서 말하는 **거짓 끼어들기 복구**가 들어 있습니다.

(2026-11-06 추가) 숫자와 순서로는 이렇습니다(코드: `agents/voice/agent_activity.ts` 2192~2324).

- **언제 참이 되나.** VAD의 `speechDuration`은 START 때 64ms이고 창마다 32ms씩 늘어나므로, 200ms 조건은 START 뒤 다섯 번째 창, 곧 말소리로 본 첫 창부터 **224ms**째에 참이 됩니다(5-5절 깊이 보기, 실측: START 1,088ms → 조건 1,248ms). [lab/07-turn-rules.mjs](lab/07-turn-rules.mjs) 4번이 같은 값을 계산합니다.
- **검사 순서.** 조건이 참이면 `interruptByAudioActivity()`가 차례로 봅니다. AEC 워밍업 중이면 아무것도 안 함(2246~2249, 7-6절) → `minWords` > 0이면 지금까지의 글(확정 + 중간 글)의 단어 수가 모자랄 때 아무것도 안 함(2257~2268) → 끼어들 수 있는 발화면 일시정지(2272~2312).
- 일시정지는 SDK 안에서 "에이전트 말 끝"으로 처리됩니다(에이전트 상태 `listening`, 2303~2311). 7-4절 dynamic 모드가 이 겹침의 쉼을 배우지 않는 이유입니다.

### 다시 말하기 전에 고객이 조용한지 본다 (2026-11-06 추가)

에이전트가 끼어들 수 있는 발화를 **재생하기 시작할 때**는 "고객이 조용하다"는 신호를 기다립니다(`agent_activity.ts` 3601~3605). 끼어들 수 없는 발화(고지)는 기다리지 않습니다. 이 신호는 VAD의 말 시작 때 꺼지고 말 끝 때 켜지며(2132·2185), 그 사이에는 창마다 갱신됩니다(2204~2208).

```text
고객이 말하는 중이고(VAD speaking) 실린 무음 ≤ minDelay / 2 (= 150ms)  →  조용하지 않음
그 밖                                                                  →  조용함
```

실린 무음은 이번 창을 더하기 전 값이라(5-4절), 0·32·…·128은 150 이하이고 여섯 번째 무음 창이 싣는 160에서 처음 넘습니다. 곧 **마지막 말소리 창 뒤 192ms**에 "조용함"이 됩니다. [lab/07-turn-rules.mjs](lab/07-turn-rules.mjs) 4번이 끼어들기 문턱과 함께 계산합니다.

```text
4) 32ms 창 단위로 본 문턱 (말 시작 = 말소리 창 연속 2개째 START, 5-4절)
   끼어들기 minDuration 200: START 뒤 5번째 창에서 speechDuration 224 ≥ 200 → 말소리 첫 창부터 224ms째
   "고객 조용함" (실린 무음 > minDelay/2 = 150): 6번째 무음 창(실린 값 160)에서 조용함 → 마지막 말소리 창 뒤 192ms
```

턴이 확정돼 답이 준비돼도, 그사이 고객이 다시 소리를 내면 이 문에서 192ms 쉼을 기다렸다가 재생을 시작합니다(그동안 새 턴이 확정되면 그 답은 끊김). 일시정지된 발화를 다시 이을지 정할 때도 같은 신호를 봅니다(5951~5958). 여기서 minDelay는 설정값(이 프로젝트 300)이고 dynamic 모드가 배운 값이 아닙니다(`endpointingOpts`, 1284~1292).

### VAD 방식의 함정: 맞장구 "네"가 대답을 끊는다

코드를 따라가면 VAD 방식에서 이런 일이 생깁니다.

1. 에이전트가 설명하는 중 고객이 "네"(200ms 이상)라고 맞장구 → 일시정지
2. 고객 말이 멈춤 → **이 프로젝트의 finalize가 Soniox에 확정 요청** → "네" FINAL이 빨리 옴
3. 에이전트가 말하는 중 FINAL이 오면 **`minDuration`과 상관없이** 중단됩니다(`voice/agent_activity.ts`의 FINAL 처리 경로)
4. "네"가 사용자 턴으로 확정되고, 에이전트가 하던 말을 버리고 "네"에 대한 새 답을 만듭니다

(2026-11-06 갱신) 3번을 정확히 쓰면, FINAL 처리(`onFinalTranscript`, 2381~2422)는 위와 같은 `interruptByAudioActivity()`를 부릅니다. 그래서 `minDuration`은 보지 않지만 AEC 워밍업과 `minWords` 검사는 거치고, 결과는 우선 일시정지입니다. 하던 말이 실제로 끊기는 것은 4번에서 턴이 확정된 뒤 "speech interrupted, new user turn detected"와 함께입니다(3381~3394).

finalize 패치는 말 끝 판단을 빠르게 하려고 넣은 것인데, VAD 방식에서는 **맞장구에 의한 중단도 빠르게** 만듭니다. 적응형 방식에서는 겹친 구간의 글을 보류했다가 맞장구로 판정되면 버리므로 이 문제가 없습니다. 운영에서 `mode: 'adaptive'`를 명시하거나, `minWords`(최소 단어 수)를 함께 검토해야 하는 이유입니다. 이 부분은 SDK 코드로 추론한 동작이므로, 실제 통화에서 맞장구를 쳐 보며 확인해야 합니다.

(2026-11-06 추가) **`minWords`의 단서: 단어는 공백으로 셉니다.** 단어 수는 `splitWords(글, true)`로 셉니다(`agent_activity.ts` 2264·2737). 이 함수는 공백 아닌 덩어리(`/\S+/`)를 단어로 보고 구두점만 뺍니다(`agents/tokenize/basic/word.ts` 9~31). 코드에도 "다국어용으로 더 나은 단어 나누기가 필요하다"는 TODO가 있습니다(2263). [lab/07-turn-rules.mjs](lab/07-turn-rules.mjs) 5번(실측):

```text
5) minWords의 단어 세기 — tokenize.basic.splitWords(text, true): 공백으로 자르고 구두점을 뺌
   "네"                       1단어 ["네"]  minWords 2면 막힘
   "아니요"                   1단어 ["아니요"]  minWords 2면 막힘
   "잠깐만요"                 1단어 ["잠깐만요"]  minWords 2면 막힘
   "아니요."                  1단어 ["아니요"]  minWords 2면 막힘
   "음..."                    1단어 ["음"]  minWords 2면 막힘
   "아니 잠깐만요"            2단어 ["아니","잠깐만요"]  minWords 2면 통과
   "네, 네."                  2단어 ["네","네"]  minWords 2면 통과
   "잠깐만요, 그게 아니라"    3단어 ["잠깐만요","그게","아니라"]  minWords 2면 통과
```

`minWords: 2`는 맞장구 "네"를 막지만, **"아니요", "잠깐만요" 같은 진짜 끼어들기도 똑같이 막습니다.** 한국어의 짧은 거절·제지 말은 대부분 한 덩어리이기 때문입니다. 반대로 "네, 네."는 통과합니다. 또 이 검사는 턴 확정 때도 한 번 더 일어나, 단어 수가 모자라면 그 턴을 "skipping user input, word count below minimum interruption threshold"로 넘깁니다(2729~2751). 이 레포에서 `minWords`를 쓰려면 이 비용을 함께 따져야 합니다.

### 적응형 방식의 흐름

```text
에이전트 첫 1초 (backchannelBoundary)  → VAD 방식으로 동작 (말 시작 직후의 정정·번복은 진짜 끼어들기일 확률이 높으므로)
그 이후 겹침 발생
  → 겹친 구간 앞 1초 + 겹친 소리를 100ms마다 클라우드 모델(/bargein)에 보냄 (최대 3초 분량)
  → 그동안 STT 글은 보류 (transcript gate)
  ├ 모델: "끼어들기" → VAD 경로 복구, 에이전트 중단, 보류한 글 내보냄
  └ 모델: "맞장구"   → 보류한 글 버림, 에이전트 계속 말함
모델 오류가 계속되면 → VAD 방식으로 전환
```

(2026-11-06 갱신) 위 그림은 `backchannelBoundary`의 앞쪽만 그렸습니다. 기본값은 `[1000, 1000]`, 곧 에이전트 말의 **첫 1초와 끝 1초** 두 경계입니다(`agents/voice/turn_config/interruption.ts` 47~59·62~71). 코드를 따라 고쳐 그리면 이렇습니다.

```text
에이전트 말 시작 → 1초 타이머 (audio_recognition.ts 926~933)
  이 1초 안에 시작한 겹침 → 판정 모델에 보내지 않고 VAD 방식 (1016~1031)
                            이때 온 "맞장구" 판정은 무시 (1547~1552)
1초 뒤에 시작한 겹침 (VAD START)
  → 겹침 앞 1초 + START까지의 말소리 64ms부터, 100ms마다 그때까지의 창 전체를 /bargein으로 (창은 최대 3초)
  → 그동안 STT 글은 보류 (transcript gate)
  ├ 모델: "끼어들기" → VAD 경로 복구, 에이전트 일시정지, 보류한 글 내보냄 (agent_activity.ts 2326~2341)
  └ 모델: "맞장구"   → 판정 1초 전보다 먼저 도착한 보류 글은 버림, 나머지는 계속 보류, 에이전트 계속 말함 (1554~1559)
에이전트 말이 끝남 (끝 1초 경계)
  → 보류 글 가운데 끝나기 전 1초 안에 도착한 것과 지금 이어지는 고객 말의 것은 살려 처리, 그보다 앞은 버림 (951~987·1079~1104)
회복할 수 없는 오류 → "adaptive interruption disabled due to unrecoverable error, falling back to VAD-based interruption" (agent_activity.ts 6146~6171)
```

- **backchannel**은 맞장구(듣고 있다는 신호로 끼는 짧은 말: "네", "음")의 영어 이름입니다. SDK 옵션과 이벤트 이름에 이 말이 쓰입니다.
- **transcript gate**는 판정이 날 때까지 STT 결과를 세션에 넘기지 않고 붙잡아 두는 문입니다(`audio_recognition.ts` 1037·1286~1290·1106~1134). 12장의 보류 버퍼와 같은 생각입니다. 붙잡힌 글은 턴 판정에도 쓰이지 않으므로, 맞장구 "네"가 새 턴이 되지 않습니다.
- **끝 1초 경계의 뜻.** 에이전트가 질문을 마무리하는 동안 고객이 겹쳐서 대답을 시작하면, 그 소리는 맞장구 판정을 받았더라도 끝 1초 안이라 살아남아 대답으로 처리됩니다. 앞쪽 경계가 "말 시작 직후의 정정"을 지키듯, 뒤쪽 경계는 "말이 끝날 무렵의 대답"을 지킵니다(SDK 주석: "The end value preserves transcripts received near the end of agent speech"). 보류 글의 시각은 STT 이벤트가 말 끝 시각을 갖고 있으면 그것을, 없으면 도착 시각을 씁니다(1091~1096).

### `minDuration`: 500 → 300 → 200ms (2026-11-04 갱신)

| 시점 | 값 | 이유 |
| --- | --- | --- |
| 스타터 기본값 | 500ms | |
| 2026-11-03 | 300ms | "아니요"(약 0.3~0.4초), "잠깐만요" 같은 **짧고 분명한 끼어들기를 놓치지 않으려고** |
| 2026-11-04 | **200ms** | 300ms에서 "멈추기까지 약 0.4초"가 걸려 더 빨리 멈추게 ([src/main.ts](../../src/main.ts) 주석) |

#### 멈추기까지 걸리는 시간은 어떻게 쌓이나

"고객이 말을 시작한 순간 → 에이전트 소리가 멎는 순간"은 대략 이렇게 쌓입니다.

```text
고객 말 시작
 ├ VAD가 말소리로 판단: 32ms 창마다 확률을 내고, 활성 기준(0.5)을 넘어야 말소리 (5장)
 ├ 말소리 길이가 minDuration에 닿을 때까지 누적        ← 설정값이 그대로 더해지는 부분
 ├ 일시정지: 방으로 나가는 오디오를 멈춤 (audioOutput.pause)
 └ 이미 보낸 소리: 네트워크·브라우저 지터 버퍼(2장)에 남은 수십 ms는 그대로 재생됨
```

300ms에서 약 0.4초가 걸렸다면 `minDuration` 밖의 몫이 0.1초 남짓이라는 뜻입니다. 200ms로 줄이면 약 0.3초가 기대값입니다. 고객 입장에서는 자기 말과 에이전트 말이 겹치는 시간이 그만큼 줄어듭니다.

(2026-11-06 추가) 창 단위로 세면 "설정값이 그대로 더해진다"보다 조금 더 붙습니다. 5장 실측 녹음(소리 시작 1,000ms, 말소리 첫 창 1,024~1,056ms, START 1,088ms)에 넣으면 조건이 참이 되는 창은 이렇습니다. `speechDuration`은 START 때 64이고 창마다 32씩 늘므로, 처음으로 64 + 32k ≥ `minDuration`이 되는 k를 찾으면 됩니다.

| `minDuration` | 조건이 참인 `speechDuration` | 그 창의 끝 | 소리 시작부터 | 근거 |
| --- | --- | --- | --- | --- |
| 200 (지금) | 224 | 1,248ms | **248ms** | 5장 실측 |
| 250 (되돌릴 후보) | 256 | 1,280ms | 280ms | 계산 |
| 300 | 320 | 1,344ms | 344ms | 계산 |
| 500 (스타터 기본) | 512 | 1,536ms | 536ms | 계산 |

300ms에서 344ms + 출력 쪽 수십 ms ≈ 0.4초로, [src/main.ts](../../src/main.ts) 주석의 "약 0.4초"와 맞습니다. 200ms에서는 약 0.25초 + 출력 쪽이 기대값입니다(추정). 소리 시작부터 말소리 첫 창까지의 24ms는 VAD가 첫 창(소리 24ms만 든 창, 0.43)을 놓친 몫이라 녹음마다 다릅니다(5-5절 깊이 보기).

#### 어느 방식에서 효과가 있나

7-5절의 두 방식에서 이 값의 쓰임이 다릅니다. SDK의 `voice/agent_activity.ts`로 확인했습니다.

| 방식 | `minDuration`이 쓰이는 곳 | 200ms로 줄인 효과 |
| --- | --- | --- |
| VAD 방식 (직접 운영 `start`) | 모든 끼어들기 (`onVADInferenceDone`에서 `speechDuration >= minDuration`) | 그대로 나타남 |
| 적응형 (LiveKit Cloud·dev, 지금 웹 테스트) | 에이전트 발화의 **첫 1초**(`backchannelBoundary`) 동안만. 그 뒤에는 VAD 경로가 꺼지고, 판정 모델이 "끼어들기"라고 하면(`onOverlapSpeech`) **`minDuration` 검사 없이 바로** 멈춤 | 첫 1초 안의 끼어들기에만. 그 뒤의 멈춤 시간은 판정 모델이 정함(100ms 단위로 보냄) |

그래서 효과를 잴 때는 **발화 시작 직후에 끼어든 경우와 한참 말하는 중에 끼어든 경우를 나눠** 봐야 합니다. 뒤쪽에서도 빨라졌다면 다른 원인이 섞인 것입니다.

#### 대가와 되돌리는 기준

짧게 할수록 사람 말이 아닌 소리에도 멈춥니다.

- 주석대로 **200ms 아래는 기침·숨소리에도** 끊깁니다.
- 짧은 맞장구 "네"도 0.2초는 넘기 쉽습니다. 적응형 방식은 첫 1초 뒤로는 모델이 걸러 주지만, **VAD 방식으로 운영하면 이 값은 맞장구를 거의 막지 못합니다**(앞의 "VAD 방식의 함정").
- 잡음으로 멈춰도 거짓 끼어들기 복구(2초 뒤 재개)가 있지만, 그동안 고객은 침묵을 듣습니다.
- 되돌리는 기준도 주석에 있습니다. 맞장구에 자꾸 멈추면 250으로 올립니다. 길이 대신 단어 수로 거르는 `minWords`도 있지만, STT 글이 나와야 판단할 수 있어 길이 기준보다 늦습니다. (2026-11-06 추가) 또 단어를 공백으로 세므로 "아니요", "잠깐만요"도 1단어입니다(위 "`minWords`의 단서").

### 판정을 로그로 보기 (2026-11-04 추가)

`minDuration`을 줄인 커밋(`ce8c7c7`)에 끼어들기 판정 로그도 함께 들어갔습니다. 적응형 방식에서 "왜 안 끊겼나"를 보려면 모델이 무엇이라고 판정했는지가 남아 있어야 합니다.

```ts
// src/main.ts
session.on(voice.AgentSessionEventTypes.OverlappingSpeech, (ev) => {
  const verdict = ev.isInterruption
    ? '끼어들기로 판단(멈춤)'
    : ev.agentEnded
      ? 'AI 말이 먼저 끝나 판단 없음'
      : '맞장구로 판단(계속 말함)';
  log().info(
    {
      probability: Number(ev.probability.toFixed(2)),
      detectionDelayMs: Math.round(ev.detectionDelayInS * 1000),
    },
    `겹친 말: ${verdict}`,
  );
});
session.on(voice.AgentSessionEventTypes.AgentFalseInterruption, (ev) => {
  log().info({ resumed: ev.resumed }, '끼어들기 취소: 고객 말이 이어지지 않아 하던 말을 이음');
});
```

`OverlappingSpeech` 이벤트(`inference/interruption/types.ts`)는 겹침 하나에 대해 이렇게 옵니다.

| 경우 | 언제 오나 | 값 |
| --- | --- | --- |
| **끼어들기** | 겹치는 중에 모델이 끼어들기라고 판정한 순간 | `isInterruption: true`. 이어서 에이전트가 멈춤 |
| **맞장구** | 고객 소리가 먼저 그쳐 겹침이 끝났을 때 | `isInterruption: false` |
| **판단 없음** | **에이전트 말이 먼저 끝나** 겹침이 끝났을 때 | `isInterruption: false`, `agentEnded: true`. 고객은 아직 말하는 중일 수 있음 |

나머지 값의 뜻입니다.

- `probability`: 모델이 낸 끼어들기 확률입니다. 기준값을 넘으면 끼어들기로 판정합니다.
- `detectionDelayInS`: 겹침이 시작된 뒤 판정이 나기까지 걸린 시간입니다. 위 "멈추기까지 걸리는 시간"에서 첫 1초 이후 구간을 정하는 값입니다.
- `numRequests`: 판정을 위해 모델에 보낸 요청 수입니다(100ms마다 한 번).

`AgentFalseInterruption`은 끼어들기로 멈췄는데 고객 말(STT 글)이 이어지지 않은 경우입니다. `resumed: true`면 하던 말을 다시 이은 것입니다.

"안 끊긴다"는 증상은 로그로 셋 중 하나로 가를 수 있습니다.

1. **이벤트가 아예 없다.** 겹침이 감지되지 않은 것입니다. 첫 1초 안이었다면 VAD 경로(`minDuration`)를 보고, 그 뒤라면 VAD가 고객 소리를 말소리로 잡았는지(5장)를 봅니다.
2. **"맞장구로 판단"인데 `probability`가 기준 근처다.** 모델 판정의 경계 문제입니다. 한국어 맞장구·끼어들기 표본을 모아 볼 대상입니다.
3. **"끼어들기로 판단" 뒤에 "끼어들기 취소"가 따라온다.** 멈췄다가 STT 글이 없어 다시 이은 경우입니다. 고객 말이 STT에서 빠졌는지(6장)를 봅니다.

#### "아니다"와 "모른다"를 나누기

처음 로그는 `isInterruption`이 false이면 모두 "맞장구로 판단"으로 적었습니다. 그러면 에이전트가 그냥 말을 마친 경우까지 "모델이 맞장구로 봤다"로 읽힙니다. 증상 2를 찾으려고 로그를 보면, 실제로는 판정이 없었던 겹침이 오판처럼 섞여 나옵니다. SDK도 자기 통계에서는 이 경우를 맞장구 수에서 뺍니다(`numBackchannels: !isInterruption && !agentEnded`). 그래서 같은 기준으로 셋을 나눠 적게 고쳤습니다.

일반화하면 이렇습니다. **참/거짓 값 하나에 "아니다"와 "판정하지 못했다"가 함께 담기면, 읽는 쪽은 둘을 구분할 수 없습니다.** 8-11절의 판정 칸에 `'미확인'`을 따로 둔 것과 같은 이유입니다. 13-5절의 `-1`처럼 "값을 얻기 전에 끝난 관측"이라는 점에서는 중도 절단과도 닮았습니다. 기록을 남길 때는 "모름"이 들어갈 자리를 먼저 정해 두는 편이 안전합니다.

### 끊긴 뒤에 일어나는 일

- LLM 생성과 TTS를 멈추고, 방으로 나가는 오디오 큐를 비웁니다(`AudioSource.clearQueue()`).
- **대화 기록에는 고객이 실제로 들은 부분까지만** 남깁니다. TTS가 알려 준 글자별 재생 시각(10장 alignment)으로 "어디까지 재생됐나"를 계산합니다. 메시지에는 `interrupted: true` 표시가 붙습니다.
- 아무것도 재생되기 전에 끊겼다면 assistant 메시지 자체가 남지 않습니다.
- 다음 턴에 LLM은 "내가 이 말을 하다가 끊겼다"를 보고 이어서 대응할 수 있습니다.

단, **`session.say()`로 말한 고정 문장은 끊겨도 전체 문장이 기록에 남습니다**(`interrupted: true`만 붙음). LLM 답처럼 잘라 주지 않습니다.

## 7-6. 끼어들 수 없는 말: AI·녹음 고지

```ts
session.say(openingNotice(call), { allowInterruptions: false });
session.say(OPENING_QUESTION, { allowInterruptions: true });
```

고지는 법적으로 끝까지 들려야 하므로 끼어들기를 막았습니다(9장). 그런데 **고지 중에 고객이 한 말은 어떻게 될까요?** SDK 코드를 따라가면 다음과 같습니다.

1. 끼어들 수 없는 발화가 재생되는 동안, 기본 설정(`discardAudioIfUninterruptible: true`)에서는 **STT에 고객 소리 대신 무음**이 들어갑니다.
2. VAD는 진짜 소리를 받으므로 사용자 상태는 `speaking`이 되지만, 글이 없어 턴이 확정되지 않습니다.
3. 설령 턴이 확정되더라도, 끼어들 수 없는 발화가 재생 중이면 그 사용자 턴은 경고와 함께 **버려집니다**.

즉 고지 중에 고객이 "아 네, 근데 저 지금 운전 중이라서요"라고 하면 **그 말은 사라집니다.** [4-setup-checklist.md 9장](../4-setup-checklist.md#9-알아-둘-점)의 "고객이 첫 멘트 중에 말하면 첫 멘트가 끝난 뒤에 반영됩니다"는 코드 동작과 다릅니다. 고지가 끝난 뒤 질문("이삼 분 정도 통화 괜찮으실까요?")이 나가므로 고객이 다시 말할 기회는 있지만, 처음 한 말은 잃습니다.

선택지는 이렇습니다.

| 선택 | 효과 |
| --- | --- |
| 지금 그대로 | 고지는 확실히 전달. 고지 중 고객 말은 버려짐 |
| `discardAudioIfUninterruptible: false` | 고지 중 고객 소리도 STT로 보냄 → 고지 후 처리 가능성. 대신 고지 중 말이 쌓여 엉뚱한 타이밍에 답할 수 있음 |
| 고지를 짧게 | 버려질 구간 자체를 줄임 |

### 갱신: `discardAudioIfUninterruptible: false`를 넣은 뒤 (2026-11-03)

[src/main.ts](../../src/main.ts)는 둘째 선택지를 택했습니다. 주석에 따르면 시뮬레이션에서 고지 중의 "전화하지 마세요"를 못 듣는 문제를 발견해서입니다.

```ts
interruption: { minDuration: 200, discardAudioIfUninterruptible: false },  // minDuration은 2026-11-04에 300 → 200
```

이제 1번(STT에 무음)은 사라져서 고지 중의 고객 말도 글로 적힙니다(2026-11-06 갱신: 단, 브라우저 테스트에서는 에이전트가 처음 말하기 시작한 뒤 3초 동안 이 설정과 상관없이 STT에 무음이 들어갑니다. 이 절 끝의 AEC 워밍업). 그런데 **3번은 그대로**입니다. SDK의 턴 확정 단계(`onEndOfTurn`)에는 "끼어들 수 없는 발화가 재생 중인가"를 보는 검사가 없고, 확정된 턴은 다음 단계(`userTurnCompletedImpl`)에서 끼어들 수 없는 발화가 재생 중이면 "skipping user input, current speech generation cannot be interrupted" 경고와 함께 버려집니다. 확정 때 글도 비워지므로 고지가 끝난 뒤 다시 처리되지 않습니다.

그래서 결과는 **고객이 언제 말을 마쳤는지**에 달려 있습니다.

| 경우 | 결과 |
| --- | --- |
| 고객 말이 고지가 끝날 때까지 이어짐 | 턴 확정이 고지 뒤에 일어나 정상 처리 |
| 고객이 고지 도중에 말을 마침 (말 끝 판단 약 0.4~0.6초 뒤 확정) | 확정 시점에 고지가 아직 재생 중 → **버려짐** |

고지는 6~7초 길이라 "전화하지 마세요"처럼 짧은 말은 고지 도중에 끝나기 쉽습니다. 따라서 이 설정만으로는 의도("고지가 끝난 뒤 처리")가 보장되지 않을 수 있습니다. 시뮬레이션은 텍스트 입력 경로라 음성의 턴 확정 시점과 다를 수 있으므로, **실제 음성으로 고지 중에 짧게 말해 보고** 로그에 위 경고가 나오는지 확인해야 합니다. 보장하려면 고지 중에 들어온 확정 글(`UserInputTranscribed`)을 따로 모아 두었다가, 고지 재생이 끝난 뒤 그 글로 답을 생성하게 하는 식의 처리가 필요합니다.

또 하나, **브라우저 테스트에서는 에이전트가 처음 말하는 3초 동안 끼어들기가 막힙니다**(AEC 워밍업, 에코 제거기가 적응하는 시간). 발신 SIP 참가자에게는 이 워밍업이 자동으로 꺼집니다. 브라우저 PoC와 실제 전화에서 첫 몇 초의 끼어들기 동작이 다를 수 있다는 뜻입니다.

## 7-8. 정리

```text
              ┌──── 말 끝 판단 ─────────────────────────────────────────────┐
고객 말소리 ─▶ VAD (256ms 무음) ─▶ 'listening' ─▶ finalize ─▶ FINAL 글
              │       └ 같은 창(무음 8창째)에서 턴 감지 모델 예측 요청 (최근 1.2초 소리만 봄, 쉼마다 한 번)
              │  FINAL 도착 → p ≥ 기준(ko 0.4)? → 300ms : 2,500ms (마지막 말소리 기준)
              │  확정 = max(마지막 말소리 + 대기, FINAL 도착, 예측 도착(최대 1초))
              └────────────────────────────────────────────────────────────┘
              ┌──── 끼어들기 ───────────────────────────────────────────────┐
에이전트 말하는 중 고객 소리 ─▶ VAD 방식: ≥200ms(창으로 224ms)면 일시정지, FINAL 오면 중단, 2초 무소식이면 재개
                            └ 적응형: 겹친 소리를 모델이 판정 (dev/Cloud 자동, 직접 운영은 명시)
                                      첫 1초는 VAD 방식, 끝 1초 안의 글은 살림
              끊기면: 들은 데까지만 기록 (say()는 전체 기록)
              └────────────────────────────────────────────────────────────┘
```

(2026-11-06 갱신) 예전 그림의 "200ms 무음 때 턴 감지 모델 예측 요청"은 기본값에서 맞지 않아 고쳤습니다. 예측 요청은 VAD가 말 끝을 내는 같은 창에서, END 처리 바로 앞에 나갑니다(7-4절 타임라인, 5-4절 깊이 보기).
