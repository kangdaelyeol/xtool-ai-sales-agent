# 1장. 큰 그림: 이 프로젝트는 무엇을, 어떻게 하는가

이 장은 책 전체의 지도입니다. 세부를 읽다가 길을 잃으면 여기로 돌아오면 됩니다.

**처음 읽는 법 (2026-11-08 추가).** 처음 읽을 때 이 장에서 잡아 갈 것은 세 가지입니다.

1. 이 프로그램이 무슨 일을 하는가 (1-1절, 1-2절)
2. 고객의 목소리가 어떤 부품을 어떤 순서로 지나 AI의 목소리로 돌아오는가 (1-3절의 첫 그림, 1-4절의 표, 1-5절의 첫 그림)
3. 통화 하나와 대화 한 차례(턴)가 시간 순서로 어떻게 흘러가는가 (1-6절의 첫 그림)

숫자가 빽빽한 표와 눈금(1-3절의 지연 표, 1-5절의 연결 표, 1-6절의 ms 눈금)은 "이런 숫자가 있구나" 하고 크기만 보고 넘어가도 됩니다. 그 숫자들은 2∼13장에서 원리부터 하나씩 다시 나옵니다. `#### 깊이 보기`로 시작하는 하위 절은 건너뛰어도 흐름이 끊기지 않습니다. 낯선 말은 바로 아래 "이 장에서 쓰는 말" 표에서 찾고, 문장 끝 괄호 속 번호(예: "(7장)", "(4-3절)")는 그 내용을 자세히 다루는 곳입니다. 뒤 장을 읽다가 지금 읽는 내용이 통화의 어느 순간인지 헷갈리면 1-6절의 그림으로 돌아오면 됩니다.

(2026-11-05 추가) 이번 판부터 지도에 **숫자**를 붙였습니다. 연결마다 무엇이 어떤 형식으로 초당 몇 바이트 오가는지(1-5절), 한 턴이 몇 ms 눈금으로 흘러가는지(1-6절), 지연이 어느 칸에서 생기는지(1-3절)를 적었습니다. 각 숫자 옆에 코드로 확인했는지, 잰 값인지, 추정인지를 표시했습니다. 자세한 원리는 링크한 장에 있으니 처음에는 숫자의 크기만 눈에 익혀 두면 됩니다.

(2026-11-08 추가) 그 표시의 뜻입니다. **코드**는 SDK나 이 레포의 소스를 읽어 확인한 값, **실측**은 실제로 돌려서 잰 값(대부분 [5-poc-results.md](../5-poc-results.md)의 PoC 측정이나 [lab/](lab/)의 실습), **실측 구간의 합**은 구간마다 따로 잰 값을 더한 것(처음부터 끝까지를 한 번에 잰 값이 아님), **추정**은 계산이나 추론으로 짐작했지만 아직 재지 않은 값입니다.

## 이 장에서 쓰는 말 (2026-11-05 추가)

처음 보면 막히는 말만 모았습니다. 자세한 뜻은 괄호 안의 장에 있고, 전체 용어집은 [17-1절](17-glossary-and-next.md#17-1-용어집)입니다. (2026-11-08 갱신) 부품 이름(STT·LLM·TTS, VAD, 턴 감지 모델), "확정"의 두 뜻, 스트리밍, 즉시 반응, 끼어들기, LiveKit과 방·참가자·트랙, AgentSession, PoC, PCM·샘플레이트, 코덱 줄을 더하고, 몇 줄에 예와 원래 영어 이름을 붙였습니다.

| 말 | 뜻 |
| --- | --- |
| STT / LLM / TTS | 음성 에이전트의 세 부품입니다. STT(Speech-to-Text, 음성 인식)는 소리를 글로 받아 적고, LLM(Large Language Model, 대규모 언어 모델)은 지금까지의 대화 글을 읽고 다음에 할 말을 글로 짓고, TTS(Text-to-Speech, 음성 합성)는 그 글을 소리로 읽습니다(6장, 8장, 10장) |
| 토큰 | LLM이 글을 읽고 쓰는 단위입니다. 한국어는 대략 한 글자가 토큰 하나입니다(추정, 8-1절). "LLM 첫 토큰"은 답의 첫 조각입니다. STT가 내는 "토큰"(단어·조각)은 이름만 같고 다른 것입니다(6-3절) |
| VAD | Voice Activity Detection(말소리 감지)입니다. 들어오는 소리에 사람 말소리가 있는지만 판단하고, 무슨 말인지는 모릅니다. 이 레포는 Silero 모델이 32ms 조각마다 "말소리일 확률"을 냅니다(5장) |
| 턴(turn) | 한 사람이 이어서 말하는 한 차례입니다. "고객 턴이 끝났다"는 "이제 AI가 답할 차례"라는 판단입니다. 고객이 한 번 말하고 AI가 한 번 답하는 것을 묶어 "한 턴"이라고도 부릅니다(7장) |
| 턴 감지 모델 | 고객 소리를 듣고 "지금 말이 끝났을 확률" p(0∼1)를 내는 작은 모델입니다. VAD는 "소리가 멈췄다"만 알지만, 이 모델은 억양까지 듣고 말을 다 해서 멈춘 것인지 생각하느라 쉬는 것인지를 가립니다(7-4절) |
| 중간 글 / 확정(final) 글 | STT가 듣는 동안 계속 고쳐 내보내는 글이 중간(interim) 글, "이제 안 바뀐다"고 못 박은 글이 확정 글(FINAL)입니다. 예를 들어 "메탈 백"(중간)이 뒷소리를 듣고 "메탈팹이랑"(중간)으로 고쳐지고, 그 뒤 "메탈팹이랑"(확정)이 됩니다. 턴을 끝내고 LLM에 넘기는 것은 확정 글입니다. **finalize**(확정 요청)는 워커가 Soniox에 "지금까지 들은 것을 바로 확정해 달라"고 보내는 메시지입니다(6-3절, 6-5절) |
| STT 확정 / 턴 확정 | 이 책의 "확정"에는 두 뜻이 있습니다. **STT 확정**은 Soniox가 글자를 확정 글로 못 박는 것이고, **턴 확정**은 워커가 "고객 말이 끝났으니 답할 차례"라고 결정하는 것입니다. 턴 확정은 그 턴의 확정 글이 하나라도 있어야 일어나므로 늘 STT 확정 뒤에 옵니다. 턴 감지 모델이 확신하는 턴이면 대개 마지막 확정 글이 도착하는 순간 턴도 확정됩니다(1-6절) |
| 워커 / 잡 | 워커는 LiveKit에 붙어 일을 기다리는 상주 프로세스, 잡은 워커가 맡은 일 하나(= 통화 하나)입니다. 잡마다 자식 프로세스가 따로 뜹니다(4장) |
| 디스패치 | LiveKit 서버가 "이 방에 이 에이전트를 보내라"는 일을 워커에 나눠 주는 것입니다. 이 책에서는 "배정"이라고도 씁니다(4-3절) |
| LiveKit / 방 / 참가자 / 트랙 | LiveKit은 실시간 음성·영상을 중계하는 서버와, 그 위에 AI 에이전트를 만드는 SDK(LiveKit Agents)의 이름입니다. LiveKit Cloud는 그 서버를 LiveKit이 대신 운영해 주는 서비스입니다. 통화 하나가 방(Room) 하나이고, 고객과 AI 에이전트가 각각 참가자(Participant)로 들어갑니다. 참가자는 자기 소리를 트랙(Track)으로 방에 내보내고(발행), 상대의 트랙을 받아 듣습니다(구독, 3-3절) |
| AgentSession | 통화 하나를 지휘하는 SDK 객체입니다. VAD·STT·턴 감지·LLM·TTS를 잇고, 언제 듣고 언제 말할지 정합니다(11장) |
| RoomIO | 방의 고객 오디오를 세션 입력으로, 세션이 만든 소리를 방의 오디오 트랙으로 잇는 SDK 부품입니다(4-6절) |
| 스트리밍 (흘려보내기) | 결과를 다 만들 때까지 기다리지 않고 만든 조각부터 바로바로 보내는 방식입니다. STT는 들은 만큼 글자를, LLM은 만든 만큼 토큰을, TTS는 합성한 만큼 소리를 흘려보냅니다. 이 덕분에 앞 단계가 끝나기 전에 뒤 단계가 일을 시작할 수 있습니다(6-3절, 8-6절, 10-2절) |
| 선제 생성 | 턴이 확정되기 전에 LLM을 미리 돌려 두는 것입니다. STT가 "지금까지 들은 글은 모두 확정"이라고 알릴 때(PREFLIGHT) 그 글로 시작하고, 턴이 확정될 때의 글과 다르면 버리고 다시 합니다(11-4절) |
| 즉시 반응 | 고객 말이 끝나자마자 "네네." 같은 짧은 고정 문장을 먼저 들려주는 기법입니다. LLM의 본 답을 기다리는 침묵을 메웁니다. 본 답이 나오는 시각은 그대로입니다(11-6절) |
| 끼어들기 / 맞장구 | 끼어들기는 AI가 말하는 중에 고객이 말을 끊는 것, 맞장구는 "네", "음"처럼 듣고 있다는 신호로 끼는 짧은 말입니다. 끼어들기면 AI가 멈추고, 맞장구면 계속 말해야 합니다(7-5절) |
| TTFT / TTFB | TTFT는 Time To First Token, TTFB는 Time To First Byte의 줄임말입니다. 요청을 보내고 첫 토큰(LLM) / 첫 바이트(TTS의 첫 소리)가 오기까지의 시간입니다. 음성에서는 다 끝나는 시간보다 이 값이 중요합니다(8-3절, 13-3절) |
| 말 끝 판단 (EOU) | EOU는 End Of Utterance(말 끝)입니다. 고객이 말을 멈춘 시각부터 턴을 확정하기까지의 시간입니다. VAD 무음 대기와 STT 확정이 이 안에 들어 있습니다(13-3절) |
| PoC | Proof of Concept(개념 검증)입니다. 본 개발 전에 부품을 붙여 "되는지"를 확인한 단계입니다. 이 장의 지연 숫자 대부분은 2026-11-03 무렵 맥(서울)에서 해외 API로 브라우저·디버거 통화를 하며 잰 PoC 값입니다([5-poc-results.md](../5-poc-results.md)) |
| PCM / 샘플레이트 | 소리를 1초에 정해진 횟수만큼 재서 숫자로 늘어놓은 것이 PCM, 1초에 재는 횟수가 샘플레이트입니다. 16kHz면 1초에 16,000번 재고, 한 번 잰 값을 16비트(2바이트) 정수로 적으면 1초에 32,000바이트입니다(2장) |
| 코덱 (Opus, G.711) | 소리를 줄여서 보내는 방식입니다. Opus는 인터넷 음성의 표준이라 WebRTC가 쓰고, G.711은 전화망의 표준(8kHz, 1초에 8,000바이트)입니다(2-5절) |
| WebSocket | TCP(+TLS) 연결 하나를 열어 두고 양쪽이 메시지를 주고받는 방식입니다. 순서와 도착이 보장되지만, 잃은 조각을 다시 보내느라 뒤의 메시지가 기다릴 수 있습니다. 워커↔LiveKit 제어, STT·TTS 연결이 이것입니다. 주소가 `wss://`면 TLS로 암호화한 WebSocket입니다 |
| WebRTC | 실시간 음성·영상을 보내는 표준입니다. UDP 위에서 늦은 패킷은 버리고 "지금 소리"를 우선합니다. 고객 ↔ 방 ↔ 에이전트의 소리가 이것으로 갑니다(3장) |
| protobuf / SSE / base64 | protobuf는 스키마가 정해진 이진 직렬화, SSE는 HTTP 응답을 끊지 않고 `event:`/`data:` 줄을 흘려보내는 형식(8-6절), base64는 이진 데이터를 글자로 바꾸는 방법(크기 4/3배)입니다 |

## 1-1. 한 문장으로

> 웹사이트에서 상담을 신청한 고객에게 **AI가 바로 전화를 걸어**, 용도·예산·할부·도입 시기를 묻고, 방문체험 희망 일시나 상담사 연락 시간을 받아 사람에게 넘기는 **음성 영업 상담원**입니다.

사람 상담사가 하던 "첫 통화(1차 판정)"를 AI가 맡습니다. 판매를 끝내는 것이 아니라 **다음 단계를 하나로 정하는 것**이 목표입니다([src/prompt.ts](../../src/prompt.ts)의 "이 통화의 목표").

(2026-11-08 추가) **1차 판정**은 고객의 상황(무엇에 쓰려는지, 예산은 얼마인지, 할부를 원하는지, 언제 들이려는지)을 물어, 영업팀이 다음에 무엇을 할지 정할 수 있게 첫 분류를 해 두는 일입니다. 지시문이 정한 다음 단계는 셋 중 하나입니다. 방문체험 희망 일시 받기, 담당 상담사가 다시 전화할 시간 받기, 자료 문자 안내입니다. 금액·할인·계약은 AI가 정하지 않고 사람 상담사가 정합니다.

(2026-11-08 추가) 대화는 대략 이렇게 흘러갑니다. 지어낸 예이고, 고객 정보는 코드에 든 가상 고객(`SAMPLE_CALL`)입니다. AI 쪽은 고객에게 들리는 대로 적었고, `/` 앞은 즉시 반응(짧은 고정 문장), 뒤는 LLM이 지은 본 답입니다.

```text
AI    안녕하세요, 김민수 고객님. 오리지널스 AI 상담사입니다. 웹사이트에서 에프투 울트라 상담 신청해
      주셔서 연락드렸어요. 통화 내용은 상담 품질을 위해 녹음됩니다.      ← 고정 문장 (AI·녹음 고지)
AI    이삼 분 정도 통화 괜찮으실까요?                                    ← 고정 문장
고객  네, 괜찮아요.
AI    네네. / 문의 주신 게 에프투 울트라 맞으시죠?
고객  네, 가죽 지갑에 각인해 보고 싶어서요.
AI    네. / 가죽 소품이요. 취미로 하실 생각이세요, 판매도 생각하세요?
      … 예산, 결제 방식(일시불·할부), 도입 시기, 방문체험 의향을 하나씩 …
AI    아, 네. / 그럼 다음 주 토요일 오후 방문체험 희망으로 담당 상담사에게 전해 드릴게요. 감사합니다.
      (같은 답에서 통화 종료 도구를 불러, 인사가 끝나면 전화를 끊음)
```

두 가지를 눈여겨보세요. 첫 두 줄은 LLM을 거치지 않는 **고정 문장**입니다(1-8절 원칙 1). 그리고 고객 말이 끝날 때마다(수신 거부·불만 같은 말은 빼고) AI는 짧은 즉시 반응을 먼저 하고 본 답을 잇습니다(11-6절). 1-6절의 "한 통화의 일생"은 이 대화를 기계 안에서 따라간 그림입니다.

## 1-2. 음성 에이전트란 무엇인가

음성 에이전트는 "말을 듣고 → 이해하고 → 말로 답하는" 프로그램입니다. 사람과 전화하듯 실시간으로 주고받아야 한다는 점이 챗봇과 다릅니다. 여기서 "실시간"은 고객이 말을 마치고 1초 안팎에 AI가 말을 시작해야 한다는 뜻입니다(13-1절).

챗봇과 비교하면 어려움이 어디서 오는지 보입니다.

| | 챗봇 | 음성 에이전트 |
| --- | --- | --- |
| 입력 | 사용자가 다 쓰고 "전송"을 누름 | 말이 계속 흘러들어옴. **언제 끝났는지 스스로 판단**해야 함 |
| 입력 품질 | 오타 정도 | 잡음, 사투리, 잘못 알아들음(음성 인식 오류) |
| 출력 | 글. 길어도 됨, 목록·표 가능 | 소리. 짧아야 함. 목록·기호를 읽을 수 없음 |
| 기다림 | 몇 초 기다려도 괜찮음 | **1초만 넘어도 어색함** |
| 끼어들기 | 없음 | 상대가 말하는 중에 말을 자를 수 있음, 맞장구도 침 |
| 실수의 비용 | 다시 읽으면 됨 | 들은 말은 되돌릴 수 없음 |

(2026-11-08 추가) "1초"의 근거는 사람의 대화입니다. 사람끼리 차례를 주고받을 때의 공백은 언어를 가리지 않고 대개 0.2초 안팎이고(7-1절), 1초 가까운 침묵은 "생각하는 중", 2초를 넘으면 "안 들리나?"로 느껴집니다(13-1절). 마지막 줄의 "되돌릴 수 없음"은 화면의 글처럼 지우고 다시 쓸 수 없다는 뜻입니다. AI가 틀린 제품명이나 엉뚱한 고객 이름을 한 번 말하면 이미 고객 귀에 들어간 것이라, 말하기 전에 막는 장치가 중요해집니다(1-8절 원칙 1·5).

이 표의 오른쪽 열이 이 책의 장 목록과 거의 일치합니다. "언제 끝났는지"는 5장(VAD)과 7장(턴 테이킹), "잘못 알아들음"은 6장(STT), "짧아야 함"은 9장(프롬프트), "1초"는 13장(지연), "끼어들기"는 7장과 11장입니다.

## 1-3. 두 가지 설계: 단계 연결형과 음성 직통형

음성 에이전트를 만드는 방법은 크게 둘입니다. 둘을 가르는 기준은 "소리 → 소리" 사이에 **글** 단계를 두느냐입니다. 이 선택이 제품명 처리, 기록, 지연까지 거의 모든 것을 정하므로 이 프로젝트의 나머지 설계를 이해하는 출발점이 됩니다.

### 단계 연결형 (Cascaded, STT → LLM → TTS)

일을 세 단계로 나눠 차례로 넘기는 구조입니다. Cascade(계단식 폭포)라는 이름처럼 앞 단계의 출력이 다음 단계의 입력으로 흘러내립니다.

```text
 소리 ──▶ [STT 음성 인식] ──글──▶ [LLM 대화 생성] ──글──▶ [TTS 음성 합성] ──▶ 소리
              ▲
        [VAD + 턴 감지] "지금 말이 끝났다"를 판단
```

부품 세 개를 이어 붙입니다. 각 부품을 독립적으로 고를 수 있습니다.

(2026-11-08 추가) 그림 읽는 법입니다. `[ ]`는 부품, `──▶`는 데이터가 흐르는 방향이고, 화살표 위의 "글"은 부품 사이에 오가는 것이 소리가 아니라 글자라는 뜻입니다. STT는 고객 소리를 글로 받아 적고, LLM은 그 글과 지금까지의 대화를 읽고 할 말을 글로 지으며, TTS는 그 글을 소리로 읽습니다. 아래의 VAD와 턴 감지는 STT와 같은 소리를 따로 들으면서 "고객 말이 끝났다"를 판단하고(`▲`), 그 순간 STT가 모아 둔 확정 글이 LLM으로 넘어갑니다. 부품 사이가 글이라서 회사가 다른 부품끼리도 이을 수 있습니다.

### 음성 직통형 (Speech-to-Speech, Realtime)

```text
 소리 ──▶ [하나의 거대한 음성 모델] ──▶ 소리
```

소리를 받아 곧바로 소리를 내는 모델 하나를 씁니다(예: OpenAI Realtime 계열, Gemini Live 계열).

모델 하나가 듣기와 답하기를 함께 하므로, 바깥에서 보면 중간에 글 단계가 없습니다. 부품을 잇는 수고가 적고 끼어들기 같은 주고받기가 자연스러운 편이지만, 우리 코드가 중간에서 글을 확인하거나 고칠 틈이 없고, 대화 기록이 필요하면 따로 받아써야 합니다([2-tech-stack.md 3장](../2-tech-stack.md#3-구조-선택-단계-연결형-vs-음성-직통형)의 비교표).

### 이 프로젝트가 단계 연결형을 고른 이유

[2-tech-stack.md 3장](../2-tech-stack.md#3-구조-선택-단계-연결형-vs-음성-직통형)에 비교표가 있습니다. 핵심 이유는 **통제력**입니다. 여기서 통제력은 모델이 듣고 말하는 내용을 우리 코드가 중간에서 확인하고 고칠 수 있는 정도를 말합니다.

1. **제품명을 정확히 듣고 말해야 합니다.** "F2 울트라", "메탈팹", "엑스툴"은 일반 모델이 모르는 단어입니다. 단계 연결형이면
   - STT에 단어 목록을 주어 잘 알아듣게 하고(`context.terms`, 6장),
   - STT가 그래도 틀린 것을 코드로 고치고(`correctTranscript`, 6장),
   - TTS 앞에서 발음을 바꿔 줄 수 있습니다(`pronunciationTransform`, 10장).

   중간에 **글**이 있기 때문에 가능한 일입니다. 음성 직통형에는 이 틈이 없습니다.
2. **기록과 감사가 쉽습니다.** 각 단계에 글이 남아 대화록 저장, 금지어 검사가 쉽습니다.
3. **부품을 바꿔 끼울 수 있습니다.** 한국어에 강한 국내 STT(리턴제로)나 TTS(Typecast)로 바꿀 수 있습니다.

(2026-11-08 추가) 1번의 장치가 한 문장에 차례로 걸리는 모습입니다. STT와 LLM 줄은 가정한 입력이고, "코드가 고침"과 "TTS 앞에서 바꿈" 두 줄은 이 레포의 함수(`correctTranscript`, `pronunciationTransform`이 쓰는 `toSpoken`)를 실제로 돌린 결과입니다.

```text
고객이 말함       "메탈팹이랑 에프투 울트라 보고 있어요"
STT가 적음        "메탈 백이랑 F two 울트라 보고 있어요"     ← 틀렸다고 가정 (PoC 때 Deepgram이 "메탈 백", "F two"로 적은 적이 있음)
코드가 고침       "메탈팹이랑 F2 울트라 보고 있어요"         ← correctTranscript, LLM에 넘기기 전
LLM이 씀          "F2 울트라는 어떤 용도로 생각하세요?"
TTS 앞에서 바꿈   "에프투 울트라는 어떤 용도로 생각하세요?"  ← pronunciationTransform, 이 글을 소리로 읽음
```

지금 쓰는 Soniox는 단어 목록 덕분에 이런 제품명을 처음부터 맞게 적었습니다(6-6절). 코드 보정은 그래도 틀릴 때를 위한 마지막 방어선입니다.

대가는 **지연과 자연스러움**입니다. 부품을 차례로 거치니 시간이 더해지고, 말 끝 판단과 끼어들기를 직접 다듬어야 합니다. 이 책의 상당 부분이 이 대가를 줄이는 기법입니다.

### 지연은 어디서 오나: 구성식에 PoC 숫자 넣기 (2026-11-05 추가)

"고객이 말을 멈춘 순간부터 AI 목소리가 들리기까지"를 칸으로 나누면 두 설계가 이렇게 다릅니다. 이처럼 전체 지연을 칸의 합으로 적은 식을 이 책에서는 구성식이라고 부릅니다.

```text
단계 연결형:  VAD 무음 + STT 확정 + 말 끝 판단 + LLM 첫 토큰 + (문장 모으기) + TTS 첫 음성 + 네트워크·재생
음성 직통형:  (서버 쪽) 말 끝 판단             + 모델 첫 오디오                            + 네트워크·재생
```

(2026-11-08 추가) 두 줄은 같은 구간을 칸으로 나눈 것이고, 위아래로 같은 자리에 놓인 칸은 같은 성격의 일입니다. 칸의 뜻은 이렇습니다.

- **VAD 무음**: 소리가 멈춘 뒤 VAD가 "말이 멈췄다"고 알리기까지 일부러 기다리는 무음 길이입니다. 숨 한 번 고를 때마다 말이 끝났다고 하지 않으려는 대기입니다.
- **STT 확정**: 워커가 확정 요청(finalize)을 보낸 뒤 Soniox가 마지막 글을 확정 글로 돌려주기까지입니다.
- **말 끝 판단**: 고객이 말을 멈춘 시각부터 워커가 턴을 확정하기까지의 전체입니다. 앞의 두 칸이 이 안에 들어 있습니다(아래 첫 번째 주의).
- **LLM 첫 토큰**: LLM에 요청을 보내고 답의 첫 조각이 오기까지입니다(TTFT).
- **문장 모으기**: LLM 답을 TTS에 넘기기 전에 첫 문장이 모이기를 기다리는 시간입니다. ElevenLabs 플러그인은 20자보다 짧은 문장을 다음 문장과 합치고, 다음 문장이 시작되거나 답이 끝나야 첫 덩어리를 보냅니다(10-4절). 따로 재는 메트릭이 없어 괄호로 두었습니다(13-2절).
- **TTS 첫 음성**: TTS에 글을 보내고 첫 소리 조각이 오기까지입니다(TTFB).
- **네트워크·재생**: 만든 소리가 방을 거쳐 고객 기기에서 소리로 나기까지입니다.
- **(서버 쪽) 말 끝 판단 / 모델 첫 오디오**: 음성 직통형에서는 말 끝 판단을 모델 서버가 합니다. 모델 첫 오디오(모델이 답의 첫 소리를 내기까지)는 단계 연결형의 LLM 첫 토큰부터 TTS 첫 음성까지를 합친 자리입니다.

음성 직통형은 STT 확정과 TTS 칸이 없으니 훨씬 빠를 것 같지만, 조사 자료의 값은 약 0.8∼1.5초로 단계 연결형(약 0.8∼1.4초)과 비슷합니다([2-tech-stack.md 3장](../2-tech-stack.md#3-구조-선택-단계-연결형-vs-음성-직통형)). 이 레포에서 잰 값은 아닙니다. 구성식으로 보면 이유를 짐작할 수 있습니다(추정).

- **말 끝 판단은 똑같이 필요합니다.** 누가 판단하든 "고객이 정말 다 말했나"를 기다리는 몫은 남습니다.
- **모델 첫 오디오는 LLM 첫 토큰과 같은 성격입니다.** 큰 모델이 입력을 다 읽고(프리필, 8-3절) 첫 출력을 내기까지의 시간입니다. 우리 측정에서 가장 큰 칸(약 0.8초)이 바로 이 몫이었습니다.
- 줄어드는 것은 STT 확정(약 0.1∼0.4초), 문장 모으기, TTS 첫 음성(약 0.17초) 정도입니다. 단계 연결형은 이 차이를 선제 생성(LLM을 미리 돌려 실제 지연을 줄임)과 즉시 반응(짧은 말을 먼저 들려줘 침묵을 느끼지 못하게 함)으로 메웁니다(1-6절, 13-4절).

## 1-5. 전체 시스템 그림

이 절은 고객이 상담을 신청한 순간부터 통화 결과가 상담사에게 가기까지 관련된 시스템을 한 그림에 담습니다. 이 레포가 그중 어디를 맡는지, 다른 레포·서비스와 무엇으로 이어지는지를 보는 것이 목적입니다.

이 레포는 그림의 **[에이전트 워커]** 부분입니다. 나머지는 originalshq 레포(functions-xtool)와 외부 서비스가 맡습니다([2-tech-stack.md 6장](../2-tech-stack.md#6-전체-아키텍처)).

```text
[웹사이트 상담 신청 폼]
   │
   ▼
functions-xtool (originalshq, Cloud Functions)
   │  ① 신청 저장 → Monday 등록 → 발신 조건 검사(동의, 시간대, 수신 거부…)
   │  ② Firestore calls/{id} 생성
   │  ③ LiveKit API: 방 만들기 + 에이전트 "xtool-sales-agent" 배정(고객 정보 = job metadata)
   │                 + SIP 참가자 생성(고객 번호로 발신)
   ▼
[LiveKit Cloud]  ── 방(Room) ──────────────────────────────┐
   ▲                 │                                       │
   │ SIP          고객 참가자                            에이전트 참가자
[Asterisk]──국내 회선──고객 휴대폰                              │
                                                    [에이전트 워커] ← 이 레포
                                                      ├ VAD · 턴 감지 · 끼어들기
                                                      ├ STT(Soniox) → 보정 → LLM(Haiku) → 발음 변환 → TTS(ElevenLabs)
                                                      └ (예정) 통화 중 도구 → functions-xtool API
   ▼
[통화 후] 대화록 전송 → functions-xtool: Firestore 저장 → 요약·판정 추출 → Monday 갱신 → 상담사 알림
```

(2026-11-08 추가) 그림 읽는 법입니다. 위에서 아래로 일이 넘어가는 순서이고, ①②③은 functions-xtool이 차례로 하는 일입니다. 이 그림은 **전화 단계까지 다 만든 뒤의 목표 모습**입니다. 2026-11-08 지금 실제로 있는 것은 에이전트 워커, 신청 저장과 Monday 등록(원래 있던 상담 신청 기능), 그리고 아래 두 그림의 웹 테스트·통화 후 경로입니다. 발신 조건 검사, 통화 전에 calls 문서를 만드는 ②, SIP 발신, Asterisk와 국내 회선, 통화 중 도구, Monday 갱신과 상담사 알림은 예정입니다. 지금은 calls 문서를 통화가 끝난 뒤 결과를 저장할 때 처음 만듭니다(15-6절). 마지막 줄의 순서(저장한 뒤 판정 추출)는 지금 코드에 맞췄습니다. 그림에 나오는 이름은 이렇습니다.

- **functions-xtool**: originalshq 레포의 Cloud Functions 코드입니다. Cloud Functions는 요청이 올 때만 잠깐 실행되는 구글 클라우드의 함수라, 몇 분씩 연결을 열어 둔 채 이어지는 통화에는 맞지 않습니다. 그래서 통화는 따로 상주하는 워커가 맡습니다(4-1절).
- **Monday**: 영업팀이 상담 신청을 관리하는 업무 보드 서비스(monday.com)입니다.
- **Firestore**: 구글의 문서형 데이터베이스입니다. `calls/{id}`는 통화 하나의 기록 문서 자리입니다.
- **SIP / Asterisk**: SIP는 전화를 걸고 받는 신호 규약이고(3-5절), Asterisk는 국내 통신사 회선과 LiveKit 사이에서 전화를 중계할 오픈소스 교환기 소프트웨어입니다(3-4절, 예정).
- **job metadata**: 에이전트를 배정할 때 함께 실어 보내는 통화별 정보 문자열입니다(바로 아래).

**두 레포의 계약**은 두 가지뿐입니다. 여기서 계약은 두 레포가 따로 바뀌어도 지켜야 하는 약속, 곧 주고받는 데이터의 모양입니다.

1. **job metadata(JSON)**: 통화를 시작할 때 functions-xtool이 고객 정보를 실어 보냅니다. 형식은 [src/call-context.ts](../../src/call-context.ts)의 zod 스키마가 정의합니다(4장, 15장). (2026-11-08 추가) zod는 들어온 JSON이 정한 모양인지 실행 중에 검사하는 TypeScript 라이브러리입니다. 실어 보내는 글은 이런 모양입니다. 값은 코드의 가상 고객이고, `callId`는 웹 테스트에서 쓰는 방 이름 형식입니다(3-7절).

   ```json
   {
     "callId": "voice-test-<시각>-<무작위>",
     "customerName": "김민수",
     "device": "F2 울트라",
     "inquiredAt": "오늘 오후",
     "installment": "희망",
     "inquiryText": "가죽 지갑에 각인하고 싶은데 가능한가요?"
   }
   ```

2. **functions-xtool API(공유 비밀키)**: (2026-11-08 갱신) 에이전트가 functions-xtool의 HTTPS 주소를 부를 때, 두 쪽만 아는 비밀 문자열을 헤더(`X-Voice-Agent-Secret`)에 실어 "우리 워커가 보낸 요청"임을 증명합니다. 지금은 통화가 끝날 때 대화록과 구간 지연을 보내는 데 씁니다(아래 통화 후 경로, 이 절 표의 ⑧, 15-6절). 통화 중 도구(방문체험 빈 시간 조회, 수신 거부 등록 등)는 아직 없습니다.

워커는 Firestore에 직접 쓰지 않습니다. 저장은 결과를 받은 functions-xtool이 합니다.

### 지금 실제로 도는 경로: 웹 테스트 (2026-11-03 추가)

위 그림의 전화 부분은 아직 준비 중입니다. 대신 **관리 화면에서 브라우저로 통화하는 경로**가 먼저 생겼습니다([6-web-test.md](../6-web-test.md)).

```text
[originalshq 관리 화면 /log "AI 상담원" 탭] 가상 고객 정보 입력
   │ functions-xtool createVoiceAgentSession: 관리자 확인 → 접속 토큰 (에이전트 배정 + 고객 정보)
   ▼
[브라우저] ──WebRTC──▶ [LiveKit Cloud 방] ──배정──▶ [에이전트 워커 (이 레포)]
```

(2026-11-08 추가) 그림 읽는 법입니다. 직원이 관리 화면에 가상 고객 정보를 넣으면, functions-xtool의 `createVoiceAgentSession`이 관리자인지 확인한 뒤 **접속 토큰**을 돌려줍니다. 접속 토큰은 "이 방에 들어가도 된다"는 서명된 출입증(JWT)이고, 그 안에 "들어오면 `xtool-sales-agent`를 배정하고 이 고객 정보를 넘겨라"는 방 설정이 들어 있습니다. 그래서 브라우저가 이 토큰으로 방에 들어오는 순간 LiveKit이 워커에 일을 줍니다(3-7절, 4-3절). 소리는 functions-xtool을 거치지 않고 브라우저와 LiveKit 사이를 WebRTC로 바로 오갑니다.

전화 대신 브라우저가 고객 자리에 앉았을 뿐, 에이전트 쪽 코드와 고객 정보 계약은 전화 단계에서도 그대로 씁니다. 브라우저 쪽 동작은 3-7절, 토큰으로 에이전트를 배정하는 방식은 4-3절, LiveKit Cloud 배포는 15-5절에서 다룹니다.

(2026-11-03 갱신) 통화가 끝난 뒤의 경로도 이어졌습니다.

```text
[에이전트] 통화 종료 → 대화록·지연 기록 전송 (공유 비밀키)          ← 이 레포, 15-6절
   ▼
```

### 연결마다 무엇이 오가나: 프로토콜·직렬화·양 (2026-11-05 추가)

위 그림의 화살표를 **에이전트 워커 쪽에서** 하나씩 풀어 봅니다. 통화 하나를 맡은 잡 프로세스가 통화 내내 열어 두는 연결이 생각보다 많습니다.

(2026-11-08 추가) 제목의 세 말은 이렇습니다. **프로토콜**은 선 위에서 주고받는 규칙(WebSocket, HTTPS, WebRTC 등), **직렬화**는 프로그램 안의 데이터를 선으로 보낼 바이트로 바꾸는 형식(JSON, protobuf 등), **양**은 1초에 오가는 바이트 수입니다. 이것을 알면 지연과 비용을 어림할 수 있고, 문제가 생겼을 때 어느 선을 의심할지 정할 수 있습니다. 처음 읽을 때는 "연결이 여덟 개 있고, 그중 소리가 가장 크다"만 잡아도 충분합니다.

```text
[워커 프로세스] ──① WSS + protobuf ─────────────────────▶ LiveKit 서버 (/agent)
   │  └ 추론 프로세스 (턴 감지 v1-mini, 4-5절)
   │ ③ Node IPC (JSON)
   ▼
[잡 프로세스 = 통화 하나]
   ├─② WebRTC (UDP 위 DTLS-SRTP, Opus) ◀────────▶ LiveKit 방 ◀──▶ 고객 (브라우저·전화)
   ├─④ WSS: PCM 바이너리 ↑ / JSON 토큰 ↓ ─────────▶ Soniox
   ├─⑤ HTTPS: JSON 요청 ↑ / SSE ↓ ───────────────▶ Anthropic (또는 Bedrock)
   ├─⑥ WSS: JSON 글 ↑ / JSON + base64 오디오 ↓ ───▶ ElevenLabs
   ├─⑦ WSS: 16kHz PCM ──────────────────────────▶ LiveKit Inference (턴 감지 v1, 끼어들기)
   └─⑧ HTTPS: JSON, 통화 끝에 한 번 ──────────────▶ functions-xtool
```

(2026-11-08 추가) 그림 읽는 법입니다. 왼쪽 `[ ]`는 우리 워커 컴퓨터 안의 프로세스입니다. **워커 프로세스**는 상주하며 LiveKit에서 일을 받고, 통화마다 **잡 프로세스**를 자식으로 하나씩 띄웁니다. 턴 감지 `v1-mini`를 돌리는 **추론 프로세스**도 워커의 자식입니다(4-4절, 4-5절). 오른쪽은 연결 상대이고, 번호 ①∼⑧은 아래 표의 행 번호입니다. `──▶`는 연결을 여는 쪽에서 상대 쪽으로 그렸을 뿐 데이터는 양쪽으로 오가고, `↑`는 워커가 내보내는 방향, `↓`는 워커가 받는 방향입니다. 표의 칸은 왼쪽부터 번호, 누가 누구와 잇는가, 어떤 규칙의 선인가(프로토콜), 바이트를 어떤 모양으로 싣나(직렬화), 무엇이 오가나, 1초에 얼마나(손 계산), 근거입니다.

(2026-11-08 추가) 표에 나오는 낯선 말입니다. 자세한 것은 괄호의 장에서 다룹니다.

- **WSS / HTTPS**: TLS로 암호화한 WebSocket(`wss://`)과 HTTP(`https://`)입니다.
- **JWT**: 내용(JSON)에 서명을 붙인 출입증 문자열입니다. 서명 키가 없으면 내용을 바꿀 수 없습니다(3-7절).
- **RTP / DTLS-SRTP**: RTP는 소리를 작은 패킷으로 잘라 차례 번호와 시각을 붙여 보내는 규약이고(3-1절), DTLS-SRTP는 WebRTC가 그 패킷을 암호화하는 방식입니다(3-2절).
- **Node IPC**: 같은 컴퓨터 안의 부모·자식 Node 프로세스가 주고받는 통로입니다. 기본 형식은 JSON 한 줄입니다(4-5절).
- **keepalive**: 오갈 데이터가 없을 때도 연결이 살아 있다고 알리려고 주기적으로 보내는 작은 메시지입니다.
- **Bedrock / SigV4**: AWS에서 Claude를 부르는 경로와, AWS 요청에 붙이는 서명 방식입니다(16장).
- **kbps**: 1초에 오가는 비트 수(천 단위)입니다. 1바이트가 8비트라 32,000B/s = 256kbps입니다.

표에서 볼 점입니다.

- **소리가 가장 큰 짐입니다.** 고객 소리 한 줄기가 워커 안에서 여러 갈래로 복사되어, 워커 안의 VAD와 함께 Soniox(④)와 턴 감지(⑦, 개발 모드·LiveKit Cloud 배포일 때)로 각각 압축 없이 나갑니다. 방에서 받을 때(②, Opus 수 KB/s로 추정)보다 공급사로 내보낼 때(32KB/s씩)가 훨씬 큽니다.
- **같은 WebSocket이라도 싣는 방식이 다릅니다.** Soniox는 오디오를 이진 프레임 그대로, ElevenLabs는 JSON 안의 base64 글자로 보냅니다. base64는 3바이트를 4글자로 바꾸므로 같은 소리가 4/3배 커지고, 받은 뒤 다시 풀어야 합니다.
- **LLM은 턴마다 요청을 새로 보냅니다.** STT·TTS처럼 한 연결 위에서 대화가 이어지는 것이 아니라, 턴마다 HTTP 요청 하나에 지시문과 대화 기록 전체를 다시 싣습니다. 대화가 길어질수록 요청이 커집니다. 프롬프트 캐시(8-4절)는 서버의 계산을 아낄 뿐 보내는 바이트를 줄이지 않습니다. 밑의 TCP·TLS 연결은 쉬는 시간이 짧으면 다시 쓰고, 4초 넘게 쉬면 새로 맺습니다(8-8절, 17-2 #28).
- **LiveKit 자체 연결은 대부분 protobuf, 공급사와 우리 API는 JSON입니다.** 워커 제어(①), 방 시그널링(②), 턴 감지 `/eot`(⑦)는 스키마가 정해진 protobuf를 쓰고, Soniox·Anthropic·ElevenLabs·functions-xtool은 JSON을 씁니다. 예외는 소리입니다. JSON에는 이진 데이터를 그대로 넣을 수 없어 base64로 바꾸거나(⑥), 소리만 이진 프레임으로 따로 보냅니다(④, ⑦ `/bargein`).

#### 깊이 보기: 초당 양을 손으로 계산하기 (2026-11-05 추가)

압축하지 않은 소리(PCM)의 양은 곱셈 하나로 나옵니다(2장). 식의 세 항은 이렇습니다. 샘플레이트는 1초에 소리를 재는 횟수, 샘플당 바이트는 한 번 잰 값을 적는 크기(16비트 = 2바이트), 채널 수는 소리 줄기의 수(모노 1, 스테레오 2)입니다. kbps는 바이트에 8을 곱해 1,000으로 나눈 값입니다. base64 식의 ⌈ ⌉는 올림이라, 바이트 수가 3으로 나누어떨어지지 않아도 마지막 묶음이 4글자를 차지합니다.

```text
PCM 초당 바이트 = 샘플레이트 × 샘플당 바이트 × 채널 수

  16kHz, 16비트(2B), 모노  = 16,000 × 2 × 1 = 32,000 B/s = 256 kbps   ← Soniox(④), 턴 감지(⑦), VAD
  24kHz                    = 24,000 × 2     = 48,000 B/s = 384 kbps   ← 워커 안의 방 오디오(②를 푼 것)
  22.05kHz                 = 22,050 × 2     = 44,100 B/s              ← ElevenLabs pcm_22050(⑥)
  (참고) 전화 G.711 8kHz, 8비트             =  8,000 B/s =  64 kbps   ← SIP 단계(3장)

base64 글자 수 = ⌈바이트 ÷ 3⌉ × 4   (약 4/3배)

  ElevenLabs 소리 1초:   44,100 B → 58,800 글자
  턴 감지 v1-mini 한 번: 1.2초 × 32,000 = 38,400 B → 51,200 글자 (③)
```

통화 하나로 늘려 보면 Soniox로만 시간당 32,000 × 3,600 ≈ 115MB, 통화 상한 8분이면 약 15MB를 올려 보냅니다. 고객이 말하지 않는 동안에도 소리는 계속 갑니다.

STT 쪽과 TTS 쪽은 "초당"의 뜻이 다릅니다. STT로 가는 소리는 고객이 말하는 속도로만 생기므로 **벽시계 1초당** 32,000B입니다. TTS에서 오는 소리는 서버가 합성하는 대로 실시간보다 빨리 몰려 오므로 **소리 1초당** 58,800글자입니다. 짧은 시간에 몇 초 분량이 한꺼번에 도착할 수 있습니다.

실습: `node docs/1-study/lab/01-wire-sizes.mjs`가 위 계산과 아래 리샘플러 측정을 키 없이 보여 줍니다.

#### 깊이 보기: Soniox로 가는 메시지는 320바이트가 아니다 (2026-11-05 추가)

(2026-11-08 추가) 먼저 낱말 둘입니다. **프레임**은 소리를 일정한 길이로 잘라 묶은 덩어리입니다. 24kHz의 10ms 프레임이면 샘플 240개입니다. **리샘플링**은 샘플레이트를 바꾸는 계산입니다. 24kHz를 16kHz로 내리려면 샘플 3개마다 2개가 되도록 그 사이 시점의 값을 다시 계산합니다. 이 계산을 하는 부품이 **리샘플러**인데, 앞뒤 샘플을 함께 봐야 하므로 입력을 조금 모아 두었다가 한꺼번에 내놓습니다(2-2절 "리샘플링").

흔히 "10ms 프레임 하나 = 16,000 × 0.01 × 2B = 320B, 초당 100개"로 계산합니다. 소리가 처음부터 16kHz로 들어오는 경로라면 맞습니다. 그런데 이 프로젝트에서는 소리가 이렇게 흐릅니다.

```text
방 → RoomIO: 24kHz 모노로 받음 (voice/room_io/room_io.ts 125, 기본값)
   → 노이즈 제거: 프레임 길이 그대로 (@livekit/plugins-ai-coustics dist/index.js의 process())
   → STT 스트림 pushFrame: 16kHz가 아니므로 AudioResampler(24000 → 16000) (stt/stt.ts 549)
   → 리샘플러가 내보낸 프레임 하나 = WebSocket 메시지 하나 (agents-plugin-soniox/src/stt.ts 325)
```

메시지 크기는 리샘플러가 정합니다. SDK와 같은 기본 설정의 리샘플러에 24kHz 10ms 프레임을 3초 동안 넣어 본 결과입니다(실측, 맥, `@livekit/rtc-node` 1.2.1, 실습 스크립트).

| 입력 | 메시지 크기 | 초당 메시지 | 첫 메시지 |
| --- | --- | --- | --- |
| 16kHz 10ms 프레임 (리샘플 없음, 가정) | 320B | 100개 | 입력 10ms 뒤 |

## 1-6. 한 통화의 일생

이 절의 대상은 통화 하나가 시작돼 끝날 때까지의 사건 순서입니다. 1-1절의 대화를 기계 안에서 본 모습이고, 뒤 장들은 이 그림의 한 줄씩을 확대해서 보여 줍니다.

시간 순서로 따라가 봅니다. 괄호는 그 내용을 다루는 장입니다.

**누가 턴을 확정하나 (2026-11-07 추가).** 눈금의 "턴 확정"은 Soniox가 아니라 **LiveKit 워커**가 정합니다. 통화마다 뜨는 잡 프로세스 안의 `AgentSession`(`voice/audio_recognition.ts`)이 세 가지 재료를 모아 판단합니다.

| --- | --- | --- |

```text

  대기 = p가 기준값 이상이면 minDelay 300ms, 낮으면 maxDelay 2,500ms
         (기준값: 로컬 v1-mini는 한국어 0.4, 클라우드 v1은 서버가 정함)
```

- 식의 max(…)는 괄호 안 세 시각 가운데 가장 늦은 것입니다. 곧 세 조건(충분히 기다림, 확정 글이 옴, 예측이 옴)이 모두 갖춰진 순간에 확정합니다. p는 턴 감지 모델이 낸 "끝났을 확률"이고, 기준값보다 낮으면 "아직 말할 게 남았다"고 보고 마지막 말소리부터 2.5초까지 기다립니다.
- 그래서 t≈300의 300ms는 "300ms가 지나면 확정"이 아니라 **"그 전에는 확정하지 않는다"는 하한**입니다. 0.3초보다 짧은 숨 고르기로는 턴이 끝나지 않습니다.
- 이 프로젝트에서는 300ms가 지날 때 확정 글이 보통 아직 없으므로, 실제 확정은 FINAL이 오는 t≈380∼640에 일어납니다. 그 사이 고객이 다시 말하면 대기는 취소되고, 다음 말 멈춤에서 다시 셉니다.
- STT는 말하는 동안에도 소리를 계속 받아 중간 글을 냅니다. 말이 멈춘 뒤에 하는 일은 finalize로 마지막 확정 글을 당겨오는 것, 곧 Soniox가 스스로 판단할 때까지 기다리지 않고 지금 바로 확정 글을 보내게 하는 것뿐입니다. Soniox에도 스스로 "말 한 덩어리가 끝났다"고 보는 끝점(endpoint) 판단이 있지만(`max_endpoint_delay_ms`, 6-3절), 이 레포는 그것을 기다리지 않고 VAD가 말 멈춤을 알리는 즉시 finalize를 보냅니다(`patches/`의 finalize 패치, 6-5절).
- 식의 근거와 실측은 [7-4절](07-turn-taking.md#7-4-이-프로젝트의-말-끝-판단-한-턴의-타임라인)의 깊이 보기 "한 턴을 ms로"에, 확정 글이 늦는 이유는 [6-5절 깊이 보기](06-stt.md#깊이-보기-126초를-식으로-나누기-2026-11-06-추가)에 있습니다.

브라우저 PoC의 값입니다. 전화 단계에서는 지터 버퍼(패킷이 들쭉날쭉 도착해도 고르게 재생하려고 잠깐 모아 두는 대기열, 2-6절)와 코덱 변환(전화망의 G.711과 인터넷의 Opus 사이를 바꾸는 일, 2-5절)이 더해지고, 고객 휴대폰까지의 네트워크·재생 칸(위 그림에 없음)도 따로 재야 합니다(13-7절).

## 1-8. 이 프로젝트를 관통하는 설계 원칙 다섯 가지

코드를 읽다 보면 같은 판단이 여러 번 반복됩니다. 미리 이름을 붙여 두면 읽기 쉽습니다.

### 원칙 1. 확실해야 하는 것은 코드로, 유연해야 하는 것은 LLM으로

- AI·녹음 고지는 **법적으로 반드시 정확해야** 하므로 LLM을 거치지 않는 고정 문장입니다(`openingNotice`).
- 제품명 오인식 보정은 프롬프트로 시켰더니 LLM이 틀린 이름을 따라 말해서(3/3회) **코드로** 옮겼습니다([5-poc-results.md](../5-poc-results.md)).
- 첫머리 맞장구도 프롬프트로 금지하고, **그래도 나오는 것을 코드로** 뗍니다(`withoutLeadingAck`).

LLM은 확률적입니다. 같은 입력에도 매번 조금씩 다른 글을 만든다는 뜻입니다(8-2절). "대부분 지킴"으로 충분하지 않은 규칙은 코드가 맡습니다.

### 원칙 2. 지연은 가장 큰 구간부터 줄인다

PoC 측정에서 병목이 STT 확정 → LLM 첫 토큰 순으로 옮겨 갔고, 그때마다 그 구간을 고쳤습니다(13장). 추측이 아니라 **측정한 뒤** 고칩니다.

(2026-11-08 추가) 병목은 전체 시간을 가장 많이 잡아먹는 구간입니다. 예를 들어 STT를 Soniox로 바꾼 뒤 말 끝 판단이 0.57∼1.42초로 늘어 1초를 넘는 턴이 생겼을 때는 finalize 패치로 0.38∼0.54초까지 줄였고, 그 뒤 가장 큰 칸이 된 LLM 첫 토큰(약 0.8초)이 지금도 남은 병목입니다(13-4절, 13-5절). 가장 큰 구간을 그대로 두고 작은 구간을 깎아 봐야 전체는 별로 줄지 않습니다(13-2절).

### 원칙 3. 기다리는 시간은 숨긴다

빨리 할 수 없는 일은 **미리 시작하거나**(선제 생성), **기다리는 동안 무언가를 들려줍니다**(즉시 반응 "네네"). 실제 지연과 체감 지연은 다릅니다.

(2026-11-08 추가) 실제 지연은 본 답이 나오기까지의 시간, 체감 지연은 고객이 침묵으로 느끼는 시간입니다. 1-6절 눈금에서 실제 지연은 약 1.4∼1.6초, 체감 지연은 "네네."까지 약 0.6∼0.8초입니다. 두 기법이 줄이는 것도 다릅니다. 선제 생성은 기다림을 겹쳐서 실제 지연을 줄이고(그만큼 체감도 줄어듦), 즉시 반응은 실제 지연은 그대로 두고 체감 지연만 줄입니다(13-4절).

### 원칙 4. 외부 부품은 감싸서 쓴다

플러그인이 필요한 옵션을 지원하지 않으면, 상속으로 감싸거나(`VoiceAnthropicLLM`, `FinalizingSonioxSTT`) 마지막 수단으로 패치합니다. 그리고 그 사실을 문서에 남겨 업그레이드 때 다시 확인하게 합니다.

(2026-11-08 추가) "상속으로 감싼다"는 플러그인의 클래스를 물려받은(`extends`) 우리 클래스를 만들어 필요한 부분만 바꾸는 것입니다. `VoiceAnthropicLLM`은 플러그인에 없는 생각 모드·effort·캐시 설정을 요청마다 끼워 넣고(8-8절), `FinalizingSonioxSTT`는 확정 요청 함수 `finalize()`를 더합니다(6-5절). 패치는 설치된 패키지의 코드 자체를 고친 차이 파일을 설치 때마다 적용하는 방법이고(15-3절), 이 레포의 패치(`patches/`)는 플러그인이 무시하던 flush 신호를 Soniox의 finalize 요청으로 바꿉니다. 패치는 패키지 버전이 바뀌면 맞지 않을 수 있어 마지막 수단입니다.

### 원칙 5. 실패해도 안전한 쪽으로

고객 정보 JSON이 깨지면 가상 고객("김민수")이 아니라 **빈 정보**("고객님")로 진행합니다. 실제 고객에게 엉뚱한 이름을 부르는 것보다 이름을 안 부르는 편이 안전하기 때문입니다([src/call-context.ts](../../src/call-context.ts)).

(2026-11-08 추가) 정확히는 metadata가 아예 없으면(Agent Console이나 `lk agent console`처럼 metadata 없이 시작하는 테스트) 가상 고객으로, 있는데 읽지 못하면 빈 정보로 진행합니다. 칸 일부만 틀렸으면 그 칸만 기본값으로 두고 나머지(통화 결과를 보낼 때 쓰는 `callId` 포함)는 살립니다(4-3절). 같은 생각이 다른 곳에도 있습니다. 노이즈 제거가 실패하면 원본 소리를 그대로 넘기고(2-7절), 즉시 반응 음성을 미리 합성하지 못했으면 그때그때 합성하며(13-5절), 통화 결과 전송이 실패하면 로그를 남깁니다(15-6절, 다시 보내기는 아직 없음).
