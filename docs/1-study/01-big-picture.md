# 1장. 큰 그림 — 이 프로젝트는 무엇을, 어떻게 하는가

이 장은 책 전체의 지도입니다. 세부를 읽다가 길을 잃으면 여기로 돌아오면 됩니다.

---

## 1-1. 한 문장으로

> 웹사이트에서 상담을 신청한 고객에게 **AI가 바로 전화를 걸어**, 용도·예산·할부·도입 시기를 묻고, 방문체험 희망 일시나 상담사 연락 시간을 받아 사람에게 넘기는 **음성 영업 상담원**입니다.

사람 상담사가 하던 "첫 통화(1차 판정)"를 AI가 맡습니다. 판매를 끝내는 것이 아니라 **다음 단계를 하나로 정하는 것**이 목표입니다([src/prompt.ts](../../src/prompt.ts)의 "이 통화의 목표").

---

## 1-2. 음성 에이전트란 무엇인가

음성 에이전트는 "말을 듣고 → 이해하고 → 말로 답하는" 프로그램입니다. 사람과 전화하듯 실시간으로 주고받아야 한다는 점이 챗봇과 다릅니다.

챗봇과 비교하면 어려움이 어디서 오는지 보입니다.

| | 챗봇 | 음성 에이전트 |
| --- | --- | --- |
| 입력 | 사용자가 다 쓰고 "전송"을 누름 | 말이 계속 흘러들어옴. **언제 끝났는지 스스로 판단**해야 함 |
| 입력 품질 | 오타 정도 | 잡음, 사투리, 잘못 알아들음(음성 인식 오류) |
| 출력 | 글. 길어도 됨, 목록·표 가능 | 소리. 짧아야 함. 목록·기호를 읽을 수 없음 |
| 기다림 | 몇 초 기다려도 괜찮음 | **1초만 넘어도 어색함** |
| 끼어들기 | 없음 | 상대가 말하는 중에 말을 자를 수 있음, 맞장구도 침 |
| 실수의 비용 | 다시 읽으면 됨 | 들은 말은 되돌릴 수 없음 |

이 표의 오른쪽 열이 이 책의 장 목록과 거의 일치합니다. "언제 끝났는지"는 5장(VAD)과 7장(턴 테이킹), "잘못 알아들음"은 6장(STT), "짧아야 함"은 9장(프롬프트), "1초"는 13장(지연), "끼어들기"는 7장과 11장입니다.

## 1-3. 두 가지 설계: 단계 연결형과 음성 직통형

음성 에이전트를 만드는 방법은 크게 둘입니다.

### 단계 연결형 (Cascaded, STT → LLM → TTS)

```text
 소리 ──▶ [STT 음성 인식] ──글──▶ [LLM 대화 생성] ──글──▶ [TTS 음성 합성] ──▶ 소리
              ▲                                                    
        [VAD + 턴 감지] "지금 말이 끝났다"를 판단
```

부품 세 개를 이어 붙입니다. 각 부품을 독립적으로 고를 수 있습니다.

### 음성 직통형 (Speech-to-Speech, Realtime)

```text
 소리 ──▶ [하나의 거대한 음성 모델] ──▶ 소리
```

소리를 받아 곧바로 소리를 내는 모델 하나를 씁니다(예: OpenAI Realtime 계열, Gemini Live 계열).

### 이 프로젝트가 단계 연결형을 고른 이유

[2-tech-stack.md 3장](../2-tech-stack.md#3-구조-선택-단계-연결형-vs-음성-직통형)에 비교표가 있습니다. 핵심 이유는 **통제력**입니다.

1. **제품명을 정확히 듣고 말해야 합니다.** "F2 울트라", "메탈팹", "엑스툴"은 일반 모델이 모르는 단어입니다. 단계 연결형이면
   - STT에 단어 목록을 주어 잘 알아듣게 하고(`context.terms`, 6장),
   - STT가 그래도 틀린 것을 코드로 고치고(`correctTranscript`, 6장),
   - TTS 앞에서 발음을 바꿔 줄 수 있습니다(`pronunciationTransform`, 10장).
   중간에 **글**이 있기 때문에 가능한 일입니다. 음성 직통형에는 이 틈이 없습니다.
2. **기록과 감사가 쉽습니다.** 각 단계에 글이 남아 대화록 저장, 금지어 검사가 쉽습니다.
3. **부품을 바꿔 끼울 수 있습니다.** 한국어에 강한 국내 STT(리턴제로)나 TTS(Typecast)로 바꿀 수 있습니다.

대가는 **지연과 자연스러움**입니다. 부품을 차례로 거치니 시간이 더해지고, 말 끝 판단과 끼어들기를 직접 다듬어야 합니다. 이 책의 상당 부분이 이 대가를 줄이는 기법입니다.

## 1-5. 전체 시스템 그림

이 레포는 그림의 **[에이전트 워커]** 부분입니다. 나머지는 originalshq 레포(functions-xtool)와 외부 서비스가 맡습니다([2-tech-stack.md 6장](../2-tech-stack.md#6-전체-아키텍처)).

```text
[웹사이트 상담 신청 폼]
   │
   ▼
functions-xtool (originalshq, Cloud Functions)
   │  ① 신청 저장 → Monday 등록 → 발신 조건 검사(동의, 시간대, 수신 거부…)
   │  ② Firestore calls/{id} 생성
   │  ③ LiveKit API: 방 만들기 + 에이전트 "xtool-sales-agent" 배정(고객 정보 = job metadata)
   │                 + SIP 참가자 생성(고객 번호로 발신)
   ▼
[LiveKit Cloud]  ── 방(Room) ──────────────────────────────┐
   ▲                 │                                       │
   │ SIP          고객 참가자                            에이전트 참가자
[Asterisk]──국내 회선──고객 휴대폰                              │
                                                    [에이전트 워커] ← 이 레포
                                                      ├ VAD · 턴 감지 · 끼어들기
                                                      ├ STT(Soniox) → 보정 → LLM(Haiku) → 발음 변환 → TTS(ElevenLabs)
                                                      └ (예정) 통화 중 도구 → functions-xtool API
   ▼
[통화 후] functions-xtool: 요약·판정 추출 → Firestore → Monday 갱신 → 상담사 알림
```

**두 레포의 계약**은 두 가지뿐입니다.

1. **job metadata(JSON)**: 통화를 시작할 때 functions-xtool이 고객 정보를 실어 보냅니다. 형식은 [src/call-context.ts](../../src/call-context.ts)의 zod 스키마가 정의합니다(4장, 15장).
2. **functions-xtool API(공유 비밀키)**: 통화 중 도구(예약 조회 등)와 결과 저장에 쓸 예정입니다. 아직 없습니다.

### 지금 실제로 도는 경로: 웹 테스트 (2026-11-03 추가)

위 그림의 전화 부분은 아직 준비 중입니다. 대신 **관리 화면에서 브라우저로 통화하는 경로**가 먼저 생겼습니다([6-web-test.md](../6-web-test.md)).

```text
[originalshq 관리 화면 /log "AI 상담원" 탭] 가상 고객 정보 입력
   │ functions-xtool createVoiceAgentSession: 관리자 확인 → 접속 토큰 (에이전트 배정 + 고객 정보)
   ▼
[브라우저] ──WebRTC──▶ [LiveKit Cloud 방] ──배정──▶ [에이전트 워커 (이 레포)]
```

전화 대신 브라우저가 고객 자리에 앉았을 뿐, 에이전트 쪽 코드와 고객 정보 계약은 전화 단계에서도 그대로 씁니다. 브라우저 쪽 동작은 3-7절, 토큰으로 에이전트를 배정하는 방식은 4-3절, LiveKit Cloud 배포는 15-5절에서 다룹니다.

(2026-11-03 갱신) 통화가 끝난 뒤의 경로도 이어졌습니다.

```text
[에이전트] 통화 종료 → 대화록·지연 기록 전송 (공유 비밀키)          ← 이 레포, 15-6절
   ▼
[functions-xtool] submitVoiceCallResult → Firestore calls/{callId}         ← 15-6절
   ▼ (문서 생성 트리거)
extractVoiceCallJudgment: Opus 5.5로 요약·판정 칸 추출               ← 8-10·8-11절
   ▼
[관리 화면] 통화 결과(요약·판정·지연·대화록) 표시
```

처음 그림의 "[통화 후] 요약·판정 추출" 부분이 실제로 생긴 것입니다. Monday 갱신과 상담사 알림은 아직입니다. (2026-11-04) 받는 쪽 코드를 읽은 내용은 8-11절(구조화 출력으로 판정 칸 채우기)과 15-6절(비밀키 비교, 멱등 저장, 트리거, 끝나는 경로별 시간표)에 있습니다.

## 1-6. 한 통화의 일생

시간 순서로 따라가 봅니다. 괄호는 그 내용을 다루는 장입니다.

```text
t=0     functions-xtool이 방을 만들고 에이전트를 배정 (4장)
        └ LiveKit이 대기 중인 워커 하나에 "일(job)"을 보냄
        └ 워커가 자식 프로세스에서 main.ts의 entry()를 실행
t≈0.x   entry(): 설정 읽기 → metadata에서 고객 정보 파싱 → AgentSession 구성
        → session.start(): 방에 접속하고 고객 오디오를 구독 (RoomIO, 4장)
t≈?     고객이 전화를 받음 (SIP 200 OK, 3장)
        session.say(고지)    "안녕하세요, 김민수 고객님. 오리지널스 AI 상담사입니다. …녹음됩니다."
                             ← LLM을 거치지 않는 고정 문장, 끼어들기 막음 (9장, 11장)
        session.say(질문)    "이삼 분 정도 통화 괜찮으실까요?"  ← 끼어들기 허용
─── 여기부터 턴의 반복 ───────────────────────────────────────────────
        고객: "네, 괜찮아요."
          ├ 소리 → 노이즈 제거 → VAD "말 시작" (2장, 5장)
          ├ STT가 글자를 흘려보냄: "네" … "네, 괜찮" … (6장)
          ├ VAD "말 멈춤" → Soniox에 확정 요청(finalize) (6장)
          ├ 턴 감지 모델: "말이 끝났을 확률 높음" → 짧게 기다리고 턴 확정 (7장)
          │   └ 이 사이 LLM을 미리 돌리기 시작 (선제 생성, 11장)
          ├ onUserTurnCompleted: 제품명 오인식 보정 + "네네." 즉시 반응 (11장)
          ├ LLM(Haiku) 스트리밍 응답: "문의 주신 게 에프투 울트라 맞으시죠?" (8장)
          │   └ 첫머리 맞장구 제거 (ack.ts, 12장)
          ├ 발음 변환: F2 → 에프투 (10장)
          ├ TTS가 소리를 흘려보냄 → 방에 발행 → 고객에게 들림 (10장)
          └ 고객이 중간에 "아니요"라고 끊으면: 멈추고 들은 데까지만 기록 (7장, 11장)
─────────────────────────────────────────────────────────────────────
        마무리: "그럼 다음 주 토요일 오후에 방문체험 원하시는 걸로…" (9장)
t=끝    고객이 끊음 → 방 종료 → 워커 프로세스 정리 (4장)
        또는 AI가 끊음: 작별 인사 + end_call 도구, 무응답·최대 8분 안전장치 (4-7절, 5-5절)
        (예정) 통화 후 처리: 요약, 판정 칸 추출, Monday 갱신
```

## 1-8. 이 프로젝트를 관통하는 설계 원칙 다섯 가지

코드를 읽다 보면 같은 판단이 여러 번 반복됩니다. 미리 이름을 붙여 두면 읽기 쉽습니다.

### 원칙 1. 확실해야 하는 것은 코드로, 유연해야 하는 것은 LLM으로

- AI·녹음 고지는 **법적으로 반드시 정확해야** 하므로 LLM을 거치지 않는 고정 문장입니다(`openingNotice`).
- 제품명 오인식 보정은 프롬프트로 시켰더니 LLM이 틀린 이름을 따라 말해서(3/3회) **코드로** 옮겼습니다([5-poc-results.md](../5-poc-results.md)).
- 첫머리 맞장구도 프롬프트로 금지하고, **그래도 나오는 것을 코드로** 뗍니다(`withoutLeadingAck`).

LLM은 확률적입니다. "대부분 지킴"으로 충분하지 않은 규칙은 코드가 맡습니다.

### 원칙 2. 지연은 가장 큰 구간부터 줄인다

PoC 측정에서 병목이 STT 확정 → LLM 첫 토큰 순으로 옮겨 갔고, 그때마다 그 구간을 고쳤습니다(13장). 추측이 아니라 **측정한 뒤** 고칩니다.

### 원칙 3. 기다리는 시간은 숨긴다

빨리 할 수 없는 일은 **미리 시작하거나**(선제 생성), **기다리는 동안 무언가를 들려줍니다**(즉시 반응 "네네"). 실제 지연과 체감 지연은 다릅니다.

### 원칙 4. 외부 부품은 감싸서 쓴다

플러그인이 필요한 옵션을 지원하지 않으면, 상속으로 감싸거나(`VoiceAnthropicLLM`, `FinalizingSonioxSTT`) 마지막 수단으로 패치합니다. 그리고 그 사실을 문서에 남겨 업그레이드 때 다시 확인하게 합니다.

### 원칙 5. 실패해도 안전한 쪽으로
