# 1장. 큰 그림 — 이 프로젝트는 무엇을, 어떻게 하는가

이 장은 책 전체의 지도입니다. 세부를 읽다가 길을 잃으면 여기로 돌아오면 됩니다.

(2026-11-05 추가) 이번 판부터 지도에 **숫자**를 붙였습니다. 연결마다 무엇이 어떤 형식으로 초당 몇 바이트 오가는지(1-5절), 한 턴이 몇 ms 눈금으로 흘러가는지(1-6절), 지연이 어느 칸에서 생기는지(1-3절)를 적었습니다. 각 숫자 옆에 코드로 확인했는지, 잰 값인지, 추정인지를 표시했습니다. 자세한 원리는 링크한 장에 있으니 처음에는 숫자의 크기만 눈에 익혀 두면 됩니다.

| RoomIO | 방의 고객 오디오를 세션 입력으로, 세션이 만든 소리를 방의 오디오 트랙으로 잇는 SDK 부품입니다(4-6절) |
| 선제 생성 | 턴이 확정되기 전에, 거의 굳은 글로 LLM을 미리 돌려 두는 것입니다. 확정 글이 다르면 버리고 다시 합니다(11-4절) |
| TTFT / TTFB | 요청을 보내고 첫 토큰(LLM) / 첫 바이트(TTS의 첫 소리)가 오기까지의 시간입니다. 음성에서는 다 끝나는 시간보다 이 값이 중요합니다(8-3절, 13-3절) |
| 말 끝 판단 (EOU) | 고객이 말을 멈춘 시각부터 턴을 확정하기까지의 시간입니다. VAD 무음 대기와 STT 확정이 이 안에 들어 있습니다(13-3절) |
| WebSocket | TCP(+TLS) 연결 하나를 열어 두고 양쪽이 메시지를 주고받는 방식입니다. 순서와 도착이 보장되지만, 잃은 조각을 다시 보내느라 뒤의 메시지가 기다릴 수 있습니다. 워커↔LiveKit 제어, STT·TTS 연결이 이것입니다 |
| WebRTC | 실시간 음성·영상을 보내는 표준입니다. UDP 위에서 늦은 패킷은 버리고 "지금 소리"를 우선합니다. 고객 ↔ 방 ↔ 에이전트의 소리가 이것으로 갑니다(3장) |
| protobuf / SSE / base64 | protobuf는 스키마가 정해진 이진 직렬화, SSE는 HTTP 응답을 끊지 않고 `event:`/`data:` 줄을 흘려보내는 형식(8-6절), base64는 이진 데이터를 글자로 바꾸는 방법(크기 4/3배)입니다 |

## 1-1. 한 문장으로

> 웹사이트에서 상담을 신청한 고객에게 **AI가 바로 전화를 걸어**, 용도·예산·할부·도입 시기를 묻고, 방문체험 희망 일시나 상담사 연락 시간을 받아 사람에게 넘기는 **음성 영업 상담원**입니다.

## 1-2. 음성 에이전트란 무엇인가

음성 에이전트는 "말을 듣고 → 이해하고 → 말로 답하는" 프로그램입니다. 사람과 전화하듯 실시간으로 주고받아야 한다는 점이 챗봇과 다릅니다.

챗봇과 비교하면 어려움이 어디서 오는지 보입니다.

| | 챗봇 | 음성 에이전트 |
| --- | --- | --- |
| 입력 | 사용자가 다 쓰고 "전송"을 누름 | 말이 계속 흘러들어옴. **언제 끝났는지 스스로 판단**해야 함 |
| 입력 품질 | 오타 정도 | 잡음, 사투리, 잘못 알아들음(음성 인식 오류) |
| 출력 | 글. 길어도 됨, 목록·표 가능 | 소리. 짧아야 함. 목록·기호를 읽을 수 없음 |
| 기다림 | 몇 초 기다려도 괜찮음 | **1초만 넘어도 어색함** |
| 끼어들기 | 없음 | 상대가 말하는 중에 말을 자를 수 있음, 맞장구도 침 |
| 실수의 비용 | 다시 읽으면 됨 | 들은 말은 되돌릴 수 없음 |

이 표의 오른쪽 열이 이 책의 장 목록과 거의 일치합니다. "언제 끝났는지"는 5장(VAD)과 7장(턴 테이킹), "잘못 알아들음"은 6장(STT), "짧아야 함"은 9장(프롬프트), "1초"는 13장(지연), "끼어들기"는 7장과 11장입니다.

## 1-3. 두 가지 설계: 단계 연결형과 음성 직통형

음성 에이전트를 만드는 방법은 크게 둘입니다.

### 단계 연결형 (Cascaded, STT → LLM → TTS)

```text
 소리 ──▶ [STT 음성 인식] ──글──▶ [LLM 대화 생성] ──글──▶ [TTS 음성 합성] ──▶ 소리
              ▲                                                    
        [VAD + 턴 감지] "지금 말이 끝났다"를 판단
```

부품 세 개를 이어 붙입니다. 각 부품을 독립적으로 고를 수 있습니다.

### 음성 직통형 (Speech-to-Speech, Realtime)

```text
 소리 ──▶ [하나의 거대한 음성 모델] ──▶ 소리
```

소리를 받아 곧바로 소리를 내는 모델 하나를 씁니다(예: OpenAI Realtime 계열, Gemini Live 계열).

### 이 프로젝트가 단계 연결형을 고른 이유

[2-tech-stack.md 3장](../2-tech-stack.md#3-구조-선택-단계-연결형-vs-음성-직통형)에 비교표가 있습니다. 핵심 이유는 **통제력**입니다.

1. **제품명을 정확히 듣고 말해야 합니다.** "F2 울트라", "메탈팹", "엑스툴"은 일반 모델이 모르는 단어입니다. 단계 연결형이면
   - STT에 단어 목록을 주어 잘 알아듣게 하고(`context.terms`, 6장),
   - STT가 그래도 틀린 것을 코드로 고치고(`correctTranscript`, 6장),
   - TTS 앞에서 발음을 바꿔 줄 수 있습니다(`pronunciationTransform`, 10장).
   중간에 **글**이 있기 때문에 가능한 일입니다. 음성 직통형에는 이 틈이 없습니다.
2. **기록과 감사가 쉽습니다.** 각 단계에 글이 남아 대화록 저장, 금지어 검사가 쉽습니다.
3. **부품을 바꿔 끼울 수 있습니다.** 한국어에 강한 국내 STT(리턴제로)나 TTS(Typecast)로 바꿀 수 있습니다.

대가는 **지연과 자연스러움**입니다. 부품을 차례로 거치니 시간이 더해지고, 말 끝 판단과 끼어들기를 직접 다듬어야 합니다. 이 책의 상당 부분이 이 대가를 줄이는 기법입니다.

### 지연은 어디서 오나: 구성식에 PoC 숫자 넣기 (2026-11-05 추가)

"고객이 말을 멈춘 순간부터 AI 목소리가 들리기까지"를 칸으로 나누면 두 설계가 이렇게 다릅니다.

```text
단계 연결형:  VAD 무음 + STT 확정 + 말 끝 판단 + LLM 첫 토큰 + TTS 첫 음성 + 네트워크·재생
음성 직통형:  (서버 쪽) 말 끝 판단                + 모델 첫 오디오             + 네트워크·재생
```

이 프로젝트의 PoC 값을 넣으면 다음과 같습니다. 측정 환경은 맥(서울) → 해외 API, 브라우저·디버거 음성 경로입니다([5-poc-results.md](../5-poc-results.md)).

| 칸 | 값 | 확인 수준 | 근거 |
| --- | --- | --- | --- |
| VAD 무음 | **0.256초** (32ms 창 8개) | 코드 | `inference/vad.ts`의 `minSilenceDuration: 250`(42행)과 창 512샘플(134행), 5-4절 |
| STT 확정 | 따로 재지 않음. 말 끝 판단 안에 들어 있음. 약 0.1~0.4초로 추정 | 추정 | 아래 설명 |
| 말 끝 판단 | **0.38~0.54초** (VAD 무음·STT 확정 포함) | 실측 | poc-results "Soniox 말 끝 판단 줄이기", finalize 패치 뒤 10턴 |
| LLM 첫 토큰 | **약 0.8초** (텍스트로 0.77~0.92초) | 실측 | poc-results "답 길이 줄이기와 LLM 비교" |
| TTS 첫 음성 | **약 0.17초** | 실측 | poc-results 첫 측정 |
| 네트워크·재생 | 따로 재지 않음 (목표 0.05~0.1초) | — | [2-tech-stack.md 8장](../2-tech-stack.md#8-응답-지연-예산) |
| **합계 (본 답 첫소리)** | **약 1.4초** | 실측 구간의 합 | poc-results "지금 한 턴 지연" |

읽을 때 두 가지를 조심합니다.

- **앞의 세 칸은 더하면 안 됩니다.** 세 일이 겹쳐서 일어나기 때문입니다. SDK의 말 끝 판단 메트릭은 "고객이 말을 멈춘 시각"부터 재므로, VAD가 무음을 기다린 0.256초와 Soniox가 확정 글을 돌려주기까지의 시간이 이미 들어 있습니다(13-3절). 위 STT 확정 0.1~0.4초는 거꾸로 뺀 값입니다. 확정 요청(finalize)은 VAD가 말 멈춤을 알린 뒤에 나가므로, 말 끝 판단(두 측정을 합친 범위 0.38~0.64초)에서 0.256초를 빼면 0.12~0.38초가 남습니다. 턴 감지 모델의 답을 기다린 시간도 섞여 있을 수 있어 **상한에 가까운 추정**입니다.
- **LLM 첫 토큰은 측정 경로마다 다르게 찍힙니다.** 텍스트로 잰 0.77~0.92초가 위 합계에 쓰인 값입니다. 음성 경로에서는 0.99~1.69초가 찍힌 적이 있는데, 선제 생성이면 턴 확정 전부터 재기 때문에 실제보다 길게 보일 수 있습니다(13-3절).

음성 직통형은 STT 확정과 TTS 칸이 없으니 훨씬 빠를 것 같지만, 조사 자료의 값은 약 0.8~1.5초로 단계 연결형(약 0.8~1.4초)과 비슷합니다([2-tech-stack.md 3장](../2-tech-stack.md#3-구조-선택-단계-연결형-vs-음성-직통형)). 이 레포에서 잰 값은 아닙니다. 구성식으로 보면 이유를 짐작할 수 있습니다(추정).

- **말 끝 판단은 똑같이 필요합니다.** 누가 판단하든 "고객이 정말 다 말했나"를 기다리는 몫은 남습니다.
- **모델 첫 오디오는 LLM 첫 토큰과 같은 성격입니다.** 큰 모델이 입력을 다 읽고(프리필, 8-3절) 첫 출력을 내기까지의 시간입니다. 우리 측정에서 가장 큰 칸(약 0.8초)이 바로 이 몫이었습니다.
- 줄어드는 것은 STT 확정(약 0.1~0.4초)과 TTS 첫 음성(약 0.17초) 정도입니다. 단계 연결형은 이 차이를 선제 생성(미리 하기)과 즉시 반응(기다림 숨기기)으로 메웁니다(1-6절, 13-4절).

## 1-5. 전체 시스템 그림

이 레포는 그림의 **[에이전트 워커]** 부분입니다. 나머지는 originalshq 레포(functions-xtool)와 외부 서비스가 맡습니다([2-tech-stack.md 6장](../2-tech-stack.md#6-전체-아키텍처)).

```text
[웹사이트 상담 신청 폼]
   │
   ▼
functions-xtool (originalshq, Cloud Functions)
   │  ① 신청 저장 → Monday 등록 → 발신 조건 검사(동의, 시간대, 수신 거부…)
   │  ② Firestore calls/{id} 생성
   │  ③ LiveKit API: 방 만들기 + 에이전트 "xtool-sales-agent" 배정(고객 정보 = job metadata)
   │                 + SIP 참가자 생성(고객 번호로 발신)
   ▼
[LiveKit Cloud]  ── 방(Room) ──────────────────────────────┐
   ▲                 │                                       │
   │ SIP          고객 참가자                            에이전트 참가자
[Asterisk]──국내 회선──고객 휴대폰                              │
                                                    [에이전트 워커] ← 이 레포
                                                      ├ VAD · 턴 감지 · 끼어들기
                                                      ├ STT(Soniox) → 보정 → LLM(Haiku) → 발음 변환 → TTS(ElevenLabs)
                                                      └ (예정) 통화 중 도구 → functions-xtool API
   ▼
[통화 후] functions-xtool: 요약·판정 추출 → Firestore → Monday 갱신 → 상담사 알림
```

**두 레포의 계약**은 두 가지뿐입니다.

1. **job metadata(JSON)**: 통화를 시작할 때 functions-xtool이 고객 정보를 실어 보냅니다. 형식은 [src/call-context.ts](../../src/call-context.ts)의 zod 스키마가 정의합니다(4장, 15장).
2. **functions-xtool API(공유 비밀키)**: 통화 중 도구(예약 조회 등)와 결과 저장에 쓸 예정입니다. 아직 없습니다.

### 지금 실제로 도는 경로: 웹 테스트 (2026-11-03 추가)

위 그림의 전화 부분은 아직 준비 중입니다. 대신 **관리 화면에서 브라우저로 통화하는 경로**가 먼저 생겼습니다([6-web-test.md](../6-web-test.md)).

- **소리가 가장 큰 짐입니다.** 고객 소리 하나가 워커 안에서 갈라져 Soniox(④)와 턴 감지(⑦, dev일 때)로 각각 압축 없이 나갑니다. 방에서 받을 때(②, Opus 수 KB/s로 추정)보다 공급사로 내보낼 때(32KB/s씩)가 훨씬 큽니다.
- **같은 WebSocket이라도 싣는 방식이 다릅니다.** Soniox는 오디오를 이진 프레임 그대로, ElevenLabs는 JSON 안의 base64 글자로 보냅니다. base64는 3바이트를 4글자로 바꾸므로 같은 소리가 4/3배 커지고, 받은 뒤 다시 풀어야 합니다.
- **LLM은 턴마다 요청을 새로 보냅니다.** STT·TTS처럼 한 연결 위에서 대화가 이어지는 것이 아니라, 턴마다 HTTP 요청 하나에 지시문과 대화 기록 전체를 다시 싣습니다. 대화가 길어질수록 요청이 커집니다. 프롬프트 캐시(8-4절)는 서버의 계산을 아낄 뿐 보내는 바이트를 줄이지 않습니다. 밑의 TCP·TLS 연결은 쉬는 시간이 짧으면 다시 쓰고, 4초 넘게 쉬면 새로 맺습니다(8-8절, 17-2 #28).
- **LiveKit 자체 연결은 대부분 protobuf, 공급사와 우리 API는 JSON입니다.** 워커 제어(①), 방 시그널링(②), 턴 감지 `/eot`(⑦)는 스키마가 정해진 protobuf를 쓰고, Soniox·Anthropic·ElevenLabs·functions-xtool은 JSON을 씁니다. 예외는 소리입니다. JSON에는 이진 데이터를 그대로 넣을 수 없어 base64로 바꾸거나(⑥), 소리만 이진 프레임으로 따로 보냅니다(④, ⑦ `/bargein`).

#### 깊이 보기: 초당 양을 손으로 계산하기 (2026-11-05 추가)

압축하지 않은 소리(PCM)의 양은 곱셈 하나로 나옵니다(2장).

```text
PCM 초당 바이트 = 샘플레이트 × 샘플당 바이트 × 채널 수

  16kHz, 16비트(2B), 모노  = 16,000 × 2 × 1 = 32,000 B/s = 256 kbps   ← Soniox(④), 턴 감지(⑦), VAD
  24kHz                    = 24,000 × 2     = 48,000 B/s = 384 kbps   ← 워커 안의 방 오디오(②를 푼 것)
  22.05kHz                 = 22,050 × 2     = 44,100 B/s              ← ElevenLabs pcm_22050(⑥)
  (참고) 전화 G.711 8kHz, 8비트             =  8,000 B/s =  64 kbps   ← SIP 단계(3장)

base64 글자 수 = ⌈바이트 ÷ 3⌉ × 4   (약 4/3배)

  ElevenLabs 소리 1초:   44,100 B → 58,800 글자
  턴 감지 v1-mini 한 번: 1.2초 × 32,000 = 38,400 B → 51,200 글자 (③)
```

통화 하나로 늘려 보면 Soniox로만 시간당 32,000 × 3,600 ≈ 115MB, 통화 상한 8분이면 약 15MB를 올려 보냅니다. 고객이 말하지 않는 동안에도 소리는 계속 갑니다.

STT 쪽과 TTS 쪽은 "초당"의 뜻이 다릅니다. STT로 가는 소리는 고객이 말하는 속도로만 생기므로 **벽시계 1초당** 32,000B입니다. TTS에서 오는 소리는 서버가 합성하는 대로 실시간보다 빨리 몰려 오므로 **소리 1초당** 58,800글자입니다. 짧은 시간에 몇 초 분량이 한꺼번에 도착할 수 있습니다.

실습: `node docs/1-study/lab/01-wire-sizes.mjs`가 위 계산과 아래 리샘플러 측정을 키 없이 보여 줍니다.

#### 깊이 보기: Soniox로 가는 메시지는 320바이트가 아니다 (2026-11-05 추가)

흔히 "10ms 프레임 하나 = 16,000 × 0.01 × 2B = 320B, 초당 100개"로 계산합니다. 소리가 처음부터 16kHz로 들어오는 경로라면 맞습니다. 그런데 이 프로젝트에서는 소리가 이렇게 흐릅니다.

```text
방 → RoomIO: 24kHz 모노로 받음 (voice/room_io/room_io.ts 125, 기본값)
   → 노이즈 제거: 프레임 길이 그대로 (@livekit/plugins-ai-coustics dist/index.js의 process())
   → STT 스트림 pushFrame: 16kHz가 아니므로 AudioResampler(24000 → 16000) (stt/stt.ts 549)
   → 리샘플러가 내보낸 프레임 하나 = WebSocket 메시지 하나 (agents-plugin-soniox/src/stt.ts 325)
```

메시지 크기는 리샘플러가 정합니다. SDK와 같은 기본 설정의 리샘플러에 24kHz 10ms 프레임을 3초 동안 넣어 본 결과입니다(실측, 맥, `@livekit/rtc-node` 1.2.1, 실습 스크립트).

| 입력 | 메시지 크기 | 초당 메시지 | 첫 메시지 |
| --- | --- | --- | --- |
| 16kHz 10ms 프레임 (리샘플 없음, 가정) | 320B | 100개 | 입력 10ms 뒤 |
| **24kHz 10ms → 16kHz (이 프로젝트)** | **1,050~1,052B** (약 33ms 분량) | **약 30개** | 입력 40ms 뒤 |

- 초당 양(약 32,000B)은 같습니다. 메시지가 세 배쯤 크고 그만큼 드물 뿐입니다. 입력 프레임을 20ms로 바꿔도 결과가 같았습니다(작성 때 따로 확인).
- 그래서 방에서 오는 프레임이 정말 10ms인지 몰라도 결론은 같습니다. 프레임 길이는 rtc-node 네이티브 코드가 정해서 이 레포에서는 확인하지 못했습니다(10ms는 **추정**, 2장 "10ms 단위가 흔함").
- 대가는 몇십 ms입니다. 리샘플러가 묶음 하나(최대 약 33ms)와 필터 지연(약 12ms)만큼 소리를 붙잡고 있다가 보내므로, 소리가 Soniox에 닿는 시각도 그만큼 늦어질 수 있습니다. 말 끝 판단(0.38~0.54초)에 비하면 작습니다.
- 순서에도 작은 결과가 있습니다. `flush()`는 리샘플러를 비우지 않고 입력 대기열에 표시만 넣으므로(`stt/stt.ts` 569~577), finalize 요청이 리샘플러에 남은 마지막 수십 ms의 소리보다 **먼저** Soniox에 갑니다. 그 수십 ms는 VAD가 256ms 무음을 확인한 뒤의 무음 구간이라 글이 빠질 일은 드물 것으로 봅니다(**추정**, 통화 중에는 재지 않음). (2026-11-06 추가) 가짜 서버 실측에서는 finalize 순간 리샘플러에 약 17ms가 남아 finalize 뒤로 밀렸고, Soniox 문서도 말 끝 뒤 약 200ms 무음 다음에 finalize하라고 권합니다([6-5절 깊이 보기](06-stt.md#깊이-보기-126초를-식으로-나누기-2026-11-06-추가)).
- 방 입력을 처음부터 16kHz로 받으면 이 묶음이 사라질 수 있지만, 노이즈 제거 모델이 받는 소리도 바뀌므로 따로 따져 봐야 합니다(**확인 필요**).

## 1-6. 한 통화의 일생

시간 순서로 따라가 봅니다. 괄호는 그 내용을 다루는 장입니다.

```text
t=0     functions-xtool이 방을 만들고 에이전트를 배정 (4장)
        └ LiveKit이 대기 중인 워커 하나에 "일(job)"을 보냄
        └ 워커가 자식 프로세스에서 main.ts의 entry()를 실행
t≈0.x   entry(): 설정 읽기 → metadata에서 고객 정보 파싱 → AgentSession 구성
        → session.start(): 방에 접속하고 고객 오디오를 구독 (RoomIO, 4장)
t≈?     고객이 전화를 받음 (SIP 200 OK, 3장)
        session.say(고지)    "안녕하세요, 김민수 고객님. 오리지널스 AI 상담사입니다. …녹음됩니다."
                             ← LLM을 거치지 않는 고정 문장, 끼어들기 막음 (9장, 11장)
        session.say(질문)    "이삼 분 정도 통화 괜찮으실까요?"  ← 끼어들기 허용
─── 여기부터 턴의 반복 ───────────────────────────────────────────────
        고객: "네, 괜찮아요."
          ├ 소리 → 노이즈 제거 → VAD "말 시작" (2장, 5장)
          ├ STT가 글자를 흘려보냄: "네" … "네, 괜찮" … (6장)
          ├ VAD "말 멈춤" → Soniox에 확정 요청(finalize) (6장)
          ├ 턴 감지 모델: "말이 끝났을 확률 높음" → 짧게 기다리고 턴 확정 (7장)
          │   └ 이 사이 LLM을 미리 돌리기 시작 (선제 생성, 11장)
          ├ onUserTurnCompleted: 제품명 오인식 보정 + "네네." 즉시 반응 (11장)
          ├ LLM(Haiku) 스트리밍 응답: "문의 주신 게 에프투 울트라 맞으시죠?" (8장)
          │   └ 첫머리 맞장구 제거 (ack.ts, 12장)
          ├ 발음 변환: F2 → 에프투 (10장)
          ├ TTS가 소리를 흘려보냄 → 방에 발행 → 고객에게 들림 (10장)
          └ 고객이 중간에 "아니요"라고 끊으면: 멈추고 들은 데까지만 기록 (7장, 11장)
─────────────────────────────────────────────────────────────────────
        마무리: "그럼 다음 주 토요일 오후에 방문체험 원하시는 걸로…" (9장)
t=끝    고객이 끊음 → 방 종료 → 워커 프로세스 정리 (4장)
        또는 AI가 끊음: 작별 인사 + end_call 도구, 무응답·최대 8분 안전장치 (4-7절, 5-5절)
        (예정) 통화 후 처리: 요약, 판정 칸 추출, Monday 갱신
```

### 한 턴의 시간 눈금 (2026-11-05 추가)

위 그림의 "턴의 반복" 한 번을 ms 눈금으로 펴 봅니다. 기준점 **t=0은 고객이 말을 멈춘 순간**입니다. 정확히는 VAD가 무음 길이만큼 거꾸로 맞춘 "마지막 말소리 시각"이고(5-5절), SDK의 말 끝 판단 메트릭도 여기서부터 잽니다(13-3절). 오른쪽 괄호는 확인 수준입니다.

```text
고객: "네, 괜찮아요." ▁▁▁▁ (침묵)

t=0 ms        고객이 말을 멈춤 ──────────────────────────────────── 기준점
t≈256         VAD "말 멈춤" (32ms 창 8개) → 'listening' → Soniox에 finalize     [코드]
                └ 같은 창에서 턴 감지 모델에 예측 요청 (아래 표, 5장)            [코드]
t≈300         턴 확정 최소 대기(minDelay 300ms)가 지남. 확정 글은 보통 아직 없음 [코드]
t≈380~640     Soniox 확정 글 도착 → 모델이 "끝남"이면 곧바로 턴 확정          [실측]
                ├ onUserTurnCompleted: 오인식 보정, 즉시 반응 "네네."를 대기열에
                └ LLM 본 답 생성 (선제 생성이 맞았으면 이미 돌고 있음)
t≈580~810     "네네." 첫소리 = 턴 확정 + TTS 첫 음성 0.17초 → 체감 0.6~0.8초   [실측]
                └ 미리 합성 뒤로는 0.17초가 빠져 약 0.4~0.65초로 예상           [추정, 미측정]
t≈1,200~1,450 LLM 첫 토큰 = 턴 확정 + 약 0.8초                               [실측 구간의 합]
t≈1,400       본 답 첫소리 (+ TTS 첫 음성 0.17초)                              [실측 약 1.4초]
```

| 눈금 | 값의 출처 |
| --- | --- |
| 256ms, 300ms | 코드. VAD `minSilenceDuration: 250`과 32ms 창은 `inference/vad.ts` 42·134행, `minDelay: 300`은 `voice/turn_config/endpointing.ts` 52행(턴 감지 모델과 함께일 때의 기본값) |
| 예측 요청 시점 | 코드. 턴 감지 예측은 무음이 200ms를 넘으면 요청합니다(`inference/eot/base.ts`의 `MIN_SILENCE_DURATION_MS`, `voice/audio_recognition.ts`의 `INFERENCE_DONE` 처리). 그런데 VAD는 이번 창의 무음을 **더하기 전** 값을 싣습니다(`inference/vad.ts` 346·391행). 그래서 200을 처음 넘는 값(224ms)은 여덟 번째 창에서 나오고, 그 창이 곧 "말 멈춤"(256ms)을 내는 창입니다. 기본값에서는 예측이 말 멈춤보다 앞서지 않습니다 |
| 380~640ms | 실측. finalize 패치 뒤 10턴 0.38~0.54초, 즉시 반응 측정 때 0.41~0.64초([5-poc-results.md](../5-poc-results.md) "Soniox 말 끝 판단 줄이기", "즉시 반응") |
| 0.6~0.8초, 본 답 약 1.4초 | 실측. poc-results "즉시 반응" 표(2026-11-03). 즉시 반응을 **미리 합성하기 전**의 값입니다 |
| 미리 합성 뒤 0.4~0.65초 | 추정. 말 끝 판단 0.41~0.64초에 재생 시작까지의 작은 지연을 더한 값입니다. 13-5절도 "실측은 아직 없다"고 적었습니다 |

눈금에서 읽을 것은 세 가지입니다.

- **0.256초까지는 고정 비용입니다.** VAD 설정이 정한 값이고 매 턴 같습니다.
- **그 뒤 확정 글이 올 때까지가 가장 흔들리는 칸입니다.** 확신이 있는 턴이면 말 끝 판단 ≈ max(0.3초, 확정 글 도착)이라서(7-4절), 확정 글이 늦으면 판단도 그만큼 늦습니다. finalize 패치 전에는 이 칸 때문에 말 끝 판단이 1초를 넘기곤 했습니다(0.57~1.42초, 6-5절).
- **첫소리(0.6~0.8초)와 내용(1.4초) 사이 약 0.6~0.8초가 LLM 첫 토큰의 몫입니다.** 즉시 반응은 이 몫을 숨길 뿐 줄이지 않습니다. 본 답은 "네네."가 끝난 뒤에야 재생될 수 있습니다(11-6절, 13-4절).

브라우저 PoC의 값입니다. 전화 단계에서는 지터 버퍼와 코덱 변환이 더해지고, 고객 휴대폰까지의 네트워크·재생 칸(위 그림에 없음)도 따로 재야 합니다(13-7절).

## 1-8. 이 프로젝트를 관통하는 설계 원칙 다섯 가지

코드를 읽다 보면 같은 판단이 여러 번 반복됩니다. 미리 이름을 붙여 두면 읽기 쉽습니다.

### 원칙 1. 확실해야 하는 것은 코드로, 유연해야 하는 것은 LLM으로

- AI·녹음 고지는 **법적으로 반드시 정확해야** 하므로 LLM을 거치지 않는 고정 문장입니다(`openingNotice`).
- 제품명 오인식 보정은 프롬프트로 시켰더니 LLM이 틀린 이름을 따라 말해서(3/3회) **코드로** 옮겼습니다([5-poc-results.md](../5-poc-results.md)).
- 첫머리 맞장구도 프롬프트로 금지하고, **그래도 나오는 것을 코드로** 뗍니다(`withoutLeadingAck`).

LLM은 확률적입니다. "대부분 지킴"으로 충분하지 않은 규칙은 코드가 맡습니다.

### 원칙 2. 지연은 가장 큰 구간부터 줄인다

PoC 측정에서 병목이 STT 확정 → LLM 첫 토큰 순으로 옮겨 갔고, 그때마다 그 구간을 고쳤습니다(13장). 추측이 아니라 **측정한 뒤** 고칩니다.

### 원칙 3. 기다리는 시간은 숨긴다

빨리 할 수 없는 일은 **미리 시작하거나**(선제 생성), **기다리는 동안 무언가를 들려줍니다**(즉시 반응 "네네"). 실제 지연과 체감 지연은 다릅니다.

### 원칙 4. 외부 부품은 감싸서 쓴다

플러그인이 필요한 옵션을 지원하지 않으면, 상속으로 감싸거나(`VoiceAnthropicLLM`, `FinalizingSonioxSTT`) 마지막 수단으로 패치합니다. 그리고 그 사실을 문서에 남겨 업그레이드 때 다시 확인하게 합니다.

### 원칙 5. 실패해도 안전한 쪽으로

고객 정보 JSON이 깨지면 가상 고객("김민수")이 아니라 **빈 정보("고객님")**로 진행합니다. 실제 고객에게 엉뚱한 이름을 부르는 것보다 이름을 안 부르는 편이 안전하기 때문입니다([src/call-context.ts](../../src/call-context.ts)).
