```text
[고객이 말함]  "네 맞아요. 가죽 지갑에 각인하려고요."
   │ RoomIO가 방의 소리를 세션에 넘김 → VAD·턴 감지·STT (5~7장)        11-1, 11-3
   │ ★ STT가 PREFLIGHT를 내면 그 글로 LLM을 미리 돌려 둠 (선제 생성)    11-4
   ▼
[턴 확정]  세션이 "고객 말이 끝났다"고 정함                              11-3
   │ 대기 중이거나 재생 중인 발화를 중단
   │ 훅 onUserTurnCompleted: 오인식 보정, 즉시 반응 "네네."를 줄에 넣음   11-5, 11-6
   │ 미리 돌린 LLM 결과를 써도 되는지 검사 → 재사용, 아니면 새로 요청     11-4
   ▼
[발화 대기열]  [즉시 반응 "네네."] → [본 답]   한 번에 하나씩 재생 허가    11-2
   │ 즉시 반응: 미리 합성해 둔 소리를 바로 재생                          11-6
   │ 본 답: llmNode(첫머리 맞장구 떼기) → TTS → 방                       11-7
   ▼
[남는 것]  대화 기록(ChatContext)에 고객 말과 본 답이 쌓임                 11-8
           상태 변화와 구간별 지연을 이벤트로 알림                         11-9
```

11-1절은 세션을 이루는 세 층(AgentSession, AgentActivity, Agent)과 우리 코드가 끼는 자리를, 11-2절은 말할 것을 한 줄로 세우는 발화 대기열을 봅니다. 11-3절이 한 턴의 전체 타임라인이고, 11-4절(선제 생성), 11-5절(훅), 11-6절(즉시 반응), 11-7절(llmNode)이 그 타임라인의 별표 부분을 하나씩 엽니다. 11-8절은 대화 기록, 11-9절은 이벤트, 11-10절은 한 장 요약입니다. `#### 깊이 보기`는 SDK 코드 행과 실습 숫자를 따라가는 하위 절이라 처음 읽을 때는 건너뛰어도 흐름이 끊기지 않습니다. 숫자와 주장 옆의 표시는 2장과 같습니다. **코드**는 SDK 코드를 읽어 확인한 것, **실측**은 이 맥(Apple M1 Pro)에서 실습으로 잰 것, **추정**과 **확인 필요**는 아직 확인하지 못한 것입니다. 실행 방식에 따라 달라지는 기본값도 앞 장들과 같습니다. 개발 모드(`lk agent dev`)와 LiveKit Cloud 배포는 클라우드 턴 감지 `v1`과 적응형 끼어들기가, 직접 운영 `start`는 로컬 `v1-mini`(한국어 기준값 0.4)와 VAD 방식 끼어들기가 기본입니다(4-5절, 7장).

## 11-1. 세 개의 층: Session, Activity, Agent

(2026-11-08 추가) 이 절은 세션이 어떤 객체들로 이루어지는지 봅니다. **AgentSession**은 통화 하나를 지휘하는 객체입니다([src/main.ts](../../src/main.ts) 42행의 `new voice.AgentSession({ … })`). **Agent**는 "어떤 상담원인가"를 적은 정의로, 지시문·LLM·도구·훅·노드를 묶습니다([src/agent.ts](../../src/agent.ts)의 `Agent.create`). **AgentActivity**는 세션이 그 Agent를 실제로 돌리려고 만드는 실행기입니다. 이 구분을 알아야 하는 까닭은, 우리가 짠 코드(훅과 노드)는 Agent에 붙지만 그 코드를 언제 부를지는 AgentActivity가 정하기 때문입니다. 이 장에서 "몇 행에서 무엇을 한다"고 짚는 SDK 코드는 거의 모두 AgentActivity(`voice/agent_activity.ts`)입니다.

```text
AgentSession          통화 하나에 하나. 입출력(RoomIO), 부품(STT·TTS·VAD·턴 감지), 이벤트, 대화 기록 전체
  └─ AgentActivity    "지금 활성화된 에이전트"의 실행 상태. 발화 대기열, 턴 처리, 끼어들기
       └─ Agent       지시문, LLM, 도구, 훅(onUserTurnCompleted, llmNode…)  ← 우리가 정의하는 부분
```

(2026-11-08 추가) 그림 읽는 법입니다. `└─`로 들여 쓴 줄은 바로 윗줄 객체 안에 들어 있다는 뜻입니다. 세션 하나에 그때 활성인 AgentActivity가 하나, AgentActivity 하나에 Agent가 하나입니다. 오른쪽 글은 그 층이 맡는 일이고, `←`는 이 레포가 직접 정의하는 층을 가리킵니다. 맨 위 줄의 RoomIO는 방의 고객 소리를 세션 입력으로, 세션이 만든 소리·자막을 방으로 잇는 부품입니다. `session.start({ room })`이 만듭니다([src/main.ts](../../src/main.ts) 130∼141행, 4장).

이 프로젝트에는 에이전트가 하나뿐이지만, 핸드오프(9장)를 쓰면 Activity가 바뀌면서 Agent가 교체됩니다. 세션(통화)과 대화 기록은 그대로 이어집니다. LLM을 세션이 아니라 에이전트에 준 이유가 이것입니다(4장).

## 11-2. 발화 대기열과 SpeechHandle

(2026-11-08 추가) **발화 대기열**(speech queue)은 에이전트가 말할 차례를 기다리는 발화들의 줄입니다. 고객에게 나가는 오디오 출력은 하나뿐이라, 두 말을 동시에 내보내면 겹쳐 들립니다. 그래서 세션은 말할 것을 모두 한 줄에 세우고 하나씩 내보냅니다. 이 레포에서는 첫 멘트 두 문장, 턴마다의 즉시 반응과 본 답, 고객이 조용할 때의 "여보세요?", 작별 인사가 모두 이 줄을 지납니다. 즉시 반응이 늘 본 답보다 먼저 나가는 것도 이 줄의 규칙 덕분입니다(11-6절).

에이전트가 "말할 것"은 모두 **SpeechHandle**이라는 객체로 표현되어 하나의 대기열에 들어갑니다.

| 말의 출처 | 만드는 곳 | 이 레포의 예 |
| --- | --- | --- |
| 고정 문장 | `session.say(text)` | 첫 멘트 두 문장([src/main.ts](../../src/main.ts) 158∼159행), 즉시 반응([src/agent.ts](../../src/agent.ts) 49행), "여보세요?"([src/call-guard.ts](../../src/call-guard.ts) 36행), 작별 인사(main.ts 152행) |
| LLM 답 | 턴 확정 후 세션이 자동으로 `generateReply` | 턴마다의 본 답 |
| 직접 요청한 LLM 답 | `session.generateReply({ instructions })` | 쓰지 않음 |

### 대기열 규칙

- 우선순위: LOW 0, NORMAL 5, HIGH 10. `say()`와 `generateReply()`는 모두 **NORMAL**입니다.
- **우선순위가 높은 순, 같으면 먼저 들어온 순**입니다. 이 레포의 발화는 모두 NORMAL이라, 결국 대기열에 들어온 순서대로 나갑니다.
- 메인 루프(mainTask)는 **한 번에 하나씩**만 재생을 허가합니다. 앞 발화의 재생이 끝나야 다음 발화가 허가를 받습니다.

### SpeechHandle이 들고 있는 것

| 속성 | 의미 |
| --- | --- |
| `allowInterruptions` | 고객이 끊을 수 있나. 지정하지 않으면 세션 설정(`interruption.enabled`, 기본 true)을 따름 |
| `addToChatCtx` (`say` 옵션) | 다 말한 뒤 대화 기록에 assistant 메시지로 남길까 (기본 true) |
| 재생 허가 / 완료 / 중단 상태 | `await handle`로 끝날 때까지 기다릴 수 있음 |
| `interrupt(force?)` | 코드로 중단. 끼어들 수 없는 발화는 `force` 없이 부르면 예외 |

### 첫 멘트 두 개는 이렇게 흘러간다

```ts
session.say(openingNotice(call), { allowInterruptions: false });  // ① 고지
session.say(OPENING_QUESTION, { allowInterruptions: true });      // ② 질문
```

```text
① 고지: 대기열에 들어감 → 바로 재생 허가 → 이때 TTS 시작 → 재생
② 질문: 대기열에서 대기 ……………………………………………………→ ① 재생 끝 → 재생 허가 → 이때 TTS 시작 → 재생
                                                               └── 이 사이에 TTS 첫 음성만큼 공백
```

(2026-11-08 추가) 그림 읽는 법입니다. 두 줄은 발화 하나씩이고, 왼쪽에서 오른쪽으로 시간이 흐릅니다. `……→`는 대기열에서 차례를 기다리는 구간, `└──`는 바로 위 줄에서 "재생 허가"와 "재생" 사이의 구간을 가리킵니다. ①의 "바로 재생 허가"는 앞에 재생 중인 발화가 없어서 대기열에 들어가자마자 허가가 난다는 뜻입니다.

`say()`의 TTS는 **재생 허가를 받은 뒤에야** 시작합니다(`voice/agent_activity.ts`의 `ttsTask`). 그래서 고지와 질문 사이에 ElevenLabs 첫 음성 시간(약 0.17초 + 연결 상태에 따라 더)만큼 틈이 생깁니다. 두 문장을 굳이 나눈 것은 끼어들기를 따로 제어하기 위해서였고(7-6절), 이 짧은 틈은 그 대가입니다. 자연스러운 숨 정도로 들리면 괜찮고, 어색하면 측정 후 조정합니다.

또 질문(②)은 끼어들 수 있는 발화라서, 재생 전에 **고객이 조용해질 때까지(userSilenceEvent)** 기다립니다. 고객이 고지 직후 말하고 있으면, 질문은 차례가 와도 고객이 멈출 때까지 TTS를 시작하지 않습니다.

(2026-11-06 갱신) 더 정확히는 **재생 허가와 "고객 조용함"을 함께** 기다리고, 둘 다 된 뒤에야 TTS를 시작합니다(`agent_activity.ts` 3601∼3605). "조용함"은 VAD의 마지막 말소리 창 뒤 192ms에 켜집니다([7-5절](07-turn-taking.md#다시-말하기-전에-고객이-조용한지-본다-2026-11-06-추가)). 그래서 고객이 고지 위에 말하고 있었다면 질문의 첫 소리는 "고지 끝"이 아니라 "고객 말 끝 + 192ms + TTS 첫 음성"입니다(아래 깊이 보기의 실습 2-2). 끼어들 수 없는 고지는 조용함을 기다리지 않습니다.

#### 깊이 보기: 힙, mainTask 루프, SpeechHandle의 상태 (2026-11-06 추가)

직접 돌려 보기: [lab/11-speech-queue.mjs](lab/11-speech-queue.mjs) (약 11초). `scheduleSpeech`와 `mainTask`는 SDK 코드 그대로이고, 발화마다 도는 작업(`ttsTask`, `pipelineReplyTask`)은 부품이 너무 많아 **기다리는 순서만 SDK와 같게 옮긴 짧은 함수**로 대신했습니다. TTS 첫 음성은 13장의 0.17초, 재생 길이는 짧게 줄인 가정 값입니다.

**① 대기열은 힙입니다 (코드).** **힙**(heap)은 "지금 가장 앞인 원소"를 늘 맨 위에 두는 이진 트리이고, 배열 하나로 구현합니다. 넣기와 꺼내기가 원소 n개에 대해 O(log n)이라, 전부 정렬해 두는 것보다 쌉니다. SDK는 `heap-js` 라이브러리의 힙에 `[우선순위, 시각, SpeechHandle]` 세 칸짜리 항목을 넣습니다(`agent_activity.ts` 548·656∼658).

```ts
// 비교 함수: 음수면 a가 앞. 우선순위가 다르면 큰 쪽이, 같으면 시각이 이른 쪽이 앞
([p1, t1], [p2, t2]) => (p1 === p2 ? t1 - t2 : p2 - p1)
// scheduleSpeech (5444~5468): 넣고, "대기열에 들어감" 표시, 루프 깨우기
this.speechQueue.push([priority, Number(process.hrtime.bigint()), speechHandle]);
speechHandle._markScheduled();
this.wakeupMainTask();
```

시각을 `Date.now()`가 아니라 `process.hrtime.bigint()`로 찍는 이유는 둘입니다. `Date.now()`는 ms 단위라 같은 ms에 두 발화가 들어오면 순서를 가를 수 없고, 벽시계라서 시간 동기화(NTP)로 뒤로 갈 수도 있습니다. hrtime은 나노초 단위의 **단조 시계**(monotonic clock, 컴퓨터가 켜진 뒤 늘기만 하는 시계)입니다. 코드 주석도 "Monotonic time to avoid near 0 collisions"라고 적습니다. `Number`로 바꾸면 2^53ns(약 104.2일)까지는 나노초가 정확합니다.

```text
1) scheduleSpeech가 힙에 넣는 [우선순위, hrtime]과 꺼내는 순서
     고지 say()               우선순위  5  hrtime +0ns
     질문 say()               우선순위  5  hrtime +81667ns
     (가정) LOW 안내          우선순위  0  hrtime +120834ns
     (가정) HIGH 긴급 안내    우선순위 10  hrtime +128750ns
     즉시 반응 say()          우선순위  5  hrtime +135584ns
   꺼내는 순서: (가정) HIGH 긴급 안내 → 고지 say() → 질문 say() → 즉시 반응 say() → (가정) LOW 안내
```

**② mainTask 루프 (코드, `agent_activity.ts` 2919∼2988).**

```text
반복:
  깨우기 신호(q_updated)를 기다림                       ← scheduleSpeech, 발화 작업 끝이 깨움
  대기열이 빌 때까지:
    h = 힙에서 꺼냄
    재생 허가가 잠시 멈춤(_authorizationPaused)이면 → 다시 넣고 멈춤
    h가 이미 중단됐거나 끝났으면 → 허가 없이 건너뜀 (2949~2952)
    _currentSpeech = h; h._authorizeGeneration()        ← 재생 허가
    (h의 이번 생성이 끝남) 또는 (h가 중단됨)을 기다림
    중단됐는데 작업이 남아 있으면 → 그 생성이 끝날 때까지 더 기다림 (2959~2961)
    _currentSpeech = undefined
```

- **재생 허가**(authorization)는 루프가 발화에게 "이제 네 차례, 소리를 내보내도 된다"고 알리는 신호입니다. 코드로는 `_authorizeGeneration()`이 **Future**(나중에 값이 채워지는 약속 객체. 보통의 Promise와 달리 `resolve()`를 바깥에서 부를 수 있음, `utils.ts`) 하나를 "생성(generation)" 목록에 넣고, **Event**(asyncio의 Event를 흉내 낸 켜고 끄는 신호. `set()`·`clear()`·`wait()`)를 켭니다(`speech_handle.ts` 557∼563). 발화 작업은 그 Event를 기다렸다가 출력을 시작하고, 끝나면 그 Future를 채웁니다. 도구 호출 뒤의 답처럼 한 발화가 여러 단계로 말하면 생성이 하나씩 늘어납니다.
- 루프는 **허가 하나 → 그 생성의 끝**을 기다리므로, 소리가 겹쳐 나가는 일이 없습니다. 오디오 출력이 하나이기 때문입니다.
- 끊긴 발화라도 정리 작업이 남아 있으면 그것이 끝날 때까지 다음 허가를 미룹니다. 정리 중의 출력(버퍼 비우기, 대화 기록 넣기)도 한 줄로 세우려는 것입니다.

**③ say()와 LLM 답은 TTS를 시작하는 때가 다릅니다 (코드).**

| | 기다리는 것 | TTS 시작 | 근거 |
| --- | --- | --- | --- |
| `say(text)` | 재생 허가 + (끼어들 수 있으면) 조용함 | **둘 다 된 뒤** | `ttsTask` 3601∼3605 → 그 뒤 `performTTSInference` |
| `say(text, { audio })` | 같음 | 없음 (받은 소리를 바로 내보냄) | 3691∼3701 |
| LLM 답 (`generateReply`) | 대기열에 들어감 → (TTS 시작) → 재생 허가 + 조용함 | **대기열에 들어가자마자**, 첫 글이 오는 대로 | `pipelineReplyTask` 4023·4042∼4049·4053∼4057 |

LLM은 그보다 앞서, 답을 만드는 순간(선제 생성이면 턴 확정 전) 시작합니다. 실습 2번이 이 차이를 시각으로 보여 줍니다(실측, 실행마다 몇 ms 다름).

```text
2-1. 첫 멘트 두 개: 고지(끼어들 수 없음, 800ms) → 질문(끼어들 수 있음, 그때 합성)
     0ms  고지: 재생 허가 → 이제 TTS 시작
   172ms  고지: 첫 소리
   974ms  고지: 재생 끝
   974ms  질문: 재생 허가 → 이제 TTS 시작
  1146ms  질문: 첫 소리                          ← 고지 끝과 질문 사이 172ms 틈

2-2. 같은 첫 멘트, 고객이 고지 위에 말하다가 1,100ms에 멈춤 (조용함은 그 192ms 뒤)
   973ms  고지: 재생 끝
  1296ms  고객 조용함 (userSilenceEvent 켜짐)
  1296ms  질문: 재생 허가 → 이제 TTS 시작        ← 허가는 973ms에 났지만 조용함을 같이 기다림
  1469ms  질문: 첫 소리

2-3. 턴 확정 뒤: 즉시 반응(미리 합성, 400ms) → 본 답(선제 생성 재사용이라 글이 이미 있음)
     2ms  본 답: 대기열에 들어감 → TTS 시작(첫 글이 오는 대로)
     2ms  즉시 반응: 재생 허가 (미리 합성한 소리, TTS 없음)
     2ms  즉시 반응: 첫 소리
   172ms  본 답: TTS 첫 음성 준비됨                ← 즉시 반응이 나가는 동안 미리 합성
   402ms  즉시 반응: 재생 끝
   402ms  본 답: 재생 허가
   402ms  본 답: 첫 소리                          ← 틈 없음

2-4. (비교) 본 답을 say()처럼 허가 뒤에 합성했다면
   403ms  본 답(가정): 재생 허가 → 이제 TTS 시작
   573ms  본 답(가정): 첫 소리                    ← 170ms 틈
```

- 2-1의 172ms가 위 "첫 멘트 두 개" 그림의 틈입니다.
- 2-3과 2-4의 차이(402 대 573ms)가 11-6절의 "비대칭"입니다. 본 답은 대기열에 들어가자마자 합성하므로 즉시 반응 뒤에 바로 이어지고, `say()`였다면 즉시 반응이 끝난 뒤에야 합성을 시작해 그만큼 틈이 생깁니다. 즉시 반응 자신도 `say()`라서 같은 문제를 겪으므로 **미리 합성해 `audio`로 넘깁니다**(2-3의 2ms 첫 소리, 13-5절 `AckAudioCache`).

**④ SpeechHandle의 상태 (코드 + 실측).**

```text
               scheduleSpeech            mainTask의 재생 허가          작업이 모두 끝남
  만듦 ──────────────────────▶ 대기열 ──────────────────────▶ 재생 중 ────────────────────▶ 끝(done)
   │  (scheduled=false)        (scheduled)                  (허가)
   │                              │                            │
   │ interrupt()                  │ interrupt()                │ interrupt()
   ▼                              ▼                            ▼
  중단(interrupted) ───── 작업이 신호를 보고 정리하고 끝냄 ─────▶ 끝(done)
                          5초 안에 안 끝나면 감시 타이머가 작업을 취소하고 끝으로 침
```

(2026-11-08 추가) 그림 읽는 법입니다. 가로줄의 이름(만듦, 대기열, 재생 중, 끝)이 SpeechHandle의 상태이고, `──▶` 위의 글은 그 상태로 넘어가게 하는 일, 이름 아래 괄호는 그 상태에서의 표시 값입니다. 어느 상태에서든 `interrupt()`를 부르면 아래 줄의 "중단"으로 내려가고, 발화 작업이 정리를 마치면 "끝"이 됩니다. 아래 실습 출력의 3번이 각 상태의 표시 값을 그대로 찍은 것입니다.

## 11-3. 한 턴의 전체 타임라인

(2026-11-08 추가) 이 절의 **한 턴**은 고객이 말을 시작해서 에이전트의 답이 끝날 때까지입니다. 5∼10장이 부품별로 본 일을, 여기서는 세션 쪽에서 시간 순서로 이어 붙입니다. 이 타임라인을 알아야 지연 숫자(13장)가 어느 구간의 것인지, 이 레포의 코드(훅과 `llmNode`)가 어디서 끼는지 짚을 수 있습니다.

고객이 "네 맞아요. 가죽 지갑에 각인하려고요."라고 말했을 때를 처음부터 끝까지 따라갑니다.

```text
[듣기]
 고객 소리 → RoomIO(24kHz) → 노이즈 제거 → ┬→ VAD (16kHz)
                                            ├→ 턴 감지 모델 (16kHz)
                                            ├→ (적응형 끼어들기 채널)
                                            └→ STT (Soniox, 16kHz)
 VAD START_OF_SPEECH → 사용자 'speaking'
 STT: INTERIM "네 맞아" … PREFLIGHT "네 맞아요." → ★선제 생성 시작 (11-4절)
 VAD END_OF_SPEECH(+256ms) → 'listening' → finalize, 턴 감지 예측 요청
     (말 끝 판정 시도 → 아직 FINAL 글이 없어 건너뜀)
 FINAL "네 맞아요. 가죽 지갑에 각인하려고요." → 글이 마지막 PREFLIGHT와 다르면 ★선제 생성 다시 시작
     → 말 끝 판정 시작 (이 프로젝트에서는 FINAL이 판정을 시작함, 7-4절)
 턴 감지: p ≥ 0.4 → 300ms 대기(대개 이미 지남) → 턴 확정
         p < 0.4 → 마지막 말소리 + 2,500ms까지 대기 (이 문장 끝은 실습에서 0.38~0.45로 기준 근처)

[턴 확정 처리: userTurnCompletedImpl]
 ① 선제 생성 재시도 횟수 초기화
 ② 지금 재생 중인 발화가 끼어들 수 없으면 → 경고 후 이 턴을 버림 (7-6절)
 ③ 대기 중인 발화들 중단, 재생 중인 발화 중단
 ④ 사용자 메시지(newMessage) 생성
 ⑤ ★ onUserTurnCompleted 훅 실행 (await) ← 이 프로젝트: 보정 + 즉시 반응 "네네."
 ⑥ 선제 생성 결과를 쓸 수 있는지 검사 → 쓰면 재사용, 아니면 새로 generateReply
 ⑦ 말 끝 판단 메트릭(EOUMetrics) 발행

[답하기]
 LLM 응답 발화가 대기열에 들어감 → 에이전트 상태 'thinking'
 대기열: [즉시 반응 "네네."] [LLM 답]  ← 같은 NORMAL, 먼저 들어온 즉시 반응이 앞
 즉시 반응: 재생 허가 → (미리 합성했으면 바로, 아니면 TTS 시작) → 재생 → 'speaking' → 끝 → 'listening'
 LLM 답:    (즉시 반응이 재생되는 동안 이미 LLM 생성 + TTS 합성 진행)
           재생 허가와 "고객 조용함"을 함께 기다림 → 재생 → 'speaking'
           llmNode(withoutLeadingAck) → ttsTextTransforms → TTS → 오디오 → 방
 재생 끝 → 대화 기록에 assistant 메시지 (끊겼으면 들은 데까지)
```

(2026-11-08 추가) 그림 읽는 법입니다. `[듣기]`·`[턴 확정 처리]`·`[답하기]`는 단계 이름이고, 위에서 아래로 시간 순서입니다. `→`는 다음 일로 이어짐, `┬`·`├`·`└`는 같은 소리가 여러 부품으로 나뉘어 들어감(괄호는 그 부품이 받는 샘플레이트), ★는 턴 확정 전에 미리 시작하는 일, ①∼⑦은 턴 확정 처리 함수(`userTurnCompletedImpl`, `agent_activity.ts` 3327∼3556)가 하는 차례입니다. 몇 군데는 실행 방식에 따라 다릅니다.

- `(적응형 끼어들기 채널)`은 개발 모드와 LiveKit Cloud 배포에서만 켜집니다(직접 운영 `start`는 기본 꺼짐). 켜져 있으면 AI가 말하는 동안 겹친 고객 말의 STT 글은, 맞장구인지 끼어들기인지 판정이 날 때까지 transcript gate에 붙잡혀 세션으로 넘어가지 않습니다(7-5절).
- `p ≥ 0.4`의 0.4는 로컬 `v1-mini`의 한국어 기준값입니다. 클라우드 `v1`(개발 모드·Cloud 배포)은 연결 때 서버가 알려 주는 기준값을 씁니다(7-4절).
- ②의 "이 턴을 버림"은 그 고객 말로 답을 만들지 않고 대화 기록에도 넣지 않는다는 뜻입니다. 경고 로그 `skipping user input, current speech generation cannot be interrupted`만 남습니다(`agent_activity.ts` 3368∼3378). 이 레포에서는 끼어들 수 없는 AI·녹음 고지가 재생되는 중에 턴이 확정되면 그렇습니다(7-6절).

(2026-11-06 갱신) 처음 판은 "p ≥ 0.4 → 턴 확정"만 그렸습니다. 이 문장 끝 "…각인하려고요."는 7장 실습(합성 음성 `say -v Yuna`)에서 p가 0.38∼0.45로 기준 0.4를 사이에 두고 갈렸습니다. 같은 소리라도 통화마다 300ms 대기와 2,500ms 대기로 나뉠 수 있다는 뜻입니다([7-4절 깊이 보기 "쉼 동안의 확률을 직접 그려 보기"](07-turn-taking.md#깊이-보기-쉼-동안의-확률을-직접-그려-보기-2026-11-06-추가)). 아래 ms 표는 확신하는 경우(p ≥ 0.4)입니다. 또 "재생 허가 → 고객이 조용한지 확인"이라고 차례로 그렸던 줄은, 실제로는 둘을 함께 기다립니다(11-2절 깊이 보기 ③).

## 11-4. 선제 생성 (Preemptive Generation)

(2026-11-08 추가) **선제 생성**(preemptive generation)은 턴이 확정되기 전에, 그때까지 STT가 확정한 글로 LLM 요청을 미리 보내 두는 기법입니다. 이 레포는 [src/main.ts](../../src/main.ts) 67행의 `preemptiveGeneration: { enabled: true }`로 켰습니다. 한 턴의 지연에서 가장 큰 칸이 LLM 첫 토큰(약 0.8초)이라(13장), 그 시작을 수백 ms 일찍 당기면 고객이 기다리는 시간이 그만큼 바로 줄어듭니다. 이 절에서 **시도**는 선제 생성이 한 번 만든 SpeechHandle(곧 LLM 요청 하나), **트리거**는 시도를 부르는 STT 사건, **재사용**은 턴 확정 때 그 시도를 본 답으로 쓰는 것, **버림**은 시도를 취소해 그 결과를 쓰지 않는 것입니다.

### 아이디어

7-1절에서 사람은 상대 말이 끝나기 전에 대답을 준비한다고 했습니다. 선제 생성은 그것을 흉내 냅니다. **턴이 확정되기 전에, 지금까지 STT가 확정한 글로 LLM을 미리 돌려 둡니다.** 턴이 확정되었을 때 고객 글이 그대로라면, 이미 만들어 둔 답을 바로 씁니다.

```text
선제 생성 없음:   [말 끝 판단 300ms+]──▶[LLM 첫 토큰 0.8초]──▶[TTS]
선제 생성 있음:   [말 끝 판단 300ms+]
                  [LLM 미리 시작 ─────────▶]──▶[TTS]      ← 겹친 만큼 이득
```

(2026-11-08 추가) 그림 읽는 법입니다. 가로가 시간이고 대괄호 하나가 한 구간입니다. 위 줄은 말 끝 판단이 끝난 뒤에야 LLM을 시작합니다. 아래 두 줄은 LLM이 말 끝 판단과 같은 시간에 겹쳐 돌아, 겹친 길이만큼 TTS가 일찍 시작한다는 뜻입니다.

컴퓨터 구조의 **투기적 실행**(speculative execution)과 같은 생각입니다. CPU가 분기 결과를 기다리지 않고 예측한 쪽을 먼저 실행해 두었다가, 예측이 틀리면 결과를 버리는 것과 같습니다.

### 언제 시작하나

- Soniox가 **PREFLIGHT**(지금까지 들은 글이 모두 STT 확정이고 미확정 글이 없다는 사건, 6장)를 보낼 때마다
- **FINAL**이 왔는데 내용이 PREFLIGHT와 다를 때

시작 조건: 기능이 켜져 있고, **지금 재생 중인 발화가 없고**, 이번 턴 시도 횟수가 `maxRetries`(기본 3) 미만이고, 고객이 말을 시작한 지 `maxSpeechDuration`(기본 10초) 이내일 때입니다. 긴 독백은 끝까지 바뀔 가능성이 크니 건너뜁니다.

(2026-11-06 갱신) 이전 선제 생성은 새 시도를 만들기 **전에**, 새 시도를 만들 수 있든 없든 취소합니다. 처음 판은 "새로 시작할 때마다 취소"라고 적어, 횟수를 다 쓴 뒤에도 마지막 결과가 남는 것처럼 읽혔습니다. 코드로 확인한 정확한 규칙은 이렇습니다.

- **PREFLIGHT는 글을 비교하지 않고 올 때마다** 선제 생성을 부릅니다(`audio_recognition.ts` 1418∼1435). **FINAL은** 지금까지의 턴 글(`audioTranscript`)이 마지막 PREFLIGHT 글과 **문자열로 다를 때만** 부릅니다(1349·1360∼1373). 여기서는 `transcriptsEquivalent`가 아니라 `!==`로 비교합니다.
- 부름을 받은 쪽(`onPreemptiveGeneration`, `agent_activity.ts` 2445∼2508)은 **① 문 → ② 앞 시도 취소 → ③ 길이 → ④ 횟수 → ⑤ 새 시도** 순서로 갑니다. ①을 통과하면 **새 시도를 만들든 못 만들든 앞 시도부터 취소**하므로, 횟수를 다 쓴 뒤의 트리거는 마지막 남은 결과까지 지웁니다(아래 깊이 보기).
- ①의 "재생 중인 발화"는 `_currentSpeech`가 있고 **중단되지 않은** 것입니다. 끼어들기로 **일시정지된** 발화(7-5절)도 중단이 아니라서 여기에 걸립니다. ①에 걸리면 앞 시도도 그대로 둡니다.
- 횟수(`_preemptiveGenerationCount`)는 턴이 확정될 때만 0으로 돌아갑니다(3336). 말 시작 시각(`speechStartTime`)도 턴 단위라, 쉼을 두고 길게 이어 말하는 턴은 횟수와 10초를 함께 씁니다.

### 무엇을 미리 하나

- **LLM은 끝까지 미리 생성합니다.** 출력 버퍼에 쌓아 둡니다.
- **TTS는 기본적으로 미리 하지 않습니다**(`preemptiveTts: false`). 버려질 수 있는 합성에 비용을 쓰지 않기 위해서입니다. 켜면 더 빠르지만 낭비가 생깁니다.
- **도구 실행은 하지 않습니다.** 도구는 재생 허가 이후에 실행되므로, 버려질 예측이 예약을 잡거나 수신 거부를 등록하는 일은 없습니다. 투기적 실행에서 **부수 효과가 있는 일은 확정 후로 미루는** 원칙 그대로입니다.

(2026-11-06 추가) 코드 위치입니다. LLM 출력은 `IdentityTransform`(기준 크기를 `Number.MAX_SAFE_INTEGER`로 둔 사실상 무제한 큐, `stream/identity_transform.ts` 6∼18)에 쌓이므로 아무도 읽지 않아도 생성이 멈추지 않습니다(역압이 걸리지 않는 이유는 12장). 시도의 작업은 `_waitForScheduled()`에서 멈춰 있다가(`agent_activity.ts` 4023), 재사용되어 대기열에 들어가야 TTS(4042∼4049), 재생 허가(4053∼4057), 도구 실행(4243)으로 갑니다. 대기열에 안 들어간 시도는 상태를 `thinking`으로 바꾸지도 않습니다(4051).

### 쓸지 버릴지 검사

턴 확정 후(⑥) 다음 네 가지가 모두 같아야 재사용합니다. (2026-11-06 갱신: 고객 글 칸을 고침, 나머지 칸에 방식을 더함) 표의 "비교"는 선제 시도를 만들 때 찍어 둔 값과 턴 확정 때의 값을 맞대 보는 항목이고, "방식"은 SDK가 둘을 "같다"고 보는 기준입니다. 하나라도 다르면 시도를 버리고 새로 요청합니다(`agent_activity.ts` 3493∼3528).

| 비교 | 방식 |
| --- | --- |
| 고객 글 | 선제 시도의 글과 **훅이 고친 뒤**의 사용자 메시지 글(`rawTextContent`)을 `transcriptsEquivalent`로 비교. 구두점·대소문자·**공백 개수**는 무시. 태국 문자·가나·한자만 한 글자씩 비교하고, **한글은 그 범위에 없어 공백으로 자른 덩어리끼리** 비교 → 띄어쓰기 위치가 다르면 다른 글("방문 체험" ≠ "방문체험") |

| 도구 목록 | `ToolContext.equals`: 같은 도구들인가 |

처음 판의 "한중일 문자는 글자 단위 비교"는 틀렸습니다. 정규식(`agent_activity.ts` 210∼228)에 한글 음절 범위(U+AC00∼D7A3)가 없어서, 한국어는 영어처럼 공백 단위로 비교됩니다. 함수 해부와 실습은 [6-8절 깊이 보기](06-stt.md#깊이-보기-선제-생성-재사용-검사가-한국어를-비교하는-법-2026-11-06-추가)와 [lab/06-transcripts-equivalent.mjs](lab/06-transcripts-equivalent.mjs)에 있습니다. 결론만 옮기면, 이 프로젝트에서 재사용을 깨는 것은 **글을 바꾸는 코드 보정**이고, 공백 정리("방문 체험" → "방문체험")도 한국어에서는 글을 바꾸는 보정입니다.

### 이 프로젝트에서 주의할 점

1. **오인식 보정이 일어난 턴은 선제 결과를 버립니다.** 훅(⑤)에서 "메탈 백"을 "메탈팹"으로 고치면 고객 글이 달라져 재사용 검사에 실패하고 LLM을 처음부터 다시 부릅니다(6-8절). 보정을 `sttNode`로 옮기면 해결됩니다. (2026-11-06 추가) 대소문자만 바꾸는 보정("p3" → "P3")은 비교에서 무시되므로 재사용됩니다(아래 깊이 보기 E).
2. **시도 횟수가 빨리 소진될 수 있습니다.** PREFLIGHT는 글이 같은지 보지 않고 올 때마다 재시작하며 횟수를 셉니다. finalize로 FINAL도 늘어납니다. 한 턴에 3회를 먼저 다 써 버리면 최종 글로는 선제 생성을 못 합니다. 로그의 "starting preemptive generation" 횟수로 확인할 수 있습니다. (2026-11-06 갱신) 더 나쁜 점이 있습니다. 앞 시도 취소가 횟수 검사보다 **먼저**이므로, 3회를 다 쓴 뒤 4번째 트리거(대개 글이 바뀐 FINAL)가 오면 **3번째 시도의 결과까지 취소되고 새 시도는 생기지 않습니다.** 턴이 확정될 때 쓸 것이 하나도 없어, 선제 생성을 끈 것과 같은 시각에 LLM을 새로 부르면서 요청은 네 번 나갑니다(깊이 보기 B). 3이 아니라 4번째 트리거부터 손해라는 뜻입니다.
3. **즉시 반응이 재생 중이면 선제 생성을 하지 않습니다.** 고객이 연달아 말하는 경우에 해당합니다. (2026-11-06 갱신) 즉시 반응만이 아니라 **중단되지 않은 발화가 재생 중이면 모두**입니다. 고객이 본 답을 끊은 턴은 그 답이 "일시정지"(중단 아님) 상태라 PREFLIGHT가 와도 아무것도 하지 않고, 그 PREFLIGHT 글은 기록되므로 같은 글의 FINAL도 트리거가 되지 않습니다(깊이 보기 G). 끼어든 턴은 선제 생성의 이득을 거의 보지 못한다고 봐야 합니다(코드에서 따라간 추론). (2026-11-08 추가) 일시정지는 FINAL이 올 때 끝납니다. `onFinalTranscript` 끝의 `cancelSpeechPause()`가 그 발화를 바로 중단으로 바꿉니다(`agent_activity.ts` 2421·6075∼6117). 그래서 이렇게 끊긴 턴은 확정될 때 이미 중단된 발화만 남아, 11-3절 ③의 info 로그 `speech interrupted, new user turn detected`가 나오지 않습니다(3368∼3393). 운영 로그에서 끼어든 턴을 이 줄로 세면 일시정지를 거쳐 끊긴 턴을 놓칩니다. 순서는 깊이 보기 G의 읽을 점에 있습니다.
4. **LLM 첫 토큰 메트릭이 달라 보입니다.** `LLMMetrics.ttftMs`는 LLM 스트림을 만든 시점부터 잽니다. 선제 생성이면 턴 확정 **전부터** 잰 값이고, 취소된 시도도 `cancelled: true`로 메트릭이 나옵니다. 통화 결과의 지연 기록은 이 값을 일부러 남깁니다(13-5절). (2026-11-06 추가) 취소된 시도의 요청은 끊기지 않고 **서버가 답을 끝까지 만듭니다**(깊이 보기 H). 시도 하나가 보통 턴 하나만큼의 비용입니다.

읽을 점입니다.

- **이득은 "마지막 PREFLIGHT = FINAL"일 때만 납니다(A).** FINAL 글이 다르면 FINAL이 새 시도를 띄우는데, 확정이 FINAL과 거의 같은 순간이라 리드 타임이 0입니다(C). 그런데도 로그는 `using preemptive generation`이라 "재사용"으로 보입니다. 효과는 이 줄의 `preemptiveLeadTime`으로 봐야 합니다.
- **같은 글의 PREFLIGHT가 되풀이되면 소진이 빨라집니다(B).** Soniox 플러그인은 메시지마다 "확정 글이 있고 미확정 글이 없으면" PREFLIGHT를 냅니다. **새 토큰이 하나도 없는 메시지에도** 그렇습니다(`agents-plugin-soniox/src/_internal.ts` 315∼339, 코드). 여기서 토큰은 Soniox가 보내는 글 조각(STT 토큰, 6장)으로, LLM 토큰과는 이름만 같습니다. 그래서 고객이 말을 멈춘 뒤 Soniox가 토큰 없는 진행 메시지를 보내면, 같은 글로 시도가 다시 시작되고 횟수가 줄어듭니다. 서버가 실제로 그런 메시지를 보내는지는 서버 동작이라 **확인하지 않았습니다**(확인 필요). 디버그 로그 `received user preflight transcript`가 한 턴에 같은 글로 여러 번 찍히는지 보면 압니다.
- **취소는 맨 앞에 있습니다(B·F).** 횟수나 10초에 걸려 새 시도를 못 만들어도, 그 직전에 앞 시도를 지웁니다. B의 4번째 트리거, F의 10초 뒤 PREFLIGHT가 그렇습니다. Python SDK와 같은 순서인지는 확인하지 않았습니다.
- **대소문자만 고치면 재사용되지만, 요청과 기록의 글이 갈립니다(E).** 재사용 때 SDK는 시도가 들고 있던 메시지 객체의 내용을 훅이 고친 글로 바꿔 끼우고(`agent_activity.ts` 3504∼3511), 대화 기록에는 그 객체가 들어갑니다(4028∼4031). 그래서 LLM이 본 글은 "p3", 기록은 "P3"입니다. 다음 턴 요청의 앞부분이 이번 요청과 그 칸에서 바이트가 달라지므로, 8장의 캐시 규칙대로라면 다음 턴은 이번 요청이 쓴 캐시 항목을 못 읽고 한 턴 앞의 항목까지만 읽어 약 한 턴 몫(어림 100토큰)을 더 씁니다(문서 규칙에서 끌어낸 추론, 실측 아님. [8-4절 깊이 보기](08-llm.md#깊이-보기-캐시-항목은-어디에-생기고-어떻게-찾나-2026-11-06-추가)).
- **10초는 턴의 첫 말소리부터입니다(F).** 쉼을 두고 이어 말해도 `speechStartTime`은 그대로라, 긴 턴의 뒷부분은 선제 생성을 못 합니다.
- (2026-11-08 추가) **G의 일시정지는 FINAL에서 중단으로 바뀝니다(코드).** 고객 말이 겹치면 세션은 발화를 바로 버리지 않고 일시정지합니다. VAD 방식이든 적응형 판정이든 같은 `interruptByAudioActivity()`를 거치고(`agent_activity.ts` 2228∼, 적응형은 `onOverlapSpeech` 2326∼2341), 이 레포의 방 출력은 일시정지를 지원하므로(`room_io/_output.ts` 593, `resumeFalseInterruption` 기본 true) 그렇습니다. 그 뒤 FINAL이 오면 `onFinalTranscript`(2381∼2422)가 끝에서 `cancelSpeechPause()`를 부르고, 이 함수는 일시정지된 발화에 `interrupt(false, 'user_turn')`을 부릅니다(6075∼6117). 턴이 확정되어 `userTurnCompletedImpl`이 "지금 재생 중이고 중단되지 않은 발화"(`activeSpeech`, 3368∼3371)를 찾을 때는 이미 중단된 뒤라 비어 있고, 그래서 `speech interrupted, new user turn detected`(3388∼3391)를 찍는 분기를 타지 않습니다. 운영에서 끼어든 턴을 세려면 대화 기록의 assistant 메시지에 붙는 `interrupted: true`를 세는 편이 확실합니다(7-5절 "끊긴 뒤에 일어나는 일").
- (2026-11-08 추가) **FINAL 글이 마지막 PREFLIGHT와 달라도, 문 ①은 대개 여전히 막힙니다(코드에서 따라간 추론, 재현하지 않음).** FINAL의 선제 생성 부름은 같은 처리 안에서 `onFinalTranscript` 바로 뒤에 동기적으로 옵니다(`audio_recognition.ts` 1333·1360∼1373). 그런데 `cancelSpeechPause()`는 앞서 만든 작업(`cancelSpeechPauseTask`)이 남아 있으면 그것부터 `await`하고 나서 중단을 부릅니다(6079∼6085). 이 작업 칸은 FINAL마다 채워지고 활동이 닫힐 때(5725∼5726)만 비워지므로, 통화에서 첫 FINAL 뒤로는 중단이 한 박자 늦게 일어나고, 그 사이에 온 선제 생성 부름은 아직 일시정지(중단 아님)인 발화를 보고 돌아갑니다.

**취소된 시도의 요청은 끝까지 갑니다 (H, 실측).** 같은 실습 끝에서, 이 프로젝트의 LLM 클래스([src/models/anthropic.ts](../../src/models/anthropic.ts))를 127.0.0.1의 가짜 Anthropic 서버에 붙이고, 첫 글 조각을 받자마자 `LLMStream.close()`를 불렀습니다. 선제 시도를 버릴 때 SDK가 결국 닿는 곳입니다(`voice/agent.ts` 570∼589의 cleanup).

```text

     170ms  LLMMetrics 나옴: cancelled true, ttftMs 113
```

워커 쪽은 170ms에 "취소됨" 지표를 내고 끝난 것처럼 보이지만, HTTP 응답은 서버가 끝까지 써서 정상 종료됐습니다. 플러그인이 `messages.create`에 취소 신호(`signal`)를 넘기지 않고(`agents-plugin-anthropic/src/llm.ts` 358∼360), `close()`(`llm/llm.ts` 504∼506)가 거는 중단(abort)의 처리는 출력 쪽만 닫기 때문입니다(같은 파일 221∼225). 취소가 어디까지 전해지는지의 사슬은 [12장](12-streams-async.md)에서 봅니다. 실제 API도 같다면, 버린 시도도 **완료된 요청 하나로** 과금됩니다(입력·캐시 쓰기·출력 전부. 추정).

**손 계산: 시도 하나의 값.** 8장 손 계산의 가정(직전 요청 R ≈ 3,530토큰을 캐시에서 읽고, assistant 한 번 + 고객 말 한 번 ≈ 100토큰을 쓰고, 답 70토큰)을 쓰면 시도 하나는 다음과 같습니다([8-4절 깊이 보기 "턴별 읽기·쓰기와 비용 손 계산"](08-llm.md#깊이-보기-턴별-읽기쓰기와-비용-손-계산-2026-11-06-추가)).

## 11-5. onUserTurnCompleted 훅

(2026-11-08 추가) **훅**(hook)은 SDK가 정해진 순간에 불러 주도록 우리가 넘겨 두는 함수입니다. `onUserTurnCompleted`는 턴이 확정된 직후, 답을 만들기 전에 불립니다(11-3절 ⑤). 이 레포의 훅은 세 가지를 차례로 합니다. STT가 잘못 적은 제품명을 고치고(`correctTranscript`), 즉시 반응을 해도 되는 말인지 보고(`shouldAck`, 11-6절), 해도 되면 즉시 반응을 대기열에 넣습니다(`say`). 답을 만드는 일은 훅이 아니라, 훅이 끝난 뒤 세션이 합니다. 아래 코드는 지금의 [src/agent.ts](../../src/agent.ts) 39∼54행에서 주석만 뺀 것입니다. 처음 판의 조각은 `shouldAck`와 미리 합성한 소리(`audio`)를 넣기 전(2026-11-03 전)의 모양이었습니다.

```ts
// src/agent.ts
onUserTurnCompleted: (ctx, _chatCtx, newMessage) => {
  newMessage.content = newMessage.content.map((part) =>
    typeof part === 'string' ? correctTranscript(part) : part,
  );
  if (!shouldAck(newMessage.textContent ?? '')) return;
  const ack = ACKS[turn++ % ACKS.length]!;
  const audio = ackAudio?.audio(ack);
  ctx.agent.session.say(ack, {
    ...(audio ? { audio } : {}),
    addToChatCtx: false,
    allowInterruptions: true,
  });
},
```

### 훅이 받는 세 인자

| 인자 | 무엇 | 바꾸면 |
| --- | --- | --- |
| `ctx` | 에이전트·세션 접근 (`Agent.create` 방식의 첫 인자) | 해당 없음. 고칠 값이 아니라 에이전트와 세션에 닿는 손잡이입니다(이 레포는 `ctx.agent.session.say`에 씀) |
| `chatCtx` (`_chatCtx`) | 이번 사용자 메시지 **직전까지**의 대화 기록 복사본 | **이번 답 생성에만** 반영, 저장 안 됨. 대신 선제 결과는 무효 |
| `newMessage` | 이번 사용자 메시지 | 고친 내용이 LLM 입력과 **영구 대화 기록**에 들어감. 새로 요청하면 그 객체가 그대로 들어가고, 선제 결과를 재사용하면 SDK가 고친 내용을 선제 시도의 메시지 객체에 옮겨 담아 그 객체가 들어감(11-4절 깊이 보기 E) |

이 프로젝트는 `newMessage`만 고칩니다. 보정된 글이 다음 턴에도 남아야 하기 때문입니다. 반면 "이번 턴에만 참고 자료를 끼워 넣는" RAG 같은 기법은 `chatCtx`에 메시지를 추가합니다. 언더스코어(`_chatCtx`)는 "쓰지 않는 인자"라는 관례 표시입니다.

몇 가지 세부 사항이 있습니다.

- 훅은 `await`됩니다. **훅이 오래 걸리면 그만큼 응답이 늦어집니다**(`onUserTurnCompletedDelayMs` 메트릭). 이 훅은 정규식 몇 개와 `say()` 호출뿐이라 거의 0입니다.
- 훅에서 `throw new voice.StopResponse()`를 던지면 답을 만들지 않습니다(빈 입력 무시 등에 씀).
  - (2026-11-06 추가) `StopResponse`는 SDK가 내보내는 `Error`의 하위 클래스입니다(`voice/stop_response.ts`). 세션이 훅의 예외를 잡아 이 클래스면 "이 턴에는 답하지 않음"으로 처리합니다(`agent_activity.ts` 3432∼3450). 다른 예외는 오류 로그만 남기고 답을 그대로 만듭니다.
  - 이때 `return`이 재사용 검사보다 앞이라, **이미 띄운 선제 시도를 취소하지 않고 남깁니다.** 다음 턴의 첫 트리거가 11-4절 ②에서 지우므로 보통 문제는 없지만 요청 하나는 헛돕니다. 또 사용자 메시지는 답 작업이 대기열에 들어갈 때 기록에 들어가므로(4028∼4031), **그 턴의 고객 말은 대화 기록에 남지 않습니다**(둘 다 코드에서 따라간 추론, 실행해 보지 않음).
- 자막·이벤트(`UserInputTranscribed`)에는 **보정 전 STT 원문**이 남습니다. 대화 기록과 자막이 다를 수 있습니다.

### `turn++ % ACKS.length`와 클로저

```ts
export function createAgent({ call, llm, ackAudio, knowledge }: { … }) {
  let turn = 0;                  // createAgent가 불릴 때 한 번 생김
  return Agent.create({
    onUserTurnCompleted: (…) => { … ACKS[turn++ % ACKS.length]! … },
  });
}
```

`turn`은 `createAgent` 함수 안의 지역 변수인데, 훅 함수가 이를 **붙잡고(클로저)** 있어 통화 내내 값이 유지됩니다. 통화마다 `createAgent`가 새로 불리므로 통화끼리 섞이지 않습니다. `% ACKS.length`로 0, 1, 2, 0, 1, 2…를 돌며 "네네." → "네." → "아, 네."를 번갈아 씁니다. 같은 말이 연달아 나오면 기계처럼 들리기 때문입니다. `shouldAck`가 거짓이라 `return`한 턴은 `turn++`까지 가지 않으므로 순서가 밀리지 않습니다. 예를 들어 "네네."를 쓴 다음 거절 턴이 끼면, 그다음 턴은 "네."입니다.

끝의 `!`는 TypeScript의 "이 값은 undefined가 아니다" 단언입니다. tsconfig의 `noUncheckedIndexedAccess`가 배열 인덱스 접근의 결과를 `string | undefined`로 보기 때문에 필요합니다. 나머지 연산으로 범위 안이 보장되므로 안전한 단언입니다.

## 11-6. 즉시 반응("네네") 기법 해부

(2026-11-08 추가) **즉시 반응**(ack)은 턴이 확정되자마자, LLM의 답을 기다리지 않고 짧은 고정 문장을 먼저 말하는 이 레포의 기법입니다. [src/ack.ts](../../src/ack.ts)의 `ACKS`("네네.", "네.", "아, 네.") 가운데 하나를 훅에서 `say()`로 대기열에 넣고([src/agent.ts](../../src/agent.ts) 44∼53행), 그 소리는 통화 시작 때 미리 합성해 둡니다([src/ack-audio.ts](../../src/ack-audio.ts), [src/main.ts](../../src/main.ts) 34∼41행). 이 절은 왜 그렇게 했는지, 대기열과 에이전트 상태에서 무슨 일이 일어나는지, 그 대가가 무엇인지 차례로 봅니다.

### 왜 필요한가

PoC 측정에서 한 턴의 지연은 약 1.4초였고, 그중 LLM 첫 토큰이 약 0.8초였습니다(13장). 고객이 말을 마치고 1.4초 동안 침묵이 흐르면 "전화가 끊겼나?" 싶습니다. LLM을 당장 더 빠르게 할 수 없다면, **기다리는 동안 무언가를 들려주는** 방법이 있습니다. 사람 상담원도 생각하는 동안 "네네", "아 네"를 먼저 합니다.

### 설계 결정 하나하나

| 결정 | 이유 |
| --- | --- |
| **고정 문장 목록** (`ACKS`) | LLM을 기다리지 않음. 작은 LLM으로 즉석 반응을 만드는 방법(LiveKit 문서의 "fast pre-response")도 있지만, 그것도 첫 토큰을 기다려야 함 |
| 짧고 중립적인 말 ("네네.", "네.", "아, 네.") | 고객이 무슨 말을 했든 어울림. "좋네요"처럼 평가가 들어간 말은 거절·불만 뒤에 어색함 |
| **`addToChatCtx: false`** | ① LLM이 기록에서 이 말투를 보고 따라 하지 않음 ② 대화 기록이 매 턴 같은 구조로 쌓여 **프롬프트 캐시가 유지됨**(8장) |
| `allowInterruptions: true` | 고객이 이어서 말하면 끼어들기 처리(일시정지, FINAL이 오면 중단)를 거쳐 멈춤 |
| 훅에서 `say()` 호출, `await` 안 함 | 대기열에 넣기만 하고 바로 돌아가야 본 답 생성이 늦어지지 않음 |
| 지시문에 "시스템이 '네네'를 먼저 말한다" (9장) | LLM은 기록에 없는 즉시 반응을 모르므로 글로 알려 줌 |
| `llmNode`에서 첫머리 맞장구 제거 | 그래도 LLM이 "네,"로 시작하면 "네네. 네, …"가 되므로 코드로 뗌 (11-7절) |

### 대기열에서 일어나는 일

훅 안의 `say()`는 NORMAL 우선순위로 대기열에 들어가고, 본 답은 **훅이 끝난 뒤** 같은 NORMAL로 들어갑니다. 같은 우선순위면 먼저 들어온 순이므로 **즉시 반응이 반드시 먼저** 재생됩니다. ③단계의 "대기 중 발화 중단"은 훅보다 먼저 일어나므로 즉시 반응을 지우지 않습니다.

```text
시간 →
즉시 반응:  [재생 허가][TTS 첫 음성 ~0.17초][ "네네." 재생 ]
본 답:      [LLM 생성 ────────────][TTS 합성 ──────]  [재생 허가][ 본 답 재생 … ]
                                                    ↑ 즉시 반응이 끝나야 허가
```

(2026-11-08 추가) 그림 읽는 법입니다. 가로가 시간이고 대괄호 하나가 한 구간입니다. 두 줄은 같은 시간에 나란히 흐릅니다. `↑`는 위 줄(즉시 반응)이 끝나는 순간에 아래 줄(본 답)이 재생 허가를 받는다는 표시입니다. 즉시 반응 줄의 `[TTS 첫 음성 ~0.17초]`는 소리를 미리 합성하지 못했을 때만 생기는 구간입니다. 지금은 대개 미리 합성한 소리라 허가 직후 바로 재생합니다(아래 2026-11-03 갱신).

여기서 중요한 비대칭이 있습니다.

- **즉시 반응(`say`)의 TTS는 재생 허가를 받은 뒤에야 시작합니다.** 그래서 "고객 말 끝 → 첫 소리"의 최소 시간은 "턴 확정 + ElevenLabs 첫 음성"입니다. 즉시 반응의 TTFB가 체감 지연의 하한입니다.
- **본 답의 TTS는 대기열에 들어가자마자 합성을 시작합니다.** 즉시 반응이 재생되는 동안 본 답이 미리 준비됩니다.

(2026-11-03 갱신) 첫째 비대칭은 코드에서 해소됐습니다. 즉시 반응 세 문장을 통화 시작 때 미리 합성해 두고 `say(ack, { audio })`로 소리를 직접 넘기므로, 재생 허가가 나면 TTS를 기다리지 않고 바로 재생합니다(13-5절 `AckAudioCache`). 그러면 체감 지연의 하한이 "턴 확정"까지 내려갑니다. 미리 합성이 끝나기 전의 첫 턴이나 합성에 실패한 경우는 이전처럼 그때 합성합니다.

(2026-11-06 추가) 두 비대칭을 시각으로 재현한 것이 11-2절 깊이 보기의 실습 2-3(미리 합성한 즉시 반응 2ms, 본 답 402ms에 틈 없이 이어짐)과 2-4(본 답을 `say()`처럼 합성했다면 573ms)입니다. 아래 표의 "첫소리까지"는 즉시 반응 기준이라 SDK의 `e2eLatency`(본 답 기준)로는 잴 수 없습니다. 재는 법은 11-3절 깊이 보기에 있습니다. 미리 합성한 뒤의 즉시 반응 첫 소리는 아직 실측하지 않았습니다(17-2 #14).

체감 지연이 "말 끝 판단 + LLM 첫 토큰 + TTS"에서 "말 끝 판단 + TTS 첫 음성"으로 줄어드는 구조입니다. 측정 결과도 이 계산과 맞습니다([5-poc-results.md](../5-poc-results.md) "즉시 반응", 2026-11-03).

| | 고객 말이 끝나고 첫소리까지 |
| --- | --- |
| 이전 (본 답만) | 약 1.4∼1.6초 |
| **즉시 반응 적용** | **약 0.6∼0.8초** (말 끝 판단 0.41∼0.64초 + TTS 0.17초) |
| 본 답 시작 | 약 1.4초 (즉시 반응 뒤에 이어짐) |

본 답이 시작되는 시각 자체는 그대로입니다. 줄어든 것은 **침묵의 길이**입니다. 13장의 표현으로는 "숨기기"입니다.

같은 측정에서 지시문의 한계도 다시 확인됐습니다. 지시문에 "답을 '네'로 시작하지 말라"고만 했을 때는 **3번 중 3번** "감사합니다", "아,", "네,"로 시작해 "네네. 네, …"처럼 겹쳤고, `llmNode`에서 코드로 떼고 나서는 **4번 중 4번** 깨끗했습니다(11-7절). 6장의 오인식 보정과 똑같은 패턴입니다. "하지 말라"는 지시가 잘 안 먹히는 버릇은 코드가 맡습니다.

### 에이전트 상태의 흐름

(2026-11-08 갱신) 상태는 이렇게 바뀝니다. 처음 판은 코드에서 따라간 예상이었고, 이번 판에서 실제 SDK 세션으로 재현해 확인했습니다(아래 깊이 보기).

```text
본 답 대기열 진입 → 'thinking' → 즉시 반응 첫 음 → 'speaking' → 즉시 반응 끝 → 'listening'
                 → 본 답 첫 음 → 'speaking' → 끝 → 'listening'
```

즉시 반응과 본 답 사이에 잠깐 `listening`이 끼는 셈입니다. 이 상태로 화면 표시(Agent Console의 상태 표시)나 다른 로직을 만들 때는 이 깜빡임을 고려해야 합니다. 이 `listening` 동안에는 고객 자리비움 타이머(`userAwayTimeout`, 10초)도 돕니다. 본 답이 아주 늦거나 실패하면 이것이 "여보세요?"가 나가는 시각을 바꿉니다(아래 깊이 보기).

(2026-11-06 추가) 왜 `listening`이 끼는지는 **상태 임대**(state lease)로 설명됩니다. 에이전트 상태를 바꿀 권한은 발화마다 하나씩 받는 "임대"(`AgentStateLease`, `agent_activity.ts` 302∼305)이고, 한 번에 하나만 유효합니다(`activeAgentStateLease`). 규칙은 셋입니다(3027∼3089).

| 동작 | 조건 | 결과 |
| --- | --- | --- |
| 쥐기 (`acquire`) | 그 발화가 중단·완료되지 않음 | 이 임대가 유효해지고 상태를 바꿈 (`thinking`이나 `speaking`) |
| 말 시작 (`tryStartAgentSpeech`) | 그 발화가 지금 재생 허가를 받은 발화(`_currentSpeech`)임 | 쥐고 `speaking` |
| 놓기 (`release`) | 이 임대가 지금 유효한 것이고, 기대한 상태(대개 `speaking`)임 | `listening`, 유효한 임대 없음 |

본 답은 대기열에 들어갈 때 `thinking`으로 임대를 쥐지만(4051), 즉시 반응이 첫 소리에서 임대를 가져가고(`speaking`), 끝날 때 놓으면서 `listening`으로 바꿉니다. 본 답은 다시 쥐지 않고 자기 첫 소리에서야 `speaking`을 쥡니다. 그래서 `thinking → speaking → listening → speaking`입니다. 끝난 발화나 다른 활동(핸드오프 전 에이전트)의 늦은 작업이 상태를 덮어쓰지 못하게 하려는 장치입니다. 화면 표시는 `AgentStateChanged`를 그대로 믿기보다 짧은 깜빡임을 걸러 쓰는 편이 안전합니다.

(2026-11-08 갱신) 본 답의 `thinking`이 즉시 반응의 첫 소리보다 늦게 오면 순서가 바뀔 수 있습니다(즉시 반응 재생 중에 `thinking` → 즉시 반응이 끝나도 임대가 남의 것이라 `listening`으로 안 바뀜). 처음 판은 어느 쪽이 먼저인지 실행해 보지 않았다고 적었습니다. 아래 깊이 보기의 재현에서는 열한 번 모두 본 답의 `thinking`이 2∼13ms 먼저였습니다(실측). 본 답은 훅이 끝나자마자 Promise 후속 처리(마이크로태스크, 12-2절) 몇 번 만에 4051행에 닿습니다. 반면 즉시 반응은 mainTask가 깨어나 재생 허가를 주고, 발화 작업이 소리를 출력 사슬에 넣어 첫 `captureFrame`을 지나야 첫 소리가 됩니다(코드에 비춘 해석). 미리 합성이 끝나기 전의 첫 턴처럼 즉시 반응을 그때 합성하면 TTS 첫 음성까지 기다리므로, 본 답이 더 확실히 먼저입니다.

#### 깊이 보기: 본 답을 기다리는 동안 도는 10초 타이머 (2026-11-08 추가)

8-7절 깊이 보기는 "본 답이 실패하면 '여보세요?'가 언제 나가나"를 계산하면서, 즉시 반응이 끝난 뒤의 `listening` 때문에 그 숫자가 달라질 수 있다는 물음을 "확인 필요"로 남겼습니다. 코드와 재현으로 확인한 결과는 **그렇다**입니다. 즉시 반응을 한 턴에서는 즉시 반응이 끝나는 순간부터 10초 타이머가 돕니다. 이 SDK 동작 때문에 생기던 어색한 경우(늦게 성공한 본 답 바로 뒤의 "여보세요?")는 같은 날 이 레포의 `guardCall`에서 고쳤습니다(아래 "고친 방법", 17-2 #56 대응).

**타이머가 도는 조건 (코드).** 고객 자리비움 타이머(`userAwayTimeout`, 이 레포 10초, [src/call-guard.ts](../../src/call-guard.ts)의 `USER_AWAY_TIMEOUT_SEC`)는 고객 상태와 에이전트 상태가 **둘 다** `listening`일 때만 돕니다. 세션은 둘 중 하나가 바뀔 때마다 이 조건을 다시 봅니다.

```ts
// agent_session.ts _updateAgentState (1916~1921). _updateUserState (1962~1967)도 같은 모양
if (state === 'listening' && this._userState === 'listening') {
  this._setUserAwayTimer();      // 있던 타이머를 지우고 userAwayTimeout × 1000ms짜리를 새로 겁니다 (2014~2032)
} else {
  this._cancelUserAwayTimer();
}
```

시간이 다 되면 고객 상태가 `away`가 됩니다. 처음 `guardCall`은 그 순간 "여보세요? 제 목소리 잘 들리세요?"를 `say()`로 대기열에 넣었습니다. 지금은 넣기 전에 본 답을 기다리는 중인지 먼저 봅니다([src/call-guard.ts](../../src/call-guard.ts)의 `askIfStillAway`, 37∼60행). 상태를 같은 값으로 다시 바꾸는 호출(`listening` → `listening`)은 아무 일도 하지 않으므로(1875∼1877), 한 번 건 타이머는 상태가 실제로 바뀔 때까지 그대로 셉니다.

**한 턴에서 일어나는 일.** 11-3절 깊이 보기의 시각(마지막 말소리 = 0, ms)으로 따라가면 이렇습니다. 표의 한 줄이 한 순간이고, 가운데 칸은 그 순간의 고객 상태 / 에이전트 상태입니다.

| 시각 | 일 | 고객 / 에이전트 상태 | 타이머 |
| --- | --- | --- | --- |
| +256 | VAD 말 끝 | `listening` / `listening` | 걸림 |
| +406 | 본 답이 대기열에 들어가며 임대를 쥠 (4051) | `listening` / `thinking` | 지워짐 |
| +406 직후 | 즉시 반응 첫 소리가 임대를 가져감 (3648) | `listening` / `speaking` | 없음 |
| 약 +906 | 즉시 반응 끝, 임대를 놓음 (3767) | `listening` / `listening` | **다시 걸림** |
| 약 +1,120 | 본 답 첫 소리 (4073) | `listening` / `speaking` | 지워짐 |

평소에는 본 답이 즉시 반응 뒤 수백 ms 안에 소리를 내므로 아무 일도 없습니다. 본 답이 약 10초 넘게 소리를 내지 못할 때만 드러납니다. 본 답이 실패해도 상태는 그대로입니다. 실패한 본 답의 작업이 끝날 때 `onPipelineReplyDone`이 임대를 놓으려 하지만(3275∼3287), 유효한 임대가 없어(즉시 반응이 이미 놓음) 아무것도 하지 않습니다. 그래서 타이머는 즉시 반응이 끝난 때부터 그대로 셉니다.

**재현 (실측).** 실제 SDK의 `AgentSession`·`AgentActivity`에 이 레포의 `createAgent`(훅과 `llmNode`), `AckAudioCache`, `guardCall`을 얹었습니다. 아래 재현 1은 고치기 전 `guardCall`으로 돌린 것입니다. 바꾼 것은 넷입니다. 방 대신 가짜 오디오 출력(방 출력처럼 첫 `captureFrame`에서 재생 시작을 알리고, 밀어 넣은 소리 길이만큼 지나면 재생 끝을 알림)을 운영과 같은 자막 동기화 출력(`SyncedAudioOutput`) 뒤에 붙였고, TTS는 첫 글이 오고 170ms 뒤에 소리를 내는 가짜, LLM은 정해진 시간 뒤 실패하거나 늦게 답하는 가짜로 바꿨고, 턴 확정은 `activity.onEndOfTurn`을 직접 불렀습니다. 즉시 반응은 0.5초짜리를 미리 합성해 두었습니다. 스크립트는 레포에 두지 않았습니다.

(2026-11-08 추가) **고친 방법(17-2 #56 대응).** `guardCall`은 `away`를 받으면 `askIfStillAway`를 부르고, 여기서 세 가지를 확인합니다(5-5절 표). 처음 제안과 달라진 점을 중심으로 적습니다.

```ts
session.on(voice.AgentSessionEventTypes.SpeechCreated, (ev) => {
  if (ev.source === 'say') return;              // 고정 문장(첫 멘트, 즉시 반응, "여보세요?")은 빼고 LLM 답만
  const reply = ev.speechHandle;
  replies.add(reply);
  reply.addDoneCallback(() => {                 // 다 말했거나, 실패했거나, 끊겼을 때
    replies.delete(reply);
    askIfStillAway();
  });
});

session.on(voice.AgentSessionEventTypes.AgentStateChanged, (ev) => {
  if (ev.oldState !== 'speaking') return;
  agentSpokeAt = Date.now();                    // AI가 마지막으로 말을 마친 시각
  askIfStillAway();
});
```

- **기다리는 답은 "끊기지 않았고 끝나지 않은 답"입니다.** 처음 제안은 대기열에 들어갔는지(`scheduled`)를 함께 보자고 했습니다. 선제 시도도 같은 `source: 'generate_reply'`로 오기 때문입니다. 코드를 따라가 보니 버려지는 선제 시도는 `_cancel`로 끊긴 표시(`interrupted`)가 먼저 서고, 끝 표시는 작업이 정리되거나 5초 감시 타이머가 울릴 때 옵니다(`speech_handle.ts` 499∼540). 그래서 `interrupted`를 보면 버려진 시도를 바로 뺄 수 있고, `scheduled`는 볼 필요가 없었습니다.
- **10초는 "답이 끝난 때"가 아니라 "AI가 마지막으로 말을 마친 때"부터 셉니다.** 처음 구현은 답이 끝난 때부터 셌습니다. 그러자 실패한 경우의 "여보세요?"가 5.3초 실패에서 15.9초, 44.1초 실패에서 54.7초로 늦어졌습니다(재현). 실패한 답은 소리를 내지 않았으므로 고객이 들은 마지막 소리는 즉시 반응입니다. 소리 기준으로 세도록 바꾸자 실패한 경우는 고치기 전 시각 그대로이고, 늦게 성공한 경우만 달라졌습니다.
- **말하는 중에는 묻지 않습니다.** 답의 끝 표시와 에이전트 상태 변경 중 어느 쪽이 먼저 오든 같은 결과가 나오도록, 말하는 중이면 미루고 말을 마칠 때 다시 확인합니다.

테스트는 [src/call-guard.test.ts](../../src/call-guard.test.ts)의 "본 답을 기다리는 동안" 묶음 다섯 개입니다. 고치기 전 코드에서 셋이 실패하는 것을 먼저 확인했습니다(나머지 둘은 고치는 중에 깨지지 않게 지키는 테스트). 그 뒤 위 재현을 고친 코드로 다시 돌렸고, 에이전트 디버거(`lk agent debugger`, 텍스트 모드)로 실제 워커에서도 "답이 끝나고 10초 → '여보세요?' → 10초 무응답 → `no_response` 종료"를 확인했습니다.

### 즉시 반응을 하지 않을 때: shouldAck (2026-11-03 추가)

"네네."는 가볍고 긍정적인 소리라, 화난 고객이나 거절하는 고객에게는 거슬립니다. 그래서 코드는 고객 말을 보고 즉시 반응을 건너뜁니다.

```ts
// src/ack.ts
const NO_ACK =
  /(전화|연락)\s*(하지|안\s*하|말)|그만\s*(하|좀)|필요\s*없|짜증|화가|불쾌|기분\s*나|사람(이랑|하고|과|한테)?\s*(통화|연결|바꿔)|상담(사|원)(이랑|하고|과|한테|으로|로)?\s*(통화|연결|바꿔)|AI\s*(말고|싫)/i;

export function shouldAck(userText: string): boolean {
  return !NO_ACK.test(userText);
}

// src/agent.ts의 onUserTurnCompleted
if (!shouldAck(newMessage.textContent ?? '')) return;   // 보정은 이미 끝났으니 반응만 건너뜀
```

| 정규식 묶음 | 잡는 말 |
| --- | --- |
| `(전화\|연락)\s*(하지\|안\s*하\|말)` | "전화하지 마세요", "연락 안 하셨으면", "전화 말고" |
| `그만\s*(하\|좀)`, `필요\s*없` | "그만하세요", "필요 없어요" |
| `짜증\|화가\|불쾌\|기분\s*나` | 불만 표현 |
| `사람…(통화\|연결\|바꿔)`, `상담(사\|원)…(통화\|연결\|바꿔)`, `AI\s*(말고\|싫)` | 사람 상담사 요청 |

몇 가지 볼 점이 있습니다.

- **판단 순서.** 보정(`correctTranscript`)을 먼저 하고 그 결과로 판단합니다. `return`은 즉시 반응만 건너뛰고 LLM 답은 그대로 나갑니다. 훅이 끝나면 세션이 답을 생성하기 때문입니다(11-5절).
- **`.test()`와 `g` 플래그.** 이 정규식은 `.test()`로 반복 호출되는데 `g` 플래그가 없습니다. 12-6절에서 본 `lastIndex` 함정을 피한 올바른 형태입니다. `g`를 붙이면 같은 문장에 번갈아 다른 결과가 나올 수 있습니다.
- **틀렸을 때의 비용이 비대칭.** 거절인데 반응을 하면 거슬리고, 보통 대답인데 반응을 빼면 조금 느리게 느껴질 뿐입니다. 그래서 넓게 잡는 편이 안전합니다. 예를 들어 "전화 말고 문자로 주세요"도 걸려서 반응이 빠지는데, 이 정도 오탐은 감수할 만합니다.
- **테스트가 짝으로** 있습니다(14장). "하지 않는다" 6문장과 "한다" 3문장("전화 상담도 되나요?"처럼 '전화'가 들어가도 거절이 아닌 문장 포함)입니다.
- **판정은 고객 말 전체**를 봅니다. "네, 근데 다시는 전화하지 마세요"처럼 앞이 긍정이어도 거절이 들어 있으면 반응을 뺍니다.

## 11-7. llmNode 재정의: 첫머리 맞장구 떼기

(2026-11-08 추가) 이 절은 Agent의 **노드** 가운데 `llmNode`를 감싸, LLM 답 첫머리의 맞장구("네,", "감사합니다." 등)를 떼는 코드를 봅니다. 즉시 반응이 이미 "네네."를 말했으므로, 본 답이 다시 "네,"로 시작하면 "네네. 네, …"로 겹쳐 들리기 때문입니다(11-6절). 무엇을 맞장구로 보는지는 [src/ack.ts](../../src/ack.ts)의 정규식 `LEADING_ACK`이 정하고, 이 절은 그 처리가 파이프라인의 어디에 끼는지와 그 대가(보류)를 봅니다.

```ts
// src/agent.ts
llmNode: async (ctx, chatCtx, toolCtx, modelSettings) => {
  const stream = await Agent.default.llmNode(ctx.agent, chatCtx, toolCtx, modelSettings);
  return stream ? withoutLeadingAck(stream) : null;
},
```

### 노드란

LiveKit은 파이프라인의 각 단계를 **노드**라는 함수로 열어 둡니다. 기본 구현을 감싸서 앞뒤에 처리를 끼울 수 있습니다.

| 노드 | 입력 → 출력 | 기본 동작 |
| --- | --- | --- |
| `sttNode` | 오디오 프레임 스트림 → STT 이벤트 스트림 | STT 스트림에 연결 |
| `llmNode` | 대화 기록 + 도구 → 글 조각·도구 호출 스트림 | `llm.chat()` 결과를 그대로 전달 |
| `ttsNode` | 글 스트림 → 오디오 프레임 스트림 | TTS에 연결 (스트리밍이 아니면 문장 분할기를 씌움) |
| `transcriptionNode` | 글 스트림 → 자막 글 스트림 | 그대로 통과 |

`Agent.default.llmNode(...)`를 불러 **기본 동작을 먼저 얻고**, 그 결과 스트림을 `withoutLeadingAck`로 감싸 돌려줍니다. 기본 동작을 다시 짜지 않고 **꾸미기**(decorator)만 하는 패턴이라, SDK가 기본 동작을 개선하면 그대로 혜택을 받습니다. LLM이 아무것도 돌려주지 않는 경우(`null`)도 그대로 전달합니다.

### 세 가지 연결 지점의 차이

이 프로젝트는 세 곳에서 글을 고칩니다. 위치에 따라 영향 범위가 다릅니다.

| 위치 | 무엇을 | 영향 범위 |
| --- | --- | --- |
| `onUserTurnCompleted` (`newMessage`) | 고객 글 보정 | LLM 입력 + 대화 기록 |
| `llmNode` (`withoutLeadingAck`) | LLM 답 첫머리 | TTS + **자막 + 대화 기록** (노드 출력이 이후 모든 경로의 원본) |
| `ttsTextTransforms` (`pronunciationTransform`) | 발음 | **TTS 입력만** (단, TTS alignment를 쓰면 기록에도 반영될 수 있음, 10-6절) |

맞장구 제거를 `ttsTextTransforms`가 아니라 `llmNode`에 둔 것은 **대화 기록에서도 지워야** LLM이 다음 턴에 "네,"로 시작하는 버릇을 이어 가지 않기 때문입니다. 발음 변환을 `ttsTextTransforms`에 둔 것은 기록에는 "F2"라는 올바른 표기가 남아야 하기 때문입니다.

`withoutLeadingAck`의 스트림 처리 기법은 12장에서 자세히 봅니다. 여기서는 "첫머리 맞장구를 판단할 수 있을 때까지만 모았다가 내보낸다"는 점만 기억해 두면 됩니다. (2026-11-06 갱신) 처음에는 "처음 12자를 모았다가 판단"했는데, 맞장구 둘이 겹치면 12자로 모자라 같은 날 고쳤습니다(17-2 #43, 12-6절).

(2026-11-06 갱신) 이 보류는 **노드의 첫 출력**을 늦추고, 그 몫은 `LLMMetrics.ttftMs`에는 안 잡히지만 본 답 메시지의 `llmNodeTtft`에는 잡힙니다. 그런데 지금 설정에서는 **TTS가 첫 글을 받는 시각은 늦추지 않습니다.** ElevenLabs 플러그인의 문장 분할기가 어차피 보류보다 훨씬 늦게 첫 덩어리를 내보내기 때문입니다(아래 깊이 보기). 처음 판은 "이 12자만큼 TTS 시작이 늦어진다"고 적었습니다. #43을 고친 뒤로는 보류 자체도 맞장구로 시작하는 답에서 토큰 두세 개, 맞장구가 아닌 답에서 0으로 줄었습니다.

#### 깊이 보기: 맞장구 보류의 값 (2026-11-06 추가)

(2026-11-06 갱신) 이 깊이 보기는 처음에 "처음 12자를 모으는" 방식으로 썼습니다. 같은 날 17-2 #43을 고쳐(커밋 `331c151`) 보류가 "판단할 수 있을 때까지"로 바뀌었으므로, 두 방식을 나란히 둡니다. 실습은 고치기 전 함수를 스크립트 안에 사본으로 두고 함께 잽니다.

**손 계산.** 지금 방식의 보류는 "첫 토큰이 온 뒤, 맞장구를 두 개까지 떼고 남은 글이 비어 있지 않고, 그 글이 맞장구 말의 앞부분일 수 없을 때까지"입니다(12-6절). 옛 방식은 "모은 글이 12자가 될 때까지"였습니다. 한국어는 글자당 약 1토큰(8-1절 추정 0.97)이고, 토큰은 흔히 앞 공백을 달고 옵니다(" 가"). 공백도 한 글자로 세므로 옛 방식의 12자는 토큰 9∼10개입니다. 첫 토큰은 이미 와 있으니 **더 기다리는 것은 (N − 1)개 간격**입니다.

```text
                          지금 방식                         옛 방식(12자)
"네, 가죽 지갑 각인이…"    토큰 3개 "네, 가" → 20ms / 40ms   토큰 9개  → 80ms / 160ms
"가죽 지갑 각인이시군요…"  토큰 1개 "가"     →  0ms /  0ms   토큰 10개 → 90ms / 180ms
                                              (100 tok/s / 50 tok/s, (N − 1) × 간격)
```

- 맞장구로 시작하는 답은 "네"(맞장구 "네"일 수도 "네일"의 앞일 수도 있음) → "네,"(맞장구를 떼면 빈 글) → "네, 가"(남은 "가"는 맞장구 말의 앞부분이 아님)에서 판단이 섭니다.
- 맞장구로 시작하지 않는 답은 첫 토큰에서 바로 나갑니다. "예산"처럼 첫 글자가 맞장구 말("예")과 같으면 둘째 글자에서 나갑니다.
- 가장 오래 모으는 것은 맞장구 둘이 겹친 답입니다. "알겠습니다. 감사합니다. 예산은요?"는 15번째 글자 "예"가 와야 판단합니다(12-7절 실습 4-B). 옛 방식이 12자에서 판단해 맞장구를 못 떼던 바로 그 답입니다. 맞장구는 두 개까지만 떼므로, 보류는 많아야 "맞장구 둘 + 한 글자"입니다.

디코드 속도(초당 토큰)는 8-3절처럼 서버 사정에 따라 흔들립니다. 또 Anthropic의 SSE `text_delta` 하나에는 토큰 여러 개가 들어 올 수 있어, 조각 수로는 이보다 적게 기다릴 수 있습니다(8-6절).

**재는 법 (코드).** 두 지표의 시작점과 끝점이 다릅니다.

| 지표 | 재는 곳 | 시작 → 끝 | 단위 |
| --- | --- | --- | --- |
| `LLMMetrics.ttftMs` | `LLMStream` 안 (`llm/llm.ts` 382·402∼404·424) | LLM 스트림 생성 → 첫 응답 청크. 노드 래퍼(`withoutLeadingAck`)를 거치기 **전** | ms (정수로 버림) |
| `llmNodeTtft` (본 답 메시지의 `metrics`) | `performLLMInference` (`voice/generation.ts` 731·755∼767), 메시지에 붙임(`agent_activity.ts` 4277∼4279) | `llmNode` 호출 직전 → 노드가 낸 첫 비어 있지 않은 글. 래퍼를 거친 **뒤** | 초 |

그래서 `llmNodeTtft × 1000 − ttftMs` ≈ 보류 몫(+ 노드를 준비하는 1ms 미만)입니다. 두 값 모두 같은 시도에서 시작하므로 선제 생성이어도 차이는 그대로 보류 몫입니다.

LiveKit Inference TTS(`TTS_PROVIDER=livekit`) 경로는 확인하지 않았습니다.
- 보류는 TTS 스트림을 여는 시각(첫 글 조각이 올 때 `produceSegments`가 엶, `agent_activity.ts` 3939∼3978)도 늦추지만, ElevenLabs 플러그인은 통화 중 WebSocket 하나를 다시 쓰므로(`tts.ts` 1001∼1018) 연결 비용이 끼지 않습니다(코드. 연결이 닫힌 뒤라면 다를 수 있음).
- 그래서 **`llmNodeTtft − ttftMs`가 0.1∼0.2초로 보여도 그만큼 체감이 늦어진 것은 아니었습니다**(옛 방식). 체감에 실제로 큰 것은 분할기의 "20자 + 다음 문장" 규칙이고, 그것은 TTS 쪽 지표로 봐야 합니다(13장). (2026-11-06 갱신) 고친 뒤로는 이 차이가 맞장구로 시작하는 답에서 토큰 두세 개 간격(수십 ms), 아닌 답에서 거의 0입니다. 보류 길이가 이제 "첫머리 맞장구가 몇 개였나"에 따라 정해지므로, 운영에서 이 차이가 토큰 십여 개 간격만큼 크게 나오면 모델이 맞장구를 두 개 겹쳐 시작했다는 뜻으로 읽을 수 있습니다(코드에 비춘 해석, 재지 않음).

**운영에서 남기기 (제안, 적용하지 않음).** 본 답 메시지가 기록에 들어갈 때 같은 시도의 `ttftMs`와 빼면 됩니다. 메시지는 재생이 끝난 뒤 들어오고, 그 시도의 LLM 지표는 스트림이 끝날 때 나오므로 보통 먼저 와 있습니다.

```ts
let lastTtftMs: number | undefined;
session.on(voice.AgentSessionEventTypes.MetricsCollected, (ev) => {
  if (ev.metrics.type === 'llm_metrics' && !ev.metrics.cancelled) lastTtftMs = ev.metrics.ttftMs;
});
session.on(voice.AgentSessionEventTypes.ConversationItemAdded, ({ item }) => {
  if (item.type !== 'message' || item.role !== 'assistant') return;
  const nodeTtft = item.metrics?.llmNodeTtft; // 초
  if (nodeTtft === undefined || lastTtftMs === undefined) return;
  log().info({ holdMs: Math.round(nodeTtft * 1000 - lastTtftMs) }, '첫머리 맞장구 보류');
});
```

## 11-8. 대화 기록(ChatContext)의 일생

(2026-11-08 추가) **대화 기록**(ChatContext)은 LLM에 매 턴 통째로 보내는 메시지 목록입니다. 지시문(system), 고객 말(user), 에이전트 말(assistant), 도구 호출과 그 결과가 차례로 들어 있습니다. Agent가 자기 기록을 들고 있고(`agent.chatCtx`), 세션은 통화 전체의 기록을 `session.history`로 보여 줍니다. 이 레포는 통화가 끝나면 `session.history`를 대화록으로 바꿔 functions-xtool에 보냅니다([src/main.ts](../../src/main.ts) 119∼128행). 그래서 기록에 무엇이 어떤 글로 남는지가 LLM의 다음 답과 통화 결과 양쪽에 닿습니다.

통화가 진행되면서 대화 기록이 어떻게 쌓이는지 정리합니다.

```text
[system]    buildInstructions(call, knowledge)            ← Agent.create의 instructions
[assistant] (고지) 안녕하세요, 김민수 고객님. …              ← say(), addToChatCtx 기본 true
[assistant] (질문) 이삼 분 정도 통화 괜찮으실까요?
[user]      네, 괜찮아요.                                   ← 턴 확정 + 보정 후 newMessage
            (즉시 반응 "네네."는 기록 안 됨)
[assistant] 문의 주신 게 F2 울트라 맞으시죠?                ← LLM 답 (맞장구 제거 후, 실제 재생된 만큼)
[user]      …
```

PREFLIGHT 세 번이 시도 1·2·3을 만들고(만들 때마다 앞 시도 취소), FINAL은 글이 마지막 PREFLIGHT와 다르므로 트리거가 됩니다. 이 4번째 트리거는 ② 앞 시도(3번째) 취소 → ④ 횟수 3/3이라 새 시도 없음으로 끝납니다. 턴이 확정되면 남은 것이 없어 새 `generateReply`가 나갑니다. 3 + 1 = 4번입니다. ⓑ 없습니다. 선제 생성을 끈 것과 같은 시각(턴 확정)에 LLM이 시작합니다. ⓒ 버려진 시도 3번이 모두 끝까지 가므로(11-4절 깊이 보기 H) 82.8 × 3 ≈ 248 백만분의 1달러, 약 $0.00025입니다. 돈보다 큰 손해는 리드 타임을 통째로 잃는 것입니다.
9. ⓐ 지금 방식은 "네"(맞장구일 수도, "네일"의 앞일 수도 있음) → "네,"(떼면 빈 글) → "네, 가"(남은 "가"는 맞장구 말의 앞부분이 아님)에서 판단하므로 토큰 3개, 첫 토큰 뒤 2개를 더 기다려 2 × 20ms = 40ms입니다. 옛 12자 방식은 공백을 포함해 12자에 닿는 토큰이 9개("네", ",", " 가", "죽", " 지", "갑", " 각", "인", "이")라 8 × 20ms = 160ms였습니다. ⓑ 어느 쪽이든 늦추지 않습니다. 기본 분할기는 완성된 문장이 20자 이상 모이고 다음 문장이 시작돼야 첫 덩어리를 내보내는데, 이 답은 첫 문장이 13자라 둘째 문장과 합쳐지고 뒤에 문장이 없어 LLM 스트림이 끝날 때 나갑니다. 그때는 보류가 이미 풀려 있습니다(실습 11-ack-hold 2번).
10. 662ms입니다. 질문은 고지가 끝날 때 재생 허가를 받지만 "고객 조용함"을 함께 기다립니다. 조용함은 고객의 마지막 말소리 창 뒤 192ms에 켜지므로 고지 끝 + 300 + 192 = 492ms에 TTS가 시작되고, 170ms 뒤인 662ms에 첫 소리가 납니다(실습 11-speech-queue 2-2와 같은 구조). 다만 고객이 한 말도 턴이 되므로, 확신하는 판정이면 말 끝 약 406ms 뒤(고지 끝 + 706ms)에 확정되어 막 시작한 질문은 끊기고 그 말에 대한 답이 나갑니다(11-3절 ③).
11. `e2eLatency`는 LLM 답 작업만 계산하고, 그 값은 본 답의 첫 프레임 기준입니다. `say()`로 낸 즉시 반응은 계산하지 않고 기록에도 남기지 않습니다. 대신 `AgentStateChanged`(`speaking`) 이벤트의 `createdAt`에서 `EOUMetrics.lastSpeakingTimeMs`를 빼면 즉시 반응의 첫 소리까지를 잴 수 있습니다.
12. 약 11.1초입니다. 본 답이 대기열에 들어가며 `thinking`(0.4초)이 되고, 즉시 반응의 첫 소리가 상태 임대를 가져가 `speaking`이 되었다가, 즉시 반응이 끝나는 0.9초에 임대를 놓아 `listening`이 됩니다. 고객도 `listening`이라 이때 10초 자리비움 타이머가 걸립니다. 6.4초의 실패는 유효한 임대가 없어 상태를 바꾸지 않으므로, `away`는 0.9 + 10 = 10.9초에 옵니다. 실패한 본 답은 이미 끝났고 AI가 말을 마친 0.9초에서 10초가 지났으므로, `guardCall`은 미루지 않고 그때 "여보세요?"를 대기열에 넣습니다. 앞에 남은 발화가 없어 TTS 첫 음성 뒤 약 11.1초에 소리가 납니다. 즉시 반응이 없으면 본 답의 `thinking`이 실패까지 이어지고, 실패한 작업이 끝날 때 `onPipelineReplyDone`이 임대를 놓아 `listening`이 됩니다. 그래서 `away`는 0.4 + 6 + 10 = 16.4초, 첫 소리는 약 16.6초입니다(11-6절 깊이 보기).
13. 끼어들기는 발화를 먼저 일시정지시키고, FINAL이 오면 `onFinalTranscript` 끝의 `cancelSpeechPause()`가 그 발화를 중단으로 바꿉니다. 턴이 확정되어 `userTurnCompletedImpl`이 "재생 중이고 중단되지 않은 발화"를 찾을 때는 이미 중단된 뒤라, 그 로그를 찍는 분기를 타지 않습니다. 끊긴 턴은 대화 기록의 assistant 메시지에 붙는 `interrupted: true`로 세는 편이 확실합니다(11-4절 깊이 보기 G).
