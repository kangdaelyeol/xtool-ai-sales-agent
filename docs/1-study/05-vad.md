# 5장. VAD — 지금 사람이 말하고 있는가

VAD(Voice Activity Detection, 음성 활동 감지)는 오디오 프레임마다 **"이 순간에 사람 말소리가 있는가"**를 판단합니다. 단순해 보이지만 음성 에이전트의 거의 모든 타이밍이 VAD에서 시작합니다. 고객이 말을 시작했는지(끼어들기), 말을 멈췄는지(턴 종료, STT 확정 요청)를 가장 먼저 알려 주는 것이 VAD입니다.

> SDK 경로는 `node_modules/@livekit/agents/src/` 기준입니다.
>
> (2026-11-06 추가) 깊이 보기에서는 이 경로를 `agents/`로 줄여 씁니다. 실습은 레포 루트에서 키 없이 돕니다: [lab/05-vad-timeline.mjs](lab/05-vad-timeline.mjs)(창 단위 타임라인), [lab/05-silero-inside.mjs](lab/05-silero-inside.mjs)(Silero의 계약·상태·속도), [lab/05-energy-vs-silero.mjs](lab/05-energy-vs-silero.mjs)(에너지 VAD와 비교). 녹음은 2장 공용 도구([lab/02-wav.mjs](lab/02-wav.mjs))로 macOS `say -v Yuna`에서 만들고, 녹음을 VAD에 흘려 넣는 도구는 [lab/05-vad-run.mjs](lab/05-vad-run.mjs)에 있습니다. 확률의 둘째 자리는 실행마다 조금 다를 수 있습니다(실측: 같은 창이 0.43~0.45). 원인은 24kHz → 16kHz 리샘플러(QUICK)가 섞는 디더로 보입니다(2-2절, 7-4절 깊이 보기).

(2026-11-06 추가) 이 장에서 **창(window)**은 모델이 한 번에 보는 소리 조각입니다. Silero는 16kHz 512샘플(32ms) 창 하나마다 확률 하나를 냅니다. 2-4절의 **프레임**(소리를 흘려보내는 단위)과는 다른 말입니다. 방에서는 10ms 프레임이 들어오고, VAD는 그것을 모아 32ms 창을 만듭니다(5-3절 깊이 보기).

## 5-2. 고전적인 방법과 그 한계

### 에너지 기준

가장 단순한 방법은 **소리 크기(에너지)가 기준보다 크면 말소리**로 보는 것입니다.

```text
에너지 ▲
       │      ████        ████████
기준선 ┼ ─ ─ ─████─ ─ ─ ─ ████████─ ─ ─ ─ ─ ─
       │ ░░░░░████░░░░▒▒▒▒████████░░▒▒▒▒░░░░░
       └─────────────────────────────────────▶ 시간
              말소리    잡음(차 소리) 말소리
```

조용한 방에서는 잘 됩니다. 하지만 차 소리, 에어컨, TV처럼 **크지만 말이 아닌 소리**를 말소리로 착각하고, **작게 말하는 사람**을 놓칩니다.

### 특징 + 통계 모델 (WebRTC VAD)

WebRTC에 들어 있는 고전 VAD는 소리를 여러 주파수 대역으로 나눠 각 대역의 에너지를 보고, "말소리일 때의 분포"와 "잡음일 때의 분포"를 가우시안 혼합 모델(GMM)로 비교합니다. 말소리는 특정 대역(포먼트, 2장)에 에너지가 몰리는 모양이 있으므로 에너지 기준보다 낫습니다. 그래도 사람 말과 비슷한 대역을 가진 잡음(웅성거림, 음악)에는 약합니다.

#### 깊이 보기: 에너지 VAD와 WebRTC VAD를 숫자로 (2026-11-06 추가)

직접 돌려 보기: [lab/05-energy-vs-silero.mjs](lab/05-energy-vs-silero.mjs). 듣기용 WAV(`vad-clean.wav`, `vad-noise-30dbfs.wav`)를 임시 폴더(`$TMPDIR/xtool-study-02/`)에 만듭니다.

**에너지 VAD의 식.** 창 하나의 RMS를 구해 dBFS로 바꾸고(2-3절 깊이 보기), 기준선과 비교합니다. 실습은 Silero와 같은 32ms 창(24kHz 입력 768샘플)을 씁니다.

```text
RMS  = √( (x₁² + x₂² + … + x₇₆₈²) / 768 )
레벨 = 20·log10(RMS / 32,768)  dBFS
레벨 > 기준선  →  말소리 창
```

손 계산: 실습에 섞은 잡음은 RMS 약 1,036입니다. 1,036 / 32,768 ≈ 0.0316이고 20·log10(0.0316) ≈ **−30.0dBFS**입니다. 실습은 이 크기의 백색 잡음을 균등 분포 난수로 만듭니다. 폭이 ±a인 균등 분포의 RMS는 a/√3이므로 a = 1,036 × √3 ≈ 1,795입니다.

계산은 쉽지만 기준선을 정할 수가 없습니다. 기준선은 잡음 바닥(noise floor, 말이 없을 때의 레벨) 위에 있어야 합니다. 그런데 말소리 중 약한 부분(받침, "ㅅ·ㅎ" 같은 마찰음, 말끝)은 잡음 바닥 근처까지 내려갑니다. 실습 녹음에서 말소리 창의 레벨은 중앙 −16.7dBFS였지만 하위 10%는 −35.3dBFS였습니다(실측). 잡음이 −30dBFS면 이 약한 창들이 잡음에 묻힙니다. 실무의 에너지 VAD는 보통 잡음 바닥을 계속 추적해(예: 최근 몇 초의 최솟값) 기준선을 그 위 몇 dB로 움직입니다. 그래도 "약한 말소리 < 잡음 바닥"인 창은 구할 수 없습니다(일반론, 이 레포와는 무관).

실습 결과입니다. 녹음은 "네, 에프투 울트라요. 음... 가죽 지갑 만들려고요."(3,887ms) 앞뒤에 무음 1초를 붙인 것이고, 정답은 깨끗한 녹음의 파형으로 정했습니다(창 레벨 > −50dBFS면 소리).

| 녹음 | 판정 | 앞뒤 무음 1초(61창) 헛탐지 | 소리 창(97창) 놓침 | 말 사이 쉼(25창)을 말로 봄 |
| --- | --- | --- | --- | --- |
| 깨끗함 | 에너지, 기준 −45dBFS | 0 | 1 | 0 |
| 깨끗함 | Silero, p ≥ 0.5 | 0 | 2 | 8 |
| −30dBFS 잡음 | 에너지, 기준 −45dBFS | **61** | 0 | 25 |
| −30dBFS 잡음 | 에너지, 기준 −25dBFS | 0 | **18** | 0 |
| −30dBFS 잡음 | Silero, p ≥ 0.5 | 1 | 3 | 13 |

```text
창별 판정 (# 말소리, . 무음). 맨 앞 31창과 맨 뒤 30창이 붙인 무음 1초
  정답(파형)              ...............................########......####.##############.###############......##########........#########..#####################################...............................
  잡음 에너지 −25dBFS     ...............................#######.......####...##..#######....############........########..........###..##.....##################################................................
  잡음 Silero ≥0.5        ................................##########...#####################################.....############......#################################################.............................
```

읽을 점입니다.

- **깨끗한 방에서는 에너지 VAD가 가장 정확해 보입니다.** 앞뒤가 디지털 0이라 쉬운 문제이기 때문입니다.
- **잡음을 섞으면 기준선을 어디에 둬도 한쪽이 틀립니다.** 앞뒤 무음 창이 모두 −30.0dBFS가 되어, 기준 −45dBFS는 전부를 말소리로 봅니다. 기준을 −25dBFS로 올리면 헛탐지는 사라지지만 소리 창 18개(19%)를 놓치고, 띠 그림처럼 단어가 조각납니다.
- **Silero는 잡음에도 거의 그대로입니다.** 잡음뿐인 앞 1초에서 확률이 최대 0.028이었습니다. 뒤 1초의 헛탐지 1창은 말 끝 바로 다음 창(0.54)으로, 잡음을 말로 본 것이라기보다 모델이 한 창 늦게 내려온 여운입니다. 사건으로 보면 START는 같고(1,088ms) END만 한 창 늦었습니다(5,152 → 5,184ms).
- "말 사이 쉼을 말로 봄"은 Silero의 실수라기보다 정답을 정한 방식 탓입니다. 파형 기준 정답은 "네," 뒤의 짧은 멈춤까지 무음으로 치고, Silero는 앞뒤 문맥으로 이어진 말로 봅니다. 사건 단위에서는 어차피 5-4절의 규칙(말 끝은 무음 창 연속 8개)이 이 정도 쉼을 메웁니다.
- 백색 잡음은 Silero에게 쉬운 잡음입니다. 말소리와 닮은 웅성거림·TV 소리에서는 결과가 다를 수 있습니다(이 실습에서는 재지 않음).

**WebRTC VAD 안쪽.** 이 레포는 WebRTC VAD를 쓰지 않으므로 실측은 없고, 공개 소스(WebRTC `common_audio/vad/`의 `vad_core.c`, `vad_filterbank.h`. 파이썬 래퍼 py-webrtcvad에 같은 C 코드가 들어 있음)에서 읽은 내용입니다.

| 단계 | 내용 |
| --- | --- |
| 입력 | 8/16/32/48kHz의 10·20·30ms 프레임. 안에서 **8kHz로 내려** 계산 |
| 특징 | 6개 대역(80~250, 250~500, 500~1,000, 1,000~2,000, 2,000~3,000, 3,000~4,000Hz)의 **로그 에너지** |
| 모델 | 대역마다 "말소리" GMM과 "잡음" GMM. 각각 가우시안 2개 |
| 판정 | 대역마다 로그우도비를 구해 (1) 어느 한 대역이라도 개별 기준을 넘거나 (2) 대역 가중 합이 전체 기준을 넘으면 말소리. 전체 에너지가 아주 작으면 바로 무음 |
| 모드 0~3 | 기준값과 행오버 길이가 다름. 숫자가 클수록 "말소리"라고 하기 어려워져 잡음을 더 거름. 예: 20ms 프레임의 전체 기준이 48(모드 0) → 80 → 260 → 1,050(모드 3) |
| 적응 | 무음으로 판정한 프레임으로 잡음 모델의 평균·표준편차를, 말소리 프레임으로 말소리 모델을 계속 고침. 일정한 잡음에는 차츰 적응 |
| 행오버(hangover) | 말소리가 이어진 뒤 몇 프레임은 무음이어도 말소리로 붙여 냄. Silero 쪽의 "무음 창 연속 8개" 규칙과 같은 역할 |

용어 풀이입니다.

- **가우시안 혼합 모델(GMM, Gaussian Mixture Model).** 가우시안은 종 모양의 정규분포입니다. 종 여러 개에 가중치를 주어 더하면 울퉁불퉁한 분포도 흉내 낼 수 있습니다. 여기서는 "말소리일 때 250~500Hz 대역의 로그 에너지는 대략 이런 분포"를 종 두 개로 나타냅니다.
- **우도(likelihood)와 로그우도비(LLR, log-likelihood ratio).** 우도 p(x | 말소리)는 관측값 x가 말소리 모델에서 나왔다고 볼 때의 그럴듯함입니다. 두 모델의 우도를 나눈 것이 우도비이고, 로그를 씌운 LLR = log p(x | 말소리) − log p(x | 잡음)이 0보다 크면 말소리 쪽이 더 그럴듯합니다. 로그를 쓰면 곱이 합이 되어 대역별 값을 더할 수 있고, 아주 작은 확률끼리 곱해 0으로 뭉개지는 일도 없습니다.
- 손 계산: 두 모델이 표준편차 1인 정규분포이고 평균이 말소리 2, 잡음 0이라 합시다. x = 1.5이면 정규분포의 로그 밀도는 −(x − μ)²/2 + 상수이므로 LLR = −(1.5 − 2)²/2 + (1.5 − 0)²/2 = −0.125 + 1.125 = **1.0**(자연로그)입니다. 말소리 쪽이 e¹ ≈ 2.7배 그럴듯하다는 뜻입니다.

WebRTC VAD가 보는 것은 프레임 하나의 **대역 6개짜리 거친 스펙트럼 모양**이고, 시간 문맥은 행오버 정도입니다. Silero는 촘촘한 스펙트럼을 보고, 앞 창들의 문맥을 내부 상태로 이어 받습니다(5-3절 깊이 보기). 웅성거림처럼 대역 모양이 말소리와 닮은 잡음에서 둘의 차이가 커지는 이유입니다.

## 5-3. 신경망 VAD: Silero

**Silero VAD**는 수많은 언어와 잡음 환경의 데이터로 학습한 작은 신경망입니다. 이 프로젝트의 VAD가 이것입니다.

| 특징 | 내용 |
| --- | --- |
| 크기 | 약 2MB. CPU에서 실시간보다 훨씬 빠르게 돎 |
| 입력 | 16kHz에서 **512샘플(32ms)** 창. 8kHz면 256샘플. (2026-11-06 갱신) 8kHz는 공개 Silero 이야기이고, 이 레포의 번들은 16kHz 512샘플만 받습니다. 전화 통화도 워커에는 24kHz로 들어오므로(2장) 같은 길로 16kHz로 내려 넣습니다 |
| 출력 | 창마다 "말소리일 확률" 0~1 |
| 문맥 | 앞 창들의 정보를 내부 상태로 이어 받음. 한 창만 보는 게 아니라 흐름을 봄. (2026-11-06 갱신) 그 상태가 LSTM 상태이고, 없애면 판정이 크게 나빠집니다(아래 깊이 보기) |
| 언어 | 언어 무관 (말소리의 소리 특성을 배움) |

에너지 기준과의 차이는 **"크기"가 아니라 "말소리다움"**을 본다는 점입니다. 시끄러운 음악은 확률이 낮게, 작은 속삭임은 확률이 높게 나옵니다.

### LiveKit에서의 Silero

이 프로젝트는 VAD를 따로 넘기지 않습니다.

```ts
// src/main.ts
// VAD는 넘기지 않으면 번들된 Silero(로컬 실행)가 자동으로 붙습니다.
```

`AgentSession`은 VAD가 없으면 `new InferenceVAD({ model: 'silero' })`를 만듭니다(`voice/agent_session.ts`). 이 VAD는 `@livekit/local-inference`라는 **네이티브 모듈**(C++/Rust로 만든 Node 확장) 안에 모델이 내장되어 있어서, 따로 모델 파일을 받을 필요가 없습니다. 예전에는 Silero 플러그인(`@livekit/agents-plugin-silero`)과 onnxruntime을 따로 설치했는데, 그것을 지워도 되는 이유가 이것입니다([4-setup-checklist.md 1-2](../4-setup-checklist.md#1-2-설치-문제-해결)).

- 각 잡 프로세스 안에서 돕니다(4장). 무겁지 않아 공유 추론 프로세스로 보내지 않습니다.
- 방 오디오(24kHz)를 **16kHz로 리샘플**해서 32ms 창으로 자릅니다(`inference/vad.ts`).

직접 돌려 보기: [lab/05-silero-inside.mjs](lab/05-silero-inside.mjs). SDK를 거치지 않고 네이티브 모듈을 직접 불러, 계약·상태·속도를 확인합니다.

**1) 계약 (코드).** `@livekit/local-inference` 0.2.7의 `index.d.ts`가 VAD에 대해 약속하는 것은 세 가지입니다.

- `createVad()`가 핸들 하나를 돌려줍니다. "오디오 스트림(화자) 하나에 핸들 하나"이고, **LSTM 상태는 그 핸들에 붙어** `reset()`하거나 가비지 컬렉션될 때까지 남습니다.
- `predict(pcm)`은 **정확히** `VAD_WINDOW_SAMPLES`(512)개의 int16 샘플(16kHz, 32ms)을 받아야 합니다.
- 돌려주는 값은 시그모이드를 거친 0~1 사이의 "말소리 확률"입니다.

모델 파일은 따로 없고, 패키지 빌드 스크립트가 `silero.onnx`를 바이너리 안에 박아 넣습니다(`package.json`의 `prebuild-blob`). Silero인 것은 확실하지만 **몇 번째 버전인지는 공개돼 있지 않습니다.** 메모리는 약 2MB로 적혀 있고, 그래서 잡 프로세스 안에서 돈다고 설명합니다(`agents/inference/_warmup.ts` 8~13). 실측으로 계약을 어겨 보면 이렇습니다.

```text
1) 창 크기 계약
   VAD_WINDOW_SAMPLES = 512 (16kHz에서 32ms)
   511샘플 → RangeError: vad.predict expects exactly 512 int16 samples (32 ms @ 16 kHz), got 511
   1024샘플 → RangeError: vad.predict expects exactly 512 int16 samples (32 ms @ 16 kHz), got 1024
   창이 완성되는 프레임(10ms 프레임 번호): 4, 7, 10, 13, 17, 20, 23, 26, 29, 33 … (계산 ⌈3.2k⌉ = 4, 7, 10, 13, 16 …)
```

오류는 바로 던져지지 않고 Promise 거부로 옵니다. `await` 없이 부르면 처리되지 않은 거부로 프로세스가 죽습니다(실측).

**2) 입력 준비 (코드).** 프레임과 창의 크기가 맞지 않으므로, `agents/inference/vad.ts`가 모아서 자릅니다. 2-4절 프레임 지도의 VAD 줄(512샘플, 입력 기준 768)과 같은 값입니다.

```text
방 입력: 24kHz, 10ms 프레임(240샘플)이 하나씩 도착
  ├ 원본은 inputFrames에 쌓음                                   (280)
  └ QUICK 리샘플러로 16kHz로 내려 inferenceFrames에 쌓음        (18·265~272·281~285)
16kHz 샘플이 512개 이상 모이면 창 하나 처리                       (289~293)
  ├ 앞 512샘플 → Silero → 확률 p                                (295~302)
  ├ 원본 쪽에서는 512 × 24,000/16,000 = 768샘플을 말소리 버퍼로   (307~323)
  │   (비율이 정수가 아니면 소수 부분을 inputCopyRemainingFrac로 넘겨 누적. 예: 44.1kHz면 1,411.2)
  ├ 카운터 갱신과 사건 (5-4절)                                   (342~417)
  └ 남은 샘플은 다음 창으로 넘김                                 (419~428)
```

손 계산: 창 k가 완성되려면 원본 768 × k샘플이 와야 하고, 프레임은 240샘플이므로 ⌈3.2 × k⌉번째 프레임이 도착할 때 창이 처리됩니다. k = 1~5면 4, 7, 10, 13, 16번째 프레임입니다. 실제로 리샘플러에 넣어 세어 보면 다섯 번째 창은 16번째가 아니라 **17번째** 프레임에서 완성됐습니다(실측: 4, 7, 10, 13, 17, 20, 23, 26, 29, 33…). `QUICK` 리샘플러가 샘플 하나쯤을 붙잡고 있어서(2-2절 깊이 보기), 프레임 경계와 딱 맞는 창은 한 프레임 늦습니다. 정리하면 프레임은 10ms마다 오지만 **창 처리는 대개 30ms, 다섯 번에 한 번 40ms 간격**으로 일어나고, 창이 끝나는 시각과 그 창이 처리되는 시각 사이에 2~10ms의 차이가 생깁니다(5-5절 깊이 보기의 +10ms).

**3) 공개 Silero v5의 구조 (공개 자료 기준, 이 레포 번들은 추정).** Silero가 공식 구조 문서를 내지는 않았습니다. 아래는 Silero 저장소의 파이썬 래퍼(`src/silero_vad/utils_vad.py`의 `OnnxWrapper`)와, 공개 모델을 다른 형식으로 옮긴 변환본들(Hugging Face의 MLX·LiteRT 변환 등)이 공통으로 적은 내용입니다.

```text
새 512샘플 + 앞 창의 마지막 64샘플(문맥) = 576샘플       ← 래퍼가 직접 붙임 (8kHz면 256 + 32)
  → STFT: 짧은 구간마다 주파수 성분을 구함 (2-8절 스펙트로그램과 같은 생각, 합성곱으로 구현)
  → 인코더: 1차원 합성곱(Conv1d) + ReLU 4층. 주파수 모양에서 특징을 뽑음
  → LSTM(은닉 128) ⇄ 상태 (h, c) = 2 × 1 × 128 을 다음 창으로 넘김
  → 1×1 합성곱(128 → 1) → 시그모이드 → p
매개변수 약 30만 개 (변환본 기준)
```

이 레포의 네이티브 `predict()`는 512샘플만 받으므로, 문맥 64샘플을 쓴다면 LSTM 상태와 함께 핸들 안에 보관하는 것으로 보입니다(추정, 확인할 방법 없음). 공개 파이썬 도구의 문턱값 규칙(`neg_threshold = max(threshold − 0.15, 0.01)`)은 SDK의 0.35 계산(`agents/inference/vad.ts` 73)과 같은 식입니다.

**시그모이드(sigmoid).** 모델의 마지막 층은 −∞~+∞ 사이의 실수 z(로짓, logit)를 냅니다. 시그모이드 σ(z) = 1 / (1 + e^(−z))는 이것을 0~1로 눌러 줍니다. z = 0이면 0.5이고, z가 크면 1에, 작으면 0에 붙습니다. 거꾸로 z = ln(p / (1 − p))입니다.

| p | z = ln(p / (1 − p)) | 이 레포에서 |
| --- | --- | --- |
| 0.01 | −4.60 | 조용한 창 |
| 0.35 | −0.62 | 말하는 중 끄는 기준 |
| 0.5 | 0 | 켜는 기준 |
| 0.99 | +4.60 | 또렷한 말소리 창 |

두 기준 사이는 z로 0.62밖에 안 됩니다. 반대로 0.99와 0.9999는 p로는 비슷해도 z로는 4.6과 9.2로 크게 다릅니다. 시그모이드는 양 끝이 납작하기 때문입니다. 또 "확률"이라고 부르지만, 0.7이 "열 번 중 일곱 번 말소리"라는 보정된 확률이라는 보장은 없습니다. 기준값과 비교하는 **점수**로 읽는 편이 안전합니다(일반론).

**LSTM(Long Short-Term Memory).** 순환 신경망(RNN)은 입력을 하나씩 받을 때마다 "상태" 벡터를 고쳐 다음 단계로 넘깁니다. 새 상태 = f(이번 입력, 이전 상태)입니다. 단순한 RNN은 오래된 정보를 금방 잊습니다. LSTM은 이 문제를 풀려고 상태를 둘로 나누고 **문(gate)** 세 개를 둡니다.

- 셀 상태 c: 오래 들고 가는 기억. 은닉 상태 h: 이번 단계의 출력.
- 잊기 문: 옛 c를 얼마나 남길지. 입력 문: 새 정보를 얼마나 적을지. 출력 문: c를 얼마나 h로 내보낼지.
- 문 하나하나가 시그모이드(0~1)라서 "얼마나"를 곱셈으로 조절합니다. 잊기 문이 1에 가까우면 정보가 여러 단계를 건너 살아남습니다.

Silero에서는 32ms 창 하나가 한 단계이고, (h, c) 각 128개 값이 다음 창으로 넘어갑니다. 실습에서 같은 녹음을 두 방식으로 판정했습니다(실측).

```text
2) 같은 녹음 183창 (# ≥0.5, + 0.35~0.5, . 0.1~0.35)
   이어서 판정 (한 핸들, 상태 유지)  |                               +########+.  .####################################.     ##########+.     #################################################                              |
   창마다 reset()                    |                                #######      ####.  ## ...++#+#+. #+#+###+#+####       +#+######         .+###.#.   .#+###+#..###...#+#++##+.#####+####.                               |
   두 방식의 차이: 평균 0.296, 0.3 넘게 다른 창 82개, ≥0.5인 창 103개 vs 57개
   말 시작 근처 창 31~34: 이어서 0.43 0.99 1.00 1.00 / reset 0.10 0.82 0.80 0.71
   같은 창을 새 핸들에 5번: 0.783 0.972 0.997 0.998 0.997
```

- 기억을 지우고 창 하나만 보게 하면 0.5를 넘는 창이 103개에서 57개로 줄고, 단어가 조각납니다. Silero의 판단은 상당 부분 **문맥**에서 나옵니다.
- 같은 입력을 넣어도 상태에 따라 출력이 다릅니다. 같은 말소리 창을 새 핸들에 거듭 넣으면 0.783에서 0.997로 올라갑니다. 증거가 쌓일수록 확신하는 모양입니다.
- 그래서 SDK는 스트림마다 핸들을 따로 만들고(`agents/inference/vad.ts` 136), 구간을 끊는 신호(flush)가 오면 `reset()`으로 기억을 지웁니다(203~204·251~253). 한 핸들을 두 소리에 같이 쓰면 상태가 섞입니다.

**4) 속도와 실시간 계수 (실측, 이 맥에서).** **실시간 계수(RTF, real-time factor)**는 처리 시간 ÷ 소리 길이입니다. 1보다 작으면 실시간보다 빠르고, 1을 넘으면 소리가 들어오는 속도를 못 따라가 밀립니다.

```text
3) 속도 (창 1830번, await 포함)
   중앙 0.031ms, 99% 0.063ms, 최대 0.12ms → 실시간 계수(RTF) 0.0010, 1초 분량(31창)에 약 1.0ms
   두 핸들 183창씩: 차례로 13.3ms, 동시에 6.8ms (동시가 짧으면 추론이 메인 스레드 밖에서 돈다는 뜻)
```

창 하나에 약 0.03ms(두 번 실행해 중앙 0.031·0.035ms)라 32ms 창의 약 1/1,000입니다. 두 핸들을 동시에 돌리면 더 빨리 끝나므로, `predict()`의 계산은 메인 스레드(이벤트 루프) 밖, libuv 작업 스레드에서 도는 것으로 보입니다(실측에서 나온 추정. `index.d.ts`는 턴 감지 모델의 `predict`에 대해서만 libuv 작업 스레드를 명시합니다). 모델 계산 자체가 이벤트 루프를 막을 가능성은 작고, 루프를 쓰는 것은 그 둘레의 JS 일(프레임 합치기, 리샘플, 버퍼 복사)입니다. 측정값은 실행할 때마다 조금씩 다릅니다.

## 5-4. 확률을 사건으로: 히스테리시스와 지속 시간

모델은 32ms마다 확률을 내놓습니다. 그런데 에이전트가 필요한 것은 "말 시작", "말 끝" 같은 **사건(event)**입니다. 확률을 사건으로 바꾸는 규칙이 필요합니다.

### 문제: 확률은 흔들린다

```text
확률
1.0 ┤        ▄▄█▄█▄▄▄       ▄▄▄█▄▄
0.5 ┤ ─ ─ ─ █─ ─ ─ ─▀█▄ ▄█▀ ─ ─ ─ █▄─ ─ ─ ─   ← 기준 하나(0.5)만 쓰면
    │      ▄█         ▀▀▀           ▀▄          "말 끝 → 말 시작 → 말 끝…"이
0.0 ┼▁▁▁▁▁▁           (단어 사이 약한 구간)  ▁▁▁▁   마구 반복됨
```

말하는 도중에도 단어 사이, 숨 쉬는 곳, 받침 소리에서 확률이 잠깐 떨어집니다. 기준 하나로 자르면 사건이 깜빡거립니다.

### 해결 1: 히스테리시스 (두 개의 기준)

**켜는 기준과 끄는 기준을 다르게** 둡니다. 온도 조절기가 22도에서 켜지고 24도에서 꺼지는 것과 같은 원리입니다.

| 기본값 (`inference/vad.ts`) | 값 | 의미 |
| --- | --- | --- |
| `activationThreshold` | 0.5 | 말하지 않는 중이면, 확률이 이 이상이어야 "말소리 창"으로 셈 |
| `deactivationThreshold` | 0.35 (= 0.5 − 0.15) | 이미 말하는 중이면, 확률이 이것보다만 크면 계속 "말소리 창"으로 셈 |

한 번 말이 시작되면 0.35까지 떨어져도 말하는 중으로 봅니다. 단어 사이의 약한 구간에 흔들리지 않습니다.

(2026-11-06 추가) **히스테리시스(hysteresis)**는 출력이 지금 상태에 따라 다른 기준을 쓰는 성질입니다. 경계는 정확히 이렇습니다. 조용할 때는 p ≥ 0.5(같아도 말소리 창), 말하는 중에는 p > 0.35(같으면 무음 창)입니다(`agents/inference/vad.ts` 366~369). 0.35는 따로 정한 값이 아니라 `max(0.5 − 0.15, 0.01)`로 계산한 값입니다(73행).

### 해결 2: 최소 지속 시간

| 기본값 | 값 | 의미 | 왜 |
| --- | --- | --- | --- |
| `minSpeechDuration` | 50ms (실제로는 32ms 창 **연속** 2개 = 64ms) | 말소리 창이 **끊기지 않고** 이만큼 이어져야 `START_OF_SPEECH` (2026-11-06 갱신) | 기침, 클릭 같은 아주 짧은 소리 무시 |
| `minSilenceDuration` | 250ms (실제로는 창 **연속** 8개 = 256ms) | 무음 창이 **끊기지 않고** 이만큼 이어져야 `END_OF_SPEECH` (2026-11-06 갱신) | 단어 사이 짧은 쉼에 말 끝으로 보지 않기 |
| `prefixPaddingDuration` | 500ms | (2026-11-06 갱신) 말 시작·끝 사건이 싣는 소리 버퍼 앞에 **판정 직전 0.5초**를 붙임 | 사건의 소리를 받아 한 번에 인식하는 **비스트리밍 STT**에서 첫 음절이 안 잘리게. 이 레포(Soniox 스트리밍)의 인식에는 쓰이지 않음(아래 깊이 보기) |

(2026-11-06 추가) **"쌓인다"는 "연속으로 이어진다"는 뜻입니다.** 코드에는 카운터가 둘 있습니다. 말소리 창이 오면 말 카운터에 32를 더하고 무음 카운터를 **0으로** 되돌립니다. 무음 창이 오면 그 반대입니다(`agents/inference/vad.ts` 366~417). 그래서 무음 창 7개 뒤에 말소리 창이 하나만 끼어도 무음 카운터는 처음부터 다시 셉니다. 창 수는 ⌈설정값 ÷ 32⌉입니다. 50ms는 ⌈1.56⌉ = 2창(64ms), 250ms는 ⌈7.81⌉ = 8창(256ms)입니다.

```text
                 ┌──────────────── 조용함 ────────────────┐
                 │ 창마다  p ≥ 0.5 → 말 +32,  무음 = 0      │
                 │         p < 0.5 → 무음 +32, 말 = 0      │
                 └────────────────────────────────────────┘
                   │ 말 카운터 ≥ 50                    ▲ 무음 카운터 ≥ 250
                   │ (말소리 창 연속 2개)               │ (무음 창 연속 8개)
                   ▼ START_OF_SPEECH                   │ END_OF_SPEECH
                 ┌─────────────── 말하는 중 ──────────────┐
                 │ 창마다  p > 0.35 → 말 +32,  무음 = 0     │
                 │         p ≤ 0.35 → 무음 +32, 말 = 0     │
                 └────────────────────────────────────────┘
```

상태가 바뀌어도 카운터는 0이 되지 않습니다. START 직후 말 카운터는 64에서 계속 늘고, END 직후 무음 카운터는 256에서 계속 늘다가 다음 말소리 창에서 0이 됩니다(실측, 아래 타임라인의 5,152~5,184 창).

`minSilenceDuration`은 트레이드오프의 중심입니다.

- 짧으면: 말 끝을 빨리 알지만, "음… 그러니까"처럼 쉬는 곳에서 말이 끝났다고 착각합니다.
- 길면: 정확하지만 모든 턴이 그만큼 늦어집니다.

LiveKit은 이 문제를 VAD 혼자 풀게 하지 않습니다. **VAD는 짧게(256ms) 끊고, "정말 턴이 끝났는가"는 턴 감지 모델이 따로 판단**하게 나눕니다(7장). 그래서 턴 감지 모델과 같이 쓸 때 `minSilenceDuration`이 250ms보다 작으면 세션이 오류를 냅니다(`voice/audio_recognition.ts`). (2026-11-06 갱신) 이유는 예측 요청 조건에 있습니다. 세션은 VAD가 실어 보낸 무음 길이가 200ms(`MIN_SILENCE_DURATION_MS`) 이상이고 **아직 말하는 중일 때만** 예측을 요청합니다(`agents/voice/audio_recognition.ts` 2196~2203, `agents/inference/eot/base.ts` 23). 그런데 실린 값은 한 창 늦습니다(아래 타임라인 깊이 보기). 말 끝이 그 전에 나면 "말하는 중"이 풀려 예측 요청이 아예 나가지 않고, 턴은 예측 없이 판정됩니다(1690~1696행). 바닥값은 200 + 50 = 250으로 계산합니다(765행).

참고로 Silero 플러그인 문서의 `min_silence_duration` 기본값은 0.55초입니다. 번들 VAD(250ms)와 다르므로, 문서 숫자를 그대로 이 프로젝트에 적용하면 안 됩니다.

#### 깊이 보기: prefixPadding은 이 레포에서 어디에 쓰이나 (2026-11-06 추가)

예전 표는 "앞을 붙여야 STT의 첫 음절이 안 잘린다"고 적었습니다. 코드를 따라가 보면 이 레포에서는 맞지 않습니다.

1. **VAD가 하는 일.** 조용한 동안에는 말소리 버퍼에 최근 0.5초(24kHz면 12,000샘플)만 남기고 앞을 버립니다(`agents/inference/vad.ts` 188~201·393~397). START가 나면 그 0.5초에 START까지의 창들을 이어 사건의 `frames`에 담고(384), END 때는 말 전체를 담습니다(409). 실측: START 13,536샘플 = 12,000 + 768 × 2창, END 111,072샘플 = 12,000 + 768 × 129창.
2. **이 소리를 쓰는 곳.** SDK와 이 레포가 쓰는 플러그인을 통틀어 VAD 사건의 `frames`를 소리로 쓰는 곳은 `agents/stt/stream_adapter.ts` 111행 하나입니다. 스트리밍을 못 하는 STT를 감싸, END 사건의 소리를 `recognize()`로 한 번에 인식합니다. 여기서는 프리픽스가 있어야 첫 음절이 들어갑니다. 이 어댑터는 STT가 스트리밍을 못 할 때만 붙습니다(`agents/voice/agent.ts` 488~496). 이 레포의 Soniox는 스트리밍이고(`node_modules/@livekit/agents-plugin-soniox/src/stt.ts` 116 `streaming: true`), 다른 선택지인 LiveKit Inference STT도 스트리밍입니다(`agents/inference/stt.ts` 548).
3. **STT는 소리를 따로 받습니다.** 세션은 입력 소리를 `tee()`로 갈라 VAD와 STT에 **처음부터 계속** 흘립니다(`agents/voice/audio_recognition.ts` 606~621). 턴 감지 모델도 입력을 직접 받습니다(552~575). VAD가 말 시작을 늦게 알아도 Soniox는 이미 첫소리를 받고 있습니다.
4. **세션이 사건 소리에서 읽는 것은 샘플레이트뿐**입니다(`audio_recognition.ts` 2165~2166). 이 값은 오디오가 떨어졌을 때 STT를 비우려고 무음 프레임을 만들 때 씁니다(2525~2526).

그래서 이 레포에서 `prefixPaddingDuration`을 0으로 해도 **인식과 타이밍은 그대로**이고 사건이 싣는 소리만 줄어듭니다. 실측: 0으로 하면 START 버퍼가 1,536샘플(768 × 2창)이 되고, START 1,088ms·END 5,152ms는 기본값과 같았습니다([lab/05-vad-timeline.mjs](lab/05-vad-timeline.mjs) 7번). 비용은 스트림마다 잡아 두는 버퍼(`maxBufferedSpeech` 60초 + 0.5초 = 24kHz에서 1,452,000샘플 ≈ 2.9MB, 256~264행)와 사건마다의 복사뿐입니다.

## 5-5. VAD 사건이 세션에 전달되는 방식

`voice/audio_recognition.ts`의 VAD 처리 루프는 사건마다 이렇게 반응합니다.

```text
[START_OF_SPEECH]
   speechStartTime = 지금 − 쌓인 말소리 길이 − 추론 지연   ← 실제 시작 시각으로 거꾸로 맞춤
   → 사용자 상태 'speaking'
   → 진행 중이던 턴 종료 판정·예측 취소 (다시 말하기 시작했으므로)

[INFERENCE_DONE]  (32ms마다. 같은 창에서는 START·END보다 먼저 옴)          (2026-11-06 갱신)
   직전 창까지 말소리 창이 이어졌으면(실린 말 카운터 > 0) lastSpeakingTime = 지금
   실린 무음(이번 창을 더하기 전) ≥ 200ms이고 아직 말하는 중이면
      → 턴 감지 모델에 예측 요청 (7장). 기본값에서는 END를 내는 창과 같은 창
   에이전트가 말하는 중이면 → 끼어들기 검사 (7장)

[END_OF_SPEECH]
   lastSpeakingTime = 지금 − 무음 길이 − 추론 지연          ← 마지막으로 말한 순간으로 거꾸로 맞춤
   → 사용자 상태 'listening'   ← 여기서 이 프로젝트가 Soniox finalize 호출
   → 턴 종료 판정 시작 (FINAL 글이 있을 때)
```

**시각을 거꾸로 맞추는(back-dating) 부분**이 중요합니다. `END_OF_SPEECH`는 무음이 256ms 쌓인 뒤에야 나오므로, 그 사건 시각은 실제로 말을 멈춘 시각보다 늦습니다. 그래서 "마지막으로 말한 시각"을 무음 길이만큼 앞으로 당겨 기록합니다. 7장의 턴 종료 대기 시간(300ms)이 **이 시각부터** 재므로, VAD의 256ms 대기는 300ms 안에 이미 포함됩니다.

#### 깊이 보기: 사건이 싣는 값과, 거꾸로 맞춘 시각의 정확도 (2026-11-06 추가)

**back-dating(시각 거꾸로 맞추기)**은 사건을 알게 된 시각에서 이미 지나간 길이를 빼, 일이 실제로 일어난 시각을 기록하는 방법입니다. 무엇을 빼는지 보려면 사건이 싣는 값을 알아야 합니다. 아래는 `agents/inference/vad.ts` 342~417을 읽고 실습 녹음으로 확인한 값입니다.

| 필드 | `INFERENCE_DONE` | `START_OF_SPEECH` | `END_OF_SPEECH` |
| --- | --- | --- | --- |
| `timestamp` | 스트림 시작부터 이 창 끝까지 누적 ms | 같은 창 값 (실측 1,088) | 같은 창 값 (실측 5,152) |
| `speechDuration` | 말하는 중: START의 64에서 창마다 +32(쉼 창 포함). 조용할 때 0 | 말 카운터 (64) | 말하는 중으로 본 시간 − 끝 무음 (실측 3,872) |
| `silenceDuration` | 조용할 때: 창마다 +32. 말하는 중 0 | 0 | 무음 카운터 (256) |
| `rawAccumulatedSpeech` / `Silence` | 두 카운터의 **갱신 전** 값 | 0 | 0 |
| `inferenceDuration` | 이 창 **하나**를 처리한 시간(ms) | 같은 창 값 | 같은 창 값 |
| `frames` | 이 창의 원본 768샘플 | 프리픽스 + START까지 (13,536) | 프리픽스 + 말 전체 + 끝 무음 (111,072) |

`speechDuration`이 창마다 32씩 늘어나므로, 끼어들기 조건(`speechDuration ≥ minDuration`, `agents/voice/agent_activity.ts` 2198~2202)은 START 다음 창부터 96, 128, 160, 192, **224**를 거쳐 다섯 번째 창에서 처음 참이 됩니다. 말소리로 본 첫 창부터 7창(224ms)째입니다(실측: START 1,088ms, 조건 1,248ms).

세션은 이 값으로 두 시각을 만듭니다.

```text
말 시작          = Date.now() − speechDuration(64)  − inferenceDuration     audio_recognition.ts 2141, agent_activity.ts 2121~2125
마지막 말소리    = Date.now() − silenceDuration(256) − inferenceDuration     audio_recognition.ts 2223, agent_activity.ts 2165~2170
```

실습 녹음에서 스트림 시각으로 계산하면 말 시작 1,088 − 64 = **1,024ms**, 마지막 말소리 5,152 − 256 = **4,896ms**입니다. 파형으로는 1,000ms와 4,850ms였습니다. 오차가 생기는 곳은 네 군데입니다.

1. **창 단위 양자화와 모델의 여운.** 시각은 32ms 창의 경계로만 잡힙니다. 말 시작은 소리가 24ms만 든 첫 창(0.43)이 기준에 못 미쳐 24ms 늦게, 말 끝은 모델이 한 창쯤 늦게 내려와(4,864~4,896 창이 0.96) 46ms 늦게 잡혔습니다(실측).
2. **`Date.now()`는 사건을 처리하는 순간입니다.** 창은 그 창의 마지막 샘플이 든 10ms 프레임이 도착해야 처리됩니다(5-3절 깊이 보기). 실측: 실시간 속도로 흘리면 END 창(끝 5,152ms)은 5,162ms에 처리되어 +10ms가 붙었습니다.
3. **`inferenceDuration`은 마지막 창 하나의 처리 시간입니다.** 이벤트 루프가 막혀 프레임이 밀려 있다가 한꺼번에 처리되면, 밀린 시간은 어디에도 기록되지 않습니다. 실측: 녹음 4,950ms 지점에서 메인 스레드를 300ms 붙잡았더니 END가 5,251~5,266ms에 처리되어 **+99~+110ms**가 틀어졌고(4회 실행), 그 창의 `inferenceDuration`은 0.04~4ms뿐이었습니다.
4. **워커 앞의 지연은 보이지 않습니다.** 네트워크, 지터 버퍼(2-6절), 음성 향상을 거치는 동안의 지연은 프레임이 워커에 오기 전 일이라 `Date.now()`에 들어 있지 않습니다. 시각은 "워커가 소리를 받은 시각" 기준입니다(코드상 그렇고, 크기는 재지 않음).

```text
6) 실시간으로 흘리며 거꾸로 맞춘 "마지막 말소리" 시각 (녹음 시각 기준, 창 기준 정답 = END − 256)
   막힘 없음              END 처리 5162ms → 거꾸로 맞춘 값 4906ms (정답 4896ms, 오차 +10ms), END 창 inferenceDuration 0.12ms, 창 하나 최대 0.86ms
   4,950ms에 300ms 막힘   END 처리 5266ms → 거꾸로 맞춘 값 5006ms (정답 4896ms, 오차 +110ms), END 창 inferenceDuration 4.08ms, 창 하나 최대 4.08ms
```

3번이 4-4절과 이어지는 곳입니다. 통화 프로세스 안에서 동기 작업이 이벤트 루프를 붙잡으면, `lastSpeakingTime`이 그만큼 늦게 찍힙니다. 턴 확정 대기(300ms)가 이 시각부터 재므로 턴도 그만큼 늦게 확정될 수 있는데, 말 끝 판단 메트릭(`now − lastSpeakingTime`, `agents/voice/audio_recognition.ts` 145)은 그만큼 **작게** 나옵니다. 고객이 겪은 지연이 지연 기록(13장)에서 빠진다는 뜻입니다(코드에서 따라간 추론, 통화로는 재지 않음). 막힌 동안 VAD는 입력을 기다리고 있었으므로, 아래 5-7절의 "slower than realtime" 경고도 나지 않았습니다(실측: 창 하나 최대 4ms).

### 사용자 상태

| 상태 | 언제 |
| --- | --- |
| `speaking` | VAD 말 시작 |
| `listening` | VAD 말 끝 |
| `away` | 사용자와 에이전트가 모두 조용한 상태로 15초가 지나면 (`userAwayTimeout` 기본값) |

`away`는 "여보세요?" 재촉이나 무응답 종료([2-tech-stack.md 7장](../2-tech-stack.md#7-우리가-직접-만들-기능-목록)의 "무응답 재촉 10초, 종료 30초")를 만들 때 쓰는 신호입니다.

### away를 쓰는 무응답 안전장치 (2026-11-03 추가)

`src/call-guard.ts`가 이 신호로 무응답과 통화 길이를 지킵니다.

| 설정 | 값 | 동작 |
| --- | --- | --- |
| `userAwayTimeout` (세션 옵션) | **10** | 고객과 AI가 모두 10초 조용하면 `away`. Node SDK에서도 이 값은 **초 단위**입니다(내부에서 ×1000). 같은 SDK의 `minDelay` 같은 값은 ms라 헷갈리기 쉬움 |
| "여보세요?" 뒤 무응답 | 10초 | "통화가 어려우신 것 같아요…" 하고 끊음 |
| 최대 통화 길이 | 8분 | "오늘 말씀해 주신 내용은…" 하고 끊음 (판정 통화 목표는 2~4분) |

```ts
session.on(voice.AgentSessionEventTypes.UserStateChanged, (ev) => {
  if (ev.newState === 'speaking') { clearTimeout(noResponseTimer); noResponseTimer = undefined; return; }
  if (ev.newState !== 'away' || noResponseTimer) return;
  const prompt = session.say(STILL_THERE, { allowInterruptions: true });   // "여보세요? 제 목소리 잘 들리세요?"
  void prompt.waitForPlayout().then(() => {
    noResponseTimer = setTimeout(() => void endCall(NO_RESPONSE_BYE, 'no_response'), NO_RESPONSE_END_MS);
  });
});
```

설계에서 볼 점이 두 가지 있습니다.

- **상태는 바뀔 때만 이벤트가 옵니다.** `away`는 고객이 다시 말할 때까지 이어지므로 "away 두 번째"라는 이벤트는 오지 않습니다. 그래서 재촉 뒤의 종료는 직접 타이머로 셉니다(파일 주석에 그 이유가 적혀 있음). 이벤트 기반 코드에서 "아무 일도 안 일어남"을 감지하려면 타이머가 필요하다는 일반 원칙입니다.
- **경쟁 조건 하나 (2026-11-03 고침).** "여보세요?"는 끼어들 수 있는 발화라, 고객이 그 도중에 "네, 들려요"라고 답하면 순서가 이렇게 됩니다: 고객 `speaking`(이때는 지울 타이머가 아직 없음) → "여보세요?" 중단 → `waitForPlayout()`이 끝나며 **타이머가 그제야 시작**. 고객은 이미 대답했는데 무응답 타이머가 돌고, 이후 10초 안에 고객이 새로 말을 시작하지 않으면(예: AI가 길게 답하는 동안) 통화가 끊깁니다. 이 순서를 그대로 재현하는 테스트(`src/call-guard.test.ts`, 14-3절)를 먼저 써서 실패를 확인한 뒤, 타이머를 걸기 직전에 고객이 아직 `away`인지 확인하도록 고쳤습니다.

```ts
void prompt.waitForPlayout().then(() => {
  // "여보세요?" 도중에 대답했으면 재생은 끼어들기로 끝났고 고객은 이미 away가 아닙니다.
  if (session.userState !== 'away') return;
  noResponseTimer = setTimeout(() => void endCall(NO_RESPONSE_BYE, 'no_response'), NO_RESPONSE_END_MS);
});
```

비동기 코드에서 **"기다리는 동안 세상이 바뀌었을 수 있다"**는 것은 흔한 버그의 원인입니다. `await`나 `.then` 뒤에서 무언가를 하기 전에, 그 일을 하기로 한 전제(여기서는 "고객이 아직 조용하다")가 아직 참인지 다시 확인하는 습관이 필요합니다.

## 5-6. VAD가 모르는 것

VAD는 **소리가 말소리인지**만 압니다. 다음은 모릅니다.

| VAD가 모르는 것 | 예 | 누가 해결하나 |
| --- | --- | --- |
| 말이 끝난 건지 잠깐 쉬는 건지 | "에프투 울트라로… (생각) …가죽 지갑에" | 턴 감지 모델 (7장) |
| 맞장구인지 끼어들기인지 | 에이전트가 말하는 중 고객의 "네" vs "아니요" | 적응형 끼어들기 모델 (7장) |
| 누구의 목소리인지 | 옆 사람, TV, **스피커로 되돌아온 에이전트 자기 목소리** | 노이즈 제거·음성 분리 (2장), 에코 제거 |
| 무슨 말인지 | — | STT (6장) |

그래서 현대 음성 에이전트는 VAD를 **"빠르지만 단순한 1차 신호"**로 쓰고, 그 위에 더 똑똑한 판단을 겹칩니다. VAD는 32ms마다 답하는 반면, 턴 감지 모델은 필요할 때만, 적응형 끼어들기 모델은 소리가 겹칠 때만 부릅니다. **싼 판단을 항상, 비싼 판단을 가끔** 하는 계층 구조입니다.

## 5-7. 알아 둘 함정

| 함정 | 내용 |
| --- | --- |
| VAD 메트릭 집계 | Node SDK의 기본 VAD 메트릭은 "추론 횟수"가 아니라 `START_OF_SPEECH` 횟수를 세어, 말 시작이 약 32번 있을 때마다 한 번 나옵니다. 의도와 다른 것으로 보여, VAD 메트릭은 참고만 합니다. (2026-11-06 갱신) 코드: START가 올 때만 횟수를 올리고 1000 ÷ 32 = 31.25 이상, 즉 32번째에 내보냅니다. 추론 시간 합은 `INFERENCE_DONE`마다 더하므로, 메트릭 하나에 말 시작 32번 사이의 모든 창 시간이 들어갑니다(`agents/vad.ts` 160~191) |
| 사건 시각의 단위 | VAD 사건의 `timestamp`는 주석상 epoch ms지만, 실제로는 스트림 시작부터 누적한 ms가 들어갑니다. 다른 시각과 비교할 때 주의합니다. (2026-11-06 갱신) 코드: 창마다 32씩 더한 값입니다(`agents/vad.ts` 31, `agents/inference/vad.ts` 306). 실측: 녹음 1,088ms 지점의 START가 `timestamp` 1088을 실었습니다. 세션은 이 값을 쓰지 않고 `Date.now()`로 시각을 만듭니다(5-5절 깊이 보기) |
| 맥에서의 성능 경고 | PoC 로그에 `VAD inference is slower than realtime`이 두 번 나왔습니다([5-poc-results.md](../5-poc-results.md)). 디버거 TTS와 같이 돌던 맥에서 생긴 것으로 보이며, VAD가 실시간을 못 따라가면 모든 타이밍이 밀리므로 서버에서 다시 확인해야 합니다. (2026-11-06 갱신) 경고 조건은 누적 지연이 아니라 **창 하나**의 처리 시간이 200ms를 넘는 것입니다(`agents/inference/vad.ts` 17·331~340). 누적값(`extraInferenceTimeMs`)은 메시지에 실릴 뿐 조건이 아닙니다. 창 하나의 처리 시간은 그 창의 `predict()`를 `await`하는 동안을 포함하고, 모델 계산은 중앙 약 0.03ms였으므로(실측, 5-3절 깊이 보기), 경고가 났다면 모델이 느렸다기보다 그 `await` 동안 메인 스레드가 다른 일에 200ms 넘게 붙잡혔을 가능성이 큽니다(추정). 거꾸로, VAD가 입력을 기다리는 사이에 루프가 막히면 경고 없이 시각만 틀어집니다(5-5절 깊이 보기) |
| 끼어들 수 없는 말 중의 고객 소리 | 고지처럼 끼어들기를 막은 발화 중에는 **STT에 무음이 들어가지만 VAD는 진짜 소리를 받습니다.** 그래서 사용자 상태는 `speaking`이 되는데 글이 없어 턴이 생기지 않습니다(7장, 11장). (2026-11-06 갱신) 이것은 **기본값**(`discardAudioIfUninterruptible: true`) 이야기입니다. 이 레포는 `false`라([src/main.ts](../../src/main.ts) 73) 지금은 STT도 진짜 소리를 받아 글이 생깁니다. 다만 고지 도중에 확정된 턴은 여전히 버려질 수 있습니다(7-6절 갱신). 또 세션 기본값 `aecWarmupDuration`(3초) 동안, 즉 에이전트가 처음 말하기 시작한 뒤 3초 동안은 이 설정과 상관없이 STT에 무음이 들어갑니다(`agents/voice/agent_activity.ts` 1807~1822, `agents/voice/agent_session.ts` 249·1901~1907). 브라우저 테스트에서는 첫 고지의 앞 3초가 여기에 걸리고, 발신 SIP 통화에서는 워밍업이 자동으로 꺼집니다(`agent_session.ts` 2074~2086). 코드로 확인했고 실측은 하지 않았습니다 |

## 5-8. 정리

```text
24kHz 프레임 ──▶ 16kHz 리샘플 ──▶ Silero (32ms 창마다 말소리 확률)
                                     │ 히스테리시스 0.5 / 0.35
                                     │ 말소리 창 연속 2개(64ms) → START_OF_SPEECH → 'speaking'
                                     │ 무음 창 연속 8개(256ms) → 같은 창에서
                                     │     ① 턴 감지 예측 요청 (실린 무음 224ms ≥ 200)
                                     │     ② END_OF_SPEECH → 'listening' → (Soniox finalize)
                                     └ lastSpeakingTime = Date.now() − 256 − 추론 시간 (거꾸로 맞춤)
```

(2026-11-06 갱신) 예전 그림의 "무음 ≥ 200ms → 턴 감지 예측 미리 요청"은 기본값에서 맞지 않아 고쳤습니다. 예측 요청은 END와 같은 창에서, END 처리 바로 앞에 나갑니다(5-4절 깊이 보기).

4. 문장 중간 쉼에 말 끝으로 착각하는 일은 줄지만 모든 턴이 1초 가까이 늦어집니다. LiveKit은 VAD는 짧게(256ms) 끊고, 턴이 정말 끝났는지는 턴 감지 모델이 판단하게 나눕니다.
5. `END_OF_SPEECH`는 무음이 256ms 쌓인 뒤에 나오므로, 실제로 말을 멈춘 시각은 그보다 무음 길이만큼 앞입니다. 턴 종료 대기 시간은 그 실제 시각부터 잽니다.
6. 992~1,024 창은 0.43 < 0.5라 무음입니다. 1,024~1,056 창이 말 카운터 32, 1,056~1,088 창이 64(≥ 50)라 **1,088ms 창 끝**에서 START입니다. 버퍼는 프리픽스 24,000 × 0.5 = 12,000샘플 + 창 2개 × 768 = **13,536샘플**입니다. 말 시작은 1,088 − `speechDuration` 64 = **1,024ms**로, 말소리로 본 첫 창의 시작입니다(실제 파형 시작은 1,000ms).
7. ⌈400 ÷ 32⌉ = **13번째** 창(416ms)에서 END입니다. 실린 무음은 한 창 늦으므로 200을 처음 넘는 값(224)은 8번째 창이 싣고, 그때 예측을 요청합니다. 13 − 8 = 5창, **160ms** 앞섭니다. 200ms면 ⌈6.25⌉ = 7번째 창에서 END가 나는데 그 창이 싣는 값은 192라, "말하는 중"이 풀리기 전에 조건을 채우지 못해 예측 요청이 나가지 않습니다. 그래서 세션은 250ms 미만을 거부합니다(실습 7번에서 확인).
8. 말하는 중 기준은 0.35보다 큰가입니다. 0.6 말(무음 0), 0.3 무음(32), 0.4 말(**0으로 되돌림**), 0.2 무음(32), 0.3 무음(64). 답은 **64ms**입니다. 쌓이는 것이 아니라 연속으로 세기 때문입니다. 조용한 상태라면 기준이 0.5 이상이라 0.6 하나만 말소리 창이고, 다음 창(0.3)에서 말 카운터가 0이 되므로 START가 나지 않습니다(연속 2창이 필요).
9. 막힌 동안 프레임이 밀렸다가 한꺼번에 처리되므로, END를 처리하는 `Date.now()`가 막힌 만큼 늦습니다. 빼 주는 것은 무음 256ms와 마지막 창 하나의 처리 시간뿐이라 `lastSpeakingTime`이 그만큼(실습: 약 +100ms) 늦게 찍히고, 그 시각부터 재는 턴 확정도 늦어지는데 말 끝 판단 메트릭(`now − lastSpeakingTime`)은 그만큼 작게 나옵니다. 경고는 창 하나의 처리 시간이 200ms를 넘을 때만 나는데, VAD가 입력을 기다리는 사이에 막히면 창 처리 시간에는 잡히지 않습니다.
