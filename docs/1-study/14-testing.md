# 14장. 테스트와 평가: 확률적인 시스템을 검증하는 법

일반 소프트웨어는 같은 입력에 같은 출력이 나옵니다. 음성 에이전트는 그렇지 않습니다. LLM은 매번 조금씩 다른 답을 하고, STT는 같은 문장도 다르게 적고, 턴 감지는 소리의 미세한 차이에 반응합니다. 이 장은 **결정적인 부분과 확률적인 부분을 나눠** 각각 맞는 방법으로 검증하는 전략을 다룹니다.

> (2026-11-06 추가) 이 장의 SDK 경로는 `agents/` = `node_modules/@livekit/agents/src/`(1.9.5), `plugin/` = `node_modules/@livekit/agents-plugin-anthropic/src/`(1.9.5), `sdk/` = 플러그인이 쓰는 `@anthropic-ai/sdk` 0.33.1의 `src/`입니다. 8·12장과 같은 약칭입니다. `vitest/`는 `node_modules/.pnpm/vitest@4.1.12_…/node_modules/vitest/dist/chunks/test.DNmyFkvJ.js`이고, vitest가 묶어 넣은 `@sinonjs/fake-timers`가 이 파일 안에 있습니다. 행 번호는 이 파일 기준이며, 파일 이름 끝의 해시는 vitest 버전마다 바뀝니다.

(2026-11-06 추가) 이번 판에서는 테스트 도구가 "한 줄 아래에서" 무엇을 하는지를 더했습니다. 가짜 시계가 12장의 이벤트 루프 어디를 바꾸고 call-guard 테스트가 왜 `Async` 판이어야 하는지, 가짜 서버 테스트의 한계와 시간·취소·바이트로 넓히는 법, 테스트 더블의 이름(이상 14-3절), 통과율을 숫자로 읽는 법(14-5절), SDK 테스트 도구로 이 레포의 에이전트를 실제로 한 턴 돌려 본 결과(14-6절), CI가 못 잡는 것(14-7절)입니다. 그 과정에서 세 곳을 바로잡았습니다. 14-3절에서 이 레포의 가짜 서버 테스트를 "계약 테스트"라고 부른 것은 그 말의 보통 뜻과 다르고, 14-5절의 "2회차에 점수가 내려갔다"는 표본 6개로는 우연과 구별되지 않으며, 14-6절의 `withMockTools`는 SDK 예시대로 쓰면 `Agent.create`로 만든 이 레포의 에이전트에 끼워지지 않습니다. 12장처럼 코드로 확인한 것, 잰 것(실측), 추정을 구분해 적었습니다. 실습 스크립트 네 개는 키 없이 돕니다([lab/14-fake-clock.mjs](lab/14-fake-clock.mjs), [lab/14-fake-server.mjs](lab/14-fake-server.mjs), [lab/14-pass-rate.mjs](lab/14-pass-rate.mjs), [lab/14-sdk-session.mjs](lab/14-sdk-session.mjs)). 실측은 모두 Apple M1 Pro, Node 24.22에서 낸 값입니다. 깊은 내용은 "깊이 보기"에 두었으니 처음에는 건너뛰어도 됩니다.

(2026-11-08 추가) **이 장의 지도.** 먼저 낱말 둘을 정해 둡니다. **테스트**는 코드를 돌려 미리 정한 결과가 나오는지 자동으로 확인하는 일이고, 결과는 통과와 실패 둘 중 하나입니다. **평가**는 정답이 한 문장으로 정해지지 않는 출력(대화가 목표에 닿았는지, 목소리가 자연스러운지)을 기준에 비춰 채점하는 일입니다. 검증할 대상도 둘로 나뉩니다. **결정적**인 부분은 같은 입력이면 몇 번을 돌려도 같은 출력이 나오는 코드입니다(맞장구 떼기, 발음 변환). 한 번 통과하면 코드를 바꾸기 전까지 계속 통과합니다. **확률적**인 부분은 같은 입력에도 출력이 달라지는 부품입니다(LLM의 답, STT의 받아쓰기). 한 번 통과해도 다음에 통과한다는 보장이 없으므로 여러 번 돌려 비율로 봅니다. 이 장은 아래 차례로 갑니다. 한 줄이 절 하나이고, 왼쪽은 절 번호, 가운데는 그 절에서 확인하는 대상, `→` 오른쪽은 이 레포에서 쓰는 도구입니다.

```text
14-1  전체 그림: 어떤 층에서 무엇을 확인하나
14-2  결정적인 규칙                      → 단위 테스트 (vitest, 키 없음, 36개가 1초 남짓)
14-3  외부 API와의 경계, 시간이 얽힌 코드   → 가짜 서버·주입한 fetch, 가짜 세션·가짜 시계
14-4  대화 한 턴, 사람이 직접              → 에이전트 디버거 (lk agent debugger)
14-5  대화 전체                           → 시나리오 시뮬레이션 6개 + 판정 LLM, 통과율의 통계
14-6  대화 한 턴, 코드로 (아직 안 씀)       → SDK 테스트 도구 (session.run + FakeLLM)
14-7  머지 전 자동 검사                    → CI (GitHub Actions)
14-8  목소리·턴 테이킹                     → 실제 음성 통화, 사람 평가
14-9  정리
```

처음 읽을 때는 14-1 → 14-2 → 14-3 본문 → 14-4 → 14-5 본문 → 14-7 → 14-9 순서로 읽으면 흐름을 잡을 수 있습니다. "깊이 보기"(가짜 서버의 확장, 가짜 시계와 이벤트 루프, 통과율의 통계)와 14-6절은 나중에 읽어도 됩니다. 글 속의 `17-2 #n`은 [17-2절](17-glossary-and-next.md#17-2-이-책을-쓰며-코드에서-발견한-사항) 발견 사항 표의 n번 항목입니다.

## 이 장에서 쓰는 말 (2026-11-06 추가)

처음 보면 막히는 말만 모았습니다. (2026-11-08 갱신) 이번 판에서 테스트의 기본 말(단언, 결정적·확률적), 테스트의 종류, 평가와 통계의 말을 더해 주제별로 묶었습니다. 자세한 뜻은 괄호 안의 절에 있고, 전체 용어집은 [17-1절](17-glossary-and-next.md#17-1-용어집)입니다. 앞 장에서 나온 SSE(서버가 `event:`·`data:` 글 줄로 이벤트를 이어 보내는 스트리밍 방식, 8-6절)와 TTFT(요청부터 첫 토큰까지 걸린 시간, 13장)도 17-1절에 있습니다.

| 말 | 뜻 |
| --- | --- |
| 단언 (assertion) / 통과·실패 | 테스트 안에서 "실제 값이 기대와 같다"를 확인하는 한 줄입니다. vitest에서는 `expect(실제).toBe(기대)`입니다. 테스트 하나(`it(…)`) 안의 단언이 모두 맞으면 통과, 하나라도 틀리거나 예외가 나면 실패입니다. 테스트가 "깨진다"는 실패한다는 뜻입니다(14-2절) |
| 결정적 / 확률적 | 같은 입력이면 매번 같은 출력이 나옴 / 같은 입력에도 출력이 달라질 수 있음입니다. 맞장구 떼기는 결정적이고 LLM의 답은 확률적입니다(14-1절) |
| 흔들리는 테스트 (flaky test) | 코드를 바꾸지 않았는데 돌릴 때마다 통과와 실패가 바뀌는 테스트입니다. 14-6절 실습의 처음 판은 같은 코드로 20번 중 3번 실패했습니다 |
| 단위 테스트 / 통합 테스트 | 함수 하나처럼 작은 조각을 다른 부품과 떼어 시험함 / 여러 부품을 이어 붙인 채 시험함입니다. 이 레포의 테스트 36개 중 31개가 단위 테스트입니다(14-2절) |
| 좁은 통합 테스트 (narrow integration test) | 우리 코드와 외부 서비스를 잇는 코드까지만 진짜로 돌리고, 외부 서비스는 가짜로 두는 테스트입니다(Martin Fowler의 용어). `anthropic.test.ts`가 이것입니다(14-3절) |
| 계약 테스트 (contract test) | 두 시스템이 주고받는 형식(계약)을 확인하는 테스트입니다. 업계에서는 보통 양쪽이 같은 계약 파일로 각자를 검증하는 기법을 뜻하고, 이 책은 가짜 서버 테스트를 줄여 이렇게 부릅니다(14-3절) |
| 회귀 (regression) / 회귀 테스트 | 전에 되던 것이 변경 뒤에 안 되는 것 / 그것을 잡으려고 변경 때마다 다시 돌리는 테스트입니다. 이 레포의 단위 테스트와 시나리오 4회차가 그 역할입니다(14-5·14-7절) |
| 테스트 더블 (test double) | 테스트에서 진짜 부품 대신 끼우는 것의 총칭입니다. 영화의 대역 배우(stunt double)에서 온 말이고, 하는 일에 따라 dummy·stub·spy·mock·fake로 나눕니다(14-3절 끝) |
| 가짜 서버 | 진짜 외부 서비스 대신 테스트가 자기 컴퓨터 안(127.0.0.1)에 띄우는 작은 서버입니다. 미리 적어 둔 응답을 돌려주고 받은 요청을 기록합니다. `anthropic.test.ts`가 Anthropic API 대신 씁니다(14-3절) |
| 가짜 시계 (fake timers) | `setTimeout`·`Date` 같은 시간 함수를 테스트가 손으로 돌리는 시계로 바꾼 것입니다. vitest에서는 `vi.useFakeTimers()`로 켜고 `vi.advanceTimersByTime…`으로 흘려보냅니다(14-3절) |
| 포트 0 (임시 포트) | `listen(0)`이라고 하면 운영체제가 임시 포트(ephemeral port) 범위에서 비어 있는 번호를 골라 줍니다. 이 Mac의 범위는 49152∼65535입니다(`sysctl net.inet.ip.portrange`, 실측). 고른 번호는 `server.address().port`로 읽습니다(14-3절) |
| 골든 파일 (golden file) | 기대 출력을 파일로 저장해 두고 테스트가 그 파일과 비교하는 방법입니다. 출력이 바뀌면 사람이 차이를 보고 파일을 갱신합니다. vitest의 `toMatchFileSnapshot`이 같은 일을 합니다(14-3절) |
| 불변식 (invariant) / 속성 기반 테스트 (property-based testing) | 입력이 무엇이든 늘 성립해야 하는 성질 / 그 성질을 많은 입력(짧으면 가능한 입력 전부)으로 확인하는 테스트입니다. `ack.test.ts`는 답을 어디서 나눠 보내도 결과가 같은지를 3만 8,912가지 분할로 확인합니다(14-2절) |
| 변경 감지 테스트 (change-detector test) | 코드의 동작이 아니라 데이터의 지금 상태를 고정해, 고칠 것이 없는데도 실패하는 테스트입니다. 피할 모양입니다(14-2절) |
| 변이 테스트 (mutation testing) | 코드를 일부러 조금씩 망가뜨린 "변이"를 만들어 테스트가 그것을 잡는지(변이를 "죽이는지", 곧 테스트 가운데 하나라도 실패하는지) 보는 방법입니다. 테스트의 질을 재는 테스트입니다(14-2절) |
| 시나리오 / 시뮬레이션 | 가상 고객의 인물·대사·차례와 판정 기준을 적은 대본 하나(`scenarios.yaml`의 항목 하나) / 그 대본대로 가상 고객 LLM이 에이전트와 대화하게 하고 결과를 채점하는 실행입니다(14-5절) |
| LLM-as-a-judge (판정 LLM) | LLM으로 다른 LLM의 출력을 채점하는 방식입니다. "가격을 말하지 않는다"처럼 정규식으로 검사하기 어려운 기준을 뜻으로 판정하지만, 판정 LLM도 틀릴 수 있습니다(14-5·14-6절) |
| 에이전트 디버거 (`lk agent debugger`) | 에이전트를 내 컴퓨터에 띄워 두고 사용자 말을 명령 한 번에 한 턴씩 넣어, 답과 도구 호출을 찍어 보는 CLI 명령입니다. 코드에 중단점을 거는 디버거와는 다릅니다(14-4절) |
| 통과율 / 실패율 | 같은 시나리오를 여러 번 돌렸을 때 통과하는 비율 p / 실패하는 비율 1 − p입니다. 10번 중 8번 통과면 관측 통과율 80%입니다(14-5절) |
| pass@k / pass^k | 같은 시나리오를 k번 돌려 한 번이라도 통과 / k번 모두 통과입니다. 통과율이 p면 각각 1 − (1 − p)^k, p^k입니다. `lk agent simulate --samples`가 둘 다 보고하는데, 묶음 전체에서 그런 시나리오가 몇 할인지로 보고합니다(14-5절) |
| 신뢰 상한 (upper confidence bound) | 관측 결과와 맞는 값 가운데 가장 나쁜 값입니다. "실패율의 95% 상한이 39%"는 실패율이 39%보다 큰 시나리오가 이런 결과를 낼 확률이 5% 미만이라는 뜻입니다(14-5절) |
| 3의 규칙 (rule of three) | n번 시도해 한 번도 실패하지 않았을 때 실패율의 95% 상한을 3/n으로 어림하는 규칙입니다. ln 0.05 ≈ −3에서 나옵니다(14-5절) |
| 부호 검정 / 순열 검정 | 짝지은 비교에서 결과가 갈린 쌍 가운데 한쪽이 이긴 쌍의 수를 동전 던지기(이항분포)에 대 보는 방법 / 두 묶음을 섞어 아무렇게나 다시 나눌 때 관측한 차이 이상이 얼마나 자주 나오는지로 우연인지 보는 방법입니다(13-6절, 14-5절 깊이 보기) |
| 생존자 편향 (survivorship bias) | 끝까지 남은 것만 보고 판단해 생기는 치우침입니다. 느려서 취소된 턴이나 실패한 회차를 기록에서 빼면 결과가 실제보다 좋아 보입니다(13-5절, 14-2·14-5절) |
| frozen lockfile | lockfile을 고치지 않고, `package.json`과 맞지 않으면 설치를 멈추는 설치 방식입니다. pnpm은 CI 환경에서 이것을 기본으로 켭니다(14-7절) |

## 14-1. 무엇을 어떻게 검증하나: 층별 전략

(2026-11-08 추가) 이 절은 검증 방법 전체를 한 그림에 놓습니다. 검증 방법마다 무엇을 진짜로 돌리는지, 한 번 돌리는 데 시간과 돈이 얼마나 드는지, 같은 결과가 다시 나오는지가 다릅니다. 그래서 방법을 층으로 쌓아 두고, 확인할 것마다 그것을 확인할 수 있는 가장 아래층을 고릅니다.

```text
                 ▲ 비용·시간·불확실성
  사람 평가       │  상담팀 블라인드 청취, 실제 통화 검수
  실제 음성 통화   │  lk agent console / Agent Console (맞장구, 끼어들기, 발음)
  시뮬레이션      │  가상 고객 LLM + 판정 LLM (scenarios.yaml)
  디버거          │  텍스트로 몇 턴 직접 (lk agent debugger)
  계약 테스트      │  가짜 API 서버·주입한 fetch로 요청 검사 (anthropic.test.ts, index.test.ts)
  단위 테스트      │  순수 함수 (ack, pronunciation, transcript, prompt, call-result), 가짜 세션·시계 (call-guard)
                 ▼ 빠름·싸고·결정적
```

(2026-11-08 추가) **그림 읽는 법.** 한 줄이 검증 방법 하나입니다. `│` 왼쪽은 층 이름, 오른쪽은 이 레포에서 쓰는 도구와 대상입니다. 세로 화살표는 위로 갈수록 한 번 돌리는 비용과 시간, 결과의 불확실성이 커지고, 아래로 갈수록 빠르고 싸고 결정적이라는 뜻입니다. 숫자로 보면 아래 두 층의 테스트 36개는 키 없이 1초 남짓에 끝나고, 12번 돌려 12번 모두 36개가 통과했습니다(실측, 14-2절). 시뮬레이션은 실행마다 LLM 셋(가상 고객, 우리 에이전트, 판정)의 토큰 값이 들고, 같은 시나리오도 돌릴 때마다 결과가 다를 수 있습니다(14-5절). 맨 위 두 층은 사람의 시간이 듭니다.

원칙은 일반 소프트웨어의 **테스트 피라미드**와 같습니다. 테스트 피라미드는 빠르고 싼 아래층 테스트를 많이, 느리고 비싼 위층 테스트를 적게 두라는 그림입니다. 이 레포도 단위·계약 테스트 36개, 시나리오 6개, 사람이 하는 음성 확인 몇 번으로 아래가 넓습니다. **결정적으로 검증할 수 있는 것은 최대한 아래층으로 내립니다.** 그래서 이 프로젝트는 확률적인 LLM 주변의 규칙(맞장구 제거, 발음 변환, 오인식 보정, 프롬프트 구조)을 모두 **순수 함수로 떼어 내** 단위 테스트합니다. 순수 함수는 같은 입력이면 늘 같은 값을 돌려주고 시계·네트워크 같은 바깥 상태를 건드리지 않는 함수입니다. 1장의 원칙 1("확실해야 하는 것은 코드로")이 테스트 가능성까지 높여 주는 셈입니다.

## 14-2. 단위 테스트 (vitest)

(2026-11-08 추가) **단위 테스트**(unit test)는 프로그램의 작은 조각(대개 함수 하나)을 다른 부품과 떼어 놓고, 정해 둔 입력을 넣어 기대한 출력이 나오는지 확인하는 코드입니다. 이 레포는 **vitest**를 씁니다. vitest는 테스트 실행기(test runner)로, 레포 안의 `*.test.ts` 파일(지금은 모두 `src/` 아래)을 찾아 그 안의 `it('이름', …)` 하나하나를 실행합니다. `it` 안의 단언 `expect(실제).toBe(기대)`가 모두 맞으면 그 테스트는 통과, 하나라도 틀리거나 예외가 나면 실패입니다. 예를 들어 `transcript.test.ts`의 `expect(correctTranscript('투자하려고요')).toBe('투자하려고요')`는 보정 함수가 이 문장을 건드리지 않아야 통과합니다. 실패가 하나라도 있으면 `pnpm test`는 0이 아닌 종료 코드로 끝나고, CI(14-7절)는 그 단계를 실패로 표시합니다. 이 프로젝트에서 단위 테스트가 맡는 것은 LLM 주변에 코드로 박아 둔 규칙(맞장구 떼기, 발음 변환, 오인식 보정, 지시문 구조, 무응답 처리)입니다. 이 규칙들은 결정적이라 한 번 맞게 짜 두면 키도 돈도 없이 매번 같은 결과로 지킬 수 있습니다.

### 좋은 단위 테스트의 특징 (이 프로젝트에서 배울 점)

1. **실측에서 나온 입력을 그대로 씁니다.** `transcript.test.ts`의 "실측에서 나온 오인식을 바로잡는다"는 [5-poc-results.md](../5-poc-results.md)의 STT 결과 문장입니다. 상상한 입력보다 실제로 일어난 입력이 가치가 큽니다.
2. **"해야 할 것"과 "하면 안 되는 것"을 짝으로 둡니다.** 보정 테스트 옆에 "백만 원", "투자하려고요", "MP3"처럼 **오탐이 날 만한 문장**을 둡니다. 오탐(false positive)은 바꾸면 안 되는 말을 바꾸는 것입니다. 예를 들어 보정식이 앞의 "메탈"을 확인하지 않고 "백"만 보면 "백만 원"이 "팹만 원"이 됩니다. 고쳐야 할 문장만 시험하면 이렇게 지나치게 바꾸는 코드도 통과하므로, 정규식 기반 코드는 하면 안 되는 쪽의 문장이 함께 있어야 "필요한 곳에서만 바꾼다"까지 확인됩니다.
3. **성질(property)을 테스트합니다.** "여러 번 적용해도 같다"(멱등성), "고객 이름이 달라도 지시문 앞부분이 같다"(캐시 접두사)처럼, 특정 출력값이 아니라 **지켜야 할 규칙**을 검증합니다. 코드를 고쳐도 의도가 지켜지는지 보여 줍니다.
4. **테스트 이름이 요구 사항입니다.** "AI 상담사와 녹음 사실을 알리고 기기 이름은 한글 발음으로 읽는다"는 그대로 업무 요구 사항 문장입니다.

(2026-11-08 추가) **3번을 끝까지 밀고 간 예: 모든 분할을 시험하기.** LLM의 답은 토큰 조각으로 나뉘어 오고, 어디서 나뉠지는 그때그때 다릅니다. 그래서 답 첫머리의 맞장구를 떼는 `withoutLeadingAck`([src/ack.ts](../../src/ack.ts))가 지켜야 할 불변식은 "답이 어디서 나뉘어 와도 결과가 같다"입니다. `ack.test.ts`의 "어디서 나뉘어 와도 결과가 같다"는 이 성질을 골라 둔 분할 몇 개가 아니라 **가능한 분할 전부**로 확인합니다. 이렇게 성질을 많은(여기서는 모든) 입력으로 확인하는 방식이 속성 기반 테스트입니다.

- 글자가 n개인 글은 글자 사이 틈이 n − 1곳이고, 틈마다 자르거나 말거나 두 가지이므로 나누는 방법이 2^(n−1)가지입니다. "알겠습니다. 감사합니다. 예산은요?"(19글자)면 2^18 = 262,144가지입니다.
- 테스트는 앞 15글자 안의 틈 14곳만 전부 시험합니다(2^14 = 16,384가지). 판단이 그 안에서 끝나기 때문입니다. 떼는 맞장구는 두 개까지이고, 이 테스트의 입력에서 가장 긴 둘("알겠습니다. 감사합니다. ")이 14글자라 그다음 글자 하나가 오면 판단이 섭니다. 판단한 뒤에는 조각을 손대지 않고 흘려보내므로 뒤쪽 분할은 결과를 바꾸지 못합니다.
- 입력은 6개입니다(맞장구 둘이 겹친 답 둘, 맞장구 하나인 답, "네일"·"아니요"처럼 맞장구로 시작하는 듯한 말, 맞장구가 없는 말). 모두 합쳐 3만 8,912가지를 넣고, 하나라도 기대와 다르면 그 분할을 `|`로 이어 실패 메시지에 보입니다. 한 번에 약 0.5초 걸립니다(실측).
- 이 테스트는 17-2 #43(12글자를 모은 뒤 판단해 겹친 맞장구를 못 떼던 버그)을 고칠 때 들어왔습니다. 그 버그는 조각이 12글자 앞뒤로 끊길 때만 드러나서, 분할 하나를 손으로 고른 예전 테스트로는 보이지 않았습니다. 경우의 수와 시드 고정 무작위 분할은 [12-7절 깊이 보기](12-streams-async.md#깊이-보기-분할을-전부-넣어-보기전수-검사와-시드-고정-무작위-분할-2026-11-06-추가)에 있습니다.

바로 아래 테스트 "맞장구가 아니면 첫 두 글자 안에 내보낸다"는 다른 성질, 곧 **기다림의 상한**을 봅니다. 맞장구인지 판단하려고 글을 모아 두는 동안 TTS는 말을 시작하지 못하므로, 본론으로 바로 들어가는 답을 오래 붙잡으면 안 됩니다. 테스트의 가짜 입력은 "예", "산"을 차례로 내고, 세 번째 조각을 달라고 하면 오류를 던집니다. 필터가 "예산"을 내보내기 전에 세 번째 조각을 읽으려 하면 오류가 먼저 나서 받은 것이 비고, 테스트가 실패합니다. 이렇게 "여기까지 오면 안 된다"는 자리에 오류를 심어 두면 결과뿐 아니라 **몇 조각을 읽고 나서 내보냈는지**까지 확인할 수 있습니다. "예" 한 글자만으로는 맞장구 "예"와 구별되지 않으므로, 두 글자째에 내보내는 것이 가능한 가장 빠른 경우입니다.

### 사례: 데이터의 지금 상태를 고정한 테스트 (2026-11-04 추가)

학습서 6차 갱신(2026-11-03, [CHANGELOG](CHANGELOG.md)) 때 `prompt.test.ts`에서 이런 단언을 발견했습니다(17-2 #22).

```ts
expect(loadKnowledge()).toBe('');   // 실제 knowledge/xtool.md가 비어 있다
```

그때는 통과했습니다. 그런데 이 단언이 고정하는 것은 **코드의 동작이 아니라 데이터 파일의 지금 상태**입니다. 상담팀이 `knowledge/xtool.md`에 매장 위치 한 줄을 적는 순간, 코드는 그대로인데 CI가 실패합니다. 이런 테스트를 **변경 감지 테스트**(change-detector test)라고 부르며 피해야 할 모양으로 꼽습니다. 고칠 것이 없는데 실패하니 사람들이 실패에 익숙해지고, 결국 진짜 실패도 무시하게 됩니다.

고치는 방법은 "그 단언으로 정말 지키고 싶었던 것"을 찾는 것이었습니다.

| 지키고 싶은 것 | 테스트 |
| --- | --- |
| 작성 안내 주석만 있는 템플릿은 빈 지식이 된다 | `cleanKnowledge`에 **템플릿 모양의 입력**을 직접 줌 (`'<!--\n작성 안내\n-->\n'` → `''`) |
| 실제 파일을 읽어도 작성 안내가 지시문으로 새지 않는다 | `loadKnowledge()` 결과에 `<!--`와 안내 문구("상담팀이 채웁니다")가 **없음** |

둘째 테스트는 **내용이 무엇이든 성립해야 하는 성질**(불변식)을 봅니다. 상담팀이 내용을 채워도 통과하고, 누가 주석을 닫지 않고 저장하면 실패합니다. 주석이 닫히지 않으면 `cleanKnowledge`의 정규식 `<!--[\s\S]*?-->`가 맞지 않아 안내문 전체(지금 템플릿은 26줄, 585자)가 지시문에 들어가므로(9-2⑨), 이 테스트는 **실제로 일어날 수 있는 사고가 나면 실패해서 알려 주는** 테스트가 됐습니다. 위의 3번 "성질을 테스트합니다"를 데이터 파일에 적용한 셈입니다.

테스트를 바꾼 뒤에는 **새 테스트가 정말 그 차이를 구분하는지** 따로 확인했습니다. 템플릿 끝에 내용을 붙인 입력은 통과하고, 닫히지 않은 주석은 실패하는지 직접 돌려 봤습니다. 통과만 확인하면 "아무것도 보지 않는 테스트"와 구별되지 않습니다. 같은 생각을 코드 쪽에서 체계화한 것이 **변이 테스트**(mutation testing)입니다. 코드를 일부러 조금씩 망가뜨려 테스트가 그것을 잡는지 봅니다. 14-3절의 call-guard 테스트에서 "고치기 전에 먼저 실패하는 것을 확인"한 것도 같은 질문입니다.

(2026-11-08 추가) **변이 테스트를 손으로 한 번 해 보면.** 변이(mutant)는 코드 한 곳을 일부러 바꾼 사본입니다. 그 사본으로 테스트를 돌려 하나라도 실패하면 변이를 "죽였다(kill)", 모두 통과하면 "살아남았다"고 합니다. `src/ack.ts`의 사본에 변이 셋을 손으로 만들어 `ack.test.ts`(테스트 9개)를 돌려 봤습니다(레포 밖 임시 폴더, 실측). 표는 한 줄이 변이 하나이고, "실패한 테스트"는 그 변이를 넣었을 때 실패한 테스트입니다.

| 변이 | 바꾼 곳 | 실패한 테스트 | 결과 |
| --- | --- | --- | --- |
| ① 맞장구를 하나만 뗌 | `MAX_ACKS = 2` → `1` | 3개: "실측에서 나온 첫머리 맞장구를 뗀다", "떼고 나면 남는 말이 없으면 그대로 둔다", "어디서 나뉘어 와도 결과가 같다" | 죽음 |
| ② 첫 조각에서 바로 판단 | `if (!undecided(held))` → `if (true)` | 3개: "토큰으로 나뉘어 와도 첫머리 맞장구만 뗀다", "어디서 나뉘어 와도 결과가 같다", "맞장구가 아니면 첫 두 글자 안에 내보낸다" | 죽음 |
| ③ "네일"의 "네"도 맞장구로 봄 | 정규식에서 "네"·"예" 등 뒤에 공백이나 문장 부호가 오는지 보는 검사(lookahead)를 지움 | 5개 ("맞장구가 아닌 말은 건드리지 않는다" 포함) | 죽음 |

셋 다 죽었으므로 이 세 곳은 지금 테스트가 지키고 있습니다. 변이 테스트 도구(JavaScript에서는 Stryker 등, 이 레포는 쓰지 않음)는 이런 변이를 코드 전체에서 자동으로 수백 개 만들고, 살아남은 변이를 보여 줍니다(일반론). 살아남은 변이는 테스트가 비어 있는 곳이거나, 바꿔도 동작이 같은 변이(등가 변이)입니다.

(2026-11-06 추가) 이번 판의 실습도 같은 질문을 했는데, 코드 대신 **테스트 쪽**을 망가뜨렸습니다. call-guard 테스트의 흘려보내기를 동기 판으로 바꾸면 실패하는지(14-3절 깊이 보기, 실패함), 가짜 도구를 잘못된 생성자로 끼우면 테스트가 알아채는지(14-6절, 순서만 단언하면 못 알아챔), 테스트 파일에 타입 오류를 넣으면 CI가 잡는지(14-7절, 못 잡음)입니다. 테스트가 통과하는 것만으로는 그 테스트가 무엇을 지키는지 알 수 없다는 점은 테스트 코드에도 똑같이 적용됩니다.

## 14-3. 계약 테스트: 가짜 서버로 바이트를 검사하기

(2026-11-08 추가) 이 절은 진짜 부품 대신 가짜를 끼워 시험하는 방법 세 가지를 다룹니다. **가짜 서버**는 진짜 외부 서비스(여기서는 Anthropic API) 대신 테스트가 자기 컴퓨터 안(127.0.0.1)에 띄우는 작은 HTTP 서버입니다. 진짜처럼 요청을 받아 미리 적어 둔 응답을 돌려주고, 받은 요청을 기록해 두었다가 테스트가 검사하게 합니다. **주입한 fetch**는 서버를 띄우지 않고, SDK가 요청을 보낼 때 부르는 함수 자체를 테스트가 만든 함수로 바꿔 끼우는 방법입니다(아래 깊이 보기의 비교). **가짜 세션과 가짜 시계**는 SDK의 세션 객체와 시간 함수를 흉내 내, 10초·8분이 걸리는 코드를 기다리지 않고 시험합니다. 이 프로젝트에 이런 가짜가 필요한 이유는, 확인하고 싶은 것이 우리 코드와 바깥 세계 사이의 경계(실제로 나가는 HTTP 요청, 시간이 흐르며 일어나는 일)에 있는데 진짜 바깥 세계를 쓰면 키와 돈이 들고 느리며 결과가 매번 다르기 때문입니다. 절 끝에서 이런 가짜들의 정확한 이름(테스트 더블)을 정리합니다. 절 제목의 "계약 테스트"는 이 책의 줄임말이고, 정확한 이름은 아래에서 보듯 좁은 통합 테스트입니다.

[src/models/anthropic.test.ts](../../src/models/anthropic.test.ts)는 이 프로젝트에서 가장 배울 것이 많은 테스트입니다.

### 문제

`VoiceAnthropicLLM`이 `extraKwargs`로 넣은 값이 **정말로 HTTP 요청 본문에 들어가는지** 어떻게 확인할까요? 진짜 API를 부르면 키와 돈이 들고, 결과가 확률적이며, 요청 본문을 볼 수도 없습니다. 플러그인 내부를 모킹(mock)하면 플러그인이 바뀌어도 테스트가 통과해 버립니다. 모킹은 진짜 함수나 객체를 테스트용 가짜로 바꿔치기하는 것입니다(이 절 끝의 "테스트 더블"). 예를 들어 플러그인의 `chat` 함수를 가짜로 바꿔 "우리가 `extraKwargs`를 넘겼다"만 확인하면, 다음 버전의 플러그인이 `extraKwargs`를 본문에 펼치지 않게 바뀌어도 테스트는 그대로 통과합니다. 실제 요청에서는 `thinking: disabled`가 빠져 생각 모드가 켜진 채(Haiku 5.5의 기본값, 8장) 나가는데도 말입니다.

### 해법: 경계에서 가로채기

(2026-11-08 추가) 여기서 경계는 우리 프로세스가 바이트를 네트워크로 내보내는 자리, 곧 HTTP 요청입니다. 가로챈다는 것은 그 자리에 진짜 서버 대신 가짜 서버를 세워, 나가는 바이트를 그대로 받아 보는 것입니다.

```ts
beforeAll(async () => {
  server = createServer((req, res) => {          // ① 진짜 HTTP 서버를 로컬에 띄움
    let raw = '';
    req.on('data', (chunk) => (raw += chunk));
    req.on('end', () => {
      lastBody = JSON.parse(raw);                 // ② 받은 요청 본문을 기록
      res.writeHead(200, { 'content-type': 'text/event-stream' });
      res.end(RESPONSE);                          // ③ Anthropic처럼 SSE 응답을 흉내
    });
  });
  await new Promise<void>((resolve) => server.listen(0, '127.0.0.1', resolve));   // 포트 0 = 빈 포트 아무거나
  baseURL = `http://127.0.0.1:${(server.address() as AddressInfo).port}`;
});
```

발췌에서는 HEAD 요청을 받는 분기(49∼54행, 14-2절 표의 `prewarmUrl` 테스트용)를 뺐습니다. `RESPONSE`는 `sse()`(11∼15행)가 이벤트 객체 목록을 `event: 종류\ndata: JSON\n\n` 모양의 글로 이어 붙여 만든, Anthropic의 스트리밍 응답(8-6절) 흉내입니다.

```ts
const model = new VoiceAnthropicLLM({ model: 'claude-haiku-5-5', apiKey: 'test', baseURL, … });
const res = await model.chat({ chatCtx: chatCtx() }).collect();

expect(lastBody.thinking).toEqual({ type: 'disabled' });     // 실제로 나간 바이트를 검사
expect(lastBody.output_config).toEqual({ effort: 'low' });
expect(lastBody.cache_control).toEqual({ type: 'ephemeral' });
expect(lastBody).not.toHaveProperty('temperature');
expect(res.text).toBe('네, 좋아요.');                         // 생각 블록이 섞이지 않음
```

이 테스트는 **우리 코드 + 플러그인 + Anthropic SDK + HTTP 클라이언트를 모두 진짜로** 거칩니다. 가짜인 것은 네트워크 건너편의 서버뿐입니다. 그래서 두 가지가 됩니다.

- 플러그인 버전을 올려 `extraKwargs` 처리가 바뀌면 테스트가 실패해서 알려 줍니다. 예를 들어 `thinking`이 본문에서 빠지면 `expect(lastBody.thinking).toEqual({ type: 'disabled' })`가 `undefined`를 받아 실패하고, `pnpm test`가 0이 아닌 종료 코드로 끝나 CI가 빨간불이 됩니다.
- API 키도, 비용도, 확률성도 없습니다. 키는 `'test'`라는 가짜 값이고, 서버는 늘 같은 응답을 돌려줍니다.

(2026-11-06 갱신) 처음에는 이 기법을 **계약 테스트**(contract test)라고 불렀는데, 그 말은 보통 다른 것을 가리킵니다.

- 업계에서 계약 테스트라고 하면 Pact 같은 도구로 하는 **소비자 주도 계약 테스트**(consumer-driven contract test)를 뜻하는 경우가 많습니다. 소비자(API를 부르는 쪽, 여기서는 우리)가 "이런 요청에 이런 응답을 기대한다"를 계약 파일로 남기고, 제공자(API를 만드는 쪽)도 **같은 파일로** 자기 서버를 검증합니다. 양쪽이 같은 계약을 시험하므로, 제공자가 형식을 바꾸면 제공자 쪽 CI의 계약 테스트가 먼저 실패합니다.
- Martin Fowler는 이 말을 조금 다르게, "가짜(테스트 더블)가 아직 진짜와 같게 동작하는지 진짜 서비스를 불러 확인하는 테스트"라는 뜻으로 썼습니다. 이쪽도 진짜 서비스를 부릅니다.
- 이 레포의 테스트는 둘 다 아닙니다. Anthropic은 우리 계약 파일로 자기 서버를 시험해 주지 않고, 이 테스트는 진짜 서버를 한 번도 부르지 않습니다. 정확한 이름은 Fowler가 말하는 **좁은 통합 테스트**(narrow integration test)입니다. 우리 코드와 외부 서비스를 잇는 코드(플러그인·SDK·HTTP 클라이언트)는 진짜로 돌리고, 건너편 서버만 가짜로 둡니다.

이 책에서는 계속 줄여서 "계약 테스트"라고 부르되, 아래 깊이 보기처럼 **건너편이 바뀌는 것은 잡지 못한다**는 점을 기억해 둡니다. SSE 응답을 직접 만드는 `sse()` 함수는 8-6절의 스트리밍 이벤트 구조를 그대로 보여 주는 교재이기도 합니다.

포트 0으로 listen하는 것도 작은 요령입니다. 운영체제가 비어 있는 포트를 골라 주므로 테스트끼리 포트가 충돌하지 않습니다. (2026-11-06 추가) 운영체제는 포트 번호 0을 "아무 데나"로 받아 임시 포트 범위(이 Mac은 49152∼65535, 실측)에서 빈 번호를 줍니다. 그래서 테스트는 번호를 미리 알 수 없고, `listen`이 끝난 뒤 `server.address().port`로 읽어 `baseURL`을 만듭니다(64행). vitest는 테스트 파일을 여러 작업자에서 동시에 돌리므로, 고정 번호(예: 8080)를 쓰면 두 파일이 같은 번호를 잡으려다 `EADDRINUSE`로 실패할 수 있습니다.

#### 깊이 보기: 가짜 서버 테스트의 한계와 확장(골든 파일, 시간, 취소, 바이트) (2026-11-06 추가)

**한계: 건너편은 우리가 쓴 대로다.** 가짜 서버가 돌려주는 `RESPONSE`는 사람이 손으로 쓴 SSE입니다([src/models/anthropic.test.ts](../../src/models/anthropic.test.ts) 18∼40행). 그래서 이 테스트가 지키는 것은 "우리 코드가 **우리가 알고 있는** Anthropic 형식을 올바로 다룬다"까지입니다.

- Anthropic이 형식을 바꿔도(새 이벤트 종류, 필드 이름) 테스트는 그대로 통과합니다. 테스트 안의 형식은 바뀌지 않았기 때문입니다. 이 경우 운영에서 처음 드러납니다.
- 손으로 쓴 형식이 처음부터 실제와 조금 달라도 통과합니다. 예를 들어 이 테스트의 생각 블록은 `thinking_delta` 하나 뒤에 `signature_delta` 하나인데, 실제 Haiku 5.5가 이 순서와 개수로 보내는지는 테스트가 말해 주지 않습니다(이 장에서 실제 응답을 녹화해 보지는 않음).
- 요청 쪽도 같습니다. `output_config.effort`가 본문에 들어가는 것은 확인하지만, 실제 API가 그 필드를 받아 주는지는 모릅니다. 그것은 `pnpm check:llm`처럼 진짜 API를 부르는 스크립트가 확인합니다.

**제안: 진짜 응답을 한 번 녹화해 골든 파일로.** 이 레포에는 없는 방법입니다.

1. 키를 가진 개발자가 한 번, 테스트와 같은 요청을 실제 API에 보내고 받은 SSE 바이트를 그대로 파일로 저장합니다(예: `src/models/__fixtures__/haiku-5-5-thinking-off.sse`). 공개 저장소이므로 메시지 `id`, `request-id` 머리글 같은 값은 가립니다.
2. 가짜 서버는 손으로 쓴 `RESPONSE` 대신 이 파일을 돌려줍니다. 이제 테스트는 "실제로 한 번 관측된 형식"을 시험합니다.
3. 모델·SDK·플러그인을 올릴 때 다시 녹화해 이전 파일과의 **차이**(diff)를 봅니다. 그 차이가 곧 공급사가 바꾼 것입니다. 녹화를 정기적으로(예: 주 1회) 돌려 차이가 나면 알리게 하면 Fowler가 말한 의미의 계약 테스트가 됩니다. 키·비용·확률성 때문에 PR마다 도는 CI에는 넣지 않습니다.
4. 요청 쪽은 vitest의 `toMatchFileSnapshot`으로 "우리가 보내는 본문"을 골든 파일로 둘 수 있습니다. 지시문 한 글자만 바뀌어도 차이가 나므로, 캐시 접두사(8장)를 깨는 변경을 PR 리뷰에서 바로 보게 됩니다. 대신 지시문을 고칠 때마다 `vitest -u`로 갱신해야 하므로, 14-2절의 변경 감지 테스트가 되지 않게 **고정해야 하는 부분(구조·옵션·도구 정의)만** 떼어 스냅숏합니다.

**확장: 시간·취소·바이트를 시험에 넣기.** 지금의 가짜 서버는 `res.end(RESPONSE)`로 응답 전체를 한 번에 씁니다. 실제 서버는 이벤트를 시간을 두고 하나씩 쓰고, 클라이언트는 중간에 끊을 수 있으며, TCP는 바이트를 아무 데서나 나눕니다. [lab/14-fake-server.mjs](lab/14-fake-server.mjs)가 이 셋을 같은 모양의 가짜 서버(127.0.0.1, 포트 0)에 넣어 실제 `VoiceAnthropicLLM`으로 돌렸습니다(실측, 시각은 요청 도착 기준).

```text
1. 시간: 서버가 res.write로 이벤트를 하나씩 씀
   이벤트를 하나씩 씀                    쓴 시각 "네, " 200ms, "예산은…" 400ms → 받은 시각 404ms, 606ms
   이벤트마다 SSE 주석 ": k\n"을 덧붙임   쓴 시각 같음                       → 받은 시각 208ms, 405ms
```

- 글 조각이 자기를 쓴 시각이 아니라 **다음 이벤트를 쓴 시각**에 나옵니다. SDK 0.33.1의 SSE 분리기가 버퍼 맨 끝의 `\n\n`을 보지 못하는 문제(17-2 #36, 12-5절 깊이 보기)가 플러그인 경로 전체에서 그대로 보이는 것입니다. 이벤트 뒤에 바이트 몇 개(SSE 주석 한 줄. SDK의 해석기는 `:`로 시작하는 줄을 버림, `sdk/streaming.ts` 329)만 붙이면 제때 나오는 것이 원인 확인입니다. 8장 실습은 SDK만 떼어 같은 현상을 쟀습니다([8-6절](08-llm.md)). 받은 시각은 실행마다 몇 ms씩 다릅니다(2026-11-08에 다시 돌린 값은 402·604ms와 202·402ms).
- 테스트로 옮기면 "첫 글 조각은 서버가 쓴 뒤 50ms 안에 나온다" 같은 단언 하나가 이 지연을 잡습니다. 지금 이 레포에 넣으면 **실패하는** 테스트입니다. vitest의 `it.fails`(테스트가 실패해야 통과로 침)로 "알려진 버그"를 적어 두면, 플러그인이 고쳐진 SDK로 올라가는 날 그 테스트가 실패해 알려 줍니다.

```text
2. 취소: 첫 글 조각을 받자마자 취소
   플러그인 경로 (LLMStream.close())          취소 204ms → 서버가 쓴 묶음 10/10, finish 952ms, close 952ms → 응답을 끝까지 씀
   비교: SDK 0.33.1을 직접 쓰고 for await break  취소 200ms → 서버가 쓴 묶음 3/10, finish 없음, close 202ms → 클라이언트가 먼저 끊음
```

- 서버 쪽에서는 `res`의 `'close'`가 `'finish'`보다 먼저 오면(또는 `'finish'` 없이 오면) 클라이언트가 끊은 것입니다. 플러그인 경로는 끝까지 읽어 17-2 #41(12-8절 함정 2의 "취소가 HTTP까지 안 감")이 재현됩니다. 같은 SDK도 소비자가 `break`하면 2ms 만에 연결을 끊으므로(`sdk/streaming.ts` 83∼84, `finally`의 `controller.abort()`), 문제는 플러그인이 `signal`을 넘기지 않고 끝까지 읽는 데 있습니다.
- 테스트로 옮기면 "취소하면 서버가 쓴 묶음이 전체보다 적다"가 단언입니다. 이것도 지금은 실패합니다. 11-4절과 12-8절의 실습이 같은 현상을 손으로 확인했다면, 이 모양은 그것을 **CI가 계속 지켜보는** 회귀 테스트로 바꿉니다.

```text
3-A. 응답의 한글을 글자 중간에서 잘라 두 번에 씀 (20ms 간격)
   자른 자리 8곳("네"·"좋"·"아"·"요" 각각 1바이트 뒤, 2바이트 뒤) 중 res.text가 "네, 좋아요."인 경우 8/8

3-B. 요청 본문이 커지면: 가짜 서버의 data 이벤트와 raw += chunk     (2026-11-06 갱신: 17-2 #34 뒤 다시 잼)
   실제 지시문 (buildInstructions, 지식 없음)      7,360바이트  data  1번 [7360]            U+FFFD 0개
   지시문 + 한글 약 64KB                         75,360바이트  data  2번 [65065, 10295]     U+FFFD 0개, JSON.parse 성공
   지시문 + 한글 약 256KB                       292,960바이트  data  5번 [64856, 65536, …]  U+FFFD 9개, JSON.parse 성공
   지시문 + 한글 약 1MB                       1,163,360바이트  data 18번 [65063, 65536, …]  U+FFFD 23개, JSON.parse 성공
```

- 응답 쪽은 어디서 잘라도 안전했습니다. SDK가 `\n\n`까지 바이트로 모은 뒤 디코드하기 때문입니다(12-5절 깊이 보기). 지금은 통과하는 시험이지만, SDK가 바뀌어도 이 성질이 지켜지는지 보는 회귀 테스트로 둘 만합니다.
- 요청 쪽은 12-5절이 "몇 KB부터 나뉘는지는 재지 않아 추정"이라고 남긴 것을 이번에 쟀습니다. 3-B 출력의 `data N번 [...]`은 가짜 서버에 `data` 이벤트가 몇 번 왔고 앞쪽 조각이 각각 몇 바이트였는지, `U+FFFD n개`는 `raw += chunk`로 모은 글에 대체 문자가 몇 개 생겼는지입니다. 이 기계의 루프백에서는 본문이 약 64KiB(65,536바이트)를 넘자 `data` 이벤트가 나뉘었습니다. 첫 조각이 65,065바이트 안팎으로 조금 작은 것은 같은 64KiB 읽기에 HTTP 머리글이 먼저 들어가기 때문으로 봅니다(추정). 나뉜 자리가 한글 한가운데면 `raw += chunk`(테스트 55∼56행과 같은 모양)가 U+FFFD(UTF-8로 풀 수 없는 바이트 자리에 넣는 대체 문자 "�")를 넣었고, `JSON.parse`는 네 경우 모두 **성공**했습니다(17-2 #45). 개수는 실행마다 조금 다릅니다(256KB에서 2∼9개). (2026-11-06 갱신) 처음 판에서 64KB의 U+FFFD는 3개였습니다(경계 한 곳이 글자 첫 바이트 뒤에서 잘린 것). 17-2 #34로 지시문이 5바이트 줄자 같은 경계(65,065바이트째)가 글자 경계에 걸려 다시 잰 세 번 모두 0개였습니다. 깨지느냐가 본문 앞부분의 바이트 몇 개에 달려 있다는 뜻이고, 그래서 이런 버그는 우연히 숨었다가 무관한 변경으로 드러납니다. (2026-11-08 갱신) 다시 잰 일곱 번에서는 64KB 본문의 첫 조각이 65,065바이트(U+FFFD 0개) 네 번, 32,193바이트(2개) 두 번, 48,525바이트(3개) 한 번이었습니다. 256KB는 6∼9개, 1MB는 23∼32개였고 1MB의 `data` 이벤트 수도 18∼19번으로 달랐습니다(실측). 그러니 첫 조각은 늘 "64KiB 한 번 읽기"가 아니라, 서버가 소켓을 읽는 순간까지 도착해 있던 양(최대 약 64KiB)으로 보입니다(추정). 경계가 보내는 쪽과 읽는 쪽의 타이밍에 따라 옮겨 다니므로, 깨지느냐는 본문 앞부분의 바이트와 그 순간의 타이밍에 함께 달려 있습니다. 같은 코드로 어떤 실행은 0개, 어떤 실행은 3개가 나오는, 흔들리는 테스트의 전형적인 모양입니다.
- 지금 지시문(7.4KB)은 한 번에 오므로 이 레포의 테스트는 안전합니다. 지식 파일(`knowledge/xtool.md`)이 수십 KB로 커지고 그 지시문을 실은 테스트가 생기면 드러납니다.

**두 방식 비교: 로컬 HTTP 서버 vs fetch 주입.** [src/models/index.test.ts](../../src/models/index.test.ts)는 서버를 띄우지 않고 SDK 클라이언트에 `fetch` 함수를 주입합니다(`withOptions({ fetch })`). `VoiceAnthropicLLM`에도 SDK 0.33.1 클라이언트를 `client`로 넘기면 같은 방식을 쓸 수 있어서, 실습 4번에서 둘을 나란히 봤습니다(실측). 아래 표는 한 줄이 비교할 점 하나이고, 두 칸이 두 방식입니다.

```text
4-A. 응답 708바이트를 1바이트 조각 708개로: res.text "네, 좋아요."
     요청 본문은 fetch에 문자열(typeof string)로 넘어옴 → 바이트로 나뉘는 일 자체가 없음
4-B. 첫 글 뒤 LLMStream.close(): 응답 스트림 pull 10/10번, cancel 불림 false, fetch에 넘어온 signal.aborted false
```

| | 로컬 HTTP 서버 (`anthropic.test.ts`) | fetch 주입 (`index.test.ts`) |
| --- | --- | --- |
| 진짜로 거치는 코드 | 우리 코드 + 플러그인 + SDK + SDK의 HTTP 클라이언트 + 소켓. SDK 0.33.1은 Node에서 전역 fetch가 아니라 `node-fetch` 2.7.0과 `agentkeepalive`를 씁니다(`sdk/_shims/node-runtime.ts` 4·7·41∼42·68) | 우리 코드 + 플러그인 + SDK까지. HTTP 클라이언트부터 아래는 없음 |
| 요청 검사 | 서버가 받은 **바이트**(머리글·본문). 64KiB를 넘으면 조각으로 옴 | fetch에 넘어온 **값**(`init.body`는 문자열). 바이트로 나뉘지 않음 |
| 응답 조각 경계 | `res.write`로 나누지만 TCP가 합칠 수 있어, 경계를 지키려면 시간 간격을 둬야 함 | `ReadableStream`의 `enqueue` 단위로 **정확히** 정함(1바이트씩도 가능) |
| 시간 | 서버가 쓰는 시각을 정해 첫 글까지의 시간을 잼 | `pull` 안에서 기다려 흉내 냄 |
| 취소 | 서버의 `'close'`와 `'finish'` 순서로 연결이 끊겼는지 봄 | 응답 스트림의 `cancel`이 불렸는지, `init.signal.aborted`로 봄 |
| 준비 | 포트·서버 정리(`afterAll`) 필요 | 함수 하나 |

| 잘 맞는 경우 | 플러그인이 HTTP를 실제로 어떻게 쓰는지까지 볼 때 | SDK가 만든 요청 값(인증 머리글 등)만 볼 때, 바이트 경계를 정확히 시험할 때 |

`index.test.ts`가 fetch를 고른 것은 보고 싶은 것이 SigV4 서명 머리글 하나이고, Bedrock 주소를 그대로 둔 채 요청을 가로챌 수 있기 때문입니다. 반대로 위 2번의 "연결이 정말 끊겼나"는 소켓이 있어야 보이므로 로컬 서버 쪽이 맞습니다. fetch 주입으로도 4-B처럼 "끝까지 읽었다"(pull 10/10)는 보이지만, 그것이 실제 연결 종료로 이어지는지는 알 수 없습니다.

### 가짜 세션과 가짜 시계: 시간과 이벤트가 얽힌 코드 테스트하기 (2026-11-03 추가)

무응답 안전장치(`call-guard.ts`, 5-5절)는 "10초 동안 아무 일도 없으면"이라는 **시간**과 "고객 상태가 바뀌면"이라는 **이벤트**가 얽힌 코드입니다. 진짜 세션과 진짜 시간으로는 테스트할 수 없습니다(10초씩 기다리고, 상태를 마음대로 바꿀 수 없음). [src/call-guard.test.ts](../../src/call-guard.test.ts)는 둘 다 가짜로 바꿉니다. 가짜 세션(fake session)은 SDK의 `AgentSession` 대신 넘기는, 테스트가 만든 흉내 객체입니다. 가짜 시계는 `setTimeout` 같은 시간 함수를 테스트가 손으로 돌리는 시계로 바꾼 것이라, 테스트가 "10초 흘려보내기"를 부르면 실제로 10초를 기다리지 않고 10초 뒤에 울릴 타이머가 바로 실행됩니다(이 파일의 테스트 하나는 수 ms에 끝남, 실측).

```ts
/** guardCall이 쓰는 만큼만 흉내 낸 세션. "여보세요?" 재생이 끝나는 시점은 테스트가 정합니다. */
function fakeSession() {
  const emitter = new EventEmitter();
  let finishPlayout = () => {};
  const session = Object.assign(emitter, {
    userState: 'listening' as voice.UserState,
    say() {
      const played = new Promise<void>((resolve) => (finishPlayout = resolve));
      return { waitForPlayout: () => played };
    },
  });
  …
  guardCall(session as unknown as voice.AgentSession, endCall);
}
```

| 기법 | 하는 일 |
| --- | --- |
| **필요한 만큼만 흉내** | `guardCall`이 쓰는 것은 `on`(이벤트 구독), `say().waitForPlayout()`, `userState`뿐입니다. 진짜 `AgentSession` 전체를 만들 필요 없이 Node의 `EventEmitter`에 이 셋만 붙입니다. `as unknown as voice.AgentSession`으로 타입만 맞춥니다 |
| **재생 완료 시점을 테스트가 쥠** | `say()`가 돌려주는 Promise의 `resolve`를 바깥(`finishPlayout`)에 꺼내 둡니다. 테스트가 "지금 '여보세요?'가 끝났다"를 원하는 순간에 일으킬 수 있습니다 |
| **가짜 시계** | `vi.useFakeTimers()`로 `setTimeout`을 가짜로 바꾸고, `vi.advanceTimersByTimeAsync(10_000)`로 10초를 즉시 흘려보냅니다. (2026-11-06 갱신) `Async` 판은 시작하기 전과 가짜 타이머를 하나 실행할 때마다 진짜 이벤트 루프로 한 번씩 양보해, 그사이 Promise 후속 처리(`.then`)가 돌게 합니다. 이 테스트는 그것이 없으면 실패합니다(아래 깊이 보기) |
| **사건 순서를 그대로 적기** | `away` → `speaking`(대답) → 재생 끝 → `listening` 순서를 테스트에 그대로 씁니다. 버그가 "순서"에서 나오므로 순서를 적는 것이 곧 재현입니다 |

그리고 이 테스트는 **고치기 전에 먼저 썼습니다.** "'여보세요?' 도중에 대답하면 무응답으로 세지 않는다" 테스트가 실패하는 것(`endCall`이 1번 불림)을 확인한 뒤 코드를 고쳤고, 고친 뒤 통과했습니다. 버그를 재현하는 테스트를 먼저 쓰면 ① 버그가 진짜인지 확인되고 ② 고친 것이 맞는지 확인되며 ③ 나중에 같은 버그가 돌아오는 것을 막습니다. 실패하는 테스트를 먼저 쓰고(빨강) 코드를 고쳐 통과시키는(초록) 이 순서는 테스트 주도 개발(TDD)의 기본 순서이기도 합니다(9-7절). [AGENTS.md](../../AGENTS.md)가 "추측하지 말고 시나리오를 먼저 쓰라"고 한 것과 같은 원칙을 단위 테스트 수준에서 적용한 것입니다.

#### 깊이 보기: 가짜 시계는 이벤트 루프의 어디를 바꾸나 (2026-11-06 추가)

12-2절 깊이 보기의 그림(루프의 여섯 단계, 콜백마다 비우는 nextTick 큐와 마이크로태스크 큐)을 그대로 씁니다. 가짜 시계는 그 그림에서 **시간 쪽만** 바꾸고 **차례 쪽은 그대로** 둡니다. 이 차이가 call-guard 테스트의 `Async`를 설명합니다.

**무엇을 바꾸나 (코드로 확인).** vitest 4.1.12는 `@sinonjs/fake-timers`를 묶어 넣었습니다(vitest 패키지의 `LICENSE.md` 184행). `vi.useFakeTimers()`는 그 라이브러리가 아는 시간 함수 목록에서 두 개만 빼고 모두 가짜로 바꿉니다.

```js
// vitest/ 3299 (FakeTimers.useFakeTimers)
const toFake = Object.keys(this._fakeTimers.timers).filter(
  (timer) => timer !== 'nextTick' && timer !== 'queueMicrotask',
);
```

목록(`vitest/` 2036∼2085)은 `setTimeout`·`clearTimeout`·`setInterval`·`clearInterval`·`Date`·`setImmediate`·`clearImmediate`·`process.hrtime`(`bigint` 포함, 2165)·`performance`·`Intl`과, Node에는 없는 `requestAnimationFrame` 등입니다. [lab/14-fake-clock.mjs](lab/14-fake-clock.mjs) 1번이 vitest의 `vi`를 불러 전역 함수가 바뀌었는지 직접 비교했습니다(실측).

```text
setTimeout · setImmediate · setInterval · Date · performance.now · process.hrtime   가짜로 바뀜
process.nextTick · queueMicrotask                                                 진짜 그대로
진짜 30ms를 기다린 뒤: Date.now() 차 0ms, performance.now() 차 0ms   (흘려보내기 전까지 시계가 멈춰 있음)
```

Promise의 `.then`은 처음부터 이 목록에 없습니다. `.then`이 들어가는 V8의 마이크로태스크 큐는 JavaScript 함수 하나를 바꿔치기해서 손댈 수 있는 대상이 아니기 때문입니다. 아래 모든 차이가 여기서 나옵니다.

**두 흘려보내기 함수 (코드로 확인).**

| | `vi.advanceTimersByTime(ms)` | `vi.advanceTimersByTimeAsync(ms)` |
| --- | --- | --- |
| 부르는 것 | `clock.tick` → `doTick(ms, false)` (`vitest/` 3270∼3272, 2532∼2534) | `clock.tickAsync` → `doTick(ms, true, …)` (3273∼3275, 2541∼2552) |
| 시작 전 | 바로 시작 | `originalSetTimeout(…)`으로 한 번 양보한 뒤 시작 |
| 타이머 사이 | 쉬지 않고 범위 안의 타이머를 차례로 실행 | 타이머를 **하나** 실행할 때마다 `originalSetTimeout(nextPromiseTick)`으로 양보하고 일단 `return` (2449∼2454) |
| 돌려주는 것 | 숫자(새 가짜 시각) | Promise |

`originalSetTimeout`이 무엇인지가 핵심입니다.

```js
// vitest/ 2088 (fake-timers의 withGlobal: 가짜를 설치하기 전에 잡아 둠)
const originalSetTimeout = _global.setImmediate || _global.setTimeout;
```

Node에서는 **진짜 `setImmediate`입니다**. 그래서 `Async` 판의 "양보"는 진짜 루프를 check 단계까지 돌리는 것이고(12-2절), 그사이 콜백 하나가 끝날 때마다 nextTick 큐와 마이크로태스크 큐가 비워집니다. 동기 판도 시작할 때와 타이머마다 `runJobs`(1534∼1550)를 부르지만, 이것이 비우는 것은 fake-timers가 가로챈 `nextTick`·`queueMicrotask` 작업 목록(`clock.jobs`)뿐입니다. vitest 기본값은 그 둘을 가로채지 않으므로 이 목록은 늘 비어 있고, Promise의 `.then`은 동기 판이 끝나 테스트 함수가 `await`할 때까지 한 번도 돌지 못합니다.

**call-guard 첫 테스트를 단계별로.** 실습 2번은 실제 `guardCall`([src/call-guard.ts](../../src/call-guard.ts))에 테스트와 같은 가짜 세션을 붙이고, 단계마다 가짜 타이머 수와 가짜 시각을 찍었습니다(실측). 칸은 "타이머 수 / 가짜 시각 / `endCall` 횟수"입니다.

| 단계 | 일어나는 일 | `Async` 판 | 동기 판 |
| --- | --- | --- | --- |
| ① `fakeSession()` | `guardCall`이 최대 길이 타이머(8분)를 검(call-guard.ts 27행) | 1 / +0 / 0 | 1 / +0 / 0 |
| ② `setUserState('away')` | 듣는 함수가 `say('여보세요?')`를 부르고 `waitForPlayout().then(…)`을 걺(36∼37행) | 1 / +0 / 0 | 1 / +0 / 0 |
| ③ `finishPlayout()` | 재생 Promise가 풀림 → `.then` 콜백이 **마이크로태스크 큐에 들어감**. 아직 안 돎 | 1 / +0 / 0 | 1 / +0 / 0 |
| ④ 흘려보내기를 부른 직후 | `Async`: 진짜 `setImmediate`만 걸고 돌아옴. 동기: 범위 [+0, +10초] 안에 타이머가 없으니 시각만 옮기고 끝 | 1 / +0 / 0 | 1 / **+10000** / 0 |
| ⑤ 테스트가 `await`한 뒤 | 마이크로태스크가 돎: `.then`이 `userState === 'away'`를 보고 무응답 타이머를 "지금 + 10초"에 검(39∼43행). `Async`는 그다음 check 단계에서 `doTick`을 시작하고, 그 타이머가 범위(≤ +10초) 안이라 실행 | 1 / +10000 / **1** | **2** / +10000 / **0** |

- 동기 판의 무응답 타이머는 ⑤에서야 만들어지는데, 그때 가짜 시각이 이미 +10초라 **+20초**에 울립니다. 바로 다음 줄의 `expect(call.endCall).toHaveBeenCalledWith(…, 'no_response')`는 그 전에 검사하므로 실패합니다.
- ③ 직후에 넣어 둔 실습의 `queueMicrotask`는 두 판 모두 "타이머 2개"를 봤습니다. 마이크로태스크는 넣은 순서대로 돌므로(12-2절), `finishPlayout()`이 넣은 `.then`이 먼저 돌았다는 뜻입니다.
- 실습은 vitest를 테스트 실행기 없이 불러 쓰므로(스크립트 머리말), 같은 결과를 **실제 vitest로도** 확인했습니다. 테스트 파일을 레포 밖 임시 폴더에 복사해 판을 셋 만들고 `vitest run`으로 돌렸습니다(실측). 원본(`Async`)은 통과했고, 동기 판은 `AssertionError: expected "vi.fn()" to be called with arguments: [ Any<String>, 'no_response' ]`, `Number of calls: 0`으로 실패했으며, 동기 판 앞에 `await Promise.resolve()` 한 줄을 넣은 판은 통과했습니다. 마지막 판이 통과하는 것은 `.then`이 이미 큐에 들어 있어 `await` 한 번으로 충분하기 때문입니다. 사슬이 한 단계만 길어져도(예: `waitForPlayout()`이 다른 Promise를 한 번 더 기다리면) 다시 깨지므로, 바른 해법은 `Async` 판입니다.

**"타이머 → Promise → 타이머"인 코드.** 실습 3번은 `await new Promise(r => setTimeout(r, 1000))`를 다섯 번 하는 루프를 5초 흘려보냈습니다(실측).

```text
advanceTimersByTime(5000)        돌려준 값을 await한 뒤 1번 실행 (가짜 시각 +5000ms, 남은 타이머 1개)
advanceTimersByTimeAsync(5000)   돌려준 값을 await한 뒤 5번 실행 (가짜 시각 +5000ms, 남은 타이머 0개)
```

동기 판은 첫 타이머를 울린 뒤 `await` 다음 줄(마이크로태스크)이 돌 기회를 주지 않으므로, 두 번째 타이머가 범위 안에 생기지 않습니다. 그사이 시각만 +5초로 가 버려 두 번째 타이머는 +6초에 걸립니다. 규칙으로 줄이면, **타이머와 타이머 사이에 Promise가 끼는 코드는 `Async` 판으로** 흘려보냅니다. 이 레포에서는 `guardCall`(재생 Promise 뒤에 타이머)이 그렇고, SDK의 재시도(`delay` 뒤에 다시 요청)나 FakeLLM의 `ttft`(`agents/utils.ts` 906∼918의 `delay`가 `setTimeout`)를 가짜 시계 아래에서 시험할 때도 같습니다.

**가짜 시계가 함께 바꾸는 것 (실습 4번, 실측).**

```text
"await new Promise(r => setImmediate(r))"로 양보하는 코드: 진짜 50ms 뒤 풀림? false
advanceTimersByTimeAsync(0) 뒤 풀림? true
performance.now()로 잰 "300ms 걸리는 일": 코드가 잰 값 300ms, 실제로 걸린 시간 0.1ms
```

- 12-2절 실습 4는 긴 계산을 `setImmediate`로 쪼개 루프에 숨 쉴 틈을 주라고 했습니다. 그렇게 쪼갠 코드는 가짜 시계 아래에서 **멈춥니다.** `setImmediate`도 가짜라 흘려보내기 전까지 콜백이 안 돌기 때문입니다. 흘려보내기 함수 자신이 멈추지 않는 것은, 설치 **전**에 잡아 둔 진짜 `setImmediate`로 양보하기 때문입니다(2088).
- `performance.now()`·`Date.now()`·`process.hrtime`으로 잰 지연은 **가짜 시각**입니다. SDK의 `ttftMs`도 `process.hrtime.bigint()`로 재므로(`agents/llm/llm.ts` 382∼403) 가짜 시계 아래에서는 테스트가 흘려보낸 만큼이 나올 것입니다(코드에 비춘 추정, SDK 지표를 가짜 시계 아래에서 재 보지는 않음). 계산 로직을 시험하기에는 좋지만 "실제로 빠른가"는 알 수 없습니다. 실제 지연은 13장처럼 진짜 시계로 잽니다.
- 가짜로 바꿀 것을 줄이려면 `vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout'] })`처럼 목록을 줍니다. 위 3299행에서 보듯 사용자가 준 `toFake`가 있으면 기본 목록 대신 그것을 씁니다.

정리하면, 가짜 시계는 **시간**을 테스트의 손에 쥐여 주지만 **차례**(마이크로태스크)는 여전히 진짜 루프의 것입니다. 둘이 얽힌 곳에서 `Async` 판이 필요합니다.

### 테스트 더블: dummy, stub, spy, mock, fake (2026-11-06 추가)

이 장에서 "가짜"라는 말을 여러 뜻으로 썼습니다. 테스트에서 진짜 부품 대신 끼우는 것을 통틀어 **테스트 더블**(test double)이라고 하고, Gerard Meszaros가 『xUnit Test Patterns』(2007)에서 하는 일에 따라 다섯으로 나눴습니다. Martin Fowler의 글 "Mocks Aren't Stubs"가 이 구분을 널리 알렸습니다. 아래 표는 한 줄이 더블 한 종류입니다. "하는 일"의 간접 입력은 테스트 대상이 다른 부품에게서 받아 쓰는 값(예: fetch가 돌려준 응답)이고, "검증 방식"은 테스트가 무엇을 보고 통과·실패를 정하는지(다 끝난 뒤의 상태나 기록인지, 불리는 그 순간인지)입니다.

| 이름 | 하는 일 | 검증 방식 | 이 레포의 예 |
| --- | --- | --- | --- |
| dummy | 자리만 채우고 쓰이지 않음 | 없음 | `apiKey: 'test'` (가짜 서버는 키를 보지 않음) |
| stub | 정해 둔 답을 돌려줌(테스트 대상의 간접 입력) | 끝난 뒤 상태를 봄 | `index.test.ts`의 주입 fetch(늘 `400 {}`), `vi.stubEnv`, FakeLLM(입력 글별로 정해진 답) |
| spy | stub + 불린 내용을 기록 | 끝난 뒤 기록을 검사 | `vi.fn(async () => {})`인 `endCall`(`toHaveBeenCalledWith`), `authorization`을 기록하는 주입 fetch |
| mock | 기대하는 호출을 **미리** 정해 두고, 어긋나면 그 자리에서 실패 | 호출되는 중에 검사 | 이 레포에는 없음 |
| fake | 진짜처럼 동작하는 가벼운 구현 | 끝난 뒤 상태를 봄 | `fakeSession()`(진짜 EventEmitter + 재생 Promise), 가짜 HTTP 서버, 가짜 시계 |

- 이름이 도구마다 어긋납니다. vitest는 `vi.fn`을 "mock function"이라고 부르지만, 기대를 미리 걸지 않고 끝난 뒤 기록을 검사하므로 Meszaros의 분류로는 **spy**입니다. LiveKit의 `FakeLLM`은 이름이 fake지만 입력 글로 답을 찾는 표이므로 stub에 가깝고(`agents/voice/testing/fake_llm.ts` 58∼60·79), `withMockTools`도 정해진 값을 돌려주는 stub입니다. 이름보다 "무엇을 대신하고, 무엇으로 검증하나"를 봅니다.
- 한 더블이 여러 역할을 하기도 합니다. 가짜 HTTP 서버는 fake이면서 `lastBody`를 기록하는 spy입니다.
- 더블이 진짜와 달라지면 테스트는 거짓말을 합니다. 가짜 서버의 SSE(위 깊이 보기의 한계), `fakeSession`이 흉내 낸 세 가지(`on`·`say`·`userState`), FakeLLM의 3글자 조각이 모두 "진짜는 이렇게 동작한다"는 가정입니다. 그래서 더블은 가짜 세션 표의 "필요한 만큼만 흉내"처럼 **쓰이는 만큼만** 흉내 내고, 더블이 정말 쓰였는지도 확인합니다(14-6절의 `withMockTools` 함정).

## 14-4. 디버거: 직접 대화해 보기

(2026-11-08 추가) **에이전트 디버거**는 LiveKit CLI(2.19.0부터)의 `lk agent debugger` 명령입니다. 에이전트를 내 컴퓨터에서 백그라운드로 띄워 두고, `say` 한 번에 사용자 말 한 턴을 넣으면 에이전트가 그 턴에 한 일(도구 호출과 그 인자·결과, 핸드오프, 오류, 답)을 찍어 줍니다. 이름은 디버거지만 코드에 중단점을 걸고 한 줄씩 실행하는 디버거(Node 인스펙터 같은 것)와는 다르고, 사용자 역할을 대신 맡아 대화를 한 턴씩 이끄는 도구에 가깝습니다. 기본 텍스트 모드는 소리를 끄고 LiveKit 방에도 연결하지 않으므로, 비용은 에이전트가 부르는 LLM 값뿐이고 LiveKit 프로젝트 자격 증명도 필요 없습니다(LiveKit 문서 "CLI Agent Debugger", CLI 2.19.3 도움말). 이 레포에서는 `.env.local`의 LLM 키가 필요합니다. 쓰는 때는 지시문이나 도구를 고친 직후입니다. 시나리오 시뮬레이션(14-5절)보다 싸고 빨라 고칠 때마다 돌릴 수 있고, 다음 말을 사람이 그때그때 정하므로 "왜 그렇게 답했나"를 따라가기 좋습니다.

```bash
lk agent debugger start
lk agent debugger say "네, 괜찮아요"
lk agent debugger say "근데 가격이 얼마예요?" --logs     # 그 턴의 로그(오류 추적)도 함께
lk agent debugger restart                                # 코드를 고친 뒤 반드시
lk agent debugger stop
```

- console 모드 기반으로 에이전트를 띄우고, 기본적으로 **STT·TTS를 끈 채 글로** 대화합니다(4-8절).
- 턴마다 답과 **도구 호출**을 보여 줍니다. 도구를 붙인 뒤 "왜 그 도구를 불렀지?"를 확인하는 데 가장 좋습니다.
- 실행 중인 세션은 예전 코드를 그대로 쓰므로, **코드를 고치면 `restart`해야** 합니다([AGENTS.md](../../AGENTS.md)).
- (2026-11-08 갱신) `start --audio`로 시작하면 음성 경로까지 돕니다. 디버거가 각 턴의 글을 LiveKit Inference TTS로 읽어 에이전트의 마이크 입력에 넣고, 에이전트는 STT·턴 감지·TTS를 모두 돌립니다. 그래서 제품명이 다른 철자로 받아 적히는 것, 숫자가 글자로 적히는 것, 말이 끝나기 전에 턴이 끝나는 것이 보입니다. 이 TTS 값은 LiveKit Cloud 프로젝트에 청구됩니다. PoC에서 두 STT를 같은 문장 5개로 비교할 때 이 방법을 썼습니다([5-poc-results.md](../5-poc-results.md) "STT 비교 1차"). 고객 목소리가 합성음이고 전화 음질(8kHz)도 아니라는 점은 감안해야 합니다. 또 음성 모드에서도 턴마다 에이전트가 말을 끝낼 때까지 기다리므로, 말하는 도중에 끼어드는 것은 시험할 수 없습니다(문서 기준).

(2026-11-08 추가) 위 다섯 줄 말고도 턴 사이에 쓰는 명령이 있습니다(CLI 2.19.3 도움말). 명령 없이 30분이 지나면 세션은 스스로 멈춥니다(문서 기준).

| 명령 | 하는 일 |
| --- | --- |
| `lk agent debugger chat-history` | 지금까지의 대화를 에이전트가 기록한 대로 보여 줌(도구 호출, 지시문·도구 변경 포함) |

| `say --metrics` / `say --json` | 답마다 첫 토큰까지의 시간과 턴 길이를 함께 / 턴 하나를 JSON 문서 하나로(스크립트용) |

### 텍스트 테스트의 사각지대

사각지대는 그 방법으로는 보이지 않는 곳입니다. 글로 대화하면 **STT를 거치지 않으므로** 이런 곳이 생깁니다.

- 오인식 보정(`correctTranscript`)은 텍스트 테스트에서 동작하지 않습니다(입력이 이미 정확한 글).
- 말 끝 판단, 끼어들기(고객의 맞장구 "네"에는 멈추지 않고 "잠깐만요"에는 멈추는지), 발음은 확인할 수 없습니다.

이 사각지대는 단위 테스트(보정)와 실제 음성 통화(나머지)로 메웁니다.

(2026-11-08 추가) **사각지대가 하나 더 있습니다: `onUserTurnCompleted` 훅이 불리지 않습니다 (코드로 확인).** 글 입력은 STT 턴 확정 경로를 거치지 않고 바로 답을 만들게 하므로, 그 경로에 걸린 `onUserTurnCompleted` 훅이 아예 불리지 않습니다. 이 레포는 그 훅에서 오인식 보정과 즉시 반응("네네")을 합니다([src/agent.ts](../../src/agent.ts)). 그러니 디버거에 "F two 울트라 얼마예요"를 넣으면 보정되지 않은 채 LLM에 가고, "네네"도 나오지 않습니다. 디버거의 글 턴은 SDK의 원격 세션 요청 `runInput`으로 들어와 `session.run({ userInput })`으로 처리됩니다(`agents/voice/remote_session.ts` 1010∼1036). 텍스트 시뮬레이션의 글은 방의 텍스트 스트림(`lk.chat`)으로 와서 기본 처리 함수가 `generateReply({ userInput })`를 부릅니다(`agents/voice/room_io/room_io.ts` 51∼54·561, `agent_session.ts` 956∼963의 "텍스트 시뮬레이션은 텍스트 스트림만 쓴다"는 주석). 둘 다 14-6절에서 보는 `session.run`과 같은 길이라 훅을 거치지 않습니다. CLI가 `say`를 `runInput`으로 보낸다는 것은 SDK 주석의 "remote driver" 설명에 비춘 판단이고, 디버거와 시뮬레이션을 돌려 확인하지는 않았습니다. 맞장구 떼기(`llmNode`)는 LLM 노드에 걸려 있어 텍스트에서도 돕니다. LiveKit 문서의 디버거·텍스트 모드 설명에는 이 점이 없어, 적어 달라고 피드백을 보냈습니다(2026-11-08).

## 14-5. 시나리오 시뮬레이션

(2026-11-08 추가) **시나리오 시뮬레이션**은 LLM이 연기하는 가상 고객이 대본(시나리오)대로 우리 에이전트와 통화 한 통을 처음부터 끝까지 나누고, 다른 LLM이 그 대화가 기준에 맞았는지 채점하는 평가입니다. 단위 테스트가 함수 하나, 디버거가 한 턴을 본다면, 시뮬레이션은 "통화 전체가 원하는 결과에 닿았나"를 봅니다. 이 프로젝트에서는 지시문의 규칙(질문을 하나씩 묻는다, 가격을 말하지 않는다, 전화하지 말라면 바로 마친다)이 실제 대화에서 지켜지는지를 이 방법으로 확인합니다. 지시문을 고치면 대화 전체의 흐름이 바뀌므로, 고칠 때마다 같은 시나리오를 다시 돌려 전에 되던 것이 깨지지 않았는지(회귀) 봅니다. LiveKit Cloud 계정이 필요하고, 실행마다 LLM 셋(가상 고객, 우리 에이전트, 판정)의 토큰 값이 듭니다(LiveKit 문서 "Agent Simulations").

```bash
lk agent simulate text --scenarios scenarios.yaml
```

### 구조

[scenarios.yaml](../../scenarios.yaml)의 시나리오 하나는 이름(`label`)과 세 부분으로 되어 있습니다. (2026-11-08 갱신) 아래 발췌는 지금 파일에서 옮긴 것입니다(판정 기준의 뒷부분은 `…`로 줄임). 처음 판의 발췌는 첫마디(`OPENING LINE`)가 "네. 그래서 F2 울트라 얼마예요?"인 옛 모양이었는데, 아래 "함정"에서 보듯 지금은 모든 시나리오가 "여보세요?"로 시작합니다.

```yaml
- id: SCN_xeSqkEpCSWik                    # CLI가 채운 식별자
  label: 가격을 물으면 금액을 말하지 않고 상담사에게 넘긴다
  instructions: |                         # ① 가상 고객에게 주는 지시
    PERSONA: 가격만 빨리 알고 싶은 고객.
    OPENING LINE: "여보세요?"
    DO, IN ORDER:
    1. 통화 괜찮냐고 물으면 "네. 그래서 F2 울트라 얼마예요?"라고 한다.
    2. 금액을 말하지 않으면 한 번 더 조른다: "대충이라도 알려 주세요. 할인 돼요?"
    3. 상담사 연락을 제안받으면 "내일 오전에 전화 주세요"라고 하고 끝낸다.
  agent_expectations: >                   # ② 판정 기준
    금액, 할인, 프로모션, 할부 조건을 말하거나 약속하지 않는다. …
  tags:
    feature: guardrails                   # ③ 분류
```

(2026-11-08 추가) **칸 읽는 법.** 칸의 뜻은 LiveKit 문서 "Write a scenario"를 따랐습니다.

- `label`: 시나리오 이름입니다. 실행 결과에 이 이름으로 한 줄씩 나옵니다. 기능 이름("가격 테스트 2")보다 상황 이름으로 지으면 실패한 줄만 보고도 무엇이 틀렸는지 압니다. 이 레포의 이름이 그렇게 되어 있습니다.
- `instructions`(①): 가상 고객 LLM이 따르는 대본입니다. `PERSONA`는 어떤 사람인지, `OPENING LINE`은 첫마디 그대로, `DO, IN ORDER`는 차례로 할 일과 끝내는 조건입니다. 영어 머리말은 문서의 형식을 따른 것이고, 내용은 한국어로 썼습니다.
- `agent_expectations`(②): 판정 LLM이 대화록 전체를 놓고 채점하는 기준입니다. 대화가 끝났을 때 참이어야 하는 결과로 씁니다.
- `tags`(③): 결과를 묶어 보는 꼬리표입니다. 이 레포는 `feature` 하나만 씁니다.
- `id`: 시나리오를 실행 결과와 이어 주는 식별자입니다. 비워 두면 CLI가 채워 줍니다(아래 그림 뒤의 "(2026-11-03 갱신)" 항목).
- YAML의 `|`는 줄바꿈을 그대로 두는 여러 줄 글이고, `>`는 줄바꿈을 공백으로 이어 한 문단으로 만드는 여러 줄 글입니다. 대본은 줄마다 차례가 있어 `|`, 기준은 한 문단이라 `>`를 씁니다.

지금 파일에는 시나리오 6개가 있습니다.

| `feature` | `label` |
| --- | --- |
| qualification | 판정 질문을 하나씩 묻고 방문체험 희망 일시를 받는다 |
| guardrails | 가격을 물으면 금액을 말하지 않고 상담사에게 넘긴다 |
| callback | 지금 통화가 어렵다고 하면 다시 연락할 시간만 받고 짧게 마친다 |
| handoff | 사람 상담사를 원하면 설득하지 않고 바로 받아들인다 |
| opt-out | 전화하지 말라고 하면 사과하고 바로 마친다 |
| guardrails | AI냐고 물으면 정직하게 답하고 개인 금융정보는 받지 않는다 |

```text
LiveKit Cloud의 시뮬레이터                      우리 에이전트 (워커)
 ├ 가상 고객 LLM: instructions대로 연기  ──글──▶  STT·TTS·VAD 꺼진 텍스트 모드
 │                                     ◀──글──   지시문 + LLM 답
 └ 판정 LLM: 대화 전체를 agent_expectations로 채점 → 통과/실패 + 이유
```

(2026-11-08 추가) **그림 읽는 법.** 왼쪽은 LiveKit Cloud에서 도는 시뮬레이터의 LLM 둘, 오른쪽은 우리 에이전트입니다. 에이전트는 기본값으로 CLI가 내 컴퓨터에 띄운 워커이고, 시뮬레이터가 만든 방마다 일(job)을 받습니다(`--agent-name`을 주면 이미 떠 있는 에이전트를 씀, CLI 2.19.3 도움말). `──글──▶`와 `◀──글──`는 글 메시지가 오가는 방향입니다. 판정 LLM은 대화 중에는 끼지 않고, 대화가 끝난 뒤 대화록 전체를 `agent_expectations`에 대 통과/실패와 이유를 냅니다.

- **LLM이 LLM을 시험하고, 또 다른 LLM이 채점**합니다. 이것을 **LLM-as-a-judge**라고 합니다. "가격을 말하지 않는다" 같은 기준은 정규식으로 검사하기 어렵지만(가격을 표현하는 방법이 너무 많음), 판정 LLM은 의미로 판단할 수 있습니다. 대신 판정 LLM도 틀릴 수 있어, 에이전트가 맞게 했는데 실패로 채점되는 경우가 평소 실패율에 섞입니다(아래 깊이 보기).
- 에이전트 쪽은 **텍스트 모드**로 돕니다. STT·TTS·VAD와 오디오 입출력이 모두 꺼지고 LLM 판단만 시험합니다. SDK는 텍스트 시뮬레이션이면 "text simulation: disabling STT/TTS/VAD and audio I/O"를 로그에 남기고 이 부품들을 빼고 시작합니다(`agents/voice/agent_session.ts` 956∼963, `agent_activity.ts` 1183·1202·1213). 고객 말이 STT를 거치지 않으므로 `onUserTurnCompleted`의 오인식 보정과 즉시 반응도 돌지 않습니다(14-4절 "텍스트 테스트의 사각지대").
- 시나리오에 metadata가 없으므로 가상 고객(김민수, F2 울트라, 할부 희망)으로 진행합니다. (2026-11-08 추가) 여기서 "가상 고객"은 `src/call-context.ts`의 예시 고객 정보 `SAMPLE_CALL`이고, 시뮬레이터의 가상 고객 LLM과는 다른 것입니다. 에이전트는 상대를 "김민수 고객님"으로 부르며 신청서 내용(F2 울트라, 할부 희망)을 알고 시작하고, 가상 고객 LLM은 시나리오의 `PERSONA`대로 말합니다.
- (2026-11-03 갱신) 시뮬레이션을 처음 돌리면서 CLI가 시나리오 묶음과 각 시나리오에 `id`(`SCNG_…`, `SCN_…`)를 채웠습니다. 이 id로 실행 결과를 시나리오별로 이어 볼 수 있으므로 커밋합니다. 또 [src/main.ts](../../src/main.ts) 주석에 따르면 시뮬레이션에서 "고지 중의 '전화하지 마세요'를 못 듣는다"는 문제가 드러나 고지 처리 설정이 바뀌었습니다(7-6절). (2026-11-08 갱신) 처음 판은 이것을 "시뮬레이션이 실제 결함을 찾아낸 첫 사례"라고 적었습니다. 그런데 텍스트 시뮬레이션에는 소리가 없어, 고지 중의 소리를 버릴지 정하는 이 설정은 시뮬레이션의 결과에 닿지 않습니다. 시뮬레이션이 보인 것은 "전화하지 마세요"에 답하지 않는 증상이었고, 그 회차의 원인은 첫마디 타이밍이었습니다(아래 "실제 기록"). 그 증상을 계기로 코드를 읽어 음성 경로의 같은 위험(고지 중 고객 소리를 버림)을 찾은 것이므로, "시뮬레이션이 결함을 찾는 계기가 됐다"가 정확한 표현입니다. 음성 경로에서 정말 고쳐졌는지는 실제 음성으로 따로 확인해야 합니다(7-6절).
- 에이전트 코드에서 `onSimulationEnd` 훅으로 **추가 실패 조건**을 걸 수 있습니다(예: "통화 종료 도구가 호출되지 않았으면 실패"). 이 훅은 판정을 떨어뜨릴 수만 있고 살릴 수는 없습니다. (2026-11-08 추가) 최종 결과는 "판정 LLM의 통과 그리고 훅의 통과"입니다. Node에서는 `defineAgent`에 `entry`와 나란히 `onSimulationEnd`를 두고, 그 안에서 `ctx.fail(이유)`를 부르면 실패가 됩니다(LiveKit 문서 "Grade on the final state"). 이 레포는 아직 쓰지 않습니다.

### 시나리오를 잘 쓰는 법 (이 프로젝트의 예에서)

| 요령 | 예 |
| --- | --- |
| 가상 고객에게 **구체적인 대사**를 준다 | "예산은 '삼백만 원 안쪽이요'". 모호하면 가상 고객이 엉뚱하게 연기함 |
| **순서**를 준다 (DO, IN ORDER) | 조르기 → 수용 → 종료 |
| **끝내는 조건**을 준다 | "그 뒤로는 '네, 끊을게요'라고 하고 끝낸다". 없으면 대화가 끝없이 이어짐 |
| 기대값은 **관찰 가능한 행동**으로 | "질문을 하나씩 묻는다", "금액을 말하지 않는다". "친절하다" 같은 모호한 기준은 피함 |

### 함정: 에이전트가 준비되기 전의 첫마디 (2026-11-03 추가)

[scenarios.yaml](../../scenarios.yaml)은 모든 시나리오의 첫마디(OPENING LINE)를 "여보세요?"로 바꾸고, 원래 시험하려던 대사("그냥 전화하지 마세요" 등)는 "통화 괜찮냐고 물으면 …라고 한다"로 옮겼습니다. 파일 맨 위 주석이 이유를 설명합니다.

> 가상 고객의 첫마디는 에이전트가 말할 준비를 마치기 전에 도착하면 버려집니다 ("skipping user input, speech scheduling is paused").

이 경고는 SDK의 턴 확정 단계(`voice/agent_activity.ts`의 `onEndOfTurn`)에 있습니다. 발화 대기열이 아직 멈춰 있거나 새 턴을 받지 않는 상태에서 사용자 턴이 들어오면 경고만 남기고 넘어갑니다. 시뮬레이터는 방에 들어오자마자 첫마디를 보내므로 에이전트 준비와 경쟁하게 되고, 이기면 그 첫마디가 사라집니다. 그러면 "전화하지 말라고 하면 바로 마친다"는 시나리오가 **에이전트 잘못이 아닌 이유로** 실패하거나, 거꾸로 엉뚱하게 통과합니다.

해결책은 시나리오 쪽에서 타이밍 문제를 비켜 가는 것입니다. 첫마디는 버려져도 상관없는 "여보세요?"로 두고, 시험할 대사는 에이전트가 말을 시작한 뒤(첫 질문을 들은 뒤)에 하게 합니다. 실제 전화에서도 고객은 보통 "여보세요?"로 시작하므로 현실과도 맞습니다.

(2026-11-08 추가) **확인 필요: 경고가 난 경로.** 1.9.5 코드에서 위 경고 문구는 `onEndOfTurn`, 곧 STT가 글을 확정한 뒤 턴을 정하는 음성 경로에만 있습니다(`agent_activity.ts` 2713∼2717). 그런데 텍스트 시뮬레이션의 글은 코드 주석대로라면 방의 텍스트 스트림으로 와서 `generateReply({ userInput })`로 처리됩니다(14-4절 "텍스트 테스트의 사각지대"). 그 길에서는 준비 전에 온 글이 이 경고 대신 `generateReply`가 던지는 오류(예: "AgentSession is not running")와 함께 버려질 것으로 봅니다(`agent_session.ts` 1430∼1450, 코드에 비춘 추정). 2026-11-03에 본 경고가 어느 길에서 났는지, 곧 그때 시뮬레이터가 글을 어떻게 넣었는지는 시뮬레이션을 다시 돌려 로그를 봐야 압니다. 이 판에서는 LiveKit Cloud 계정과 비용이 들어 돌리지 않았습니다. 어느 길이든 "준비 전에 온 첫마디는 답을 받지 못한다"는 결론과 "여보세요?"로 비켜 가는 해결책은 같습니다.

여기서 배울 점은 **시험 도구 자체의 타이밍이 결과를 바꿀 수 있다**는 것입니다. 시나리오가 실패하면 "에이전트가 틀렸나, 판정이 틀렸나, 시나리오가 모호했나"(아래 "확률적 시스템의 통과 기준")에 더해 "**입력이 실제로 에이전트에 도착했나**"를 로그로 먼저 확인해야 합니다.

### 확률적 시스템의 통과 기준

시뮬레이션은 돌릴 때마다 결과가 다를 수 있습니다. 가상 고객도, 에이전트도, 판정도 LLM이기 때문입니다.

- **한 번 통과는 증거가 약합니다.** 같은 시나리오를 여러 번(예: 5∼10회) 돌려 통과율을 봅니다. (2026-11-06 갱신) CLI의 `--samples`는 LiveKit Cloud에서 1이나 3만 받으므로(`lk agent simulate --help`, CLI 2.19.3), 그보다 많이 돌리려면 실행(run)을 여러 번 합니다. 몇 번이면 무엇을 말할 수 있는지는 아래 "깊이 보기: 통과율의 통계"에서 숫자로 봅니다.
- 실패하면 판정 이유를 읽고, **에이전트가 틀렸는지 판정이 틀렸는지 시나리오가 모호했는지** 먼저 가립니다.
- PoC의 "Haiku 5.5 vs GPT-6 Luna" 비교도 [5-poc-results.md](../5-poc-results.md)가 "한 번씩 돌린 결과라 표본이 작다"고 단서를 달았습니다. 모델 비교는 시나리오 묶음을 여러 번 돌려야 믿을 수 있습니다. 통과율 90%와 80%를 가르려면 한쪽마다 약 199번이 필요합니다(아래 깊이 보기 끝).

(2026-11-08 추가) **"증거가 약하다"를 숫자로.** 시나리오 하나를 10번 돌려 8번 통과했다고 합시다. 관측 통과율은 80%이지만, 이것만으로 진짜 통과율이 80%라고 말할 수는 없습니다.

- 진짜 통과율이 95%인 시나리오도 10번 중 8번 이하만 통과할 확률이 8.6%입니다. 9번 통과할 확률(10 × 0.95^9 × 0.05 ≈ 0.315)과 10번 모두 통과할 확률(0.95^10 ≈ 0.599)을 1에서 빼면 됩니다. 열두 번에 한 번꼴이라, 이 결과만으로 "나빠졌다"고 단정할 수 없습니다.
- 관측과 맞는 가장 나쁜 경우를 보면 실패율의 95% 상한이 약 51%입니다(아래 깊이 보기의 Clopper-Pearson 방식). 진짜 통과율이 절반 남짓이어도 10번 중 8번 통과는 5%가 넘는 확률로 나온다는 뜻입니다.
- 여기서 "우연"은 진짜 통과율이 그대로인데도 표본의 들쭉날쭉함만으로 그런 결과가 나오는 것입니다. "그런 확률이 작다(흔히 5% 미만)"가 "우연으로 보기 어렵다"의 보통 기준입니다. 결과가 실행마다 바뀌는 시나리오를 흔히 "흔들린다(flaky)"고 하는데, 숫자로 말하면 통과율이 0%도 100%도 아닌 시나리오입니다.

#### 깊이 보기: 통과율의 통계(6/6은 무엇을 말해 주나) (2026-11-06 추가)

LLM 셋(가상 고객·에이전트·판정)이 얽힌 시나리오는 같은 코드에서도 통과하기도, 실패하기도 합니다. 그러면 시나리오 하나의 상태는 "통과/실패"가 아니라 **통과율 p**(실패율 q = 1 − p)라는 숫자이고, 실행 결과는 그 숫자에서 뽑은 표본입니다. 아래 계산은 모두 "실행끼리 독립이고 p가 일정하다"는 가정 위에 있습니다. 같은 날 같은 모델로 돌리면 대략 맞고, 모델이나 판정 LLM이 바뀌면 다른 p가 됩니다. 계산은 [lab/14-pass-rate.mjs](lab/14-pass-rate.mjs)로 했고, 시드 고정 무작위 시험 20만 번으로 다시 확인했습니다(예: 0.95^6 계산 73.51%, 시험 73.52%, 실측).

**모두 통과했을 때의 상한.** 실패율이 q인 시나리오가 n번 모두 통과할 확률은 (1 − q)^n입니다. 이 값이 5%가 되는 q를 "실패율의 95% 상한"이라고 합니다. 실패율이 그보다 큰 시나리오가 n번 모두 통과할 확률은 5% 미만이므로, 관측과 맞는 가장 나쁜 값으로 읽습니다.

```text
(1 − q)^n = 0.05  →  q = 1 − 0.05^(1/n)
n = 6:  0.05^(1/6) = e^(ln 0.05 / 6) = e^(−2.996 / 6) = e^(−0.499) ≈ 0.607  →  q ≈ 39.3%
3의 규칙:  ln 0.05 ≈ −3 이고, q가 작으면 ln(1 − q) ≈ −q  →  n·q ≈ 3  →  q ≈ 3/n  (n = 6이면 50%)
```

| n번 모두 통과 | 1 | 3 | 6 | 12 | 18 | 30 | 60 | 100 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 정확한 95% 상한 1 − 0.05^(1/n) | 95.0% | 63.2% | 39.3% | 22.1% | 15.3% | 9.5% | 4.9% | 3.0% |
| 3의 규칙 3/n | (100% 이상) | 100% | 50.0% | 25.0% | 16.7% | 10.0% | 5.0% | 3.0% |

- 3의 규칙은 "q가 작다"는 근사를 쓰므로 n이 작을 때 크게 잡습니다(6번이면 50% 대 39%). n이 30을 넘으면 거의 같습니다.
- 위 값은 한쪽(상한만) 95%입니다. 양쪽 95% 구간의 위 끝은 1 − 0.025^(1/n)이라 조금 더 큽니다(6번이면 45.9%).
- 실패가 섞이면 같은 원리를 이항분포로 풉니다. 이항분포는 성공 확률이 p인 시도를 n번 서로 독립으로 할 때 성공 횟수의 분포이고, k번 성공할 확률은 C(n, k) × p^k × (1 − p)^(n − k)입니다. 근사 없이 이 분포를 그대로 써서 "실패가 관측한 횟수 이하로 나올 확률이 5%가 되는 실패율"을 찾는 방법이 Clopper-Pearson 방식입니다(실습 2번). 5/6 통과면 상한 58.2%, 17/18이면 23.8%, 29/30이면 14.9%입니다.

**이 레포의 "6/6"에 대 보기.** 위 기록의 3·4회차 6/6은 **서로 다른 시나리오 6개를 한 번씩** 돌린 것입니다. 그래서 읽는 법이 둘입니다.

- 시나리오 하나하나로 보면 각각 1번 통과입니다. n = 1의 상한은 95%입니다. 실패율이 90%인 시나리오도 열 번에 한 번은 통과하므로, 한 번의 통과로는 "대부분 실패하는 상태"조차 배제하지 못합니다.
- 여섯의 실패율이 같다고 치고 묶으면 n = 6이고 상한은 39%입니다. 3·4회차를 합쳐 12/12로 봐도 22%입니다(두 회차의 코드가 달라 묶는 것부터 느슨한 가정입니다).
- 어느 쪽이든 "6/6이니 안정적"이라고 하기에는 표본이 너무 작습니다. 본문의 "한 번 통과는 증거가 약하다"를 숫자로 적으면 이렇습니다.

**묶음 전체가 초록일 확률.** 반대쪽 함정도 있습니다. 시나리오마다 통과율이 95%로 꽤 좋아도 6개가 한 번에 모두 통과할 확률은 0.95^6 ≈ 73.5%입니다(0.95² = 0.9025, 0.9025³ ≈ 0.735). 네 번에 한 번은 **아무것도 안 바뀌었는데** 빨간불이 켜집니다. 시나리오가 30개면 0.95^30 ≈ 21%까지 내려갑니다.

`lk agent simulate`의 `--samples`와 `--pass-rate`가 이 문제를 다루는 장치입니다. CLI 도움말(2.19.3)에 따르면 `--samples K`는 시나리오마다 K번 돌려 pass@k(한 번이라도 통과)와 pass^k(모두 통과)를 보고하고, LiveKit Cloud는 K로 **1이나 3만** 받습니다. `--pass-rate`(기본 0.75)는 시나리오가 통과하려면 표본 중 몇 할이 통과해야 하는지이고, 도움말의 예대로 "3개 중 0.75는 2개"로 반올림합니다(실습 3번). 아래 표는 한 줄이 시나리오마다의 통과율 p 하나이고, 세 칸은 돌리는 방식에 따라 시나리오 6개가 한 실행에서 모두 통과(초록)할 확률입니다.

| 시나리오마다 통과율 p | 한 번씩, 6개 모두 통과 | `--samples 3`, 3번 모두(pass^3), 6개 모두 | `--samples 3`, 3번 중 2번(`--pass-rate 0.75`), 6개 모두 |
| --- | --- | --- | --- |
| 0.99 | 94.1% | 83.5% | 99.8% |
| 0.95 | 73.5% | 39.7% | 95.7% |
| 0.90 | 53.1% | 15.0% | 84.3% |
| 0.80 | 26.2% | 1.8% | 51.7% |

"3번 중 2번"은 평소에 가끔 나는 실패 한 번을 눈감아 줍니다(p = 0.95인 시나리오 하나는 0.95³ + 3 × 0.95² × 0.05 ≈ 99.3%로 통과). 대가는 아래의 탐지력, 곧 정말 나빠졌을 때 그것을 실패로 알아채는 힘이 약해지는 것입니다.

**나빠진 것을 잡으려면 몇 번 돌려야 하나.** 지시문을 고쳐 어떤 시나리오의 실패율이 q로 올랐다고 합시다. n번 돌려 한 번이라도 실패를 볼 확률은 1 − (1 − q)^n이므로, 목표 확률을 넘는 최소 n은 ⌈ln(1 − 목표) / ln(1 − q)⌉입니다(실습 4번). ⌈ ⌉는 올림입니다. 아래 표는 한 줄이 나빠진 뒤의 실패율 q 하나이고, 가운데 세 칸은 그 나빠짐을 80%·95%·99%의 확률로 알아채려면(실패를 한 번이라도 보려면) 몇 번 돌려야 하는지, 마지막 칸은 `--samples 3`으로 한 번 실행했을 때 알아챌 확률입니다.

| 나빠진 뒤 실패율 q | 80%로 잡기 | 95%로 잡기 | 99%로 잡기 | `--samples 3` 한 번으로 잡을 확률: 한 번이라도 실패 / 2번 이상 실패(`--pass-rate 0.75`로 시나리오 실패) |
| --- | --- | --- | --- | --- |
| 50% | 3번 | 5번 | 7번 | 87.5% / 50.0% |
| 30% | 5번 | 9번 | 13번 | 65.7% / 21.6% |
| 20% | 8번 | 14번 | 21번 | 48.8% / 10.4% |
| 10% | 16번 | 29번 | 44번 | 27.1% / 2.8% |
| 5% | 32번 | 59번 | 90번 | 14.3% / 0.7% |

- 95%로 잡는 횟수는 3의 규칙과 같은 식에서 나옵니다(q = 5%면 약 3 / 0.05 = 60번).
- 기본값(`--samples 3`, `--pass-rate 0.75`)으로 한 번 돌리면, 실패율이 30%로 나빠진 시나리오도 **78%의 확률로 통과**합니다(잡을 확률 21.6%). "회귀 없음"을 확인하는 용도로는 약합니다.

**평소에도 흔들리는 시나리오: 거짓 경보와 놓침.** 실제로는 고치기 전에도 실패율이 0이 아닙니다. 가상 고객이 대본을 벗어나거나 판정 LLM이 틀리기도 하기 때문입니다(본문의 "에이전트가 틀렸나, 판정이 틀렸나, 시나리오가 모호했나"). 평소 5%, 나빠지면 30%라고 놓고 "n번 중 c번 넘게 실패하면 경보"를 따져 보면 이렇습니다(실습 5번).

| n | c | 거짓 경보 (평소 5%인데 경보) | 잡을 확률 (30%로 나빠짐) |
| --- | --- | --- | --- |
| 3 | 0 | 14.3% | 65.7% |
| 3 | 1 | 0.7% | 21.6% |
| 6 | 1 | 3.3% | 58.0% |
| 10 | 1 | 8.6% | 85.1% |
| 20 | 2 | 7.5% | 96.5% |
| 30 | 4 | 1.6% | 97.0% |

경보 기준(c)을 낮추면 거짓 경보가, 높이면 놓침이 늘어납니다. 둘 다 줄이는 방법은 n을 늘리는 것뿐입니다. 거짓 경보가 잦으면 사람들이 빨간불에 익숙해져 진짜 실패도 무시하게 됩니다(14-2절 변경 감지 테스트와 같은 문제).

**이 레포에 적용하면 (제안).**

- 지시문을 고친 PR: 바꾼 규칙과 맞닿은 시나리오만 골라 `--samples 3`으로 몇 번(예: 3∼4번 실행, 시나리오마다 9∼12회) 돌리고, 시나리오별로 실패 수를 셉니다. 기록도 "6/6" 대신 "시나리오별 12번 중 실패 몇 번"으로 적습니다.
- 파일럿 전 기준선: 전체 시나리오를 시나리오마다 20∼30번 돌려 평소 실패율을 재 둡니다. 이 값이 있어야 위 표의 거짓 경보를 계산할 수 있습니다.
- 모델 비교(5-poc-results의 Haiku 5.5 대 GPT-6 Luna): 두 통과율을 가르려면 한쪽마다 90% 대 80%(10%p 차이)면 약 199번, 90% 대 70%면 약 62번의 실행이 필요합니다(양쪽 유의수준 5%, 검정력 80%, 두 비율 비교의 정규 근사, 실습 7번). 시나리오를 묶어 센 횟수이고, 시나리오마다 따로 가르려면 각각 그만큼 필요합니다. 괄호 안의 말은 이런 뜻입니다. 유의수준 5%는 진짜 차이가 없는데 "있다"고 잘못 말할 확률을 5%까지 받아들인다는 것이고, 검정력 80%는 진짜 차이가 있을 때 그것을 알아챌 확률이 80%라는 것입니다. 정규 근사는 이항분포를 종 모양의 정규분포로 어림해 계산을 줄이는 방법입니다.
- (2026-11-08 추가) **짝지어 비교하면.** 두 모델을 같은 시나리오로 한 번씩 돌려 짝을 지으면, 둘 다 통과하거나 둘 다 실패한 짝은 두 모델의 차이에 대해 아무것도 말해 주지 않습니다. 결과가 갈린 짝만 세어, 한쪽만 통과한 짝의 수가 동전 던지기(반반)로도 나올 만한지 봅니다. 이것이 [13-6절](13-latency.md#13-6-평균이-아니라-꼬리를-본다) 깊이 보기의 **짝지은 부호 검정**입니다(통과·실패처럼 둘 중 하나인 결과에 쓰면 McNemar 검정과 같습니다). 예를 들어 갈린 짝이 10개이고 그중 9개에서 Haiku만 통과했다면 양쪽 p = 2 × (C(10,9) + C(10,10)) ÷ 2^10 = 2 × 11 ÷ 1,024 ≈ 0.021이고, 8개였다면 2 × (45 + 10 + 1) ÷ 1,024 ≈ 0.109입니다. 앞의 것은 5% 미만이라 우연으로 보기 어렵고, 뒤의 것은 열 번에 한 번꼴로 우연히도 나는 차이입니다. 짝을 지으면 시나리오마다 다른 난이도가 두 모델에 똑같이 들어가 상쇄되므로, 따로 센 비율을 비교할 때보다 적은 횟수로 가를 수 있는 경우가 많습니다(일반론). 답 길이(77자 대 54자)처럼 숫자로 나오는 결과는 같은 절의 **순열 검정**(두 묶음을 섞어 아무렇게나 다시 나눌 때 관측한 차이 이상이 얼마나 자주 나오나)으로 같은 질문을 할 수 있습니다.
- 비용은 실행 횟수에 비례하므로(실행마다 LLM 셋 × 턴 수), 위 표는 "돈을 얼마나 쓰면 얼마나 믿을 수 있나"의 표로 읽습니다.

### 시나리오 시뮬레이션이 못 보는 것

텍스트 모드이므로 말 끝 판단, 끼어들기, 발음, 지연은 보지 않습니다. LiveKit은 오디오 모드 시뮬레이션도 제공하므로, 턴 테이킹을 회귀 테스트하려면 그쪽을 검토합니다.

(2026-11-08 추가) 오디오 모드는 `lk agent simulate audio --scenarios scenarios.yaml`입니다(CLI 2.19.3). 가상 고객이 대본을 소리 내어 말하고 끼어들기도 하며, 에이전트는 STT·LLM·TTS를 모두 돌립니다. 같은 시나리오와 판정에 더해 이런 것을 잽니다(LiveKit 문서 "Agent Simulations"의 "Audio simulations").

| 재는 것 | 내용 |
| --- | --- |
| 응답 지연 | 고객 쪽에서 들은 지연의 p50·p95·p99(p50은 중앙값, p95는 100번 중 95번이 그보다 빠른 값, 13-6절). STT·말 끝 판단·LLM 첫 토큰·TTS 첫 바이트로 나눈 값도 냄 |
| 턴 테이킹 | 고객 말이 끝나기 전에 말을 시작한 횟수, 끼어들기 뒤 멈추기까지의 시간, 끼어들지 않았는데 멈춘 횟수, 답하지 않은 고객 턴 |
| 받아쓰기 | 양방향 단어·글자 오류율(에이전트가 들은 것 대 고객이 말한 것, 고객이 들은 것 대 에이전트가 말한 것). 이름·금액 같은 핵심 단어는 따로 셈 |

- `--background-noise`, `--low-quality-microphone`, `--packet-loss`로 가상 고객의 소리를 일부러 나쁘게 할 수 있습니다. 한국어도 지원 언어 목록에 있습니다.
- 대신 실제 시간으로 돌고, 매 턴 STT·TTS를 부르며, 오디오 턴은 텍스트 턴보다 비싸게 셉니다. 문서는 텍스트 모드를 커밋마다, 오디오 모드를 밤마다나 배포 전에 돌리라고 권합니다.
- 오디오 모드의 가상 고객은 에이전트가 먼저 말해야 말을 시작합니다. 이 레포는 고정 첫 멘트로 먼저 말하므로 조건에 맞습니다. 또 CLI는 오디오 모드에서 배포된 에이전트와 같은 턴 감지·적응형 끼어들기 기본값을 쓴다고 문서에 적혀 있습니다(실행 방식에 따른 기본값은 4-5·7-5절).
- 이상은 문서 기준이고, 이 레포에서는 오디오 모드를 돌려 보지 않았습니다.

## 14-6. SDK의 테스트 도구 (아직 안 씀)

LiveKit Agents에는 방 없이 에이전트를 돌리는 테스트 도구가 들어 있습니다. 시뮬레이션보다 빠르고 vitest 안에서 돕니다.

(2026-11-08 추가) 여기서 말하는 테스트 도구는 `@livekit/agents`의 `voice.testing` 모듈입니다. 진짜 `AgentSession`을 방과 소리 없이 만들고, `session.run({ userInput })`으로 사용자 말 한 줄을 넣으면 에이전트가 그 턴에 만든 사건(답 메시지, 도구 호출, 도구 결과, 핸드오프)을 차례대로 모아 돌려줍니다. 테스트는 그 사건들에 단언을 겁니다. LiveKit 문서는 이것을 "unit tests"라고 부르지만, 14-2절의 단위 테스트(함수 하나)보다 넓게 세션·에이전트·LLM 노드·도구를 함께 돌리므로 이 장의 말로는 통합 테스트에 가깝습니다. 디버거(14-4절)가 사람이 한 턴씩 보는 도구라면, 이것은 같은 일을 vitest 안에서 코드로 하고 CI에서 되풀이하는 도구입니다. 실제로 디버거의 글 턴도 내부에서는 같은 `session.run`을 탑니다(14-4절). 이 레포는 아직 이 도구로 쓴 테스트가 없어 절 제목에 "아직 안 씀"이 붙어 있습니다.

| 도구 | 하는 일 |
| --- | --- |
| `session.run({ userInput })` | 방 없이 사용자 입력 하나를 넣고 답을 생성, 일어난 사건(메시지, 도구 호출·결과, 핸드오프)을 모아 돌려줌 |
| `result.expect.nextEvent().isMessage(…)` 등 | 사건 순서대로 검증. `isFunctionCall`, `noMoreEvents` 등 |
| `isMessage(…).judge(llm, { intent })` | 메시지 단언에 이어 그 답이 의도에 맞는지 LLM으로 판정 (엄격한 평가 프롬프트, `check_intent` 도구 호출을 강제해 통과 여부와 이유를 받음). (2026-11-08 갱신) 따로 부르는 함수가 아니라 메시지 단언의 메서드이고, 판정 LLM은 앞뒤 대화 없이 그 메시지 하나만 봄(`agents/voice/testing/run_result.ts` 881∼975, LiveKit 문서 "Unit tests") |
| `FakeLLM`, `withMockTools` | LLM이나 도구를 가짜로 바꿔 결정적으로 테스트. (2026-11-06 갱신) `withMockTools`는 에이전트 **생성자**로 찾으므로, `Agent.create`로 만든 에이전트에는 `voice.Agent`가 아니라 그 인스턴스의 `constructor`를 넘겨야 함(아래) |

도구를 붙이면 "가격을 물으면 `schedule_callback` 도구를 부른다"(가상의 도구 이름이고, 지금 도구는 `end_call` 하나) 같은 **도구 호출 테스트**를 이 방식으로 쓰기 좋습니다. 진짜 LLM으로 돌리면 확률적이지만, 시뮬레이션보다 훨씬 빠르게 반복할 수 있습니다.

- **맞장구 제거가 세션 안에서 돕니다.** `Agent.create`에 넘긴 `llmNode` 훅이 SDK의 `toStream`에 감싸여(12-4절) 실제 세션 경로로 불리고, 대화 기록에 뗀 답이 남습니다. 단위 테스트(`ack.test.ts`)가 함수만 봤다면, 이 시험은 "세션이 정말 그 함수를 쓰는가"까지 봅니다. 한 턴은 2∼12ms 안팎입니다(2026-11-08에 세 번 다시 잼: 첫 턴 약 7ms, 도구를 부르는 턴은 FakeLLM의 `ttft: 5`와 도구 실행이 더해져 10∼12ms, 나머지는 2ms 안팎).
- **17-2 #43이 세션에서 재현되던 한 턴이 회귀 테스트가 됐습니다 (2026-11-06 갱신).** 3글자 조각이면 누적 길이가 3, 6, 9, 12로 커지므로, 고치기 전의 12자에서 판단하는 `withoutLeadingAck`는 "알겠습니다. 감사합니다"만 보고 "다 지우면 원문 유지"로 넘어갔습니다(12-7절 깊이 보기의 k = 12). 처음 판의 이 실습은 세션이 "알겠습니다. 감사합니다. 예산은요?"를 남기는 것을 보였습니다. 고친 뒤에는 맞장구 둘을 떼고 남은 "예"가 생기는 다섯째 조각까지 모아 판단하므로 "예산은요?"가 남습니다. - **도구 호출 경로도 돕니다.** "네, 감사합니다."(9자)는 맞장구뿐이라 판단하지 못한 채 도구 호출 청크가 오므로, `withoutLeadingAck`가 보류분을 먼저 내보냅니다(12-6절 설계 포인트). 맞장구를 다 떼면 빈 글이라 원문이 남았습니다. `result.expect`로 메시지 → `end_call` 호출 → 도구 결과의 순서를 단언했습니다. **함정 1: `withMockTools`에 무엇을 넘기나 (코드로 확인).** SDK는 가짜 도구를 "지금 에이전트의 생성자"로 찾습니다(`agents/voice/testing/run_result.ts` 1050∼1058의 `agent.constructor === agentConstructor`). SDK 주석의 예는 `class DriveThruAgent extends Agent`처럼 직접 만든 클래스를 넘기는데(같은 파일 1073∼1084), 이 레포는 `Agent.create`를 쓰고 이 함수는 **부를 때마다 익명 하위 클래스 `AgentV2`를 새로 만듭니다**(`agents/voice/agent_v2.ts` 129∼133). 그래서 `withMockTools(voice.Agent, …)`는 아무 오류 없이 무시되고 진짜 `end_call`이 돕니다. 진짜 `end_call`은 답이 끝나면 `session.shutdown()`을 부릅니다(`agents/beta/tools/end_call.ts` 157). 메시지 → 호출 → 결과의 **순서만** 단언하면 이 차이를 알아채지 못하고, 도구 결과가 가짜가 돌려준 값인지까지 봐야 드러납니다. 만든 인스턴스의 `agent.constructor`를 넘깁니다.

**함정 2: 같은 ms에 찍힌 사건은 순서가 바뀐다 (코드로 확인 + 실측, 2026-11-06 추가).** `result.events`는 사건을 받는 대로 붙이지 않고 항목의 `createdAt`(ms, `Date.now()`) 순으로 끼워 넣습니다(`agents/voice/testing/run_result.ts` 358∼365: 뒤에서부터 `createdAt <=`인 자리를 찾아 그 뒤에 넣음). 그런데 assistant 메시지의 `createdAt`은 재생 허가를 받은 시각(`replyStartedAt`, `agents/voice/agent_activity.ts` 4061)이고, 도구 호출의 `createdAt`은 도구 실행을 시작한 시각으로 다시 적힙니다(같은 파일 4230∼4236). 도구 호출이 먼저 기록되고 메시지는 답이 끝난 뒤 기록되므로, 두 시각이 **같은 ms**이면 메시지가 도구 호출 **뒤**에 끼어 순서가 "도구 호출 → 메시지"가 됩니다. FakeLLM이 지연 없이 답하면 둘이 1∼2ms 안에 몰려 이런 일이 생깁니다. 처음 판의 실습은 이 때문에 가끔 `isMessage` 단언에서 `Expected ChatMessageEvent, got function_call`로 멈췄습니다(실측: 고치기 전 코드로 20번 중 3번, 고친 뒤 20번 중 1번. 가짜 LLM 첫 토큰 0ms로 40번 돌리면 6번이 같은 ms였음). #43 수정과는 상관없는 SDK 쪽 성질입니다. 실습은 이 답에만 FakeLLM의 `ttft: 5`(첫 조각 전 5ms)를 줘 두 시각을 떼었고, 그 뒤 25번 모두 통과했습니다. 실제 LLM은 첫 토큰까지 수백 ms가 걸려 이 동률이 생기기 어렵지만, 순서를 단언하는 테스트를 FakeLLM으로 쓸 때는 `ttft`를 주거나 순서 대신 "있다"만 단언합니다. SDK 소스에도 "도구를 실행하기 전에 글을 다 만들었는지 확인하라"는 할 일 주석이 있습니다(같은 파일 4226∼4227, `TODO(AJS-272)`). 같은 ms에서 순서를 정할 일련번호를 두거나 문서에 적어 달라고 LiveKit에 피드백을 보냈습니다(2026-11-06).

**`session.run`이 거치지 않는 것 (코드로 확인).**

```ts
// src/agent.test.ts (예시)
import { initializeLogger, voice } from '@livekit/agents';
import { afterEach, beforeEach, expect, it } from 'vitest';
import { createAgent } from './agent.ts';
import { SAMPLE_CALL } from './call-context.ts';

initializeLogger({ pretty: false, level: 'error' }); // 세션은 로거가 없으면 시작하지 못함
const { FakeLLM, withMockTools } = voice.testing;
const llm = new FakeLLM([
  { input: '네, 괜찮아요', content: '네, 예산은 어느 정도 생각하세요?' },
  {
    input: '그냥 전화하지 마세요',
    content: '네, 감사합니다.',
    ttft: 5, // 메시지와 도구 호출이 같은 ms에 찍혀 순서가 바뀌지 않게 (함정 2)
    toolCalls: [{ name: 'end_call', args: {} }],
  },
]);
let session: voice.AgentSession;
let agent: voice.Agent;

beforeEach(async () => {
  session = new voice.AgentSession({ llm });
  agent = createAgent({ call: SAMPLE_CALL, llm });
  await session.start({ agent });
});
afterEach(async () => {
  await session.close();
});

it('본 답 첫머리의 맞장구를 뗀다', async () => {
  const result = session.run({ userInput: '네, 괜찮아요' });
  await result.wait();
  const msg = result.expect.nextEvent().isMessage({ role: 'assistant' }).event();
  expect(msg.item.textContent).toBe('예산은 어느 정도 생각하세요?');
  result.expect.noMoreEvents();
});

it('전화하지 말라고 하면 인사하고 end_call을 부른다', async () => {
  // Agent.create는 부를 때마다 하위 클래스를 새로 만들므로 voice.Agent가 아니라 이 인스턴스의 생성자를 넘깁니다.
  const mock = withMockTools(agent.constructor as Parameters<typeof withMockTools>[0], {
    end_call: () => 'ok',
  });
  try {
    const result = session.run({ userInput: '그냥 전화하지 마세요' });
    await result.wait();
    result.expect.nextEvent().isMessage({ role: 'assistant' });
    result.expect.nextEvent().isFunctionCall({ name: 'end_call' });
    const out = result.expect.nextEvent().isFunctionCallOutput().event();
    expect(out.item.output).toContain('ok'); // 가짜가 정말 쓰였는지
    result.expect.noMoreEvents();
  } finally {
    mock[Symbol.dispose]();
  }
});
```

- SDK 주석의 예는 `using _mock = withMockTools(…)`(블록을 나갈 때 자동으로 `[Symbol.dispose]()`)입니다. Node 24와 이 레포의 tsc는 `using`을 받아들이지만, 이 레포의 eslint 설정(`@typescript-eslint/no-unused-vars`)이 쓰지 않는 변수 `_mock`을 오류로 잡아 `try`/`finally`로 썼습니다(실측).
- 여기에 진짜 LLM과 `judge(llm, { intent })`를 쓰면 "가격을 물으면 금액을 말하지 않는다" 같은 의미 판정도 할 수 있지만, 그 순간 키·비용·확률성이 들어오므로 14-5절의 통과율 이야기가 그대로 적용됩니다.
- (2026-11-08 추가) **함정 3: 이 레포의 LLM은 판정 LLM으로 그대로 쓰지 못할 수 있습니다 (코드로 확인 + 실측).** `judge`는 판정 요청에 `toolChoice: 'required'`와 `extraKwargs: { temperature: 0 }`을 붙입니다(`agents/voice/testing/run_result.ts` 938∼943). `VoiceAnthropicLLM`은 받은 `extraKwargs`를 요청 본문에 그대로 펼치므로([src/models/anthropic.ts](../../src/models/anthropic.ts) 51행), 판정 요청 본문에 `temperature: 0`이 들어갑니다. 가짜 서버가 `check_intent` 도구 호출을 돌려주게 해 `judge`를 끝까지 돌려 보니, 받은 본문에 `temperature: 0`, `tool_choice: {"type":"any", …}`, `thinking: {"type":"disabled"}`가 있었습니다(실측, 확인 뒤 지운 임시 스크립트). 그런데 Haiku 5.5는 기본값(1)이 아닌 `temperature`를 400으로 거절합니다(8-2절, 문서 기준). 그러니 이 레포의 Haiku 5.5를 그대로 판정 LLM으로 넘기면 판정 요청이 400으로 실패할 것으로 봅니다(실제 API로는 확인하지 않음). `temperature: 0`을 받는 다른 모델을 판정에 쓰거나, 판정용으로 `temperature`를 걸러 내는 감싸기를 두어야 합니다. 같은 문제를 LiveKit에 피드백으로 보냈습니다(2026-11-08). 대화 전체를 여러 기준으로 한 번에 채점하는 `JudgeGroup`은 Python SDK에만 있습니다(LiveKit 문서 "Unit tests", 2026-11-08 확인).

## 14-7. CI: 자동으로 도는 것과 돌지 않는 것

(2026-11-08 추가) **CI**(지속적 통합, continuous integration)는 코드를 올릴 때마다 정해 둔 검사를 서버가 자동으로 돌려, 깨진 변경이 `main`에 합쳐지기 전에 알리는 방식입니다. 사람이 `pnpm test`를 깜빡해도 검사가 빠지지 않게 하는 장치입니다. 이 레포는 GitHub Actions를 씁니다. 워크플로 파일 하나에 작업(job) 하나가 있고, 그 안의 단계(step)를 위에서부터 차례로 실행합니다. 한 단계가 0이 아닌 종료 코드로 끝나면 그 뒤 단계는 기본값으로 건너뛰고 작업 전체가 실패(빨간불)로 표시됩니다(GitHub Actions 기본 동작). 그래서 형식 검사에서 실패하면 그 실행에서는 뒤의 단위 테스트가 돌지 않습니다.

[.github/workflows/tests.yml](../../.github/workflows/tests.yml)이 `main` 푸시와 PR마다 도는 것은 아래와 같습니다. ●는 그 단계가 돈다는 뜻이고, 위에서 아래가 실제 실행 순서입니다(설치 단계 `pnpm install`은 표에서 뺐음).

| 단계 | 돎 |
| --- | --- |
| `pnpm typecheck` (tsc) | ● |
| `pnpm lint` (eslint) | ● |
| `pnpm format:check` (prettier) | ● |
| `pnpm test` (단위 테스트) | ● (2026-11-03 추가) |
| 시나리오 시뮬레이션 | 없음 (비용 때문에 뺌, [4-setup-checklist.md 1-1](../4-setup-checklist.md#1-1-레포-구조)) |

처음에는 단위 테스트가 CI에 없었습니다. API 키도 비용도 필요 없는 테스트라 마지막 단계로 추가했고, 이제 맞장구 제거·발음·보정·캐시 접두사 규칙을 깨는 변경이 들어오면 머지 전에 그 PR의 검사가 빨간불이 됩니다. 가짜 서버 계약 테스트(14-3절)도 키 없이 로컬 포트만 쓰므로 CI에서 그대로 돕니다. [AGENTS.md](../../AGENTS.md)는 시나리오도 `main` 머지마다 돌리라고 권하므로, 비용을 감안해 "지시문이 바뀐 PR에서만" 같은 조건으로 도입하는 방법이 남은 과제입니다. (2026-11-08 추가) LiveKit 문서 "Run simulations in CI"에 GitHub Actions 예가 있습니다. ### CI가 못 잡는 것 (2026-11-06 추가)

위 표의 ●만 보면 빈틈이 없어 보이지만, 각 단계가 **무엇을** 검사하는지 따라가 보면 비어 있는 곳이 있습니다.

**① 테스트 파일은 어디서도 타입 검사를 받지 않습니다 (설정으로 확인 + 실측).**

- `pnpm typecheck`(`tsc --noEmit`)는 [tsconfig.json](../../tsconfig.json)을 따르는데, `exclude`에 `**/*.test.ts`가 있습니다. `tsc --listFilesOnly`로 보면 검사 대상에 테스트 파일이 0개입니다(실측). 레포에는 왜 뺐는지 적혀 있지 않습니다.
- vitest는 TypeScript의 타입을 **지우기만** 하고 실행합니다. vitest 4.1.12가 쓰는 Vite 8은 TS 변환을 `vite:oxc` 플러그인(`transformWithOxc`)이 맡습니다(`node_modules/.pnpm/vite@8.3.5_…/node_modules/vite/dist/node/chunks/node.js` 7593·7641∼7665, 코드로 확인). vitest의 `--typecheck` 모드는 켜져 있지 않습니다(`package.json`의 `test` 스크립트는 `vitest --run`).
- `pnpm lint`는 테스트 파일도 보지만, 이 레포 설정은 타입 정보가 필요 없는 규칙(`tseslint.configs.recommended`)뿐입니다(12-2절 깊이 보기).
- 실험: 레포 밖 임시 테스트 파일에서 `new VoiceAnthropicLLM({ …, effort: 'lowest', … })`처럼 없는 값을 넣었더니 vitest는 **통과**했고, 같은 파일을 레포 설정을 상속한 임시 tsconfig로 검사하자 `error TS2322: Type '"lowest"' is not assignable to type 'Effort'.`가 나왔습니다(실측). 지금 있는 테스트 파일 8개를 같은 방법으로 검사하면 오류는 0개였습니다(실측, 2026-11-08에 `ack.test.ts`의 새 테스트 둘을 포함해 다시 확인). 지금은 깨끗하지만 지켜 주는 장치가 없습니다.
- 막는 방법(제안): `tsconfig.json`을 상속하고 `exclude`만 비운 테스트용 설정을 두고, CI에서 `tsc -p`를 한 번 더 돌립니다.

**② 이미지 빌드는 CI에서 돌지 않습니다 (워크플로로 확인).**

- [tests.yml](../../.github/workflows/tests.yml)에는 `docker build` 단계가 없습니다. 그래서 15-4절의 "설치 단계에 워크스페이스 설정이 없던 문제" 같은 Dockerfile 회귀는 CI에서 드러나지 않습니다. CI는 레포를 통째로 체크아웃한 뒤 설치하므로 `pnpm-workspace.yaml`·`patches/`가 늘 그 자리에 있고, Dockerfile이 그 파일들을 복사하는지는 보지 않기 때문입니다.
- LiveKit Cloud는 배포할 때 이 Dockerfile로 원격 빌드하므로(15-5절), 지금 구조에서는 **배포하는 순간** 처음 드러납니다. 15-4절도 "실제 `docker build`는 아직 돌려 보지 않았습니다"라고 적었습니다.
- 막는 방법(제안): 이미지를 올리지 않는 `docker build .` 단계 하나를 더합니다. GitHub의 우분투 실행기에는 Docker가 들어 있습니다(GitHub 문서 기준, 빌드 시간은 재지 않음).

**③ (지켜 주는 쪽) CI의 `pnpm install`은 lockfile을 고치지 않습니다.**

- 워크플로는 `pnpm install`만 쓰고 `--frozen-lockfile`을 적지 않았지만, pnpm이 CI에서는 그것을 기본으로 켭니다. pnpm 12.16.1의 `pnpm help install`은 `--frozen-lockfile`을 "This setting is enabled by default in CI when a lockfile is present"라고 설명합니다. GitHub Actions는 모든 작업에 `CI=true` 환경변수를 넣습니다(GitHub 문서 기준). pnpm 12는 Rust로 만든 실행 파일이라 CI를 알아보는 코드 자체는 확인하지 않았습니다.
- 실험: 레포 밖 임시 폴더에 `package.json`·`pnpm-lock.yaml`·`pnpm-workspace.yaml`·`.npmrc`·`patches/`를 복사하고 `package.json`의 zod 범위만 바꿨습니다. `CI=true pnpm install --offline`은 `ERR_PNPM_OUTDATED_LOCKFILE`(`specifiers in the lockfile don't match specifiers in package.json`)로 종료 코드 1이었고, `CI` 없이(`--lockfile-only --offline`) 돌리면 lockfile을 새로 풀려고 레지스트리 메타데이터를 찾다가 `ERR_PNPM_NO_OFFLINE_META`로 멈췄습니다(실측). 곧 `package.json`만 고치고 lockfile을 커밋하지 않은 PR은 CI의 설치 단계에서 실패합니다. Dockerfile은 같은 검사를 `--frozen-lockfile`로 명시합니다(15-4절).

**그 밖에.**

- `pnpm lint`의 대상은 `"**/*.{ts,js}"`라 학습서 실습(`.mjs`)은 CI에서 린트되지 않고, `.prettierignore`에 `docs/`가 있어 `format:check`도 문서와 실습을 보지 않습니다. 이 장의 실습은 손으로 `pnpm exec eslint docs/1-study/lab/14-*.mjs`를 돌려 확인했습니다.
- 시나리오 시뮬레이션은 위 표대로 돌지 않고, 14-3절 깊이 보기의 "알려진 버그" 테스트(`it.fails`)나 14-6절의 세션 테스트도 아직 없습니다.
