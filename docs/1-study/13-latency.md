# 13장. 지연 공학 — 1초를 쪼개 쓰는 법

음성 에이전트의 품질을 숫자 하나로 말하라면 **"고객이 말을 마치고 AI가 말을 시작하기까지의 시간"**입니다. 이 장은 그 시간을 구간으로 나눠 재고, 어디를 어떻게 줄였는지, 남은 병목은 무엇인지를 정리합니다. 앞 장들에서 흩어져 나온 기법을 "지연"이라는 하나의 관점으로 다시 묶는 장입니다.

---

## 13-1. 왜 1초인가

- 사람 대화의 공백은 언어를 막론하고 대개 **0~200ms** 근처입니다(7장).
- 1초 가까운 침묵은 "생각하는 중"으로 느껴지고, 2초를 넘으면 "안 들리나?" "끊겼나?"를 의심하게 됩니다.
- 업체 서비스 수준은 0.6~0.95초입니다([2-tech-stack.md 8장](../2-tech-stack.md#8-응답-지연-예산)).

그래서 목표를 **1초 안팎**으로 잡았습니다. 사람 수준(0.2초)은 단계 연결형 구조로는 현실적으로 어렵고, 1초 안쪽이면 "조금 생각하고 답하는 사람" 정도로 느껴집니다.

## 13-2. 지연 예산: 직렬 구간의 합

```text
고객 말 끝 ─┬─ 말 끝 판단 ─┬─ LLM 첫 토큰 ─┬─ (문장 모으기) ─┬─ TTS 첫 음성 ─┬─ 네트워크·재생 ─▶ 고객이 들음
            │ VAD 256ms    │ (새 연결)      │ 단어 보류        │ ElevenLabs     │ 방·지터 버퍼
            │ + FINAL 도착 │ + 네트워크 왕복 │ + blingfire     │ TTFB           │
            │ + 턴 판정    │ + 프리필       │ 20자 규칙        │ (+ 프레임 보류) │
            │              │ (+ 생각 토큰)  │ (12자 보류는 가려짐)│              │
```

(2026-11-06 갱신) 처음 판의 그림은 문장 모으기 칸에 "+ 맞장구 보류 12자"를 더했습니다. 지금 설정에서는 더해지지 않습니다(아래 표 뒤). 연결과 프레임 보류는 새로 넣었습니다.

이 구간들은 **차례로** 일어나므로 지연은 합입니다. 한 구간을 줄이면 전체가 줄지만, 가장 큰 구간을 놔두고 작은 구간을 줄여 봐야 효과가 작습니다. 병렬 처리 이론의 **암달의 법칙**과 같은 직관입니다. 전체 개선 효과는 그 부분이 전체에서 차지하는 비율에 묶입니다.

| 구간 | 목표 ([2-tech-stack.md 8장](../2-tech-stack.md#8-응답-지연-예산)) |
| --- | --- |
| 말 끝 판단 | 0.3~0.5초 |
| STT 확정 | 0.15~0.3초 (말 끝 판단에 포함되어 측정됨) |
| LLM 첫 토큰 | 0.2~0.4초 |
| TTS 첫 음성 | 0.1~0.2초 |
| 네트워크 | 0.05~0.1초 |

(2026-11-06 갱신) 표의 값은 목표이고, 앞 장에서 확인한 사실로 두 칸에 단서가 붙습니다.

- **말 끝 판단 0.3~0.5초는 턴 감지 모델이 확신할 때만입니다.** p가 기준(`v1-mini`의 ko 0.4)보다 낮으면 `maxDelay` 2.5초를 기다립니다. 합성 음성 "네."는 p 0.12~0.20이라 2.5초를 기다렸습니다([7-4절 깊이 보기](07-turn-taking.md#깊이-보기-쉼-동안의-확률을-직접-그려-보기-2026-11-06-추가), 17-2 #39). 그래서 이 칸은 봉우리가 둘(약 0.4초와 약 2.5초)인 분포이고, 꼬리를 정하는 것은 두 번째 봉우리입니다(13-6절).
- **맞장구 보류 12자는 지금 설정에서 직렬로 더해지지 않습니다.** ElevenLabs 플러그인의 blingfire 분할기가 "20자 이상 + 다음 문장 시작"을 기다리는 동안 12자 보류는 이미 풀려 있습니다. 보류가 있든 없든 TTS 첫 글은 같은 시각이었습니다([11-7절 깊이 보기](11-session-pipeline.md#깊이-보기-12자-보류의-값-2026-11-06-추가): 둘 다 550ms). 대신 이 레포의 실제 경로(12자 보류 → `filter_markdown` → 발음 변환 → 분할기)는 **단어 끝까지 붙잡는 단계 때문에** 분할기만 쓸 때보다 첫 덩어리가 125~200ms 늦습니다([10-4절 깊이 보기](10-tts.md#깊이-보기-한-글자씩-넣어-잰-분할-시각-2026-11-06-추가), 25ms/글자: 기본값 700 → 900ms, `minSentenceLength` 8이면 225 → 350ms). `minSentenceLength`만 낮춰서는 이 앞단 보류가 줄지 않고, 12보다 낮추면 12자 보류가 다시 드러납니다(11-7절).

#### 깊이 보기: 왕복(RTT)으로 세는 네트워크 비용 (2026-11-06 추가)

LLM 첫 토큰과 TTS 첫 음성 안에는 네트워크가 들어 있습니다. 그 몫을 **왕복 시간(RTT, round-trip time)**의 배수로 세면 어디를 줄일 수 있는지 보입니다. RTT는 패킷 하나가 상대에게 갔다가 답이 돌아오기까지의 시간입니다.

**새 HTTPS 연결 하나가 첫 바이트를 받기까지 (규격으로 확인).**

```text
클라이언트                                         서버(TLS를 끝내는 곳)
 ── DNS 조회 (OS 캐시에 있으면 수 ms) ──
 SYN ─────────────────────────────────────────▶            ┐ TCP 3방향 악수: 1 RTT
 ◀───────────────────────────────────── SYN, ACK           ┘ (RFC 9293 3.5절. 셋째 ACK와 함께 데이터를 보낼 수 있음)
 ClientHello (키 공유 포함) ─────────────────────▶           ┐ TLS 1.3 전체 악수: 1 RTT
 ◀── ServerHello, {EncryptedExtensions, Certificate,        │ (RFC 8446 2절. { }는 이미 암호화된 메시지)
      CertificateVerify, Finished}                          ┘
 {Finished} + HTTP 요청(POST) ─────────────────▶             ┐ 요청 → 첫 바이트: 1 RTT
                                           (서버 처리)      │ + 서버 처리
 ◀───────────────────────────────────── 응답 머리글          ┘
```

curl의 `-v` 출력에서 TLS 줄만 남기면 이 흐름이 그대로 보입니다(실측, IP가 든 줄은 버림). `Unknown (8)`은 EncryptedExtensions입니다.

```text
* (OUT), TLS handshake, Client hello (1):
* (IN), TLS handshake, Server hello (2):
* (IN), TLS handshake, Unknown (8):
* (IN), TLS handshake, Certificate (11):
* (IN), TLS handshake, CERT verify (15):
* (IN), TLS handshake, Finished (20):
* (OUT), TLS handshake, Finished (20):
* SSL connection using TLSv1.3 / AEAD-AES128-GCM-SHA256 / [blank] / UNDEF      ← Bedrock 도쿄 (api.anthropic.com도 TLSv1.3)
* ALPN: server accepted http/1.1
```

| 경우 | 첫 바이트까지 | 비고 |
| --- | --- | --- |
| 새 연결, TLS 1.3 | DNS + 3 RTT + 서버 처리 | 위 그림 |
| 새 연결, TLS 1.2 | DNS + 4 RTT + 서버 처리 | 전체 악수가 2 RTT(RFC 5246). 비교용 |
| 연결 재사용(keep-alive) | 1 RTT + 서버 처리 | TCP·TLS를 건너뜀 |
| TLS 1.3 세션 재개 | 새 연결과 같은 3 RTT | 인증서를 다시 받고 검증하는 몫(바이트·계산)만 줄어듦. 왕복을 줄이는 0-RTT(early data)는 재전송 공격에 안전하지 않다고 규격이 적고(RFC 8446 2.3·8절. 2026년 7월 RFC 9846이 8446을 대체했으므로 절 번호는 새 판에서 다시 확인, 17-3절), POST 같은 멱등하지 않은 요청에는 맞지 않으므로 이 장의 계산은 0-RTT 없이 셈 |

**잰 값 (실측, 2026-11-06, 맥 서울, curl 8.7.1).** [lab/13-rtt.mjs](lab/13-rtt.mjs) `--curl`로 두 주소에 **키 없이** POST를 보내 401·403만 받았습니다(과금 없음). Node 쪽(SDK 0.33의 node-fetch, Node 내장 fetch)과 같게 HTTP/1.1로 맞췄고, 두 번 실행해 새 연결 9회·재사용 18회씩입니다. 시간만 적고 IP는 적지 않습니다.

| 구간 | api.anthropic.com | Bedrock 도쿄 (`bedrock-runtime.ap-northeast-1`) |
| --- | --- | --- |
| DNS (OS 캐시) | 2.5~6.5ms | 2.7~7.7ms. 캐시가 비었던 첫 조회는 75ms(이 실습), 873ms(그 전에 HTTP/2로 돌려 본 첫 실행) |
| TCP = 1 RTT | 6.2~8.0ms | 38.8~43.9ms |
| TLS 1.3 | 9.9~13.0ms | 40.7~47.2ms |
| 요청 → 첫 바이트 (재사용) | **198~225ms** | 41~46ms |
| 새 연결의 첫 바이트 (DNS가 따뜻할 때) | 225~272ms | 124~143ms |
| 다시 맺는 비용 (DNS + TCP + TLS) | **약 20~30ms** | **약 80~100ms** |

[lab/13-rtt.mjs](lab/13-rtt.mjs) 1·2번(계산만)은 같은 식에 대략의 RTT를 넣어 비교합니다. 광섬유 속 빛은 1ms에 약 200km를 가므로 왕복의 바닥은 거리(km) ÷ 100ms입니다. 서울–도쿄 약 1,160km면 약 12ms, 서울–미국 서부 약 9,000km면 약 90ms, 동부 약 11,100km면 약 111ms이고, 실제 RTT는 경로가 직선이 아니고 장비를 거쳐 이보다 큽니다(미국 쪽 대략 130~180ms, 재지 않음).

```text
실습 2번 (계산. RTT는 위 실측 또는 대략의 값, DNS 5ms 가정, back = 접속 지점 뒤의 몫: 도쿄 2ms, Anthropic 200ms)
   경로                                  새 연결 TLS1.3  새 연결 TLS1.2  재사용  다시 맺는 비용
   Bedrock 도쿄 (실측 RTT 약 41ms)             130ms           171ms     43ms        +87ms
   Anthropic 접속 지점 (실측 RTT 약 7ms)        226ms           233ms    207ms        +19ms
   미국 서부를 바로 (RTT 대략 130ms)            397ms           527ms    132ms       +265ms
   미국 동부를 바로 (RTT 대략 180ms)            547ms           727ms    182ms       +365ms
```

읽을 점입니다.

- **도쿄는 그림의 3 RTT가 숫자로 보입니다.** TCP, TLS, 요청이 각각 약 41ms입니다. 서명 없는 요청의 403은 지역 끝점이 바로 돌려주므로 "요청 → 첫 바이트"도 거의 1 RTT입니다.
- **Anthropic은 접속 지점이 약 7ms 거리인데, 401이 오는 데 약 0.2초가 걸립니다.** TCP·TLS는 가까운 접속 지점에서 끝나고, 키를 검사해 401을 돌려주는 곳은 그 뒤로 약 0.2초 왕복 거리에 있습니다. 위치는 공개되지 않았고, 미국까지의 왕복에 처리 시간을 더한 크기와 맞습니다(추정). 실제 요청도 이 문을 지나므로, Anthropic 경로의 첫 토큰 약 0.8초 가운데 **약 0.2초는 "문까지의 왕복"**으로 봅니다(추정). 13-5절의 "접속 지점과 처리 위치는 다르다"를 숫자로 본 것입니다.
- **두 경로의 차이는 약 0.16초(0.2 − 0.04)입니다.** 2026-11-05 A/B의 최소 차이 0.21초, 중앙값 차이 0.11초(13-5절)와 같은 크기입니다. A/B는 연결을 재사용한 값이므로(8-9절) 재사용 줄과 견줍니다.
- **#28의 "다시 맺는 비용 약 0.07~0.1초"는 도쿄 쪽에 맞는 값입니다.** 그 실험은 Bedrock 주소로 했고(8-8절 표), 도쿄의 DNS + 2 RTT ≈ 80~100ms와 맞습니다. Anthropic 경로는 접속 지점이 가까워 약 20~30ms입니다. curl 기준이고, Node와 SDK 0.33의 TLS 처리 시간은 재지 않았습니다.
- **DNS가 비어 있으면 한 번에 수백 ms일 수 있습니다.** 도쿄 주소의 첫 조회가 한 번은 873ms, 한 번은 75ms였습니다. Node는 DNS 결과를 스스로 캐시하지 않고 OS에 묻습니다(`dns.lookup`, 일반론). 미리 연결(8-8절)은 연결이 닫힌 뒤에도 이 OS 캐시를 데워 둔 몫이 남습니다.
- **13-5절의 "TCP 연결 0.04초"와 다릅니다.** 이번에는 DNS를 빼고 6~8ms였습니다. 그날 값이 DNS를 포함했는지, 다른 네트워크였는지는 기록이 없어 모릅니다.

(추론, 미측정) **취소된 요청이 연결을 붙잡으면.** HTTP/1.1은 연결 하나에 요청 하나씩 차례로 오갑니다. 끼어들기나 선제 생성 취소 뒤에도 응답은 끝까지 읽힙니다([12-8절](12-streams-async.md#12-8-취소의-전파-끼어들면-사슬이-어떤-순서로-멈추나-2026-11-06-추가), 17-2 #41). 그동안 다음 요청은 쉬고 있는 다른 연결을 쓰거나 새로 맺어야 하고, 쉬는 연결이 없으면 위 표의 "다시 맺는 비용"이 그 턴의 첫 토큰에 더해집니다.

**고객 쪽 음성 경로 (앞 장 값과 일반론, 이 레포에서 미측정).** SDK의 메트릭은 워커가 소리를 받은 때부터 워커가 소리를 내놓은 때까지만 봅니다(13-3절 깊이 보기). 고객 쪽 양 끝은 이렇습니다.

| 칸 | 올라올 때 (고객 입 → 워커) | 내려갈 때 (AudioSource → 고객 귀) | 근거 |
| --- | --- | --- | --- |
| 패킷화 | 20ms를 모아야 패킷 하나 (Opus 20ms, 전화망 `ptime=20`) | 같음 (워커가 Opus로 인코드) | 2-4절, 3-1절 |
| 코덱 선행(look-ahead) | Opus는 CELT 층 2.5ms, SILK 층 5ms(+ 표본율 변환 최대 1.5ms) | 같음 | RFC 6716 2절 (문서 기준) |
| 네트워크 편도 | 브라우저 → LiveKit Cloud(SFU) → 워커 | 워커 → SFU → 브라우저 | 3-3절. 리전에 따라 다름 |
| 지터 버퍼 | 워커 안 NetEq | 브라우저 NetEq | 2-6절. 손 계산 예 50ms |
| 그 밖 | 워커의 FFI 큐(자리 약 10프레임, 밀릴 때만 지연) | 브라우저·장치의 출력 버퍼 | 2-6절 |
| 전화 단계에서 더해짐 | G.711 20ms, Asterisk 코덱 변환, 통신사 장비의 지터 버퍼 | 같음 | 2-5절, [7-telephony-setup.md](../7-telephony-setup.md) |

어림하면 한 방향에 패킷화 20ms + 선행 수 ms + 편도 수십 ms + 지터 버퍼 수십 ms, **약 50~150ms**입니다(추정). 고객이 느끼는 "말 끝 → 첫 소리"에는 **올라올 때와 내려갈 때가 모두** 더해집니다. 13-3절 깊이 보기의 자에서 U→A, H→I 칸입니다.

## 13-3. 무엇을 재는가: LiveKit 메트릭의 정확한 의미

[src/main.ts](../../src/main.ts)는 세션 메트릭을 통화마다 로그로 남깁니다.

```ts
session.on(voice.AgentSessionEventTypes.MetricsCollected, (ev) => metrics.logMetrics(ev.metrics));
```

메트릭은 이름만 보고 해석하면 틀리기 쉽습니다. SDK 코드(`metrics/base.ts`와 기록 위치)에서 확인한 정확한 정의입니다.

| 메트릭 | 필드 | 시작점 → 끝점 | 해석 주의 |
| --- | --- | --- | --- |
| **EOU** (말 끝) | `endOfUtteranceDelayMs` | **마지막 말소리 시각** → 턴 확정 | VAD의 무음 대기(256ms)가 **포함**됨. "VAD 말 끝부터"가 아님. (2026-11-06 추가) 식은 `max(턴 확정 − lastSpeakingTime, 0)`(`agents/voice/audio_recognition.ts` 145). 기준점이 VAD가 거꾸로 맞춘 워커 시각이라, 이벤트 루프 막힘과 워커 앞(네트워크·지터 버퍼)의 지연은 빠질 수 있음(5-5절 깊이 보기) |
| | `transcriptionDelayMs` | 마지막 말소리 시각 → 마지막 FINAL **또는 PREFLIGHT**를 처리한 시각 | STT 확정 지연. 6장 finalize의 효과가 여기 보임. (2026-11-06 갱신) 식은 `max(lastFinalTranscriptTime − lastSpeakingTime, 0)`(같은 파일 144). 그 밖에 체감 지연에 가장 가까운 값이 있습니다. assistant 메시지의 `metrics`에 붙는 **`e2eLatency`**(초)입니다. 개별 메트릭을 더하는 것보다 이 값을 보는 것이 정확합니다. (2026-11-06 갱신) 처음 판은 이 값을 "에이전트 첫 오디오 프레임이 실제로 재생된 시각"까지로, "즉시 반응이 있으면 즉시 반응의 첫 소리 기준"으로 적었는데, 코드로 보면 둘 다 틀렸습니다.

- **끝점은 본 답(LLM 답)의 첫 프레임을 에이전트 쪽 오디오 출력에 넘긴 시각입니다.** 방 출력은 첫 프레임을 `AudioSource`에 넣기 직전에 `onPlaybackStarted(Date.now())`로 "재생 시작"을 스스로 알리고(`agents/voice/room_io/_output.ts` 701~704), LLM 답 작업이 이 시각에서 사용자 메시지의 `stoppedSpeakingAt`(= `lastSpeakingTime`)을 뺍니다(`agents/voice/agent_activity.ts` 4283~4296). SDK 주석도 방 출력의 재생 시작은 "트랙에 넣을 때의 자가 보고라 클라이언트까지의 전달은 들어 있지 않다"고 적습니다(`agents/llm/chat_context.ts` 285~303의 `playbackLatency` 설명). 같은 메시지의 `playbackLatency`(첫 프레임을 넘기기 시작한 때 → 재생 시작 보고)가 방 출력에서 거의 0인 이유입니다.
- **즉시 반응은 들어가지 않습니다.** `say()`의 작업(`ttsTaskImpl`)은 `playbackLatency`까지만 계산하고 `e2eLatency`는 계산하지 않으며(3740~3764), 이 프로젝트의 즉시 반응은 `addToChatCtx: false`라 메시지도 남기지 않습니다(11-3절). 거꾸로 본 답의 `e2eLatency`에는 "네네."가 끝나기를 기다린 시간이 들어갈 수 있습니다.
- 그래서 `e2eLatency`는 고객이 느끼는 지연보다 **짧게** 나옵니다. 시작점(워커가 받은 소리 기준)은 고객이 실제로 멈춘 때보다 늦고, 끝점(워커가 내놓은 때)은 고객이 듣는 때보다 이릅니다. 빠진 양 끝은 13-2절 깊이 보기의 고객 쪽 음성 경로입니다.
- 이 레포는 지금 `e2eLatency`를 남기지 않습니다. [src/main.ts](../../src/main.ts)는 `MetricsCollected`만 듣고(108~111행), 통화 결과의 지연 기록([src/call-result.ts](../../src/call-result.ts)의 `CallLatency`)도 말 끝 판단·LLM 첫 토큰·TTS 첫 음성 세 칸뿐입니다. 남기려면 `ConversationItemAdded`에서 assistant 메시지의 `metrics.e2eLatency`를 읽습니다(11-7절의 제안 코드와 같은 자리, 적용하지 않음).

**교훈:** 메트릭을 더해서 전체 지연을 추정하면, 겹치는 구간(선제 생성)과 빠진 구간(문장 모으기, 맞장구 보류)이 있어 틀립니다. 구간 메트릭은 **어디가 병목인지 찾는 데**, 종단 지연은 **고객 경험을 판단하는 데** 씁니다. (2026-11-06 추가) 다만 `e2eLatency`도 양 끝의 네트워크가 빠진 **하한**입니다.

읽을 점입니다.

- **어느 메트릭도 덮지 않는 칸이 셋입니다.** 올라오는 길(U→A), 앞단 보류와 문장 모으기(E→F), 내려가는 길(H→I). 즉시 반응의 첫 소리도 어느 메트릭에도 없습니다.
- **메트릭을 더하면 모자랍니다.** EOU 406 + `ttftMs` 800 + `ttfbMs` 170 = 1,376ms인데 `e2eLatency`는 약 1,678ms입니다. 차이 약 300ms는 D→F(12자 보류와 문장 모으기를 합친 몫인데, 지금 설정에서는 문장 모으기가 정함)와 G→H입니다.

#### 깊이 보기: 어느 시계로 재나 (2026-11-06 추가)

컴퓨터에는 성질이 다른 시계가 셋 있고, 이 장의 메트릭은 이것들을 나눠 씁니다.

| 시계 | Node에서 | 성질 |
| --- | --- | --- |
| 벽시계 | `Date.now()` | 1970년부터의 ms(정수). OS가 NTP로 맞추므로 **뛰거나 뒤로 갈 수 있음**. 다른 기계와 견줄 수 있는 유일한 시계 |
| 단조 시계 | `performance.now()`(ms, 소수), `process.hrtime.bigint()`(ns, BigInt) | 앞으로만 감. 간격 재기용. 기계 사이에서는 뜻이 없음 |
| 오디오 시계 | 샘플 수 ÷ 표본율 | "소리 안에서 몇 초째인가". VAD 사건의 `timestamp`, STT 결과의 `startTime`·`endTime`, RTP 타임스탬프(3장) |

메트릭마다 쓰는 시계입니다(코드로 확인).

| 값 | 시계 | 코드 |
| --- | --- | --- |
| `ttftMs`, `durationMs` (LLM) | `process.hrtime.bigint()` → ms로 버림 | `agents/llm/llm.ts` 382·403·418·424 |
| `ttfbMs` (TTS) | `process.hrtime.bigint()`. 같은 시작점을 `performance.now()`로도 찍어 오디오 프레임에 붙임 | `agents/tts/tts.ts` 549~550·685, 주석 144~150("TTFB에 쓰는 두 시계") |

- **한 메트릭 안에서는 같은 시계끼리 뺍니다.** 서로 다른 시계를 빼는 곳은 찾지 못했습니다. TTS가 시작 시각을 두 시계로 찍어 두는 것도 그래서입니다.
- **벽시계로 잰 간격은 그 사이에 시계가 뛰면 틀립니다.** NTP가 시각을 한 번에 고치면(step) 그 간격이 그만큼 늘거나 줄어듭니다. `transcriptionDelay`·`endOfUtteranceDelay`는 `Math.max(…, 0)`으로 음수만 막고, `e2eLatency`는 그런 처리도 없습니다(4293). NTP는 보통 작은 차이를 천천히 맞추므로(slew) 드문 일이지만, 시각 동기화 직후(가상 머신이 막 떴을 때 등)의 통화에서 이상한 값이 나오면 의심할 거리입니다(일반론). 단조 시계를 쓰는 `ttftMs`·`ttfbMs`는 이 영향을 받지 않습니다.
- **오디오 시계를 벽시계로 옮기는 곳.** STT가 단어의 끝을 오디오 시각으로 주면 세션은 "입력이 시작된 벽시계 시각 + STT 시각"으로 옮기고(`audio_recognition.ts` 1235~1246), 미래가 되지 않게 `Math.min(…, Date.now())`으로 자릅니다(1303~1311). 주석은 "재사용된 STT 스트림의 시계가 이 활동의 입력 기준보다 훨씬 앞설 수 있고(핸드오프 뒤 등), 미래의 `lastSpeakingTime`은 판정 대기를 그만큼 멈춰 세운다"고 적습니다. STT가 말 끝을 직접 내는 `stt` 모드에도 같은 자르기가 있고, 그 주석은 "공급사 시계 차"라고 부릅니다(1527~1531). **이 프로젝트는 VAD가 있어서** 말소리를 본 뒤로는 STT 시각이 `lastSpeakingTime`을 덮어쓰지 않습니다(1315~1319, 6-5절 깊이 보기 ①). 기준은 VAD 쪽의 "벽시계 − 쌓인 무음 길이(오디오 시계)"입니다(5-5절).
- **해상도.** `Date.now()`는 1ms 정수이고 `ttftMs`도 ms로 버리므로, 이 메트릭들에서 ±1ms는 뜻이 없습니다.

## 13-4. PoC에서 실제로 줄인 과정

[5-poc-results.md](../5-poc-results.md)의 측정을 시간 순서로 다시 보면, 병목이 옮겨 다니는 모습이 보입니다.

```text
첫 측정 (Deepgram STT)

     │ ① 생각 모드 끔 (LLM 단독 2.5~3.0초 → 0.8초)
     │    ※ 첫 측정 전에 이미 적용됨. 켰다면 3초대
     ▼
STT를 Soniox로 교체 (정확도 ↑)
  말 끝 0.57~1.42초                                 ← 새 병목: STT 확정
     │ ② 끝점 지연 조정 3, 언어 감지 끔 → 0.40초 대부분, 가끔 1.26~1.29초
     │ ③ VAD 말 멈춤 때 finalize (패치) → 0.38~0.54초, 1초 넘는 턴 사라짐
     ▼
  말 끝 0.4~0.5 + LLM 0.8 + TTS 0.17 ≈ 1.4초        ← 병목: 다시 LLM
     │ ④ 지시문으로 답 길이 119자 → 77자 (LLM 생성·TTS 시간 감소)
     │ ⑤ 즉시 반응 "네네" + 첫머리 맞장구 코드 제거 (11장)

  본 답 시작은 그대로 약 1.4초                       ← 실제 병목은 여전히 LLM
     ▼
  다음 과제: LLM 첫 토큰, 즉시 반응 미리 합성, 본 답 길이 다시 잡기
```

#### LLM을 아시아에서 처리할 수 있나 (2026-11-03 조사, poc-results)

[5-poc-results.md](../5-poc-results.md) "LLM을 아시아에서 돌릴 수 있나"의 결과입니다.

- 서울에서 `api.anthropic.com`까지 **TCP 연결은 0.04초**였습니다. 가까운 접속 지점이 있다는 뜻이고, 첫 토큰 0.7~1.2초의 대부분은 **접속 지점 뒤의 처리**(실제 모델 서버까지의 거리, 대기열, 프리필)에 있습니다. "네트워크가 가까우니 빠르겠지"라는 추측을 잰 값이 바로잡은 사례입니다. (2026-11-06 갱신) 2026-11-06에 curl로 다시 재니 DNS를 뺀 TCP 연결은 6~8ms였고(그날의 0.04초가 DNS를 포함했는지는 기록이 없음), 대신 키 없는 요청이 401을 받기까지 연결을 재사용해도 약 0.2초가 걸렸습니다(13-2절 깊이 보기). 접속 지점은 아주 가깝고, 요청을 실제로 처리하는 곳(적어도 키를 검사하는 곳)은 약 0.2초 왕복 뒤에 있습니다.
- Haiku 5.5를 **아시아에서 처리한다고 문서로 보장되는 선택지는 Amazon Bedrock의 `jp.` 추론 프로필(도쿄·오사카)뿐**이었습니다. Anthropic API의 처리 위치 옵션(`inference_geo`)은 `global`·`us`뿐이고, Vertex AI와 Anthropic 운영 클라우드 경로도 아시아 처리는 없었습니다. Bedrock `jp.`는 글로벌보다 약 10% 비쌉니다.
- 판단은 "바꾸기 전에 같은 프롬프트로 Anthropic API와 Bedrock `jp.`를 A/B로 잰다"입니다. 그리고 쓰려면 지금의 Anthropic 플러그인(오래된 SDK 0.33 기반)이 Bedrock 클라이언트를 받을 수 있는지부터 확인해야 합니다. 8-8절처럼 플러그인을 감싸는 방식이 다시 필요할 수 있습니다.

**접속 지점(edge)과 처리 위치(region)는 다르다**는 점이 이 조사의 핵심입니다. 요청이 가까운 곳으로 들어가도 모델은 먼 곳에서 돌 수 있고, 지연은 후자가 정합니다.

(2026-11-05 추가) A/B를 위해 AWS 계정을 준비하며 Bedrock을 부르기까지 계정 플랜, 리전, 조직 정책(SCP), 모델 사용 신청에서 차례로 막혔습니다. 그 과정과 인증·권한 이론은 [16장](16-cloud-accounts-iam.md)에 있습니다. `jp.`와 `global.` 프로필의 차이는 [16-6절](16-cloud-accounts-iam.md#16-6-bedrock에서만-쓰는-개념)에 있습니다.

- (2026-11-06 추가) **12회 요약으로 무엇을 믿을 수 있나**는 13-6절 깊이 보기에서 따져 봅니다. 요지는 "중앙값이 줄었다는 방향은 요약만으로도 꽤 확실하지만, 0.1초라는 크기는 넓게 봐야 하고, 원 값을 남겨야 다시 따질 수 있다"입니다.

  - Haiku 5.5끼리, 운영 경로(`VoiceAnthropicLLM` 옵션 포함)로 다시 재기. 옵션을 Bedrock이 받는지부터 확인합니다(8-8절).

### 즉시 반응 미리 합성 (2026-11-03 갱신: 구현됨)

[5-poc-results.md](../5-poc-results.md)의 즉시 반응 측정도 남은 과제로 "즉시 반응 음성을 미리 합성해 두거나, 반응 종류를 늘린다"를 적었습니다. 즉시 반응은 세 문장뿐이고 매번 같습니다. 통화 시작 때 한 번 합성해 오디오 프레임 배열로 저장해 두고, `say()`에 오디오를 직접 넘기면 TTS 왕복이 사라집니다. SDK의 `session.say(text, { audio })`는 `audio`에 `ReadableStream<AudioFrame>`을 받습니다(`voice/agent_session.ts`).

이 아이디어가 코드에 [src/ack-audio.ts](../../src/ack-audio.ts)로 들어갔습니다.

```ts
export class AckAudioCache {
  #frames = new Map<string, AudioFrame[]>();

  async preload(engine: tts.TTS): Promise<void> {
    await Promise.all(                         // 세 문장을 동시에 합성
      ACKS.map(async (text) => {
        try {
          const frames: AudioFrame[] = [];
          for await (const audio of engine.synthesize(text)) frames.push(audio.frame);
          if (frames.length) this.#frames.set(text, frames);
        } catch (error) {
          log().warn({ error, text }, '즉시 반응 음성을 미리 만들지 못했습니다');   // 실패해도 통화는 계속
        }
      }),
    );
  }

  audio(text: string): ReadableStream<AudioFrame> | undefined {
    const frames = this.#frames.get(text);
    return frames ? ReadableStream.from(frames) : undefined;   // 꺼낼 때마다 새 스트림
  }
}
```

```ts
// src/main.ts: 첫 멘트와 동시에 미리 합성 시작 (기다리지 않음)
const ackAudio = new AckAudioCache();
void ackAudio.preload(tts);

// src/agent.ts: 준비된 소리가 있으면 넘기고, 없으면 평소처럼 합성
const audio = ackAudio?.audio(ack);
ctx.agent.session.say(ack, { ...(audio ? { audio } : {}), addToChatCtx: false, allowInterruptions: true });
```

볼 점입니다.

| 설계 | 이유 |
| --- | --- |
| `synthesize()` (비스트리밍) | ElevenLabs 플러그인의 `synthesize()`는 웹소켓이 아니라 **HTTP 요청 한 번**으로 문장 전체를 합성합니다(`ChunkedStream`). 대화용 웹소켓 연결(10-3절)과 따로 돌아 첫 멘트 합성을 방해하지 않습니다 |
| `void preload(...)`, 기다리지 않음 | 미리 합성(약 1초)을 기다리면 첫 멘트가 늦어집니다. 첫 턴 전에 끝날 가능성이 높으니 병렬로 둡니다 |
| 준비 안 됐으면 `undefined` → 평소 합성 | **점진적 개선**. 캐시가 비어도 기능은 그대로이고 빨라지기만 합니다 |
| 실패를 삼키고 로그 | 즉시 반응은 "있으면 좋은" 기능이라 실패가 통화를 막으면 안 됩니다(1장 원칙 5) |
| 꺼낼 때마다 `ReadableStream.from(frames)` | 스트림은 한 번 읽으면 끝나므로(12장), 원본은 배열로 두고 매번 새 스트림을 만듭니다 |
| `...(audio ? { audio } : {})` | `exactOptionalPropertyTypes` 때문에 쓰는 조건부 스프레드(15-1절) |

기대 효과는 "고객 말 끝 → 첫 소리"에서 TTS 첫 음성(약 0.17초)이 빠져 **말 끝 판단 시간만 남는 것**입니다. 턴마다 TTS를 부르지 않으니 비용도 줄어듭니다. 실측은 아직 없습니다. 미리 합성한 소리는 `ttsTextTransforms`를 거치지 않지만, 즉시 반응에는 제품명이 없어 상관없습니다.

### 지연 기록에 섞이는 값 (2026-11-04 갱신: 고침)

[src/call-result.ts](../../src/call-result.ts)는 통화마다 구간별 지연을 모아 통화 결과로 보내고, 관리 화면은 그 **평균**을 보여 줍니다(15-6절). 13-3절의 메트릭 정의를 떠올리면, 이 기록에 의도와 다른 값이 섞였습니다. 같은 날 코드로 확인하고 고쳤습니다(17-2 #20).

| 섞이던 값 | 이유 | 대응 (지금 코드) |
| --- | --- | --- |
| **`-1`** (첫 토큰·첫 음성이 나오기 전에 취소된 시도) | SDK는 첫 토큰이 없으면 `ttftMs`·`ttfbMs`에 `-1`을 넣음(`llm/llm.ts`, `tts/tts.ts`). `Math.round(-1)`도 숫자라 그대로 쌓이고, 받는 쪽 검사도 통과함 → **화면 평균이 실제보다 낮게** 나옴 | **0 미만은 뺌.** SDK도 자기 텔레메트리에서는 `ttftMs >= 0`일 때만 씀 |
| 취소된 시도의 지표 (`cancelled: true`) | 선제 생성이 버려지거나(11-4절) 끼어들기로 생성이 끊겨도 지표가 나옴. 첫 토큰까지 나온 뒤 취소됐으면 값은 정상 | **남김.** 값은 실제로 잰 시간임. 빼면 느린 턴이 골라서 빠짐 (아래 "무엇을 빼면 안 되나") |
| 선제 생성의 TTFT 기준점 | 턴 확정 전부터 잰 값이라 체감보다 길게 보임 | 해석할 때 감안. 체감은 `e2eLatency`로. (2026-11-06 갱신) 단 `e2eLatency`는 본 답 기준이고 양 끝 네트워크가 빠진 하한이며, 지금은 기록하지 않음(13-3절) |
| 미리 합성 3건의 TTS 지표 | 세션은 TTS 객체의 `metrics_collected`를 구독하는데, `preload`도 **같은 TTS 객체**로 합성했음. 세션이 구독을 시작한 뒤에 끝난 미리 합성은 통화 초반 `ttsTtfbMs`에 들어감. 디버거 로그로 보니 **3건 모두** 첫 멘트보다 먼저 들어갔고, 셋을 한꺼번에 요청해 첫 음성이 약 1.1초로 평소 답(약 0.2초)보다 훨씬 길었음 → TTS 평균을 **높이는** 쪽 | **미리 합성용 TTS 객체를 따로 만듦** ([src/main.ts](../../src/main.ts)). 세션이 구독하지 않는 객체라 처음부터 섞이지 않음. 다 만든 뒤 닫음. 고친 뒤 디버거 로그에는 첫 멘트·첫 질문의 2건만 남음 |
| 즉시 반응과 본 답의 TTS | 둘 다 TTS 지표로 잡힘 | 미리 합성이 되면 즉시 반응 몫은 사라짐. 미리 합성이 끝나기 전 첫 턴에만 남을 수 있음 |

```ts
// src/call-result.ts
export function addLatency(latency: CallLatency, metric: metrics.AgentMetrics): void {
  const add = (list: number[], ms: number) => {
    if (ms >= 0) list.push(Math.round(ms));   // -1(값 없음)만 뺌
  };
  if (metric.type === 'eou_metrics') add(latency.endOfUtteranceMs, metric.endOfUtteranceDelayMs);
  if (metric.type === 'llm_metrics') add(latency.llmTtftMs, metric.ttftMs);
  if (metric.type === 'tts_metrics') add(latency.ttsTtfbMs, metric.ttfbMs);
}
```

미리 합성은 **거르지 않고 처음부터 섞이지 않게** 했습니다. 걸러 내려면 "이 지표가 미리 합성에서 나왔나"를 지표만 보고 알아야 합니다. SDK는 발화 안에서 나온 지표에 `speechId`를 붙이므로, `speechId`가 없는 TTS 지표를 빼는 방법도 있었습니다. 하지만 이 방법은 SDK 안의 실행 문맥 전달(`AsyncLocalStorage`)에 기댑니다. 그 동작이 바뀌면 TTS 기록이 통째로 비어도 알아채기 어렵습니다. 따로 만든 객체는 세션이 아예 구독하지 않으니, SDK 안쪽 동작과 상관없이 성립합니다. ElevenLabs의 `synthesize()`는 HTTP로 따로 요청해 세션의 웹소켓 연결을 쓰지 않으므로, 객체를 나눠도 연결 예열을 잃지 않습니다(플러그인 `tts.ts`).

#### 무엇을 빼면 안 되나: 중도 절단과 생존자 편향

처음에는 `cancelled: true`인 지표도 빼려고 했습니다(이 절의 이전 판). 다시 보니 그러면 기록이 거꾸로 틀어집니다.

- LLM이 느리면 고객이 침묵을 못 견디고 다시 말합니다("여보세요?"). 그러면 진행 중이던 생성이 취소됩니다.
- 즉 **느린 턴일수록 `cancelled`가 됩니다.** 이것을 빼면 빠른 턴만 남아 평균이 실제보다 좋아 보입니다. 끝까지 살아남은 것만 보고 판단하는 **생존자 편향**입니다.
- 취소됐어도 첫 토큰이 나온 뒤라면 그 `ttftMs`는 실제로 잰 시간입니다. 버릴 이유가 없습니다.

`-1`도 같은 성질이 있습니다. 첫 토큰이 나오기 전에 취소됐다는 것은 "TTFT가 적어도 취소될 때까지보다 길다"는 뜻입니다. 통계에서는 이런 관측을 **중도 절단(censoring)**이라고 부릅니다. 값은 모르지만 "어느 값보다 크다"는 정보는 있는 관측입니다.

- `-1`을 그대로 평균에 넣는 것은 "아주 빨랐다"로 읽는 셈이라 가장 나쁩니다.
- 빼는 것은 그보다 낫지만, 가장 느린 시도 일부가 빠지므로 여전히 평균을 조금 낮춥니다.
- 제대로 하려면 "값 없음"의 건수를 따로 세어야 합니다. 그러려면 originalshq와 맞춘 기록 모양(`CallLatency`, 4-3절 계약)을 바꿔야 해서 이번에는 하지 않았습니다. 대신 원래 값은 모두 `metrics.logMetrics` 로그에 남습니다.

같은 기록에 섞이던 값이라도 기울이는 방향이 서로 달랐다는 점도 눈여겨볼 만합니다. `-1`은 평균을 낮추고, 미리 합성 3건은 높였습니다. 두 오류가 일부 상쇄되면 평균이 그럴듯해 보여서, 숫자만 보고는 섞인 것을 알아채기 더 어렵습니다.

"측정값에 표지값(sentinel, 여기서는 `-1`)이 섞여 있으면 평균이 조용히 틀어진다"는 것은 지표를 다룰 때 자주 만나는 함정입니다. `NaN`이나 `null`이었다면 바로 눈에 띄었을 텐데, `-1`은 평범한 숫자라 계산을 통과합니다. 그리고 표지값을 걸러 낼 때는 **무엇을 빼는지가 결과를 어느 쪽으로 기울이는지**를 같이 봐야 합니다.

## 13-6. 평균이 아니라 꼬리를 본다

[5-poc-results.md](../5-poc-results.md)의 Soniox 측정에서 5턴 중 3턴은 0.40초, 2턴은 1.26~1.29초였습니다. 평균은 0.75초로 그럭저럭 괜찮아 보이지만, **고객은 평균을 경험하지 않습니다.** 다섯 번 중 두 번 1.3초를 기다린 고객은 "가끔 굼뜨다"고 느낍니다.

그래서 지연은 **백분위수**로 봅니다.

| 지표 | 의미 |
| --- | --- |
| p50 (중앙값) | 보통의 경험 |
| p90, p95 | **열 번에 한 번, 스무 번에 한 번**의 나쁜 경험 |
| 최댓값 | 최악의 경험 (원인 분석용) |

finalize 패치의 진짜 가치는 평균을 조금 줄인 것이 아니라 **1초 넘는 꼬리를 없앤 것**("10턴 모두 0.38~0.54초")입니다. 측정 표본이 작을 때는 평균 대신 **범위(최소~최대)**를 적는 [5-poc-results.md](../5-poc-results.md)의 방식이 꼬리를 보여 주는 좋은 습관입니다.

#### 깊이 보기: 백분위를 손으로 — 12회의 p90은 몇 번째 값인가 (2026-11-06 추가)

직접 돌려 보기: [lab/13-percentiles.mjs](lab/13-percentiles.mjs) (4초 남짓, 키·네트워크 없음). 3·4번의 값은 모두 가상입니다.

**정의가 여럿입니다.** p 백분위수는 "값의 p만큼이 이보다 작거나 같은 값"이지만, 표본이 유한하면 어느 값을 고를지 정의가 여러 가지입니다. A/B 도구 [scripts/compare-llm.ts](../../scripts/compare-llm.ts)의 식은 이렇습니다(66~69행, 코드로 확인).

```ts
const percentile = (values: number[], p: number) => {
  const sorted = [...values].sort((a, b) => a - b);
  return Math.round(sorted[Math.min(sorted.length - 1, Math.floor(sorted.length * p))]!);
};
```

0부터 센 `floor(n·p)`번 칸, 곧 1부터 세면 floor(n·p) + 1번째 값 하나를 고르고 보간하지 않습니다. 정렬한 값의 몇 번째인지로 쓰면 이렇습니다(실습 1번).

| n | p50 | p90 | p95 |
| --- | --- | --- | --- |
| 10 (compare-llm 기본값) | 6번째 (위쪽 중앙값) | **10번째 = 최댓값** | 10번째 = 최댓값 |
| 12 (2026-11-05 A/B) | 7번째 | 11번째 (두 번째로 느린 값) | 12번째 = 최댓값 |
| 20 | 11번째 | 19번째 | 20번째 = 최댓값 |

비교하면 **가장 가까운 순위**(ceil(n·p)번째)는 12회에서 p50 = 6번째, p90 = 11번째이고, **선형 보간**(R-7. 스프레드시트의 PERCENTILE.INC와 같은 방식)은 (n − 1)·p + 1 = 6.5번째, 10.9번째입니다. 10.9번째는 10번째 값과 11번째 값 사이를 9 : 1로 나눈 점입니다. 가상의 12개로 보면 이렇습니다.

```text
예시 12개 (가상, ms, 정렬됨): 612 640 655 671 688 702 719 735 760 798 905 1340
  p50: compare-llm 719  가까운 순위 702  보간 710.5
  p90: compare-llm 905  가까운 순위 905  보간 894.3
  평균 768.8 (튄 값 1,340 하나가 평균을 58.3ms 끌어올림)
```

- 표본이 작으면 p90은 "열 번에 한 번"이라기보다 **느린 쪽 한두 개의 값**입니다. 10회의 p90은 최댓값이라 한 번 튄 값이 그대로 p90이 됩니다. [8-9절](08-llm.md#ab-도구-compare-llm-2026-11-05-추가)의 "10~12회면 p90은 사실상 두 번째로 느린 값"은 12회에서만 맞습니다.
- 이 절 처음의 Soniox 5턴(0.40 ×3, 1.26, 1.29)에 같은 식을 쓰면 p50 = 3번째 = 0.40초, p90 = 5번째 = 1.29초입니다. 평균 0.75초보다 p90이 "가끔 굼뜨다"는 경험에 가깝습니다.
- 비교는 **같은 정의끼리** 합니다. 관리 화면의 평균(15-6절), compare-llm의 floor 칸, 스프레드시트의 보간은 같은 원 값에서 다른 숫자를 냅니다. 2026-11-05 A/B는 임시 스크립트로 쟀으므로(8-9절) 같은 식이었는지는 기록이 없습니다.

**꼬리 증폭.** 한 통화는 턴 여러 개입니다. 턴마다 서로 독립으로 q의 확률로 느리다면, T턴 통화가 적어도 한 번 느린 턴을 겪을 확률은 1 − (1 − q)^T입니다(실습 2번).

```text
        q \ T       1      5      8     15     30
       0.01     1.0%   4.9%   7.7%  14.0%  26.0%
       0.05     5.0%  22.6%  33.7%  53.7%  78.5%
       0.10    10.0%  41.0%  57.0%  79.4%  95.8%
       0.20    20.0%  67.2%  83.2%  96.5%  99.9%
```

- 턴의 10%가 느리고 통화가 15턴이면 1 − 0.9^15 ≈ 0.794, 곧 **통화의 약 79%가 적어도 한 번 느린 턴을 겪습니다.** 통화당 느린 턴의 기댓값은 q·T = 1.5개입니다.
- 거꾸로 "통화의 90%가 느린 턴 없이" 끝나려면 턴당 q ≤ 1 − 0.9^(1/15) ≈ 0.7%, 곧 **턴의 p99.3**이 목표 아래여야 합니다. 턴 단위 p90을 보고 안심하면 안 되는 이유입니다.
- 이 계산은 턴끼리 독립이라고 가정합니다. 실제로는 서버가 붐비는 때 느린 턴이 몰리므로(양의 상관), 느린 턴을 겪는 통화 수는 이 표보다 적고 겪은 통화는 여러 번 겪을 것입니다(추정).
- 이 프로젝트에서 가장 큰 "느린 턴" 후보는 말 끝 판단의 2.5초 대기입니다(#39). 영업 통화는 "네." 대답이 많아 q가 작지 않을 수 있습니다.

**구간 p95의 합은 한 턴의 p95가 아닙니다.** 평균은 더해집니다(기댓값의 선형성). 백분위는 더해지지 않습니다. 실습 3번은 가정한 분포(말 끝 판단 380~540ms에 고르게, LLM 첫 토큰은 중앙 800ms, TTS 첫 음성은 중앙 170ms의 로그정규 분포)로 가상의 턴 100,000개를 만들어 더했습니다.

```text
(a) 말 끝 판단이 늘 확신            구간 p95의 합 1790 vs 한 턴 p95 1675 (차 115ms)   평균: 460 + 809 + 173 = 1442 = 한 턴 평균 1442
(b) 8% 턴에서 말 끝 2.5초 대기       구간 p95의 합 3760 vs 한 턴 p95 3434 (차 326ms)   말 끝 판단의 p95 = 2500
```

- 세 구간이 독립이면 셋이 **동시에** 자기 p95를 넘을 확률은 0.05³ 정도로 작습니다. 그래서 p95를 더하면 한 턴의 p95보다 큽니다. 세 구간이 늘 함께 느리면(완전한 양의 상관) 그때만 p95가 정확히 더해집니다. 실제는 그 사이입니다.
- (b)처럼 한 구간이 봉우리 둘이면 그 구간의 p95(2,500ms)가 한 턴의 p95를 거의 정합니다. **중앙값은 가장 큰 구간이, 꼬리는 가장 꼬리가 긴 구간이 정합니다.** 13-2절의 "가장 큰 구간부터"는 중앙값의 이야기입니다.
- 그래서 한 턴의 꼬리는 구간 메트릭을 더해서 구하지 않고, 한 턴 전체를 덮는 값(`e2eLatency`)의 분포에서 바로 셉니다.

**0.11초 차이는 우연인가.** 2026-11-05 A/B(13-5절)는 p50 0.77 → 0.66초를 "턴마다 약 0.1초"로 읽었습니다. 12회씩의 표본으로 이 차이를 믿어도 되는지 묻는 방법은 이렇습니다.

| 방법 | 묻는 것 | 필요한 것 |
| --- | --- | --- |
| 순열 검정 (중앙값 차) | 두 경로가 같다면, 24개를 아무렇게나 12·12로 다시 나눠도 이만한 중앙값 차가 얼마나 자주 나오나 | 회차별 원 값 |
| Mann–Whitney U | 144짝(12 × 12) 가운데 한쪽 값이 더 작은 짝이 몇 개인가 | 회차별 원 값 |
| 부트스트랩 | 원 값을 복원 추출로 다시 뽑을 때 중앙값 차가 얼마나 흔들리나(구간) | 회차별 원 값 |
| 짝지은 부호 검정 | 번갈아 부른 회차끼리 짝지을 때 B가 빠른 쌍이 몇 개인가 | 회차 순서까지 |

[5-poc-results.md](../5-poc-results.md)에는 요약(p50·p90·최소)만 있고 회차별 원 값이 없습니다. 그래서 실제 검정은 할 수 없고, 실습 4번은 **그 요약에 똑같이 맞는 가상 원 값**을 만들어 "요약만으로 어디까지 말할 수 있나"를 봤습니다(그날도 compare-llm의 식으로 요약했다고 가정).

```text
분리가 큰 경우  중앙값 차 116.5ms 순열 p = 0.0145 / U = 130/144 순열 p = 0.0004 / 부트스트랩 95% 구간 [101.5, 243.5]ms
겹침이 큰 경우  중앙값 차  98.5ms 순열 p = 0.0036 / U =  92/144 순열 p = 0.2708 / 부트스트랩 95% 구간 [-43.0, 121.5]ms
무작위 1,000벌  중앙값 차 102.0~152.5ms, 중앙값 차 순열 p 0.0010~0.0360 (0.05 이상 0벌), U 순열 p 0.0010~0.1399 (0.05 이상 15벌)
```

- **요약이 이미 많은 것을 말합니다.** compare-llm의 식이면 Bedrock의 7번째 값(p50 0.66초)까지 7개가 Anthropic의 최솟값(0.74초)보다 모두 작습니다. 그래서 "중앙값이 다르다"는 원 값이 어떻든 순열 검정에서 p < 0.05였습니다(무작위 1,000벌과 손으로 만든 두 극단).
- **"분포 전체가 다르다"(U)는 원 값에 따라 갈립니다.** 요약에 맞는 U는 92~130만 가능합니다(손 계산: Bedrock의 아래 7개 × Anthropic 12개 = 84짝은 늘 들어가고, 나머지 60짝 중 8~46짝이 더 들어감). 양쪽 유의수준 0.05의 경계(12·12면 U ≤ 37 또는 U ≥ 107)가 이 범위 한가운데를 지나므로, p는 0.0004부터 0.27까지 갈렸습니다.
- **차이의 크기는 더 불확실합니다.** 부트스트랩 구간이 원 값에 따라 [−43, 122]ms부터 [102, 244]ms까지 달랐습니다. 표본 12개의 중앙값 부트스트랩은 거친 방법이라 구간 자체도 참고용입니다. 그래서 "약 0.1초 줄었다"는 **방향은 믿을 만하고 크기는 넓게** 봐야 합니다.
- 짝지은 부호 검정은 손으로 됩니다. 12쌍 중 B가 빠른 쌍이 10개면 양쪽 p = 2 × (C(12,10) + C(12,11) + C(12,12)) ÷ 2^12 = 2 × (66 + 12 + 1) ÷ 4,096 ≈ 0.039, 9개면 0.146입니다(실습 끝 줄). 번갈아 부른 설계(8-9절)의 장점을 살리는 검정인데, 회차 순서가 남아 있어야 합니다.
- 어느 검정이든 "그날 그 시간대 12회 안에서"의 결론입니다. 다른 날·다른 혼잡에서도, Haiku 5.5와 운영 경로에서도 같은지는 다시 재야 압니다(13-5절의 남은 확인 세 가지).

**제안 (scripts/는 고치지 않음).** `compare-llm`이 요약과 함께 **회차 순서대로 원 값**(공급자, 회차, 첫 토큰 ms, 같은 공급자의 직전 호출 이후 경과 ms)을 출력하고 poc-results에 그대로 남기면, 위 검정을 언제든 다시 할 수 있고 연결 재사용 여부(4초)도 함께 볼 수 있습니다. 검정 방법은 재기 **전에** 정해 둡니다. 결과를 보고 고르면 유의한 쪽을 고르게 되기 때문입니다.

