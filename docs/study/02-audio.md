# 2장. 소리를 데이터로 — 디지털 오디오의 기초

음성 에이전트가 다루는 원재료는 "소리"입니다. STT, VAD, 턴 감지, TTS, 노이즈 제거가 모두 같은 형식의 데이터를 주고받습니다. 이 장에서는 그 데이터가 무엇인지, 왜 그런 모양인지를 다룹니다. 이후 장에서 "16kHz 프레임", "8kHz 전화 음질", "20ms 패킷" 같은 말이 나올 때 이 장의 내용이 바탕이 됩니다.

---

## 2-1. 소리는 공기의 압력 변화다

소리는 공기 분자가 밀렸다 당겨졌다 하는 **압력의 파동**입니다. 마이크는 이 압력 변화를 전압 변화로 바꿉니다. 이 전압은 시간에 따라 연속적으로 변하는 **아날로그 신호**입니다.

소리를 설명하는 두 가지 축이 있습니다.

| 축 | 뜻 | 사람이 느끼는 것 |
| --- | --- | --- |
| **주파수** (Hz) | 1초에 몇 번 진동하는가 | 음높이. 낮으면 굵은 소리, 높으면 가는 소리 |
| **진폭** | 압력 변화가 얼마나 큰가 | 크기(음량). 보통 데시벨(dB)로 표시 |

사람 목소리는 여러 주파수가 섞인 복합음입니다.

- **기본 주파수(F0)**: 성대가 떨리는 속도입니다. 남성 약 85~180Hz, 여성 약 165~255Hz입니다. 말의 억양(올라가고 내려가는 음높이)이 바로 이 F0의 변화입니다. 7장에 나오는 "억양으로 말 끝을 판단하는 턴 감지 모델"은 이 F0의 움직임을 봅니다.
- **포먼트(formant)**: 입 모양과 혀 위치에 따라 강해지는 주파수 대역입니다. "아"와 "이"를 구분하는 정보가 여기에 있습니다. 대략 300Hz~3,500Hz에 몰려 있습니다.
- **마찰음·파열음 성분**: "ㅅ", "ㅆ", "ㅊ" 같은 소리는 4,000Hz 이상 높은 대역에 에너지가 많습니다.

이 사실이 뒤에서 아주 중요해집니다. **전화는 3,400Hz 위를 잘라 버리기 때문에** "ㅅ"과 "ㅆ", "에프(F)"와 "에스(S)" 같은 소리를 구분하기 어려워집니다.

## 2-2. 샘플링: 연속을 띄엄띄엄 재기

컴퓨터는 연속 신호를 그대로 저장할 수 없습니다. 그래서 **일정한 간격으로 값을 재서 숫자로 적습니다.** 이것이 샘플링(표본화)입니다.

```text
아날로그 파형                       샘플링 (점마다 숫자 하나)
   ╭─╮       ╭─╮                     •       •
  ╱   ╲     ╱   ╲                  •   •   •   •
 ╱     ╲   ╱     ╲               •       •       •
        ╲_╱       ╲_            ─────────────────────▶ 시간
                                 간격 = 1 / 샘플레이트
```

- **샘플레이트(sample rate)**: 1초에 몇 번 재는가. 단위는 Hz.
  - 8,000Hz(8kHz): 1초에 8,000개의 숫자. 전통적인 전화.
  - 16,000Hz(16kHz): 음성 인식 모델 대부분이 학습에 쓰는 값. "광대역(wideband)" 음성.
  - 24,000Hz(24kHz): TTS 출력에 자주 쓰는 값.
  - 48,000Hz(48kHz): WebRTC(Opus)와 고품질 오디오의 표준.

### 나이퀴스트 정리 — 왜 8kHz면 4kHz까지만 담기는가

**나이퀴스트-섀넌 샘플링 정리**: 신호에 들어 있는 가장 높은 주파수를 *f*라고 하면, 샘플레이트가 **2*f*보다 커야** 원래 신호를 복원할 수 있습니다. 반대로 말하면 샘플레이트 *Fs*로 담을 수 있는 최대 주파수(나이퀴스트 주파수)는 *Fs*/2입니다.

| 샘플레이트 | 담을 수 있는 최대 주파수 | 음성에서 의미 |
| --- | --- | --- |
| 8kHz | 4kHz | 모음은 대부분 담기지만 "ㅅ", "ㅆ", "F/S" 구분 정보가 많이 잘림 |
| 16kHz | 8kHz | 말소리를 알아듣는 데 필요한 정보 거의 전부 |
| 48kHz | 24kHz | 사람 귀의 가청 한계(약 20kHz) 이상 |

나이퀴스트 주파수보다 높은 소리를 그대로 샘플링하면, 그 소리가 낮은 주파수로 "접혀서" 엉뚱한 소리로 섞입니다. 이것을 **에일리어싱(aliasing)**이라고 합니다. 그래서 샘플링이나 리샘플링 전에는 나이퀴스트 주파수 위를 잘라 내는 **저역 통과 필터(anti-aliasing filter)**를 먼저 겁니다.

### 리샘플링

부품마다 원하는 샘플레이트가 다릅니다. 이 프로젝트 한 통화 안에서도 여러 번 바뀝니다.

```text
고객 휴대폰 ─(8kHz G.711)─▶ 통신사 ─▶ Asterisk ─▶ LiveKit SIP
   ─(48kHz Opus)─▶ 에이전트 워커가 24kHz 모노 PCM으로 받음 (RoomIO 기본값)
                    ├─▶ 노이즈 제거 (24kHz 그대로)
                    ├─▶ VAD (16kHz로 내려서)
                    └─▶ Soniox STT (16kHz로 내려서 전송)
ElevenLabs TTS (22.05kHz PCM) ─▶ 워커가 24kHz로 맞춤 ─(48kHz Opus)─▶ LiveKit ─▶ … ─(8kHz)─▶ 고객 휴대폰
```

이 숫자들은 SDK 코드에서 확인한 기본값입니다. 워커는 방의 오디오를 24kHz 모노로 받고(`voice/room_io/room_io.ts`), Soniox 플러그인은 16kHz를 요구해서 코어가 리샘플한 뒤 보냅니다(`stt/stt.ts`의 `pushFrame`). ElevenLabs는 기본 출력 형식이 `pcm_22050`이라 출력 쪽에서도 한 번 변환합니다.

**중요한 직관:** 8kHz로 한 번 잘린 정보는 48kHz로 올려도 돌아오지 않습니다. 업샘플링은 숫자 개수를 늘릴 뿐, 사라진 4kHz 이상의 소리를 만들어 내지 못합니다. 그래서 전화 연결 단계에서는 브라우저 PoC보다 STT 정확도가 떨어질 가능성이 큽니다. [poc-results.md](../poc-results.md)가 "사람 목소리·전화 음질(8kHz)은 아니므로 실제 녹음 비교는 따로 해야 한다"고 적어 둔 이유입니다.

## 2-3. 양자화와 PCM: 값 하나를 몇 비트로 적나

샘플 하나의 크기를 몇 비트로 적을지 정하는 것이 **양자화**입니다.

- **16비트 정수(int16)**: -32,768 ~ 32,767. 음성 처리에서 가장 흔한 형식입니다.
- 비트 하나가 늘 때마다 표현할 수 있는 크기 범위(다이내믹 레인지)가 약 **6dB** 넓어집니다. 16비트면 약 96dB입니다.
- 너무 큰 소리가 들어와 최댓값을 넘으면 파형 꼭대기가 잘립니다(**클리핑**). 찢어지는 소리가 나고 STT 정확도가 떨어집니다.

이렇게 샘플들을 압축 없이 그대로 늘어놓은 형식을 **PCM(Pulse Code Modulation)**이라고 합니다. LiveKit Agents 안에서 오디오는 대부분 이 형식입니다.

```text
AudioFrame
├─ data: Int16Array        ← 샘플 값들 (채널이 여럿이면 번갈아 섞어 둠: L R L R ...)
├─ sampleRate: 48000       ← 1초에 샘플 몇 개
├─ channels: 1             ← 모노
└─ samplesPerChannel: 480  ← 이 프레임에 든 샘플 수 (채널당)
```

프레임 길이(시간)는 `samplesPerChannel / sampleRate`로 계산합니다. 위 예는 480 / 48,000 = **0.01초 = 10ms**입니다.

### 바이트 수 계산 연습

| 형식 | 1초 데이터 크기 |
| --- | --- |
| 16kHz, 16비트, 모노 PCM | 16,000 × 2바이트 = 32,000바이트 = 256kbps |
| 48kHz, 16비트, 모노 PCM | 96,000바이트 = 768kbps |
| 8kHz, 8비트 G.711 | 8,000바이트 = **64kbps** |

이 숫자 감각은 STT·TTS를 WebSocket으로 주고받을 때 대역폭을 가늠하는 데 씁니다. 16kHz PCM 실시간 전송은 초당 32KB 정도라 요즘 네트워크에서는 부담이 없습니다.

## 2-4. 프레임: 소리를 잘게 썰어 흘려보내기

실시간 시스템은 소리를 다 모았다가 처리하지 않습니다. **10~30ms 정도의 짧은 조각(프레임)으로 잘라 계속 흘려보냅니다.** 이유는 세 가지입니다.

1. **지연**: 조각이 길수록 그만큼 기다려야 다음 단계로 넘어갑니다. 100ms 조각을 쓰면 최소 100ms가 지연됩니다.
2. **네트워크 패킷**: 인터넷 전화는 보통 20ms 분량을 한 패킷에 담습니다(전화망의 `ptime=20`). 패킷 하나를 잃어도 20ms만 비고 끝납니다.
3. **모델 입력 단위**: VAD나 음성 특징 추출은 정해진 길이의 창(window)으로 계산합니다.

| 쓰임 | 흔한 프레임 길이 |
| --- | --- |
| WebRTC Opus 패킷 | 20ms |
| 전화망(RTP, G.711) | 20ms (`ptime`) |
| LiveKit 오디오 프레임 | 10ms 단위가 흔함 |
| Silero VAD 입력 창 | 16kHz에서 512샘플 = 32ms |
| 음성 인식 특징(멜 스펙트로그램) | 25ms 창, 10ms 간격 |

---

## 2-5. 코덱: 소리를 줄여서 보내기

PCM은 크기가 큽니다. 네트워크로 보낼 때는 **코덱**(coder-decoder)으로 압축합니다.

### G.711 — 전화망의 기본

- 1972년 ITU 표준입니다. 8kHz 샘플을 **8비트**로 줄여 64kbps로 보냅니다.
- 그냥 8비트로 자르면 작은 소리가 뭉개지므로, **작은 값은 촘촘하게 큰 값은 성기게** 적는 로그 압축(companding)을 씁니다. 사람 귀가 작은 소리 변화에 더 민감하다는 사실을 이용한 것입니다.
- 방식이 둘입니다: **μ-law**(북미·일본)와 **A-law**(유럽과 그 밖의 많은 지역). 어느 쪽을 쓰는지는 통신사 연동 규격서를 따릅니다([telephony-setup.md 3장](../telephony-setup.md#3-통신사에-요구할-것)).
- 압축 연산이 거의 없어 지연이 사실상 0이고, 어떤 장비든 지원합니다. 그래서 AI 음성 시스템과 통신사 연동의 공통분모입니다.
- **G.729**는 8kbps까지 줄이는 대신 음질이 더 나빠집니다. 음성 인식에는 불리해서 피합니다.

### Opus — 인터넷 음성의 표준

- 2012년 IETF 표준(RFC 6716)입니다. WebRTC의 필수 코덱입니다.
- 6kbps부터 510kbps까지, 협대역(8kHz)부터 전대역(48kHz)까지 상황에 맞게 바뀝니다.
- 프레임 길이를 2.5ms~60ms로 고를 수 있고 WebRTC는 보통 20ms를 씁니다.
- 패킷이 사라졌을 때 앞뒤 소리로 메꾸는 **패킷 손실 은닉(PLC)**, 다음 패킷에 이전 정보를 조금 덧붙이는 **FEC**가 들어 있습니다.

### 이 프로젝트에서의 경로

```text
[고객 휴대폰]──(G.711, 8kHz)──[통신사 SBC]──(G.711)──[Asterisk]
                                                    │ 코덱 변환
                                            [LiveKit SIP]──(Opus, 48kHz)──[에이전트]
```

에이전트 코드([src/main.ts](../../src/main.ts))는 코덱을 직접 다루지 않습니다. LiveKit이 Opus를 풀어 PCM 프레임으로 넘겨 주기 때문입니다. 하지만 **고객의 목소리가 어디서 몇 번 압축·변환을 거쳤는지**는 STT 품질을 해석할 때 꼭 알아야 합니다.

## 2-6. 지터와 지터 버퍼

인터넷은 패킷을 일정한 간격으로 배달해 주지 않습니다. 20ms마다 보낸 패킷이 15ms, 40ms, 5ms 간격으로 도착하기도 하고 순서가 뒤바뀌기도 합니다. 이 도착 간격의 흔들림을 **지터(jitter)**라고 합니다.

받는 쪽은 패킷을 바로 재생하지 않고 잠깐 모아 두었다가 순서를 맞춰 일정한 속도로 꺼냅니다. 이 대기열이 **지터 버퍼**입니다.

- 버퍼가 길면 → 끊김은 줄지만 **지연이 늘어납니다.**
- 버퍼가 짧으면 → 지연은 짧지만 늦게 온 패킷을 버리게 되어 **소리가 끊깁니다.**
- 그래서 WebRTC는 네트워크 상태를 보며 버퍼 길이를 계속 조절합니다(적응형 지터 버퍼).

음성 에이전트의 "응답 지연"을 잴 때 이 구간은 보통 계산에서 빠지지만, 실제 고객이 느끼는 지연에는 들어갑니다. 전화 연결 단계에서 체감 지연을 다시 재야 하는 이유 중 하나입니다([telephony-setup.md 8장](../telephony-setup.md#8-테스트-체크리스트)).

## 2-7. 잡음, 에코, 그리고 음성 향상

### 잡음(noise)

전화 상대는 차 안, 길거리, 공장에 있을 수 있습니다. 잡음은 모든 단계를 망칩니다.

- **VAD**: 잡음을 말소리로 착각하면 고객이 말하는 중이라고 판단해 AI가 끼어들기를 당하거나 턴이 끝나지 않습니다.
- **STT**: 잘못된 글자가 생기거나 없는 말을 지어냅니다(특히 무음·잡음 구간의 환각).
- **턴 감지**: 억양 정보가 묻힙니다.

### 에코(echo)

AI가 하는 말이 고객 휴대폰 스피커로 나와 다시 마이크로 들어오면, AI는 **자기 목소리를 고객 말로 착각**할 수 있습니다. 스피커폰으로 받을 때 특히 심합니다. 휴대폰과 브라우저(WebRTC)에는 **AEC(음향 에코 제거)**가 들어 있어 대부분 단말에서 걸러지지만, 완벽하지 않습니다. AI가 말하는 동안 들어오는 소리를 "끼어들기"로 볼지 판단하는 7장의 내용과 직결됩니다.

### 신경망 음성 향상

전통적인 잡음 제거는 "잡음의 주파수 모양"을 추정해 빼는 신호 처리(스펙트럼 차감, 위너 필터)였습니다. 요즘은 **신경망이 깨끗한 목소리만 남기도록 학습**합니다. 학습 데이터는 "깨끗한 음성 + 잡음"을 인공으로 섞어 만들고, 모델은 섞인 소리에서 원래 음성을 복원하는 법을 배웁니다.

더 나아가 **다른 사람 목소리까지 지우는 모델**(배경 음성 제거, voice isolation)도 있습니다. 옆자리 사람 말소리, TV 소리를 "주 화자가 아니다"라고 판단해 지웁니다.

**이 프로젝트에서는** 스타터 기본값인 ai-coustics의 QUAIL 모델을 입력에 겁니다.

```ts
// src/main.ts
inputOptions: {
  noiseCancellation: audioEnhancement({ model: EnhancerModel.QuailVfS }),
},
```

SDK와 플러그인 코드를 따라가면 동작 방식은 다음과 같습니다.

- `audioEnhancement()`는 rtc-node의 **FrameProcessor**(프레임을 받아 프레임을 돌려주는 처리기)를 만듭니다. 세션이 고객 트랙을 `AudioStream(24kHz, 모노)`으로 열 때 이 처리기를 끼웁니다(`voice/room_io/_input.ts`).
- 실제 계산은 플러그인에 들어 있는 **Rust 네이티브 코어가 워커 프로세스 안에서** 합니다. 소리를 클라우드로 보내지 않습니다. 다만 사용 인증은 방의 LiveKit Cloud 자격 증명으로 하므로, 자격 증명이 없으면 경고만 남기고 원본을 그대로 통과시킵니다.
- 모델은 여러 개입니다(`QuailL`이 기본값, 프로젝트는 `QuailVfS`). 이름의 `Vf`는 주 화자에 집중(Voice Focus), `S`는 작은 모델로 보이지만 패키지에 설명이 없어 추정입니다.
- 처리에 실패하면 원본 프레임을 통과시킵니다. **음성 향상이 고장 나도 통화는 끊기지 않게** 만든 설계입니다.

이 처리는 VAD·STT·턴 감지보다 **앞에서** 일어납니다. 그래서 여기서 소리를 깨끗하게 만들면 뒤의 모든 판단이 같이 좋아집니다. 반대로, 음성 향상 모델이 목소리 일부를 잘못 지우면 뒤의 모든 단계가 같이 나빠집니다. 전화 음질에서 어떤 모델이 나은지는 실측으로 정해야 합니다. LiveKit 문서는 SIP 참가자에게 전화용으로 조정된 모델(Krisp `TelephonyBackgroundVoiceCancellation`)도 안내합니다.

## 2-8. 소리를 "보는" 방법: 스펙트로그램

STT, VAD, 턴 감지 모델은 대부분 파형을 그대로 보지 않고 **스펙트로그램**으로 바꿔서 봅니다.

1. 소리를 25ms 정도의 창으로 자르고, 10ms씩 밀면서 반복합니다(창이 겹칩니다).
2. 창마다 **푸리에 변환(FFT)**으로 "어떤 주파수가 얼마나 강한가"를 계산합니다.
3. 결과를 시간(가로) × 주파수(세로) × 세기(색)로 늘어놓은 그림이 스펙트로그램입니다.

```text
주파수 ▲
 8kHz │      ░░        ▓▓            ← "ㅅ" 같은 마찰음은 높은 대역에 에너지
 4kHz │ ░    ░░  ░     ▓▓   ░
 2kHz │ ▓▓  ▒▒▒ ▓▓▓   ▒▒  ▓▓▓        ← 모음의 포먼트 띠
 1kHz │ ▓▓▓ ▓▓▓ ▓▓▓   ▓▓  ▓▓▓
  0Hz └──────────────────────────▶ 시간
        "안" "녕" "하"  "세" "요"
```

**멜 스케일(mel scale)**: 사람 귀는 낮은 주파수의 차이(100Hz vs 200Hz)는 잘 구분하지만 높은 주파수의 차이(7,000Hz vs 7,100Hz)는 잘 못 느낍니다. 그래서 주파수 축을 귀의 감각에 맞게 휘어 낮은 쪽을 촘촘하게, 높은 쪽을 성기게 나눈 것이 멜 스케일입니다. 여기에 로그를 씌운 **로그 멜 스펙트로그램**(보통 80개 대역)이 음성 인식 모델의 표준 입력입니다. Whisper 같은 모델도 이것을 입력으로 받습니다.

8kHz 전화 음성을 스펙트로그램으로 보면 **4kHz 위가 텅 비어** 있습니다. 16kHz로 학습한 모델에게 이 그림은 "평소와 다른 그림"이라서 정확도가 떨어집니다. 전화 전용 STT 모델(예: 리턴제로 `sommers_ko`의 전화 도메인)이 따로 있는 이유입니다([tech-stack.md 4-2](../tech-stack.md#4-2-stt-음성-인식)).
