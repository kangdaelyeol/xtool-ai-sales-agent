### 대화 품질 (텍스트, 판정 흐름 한 통화)

- 첫 멘트(고정 문장, AI·녹음 고지)부터 판정 질문 8개, 마무리 요약까지 끝까지 진행됐습니다.
- 질문은 한 번에 하나씩 묻고, 고객이 답한 것은 다시 묻지 않았습니다. 가격·할인은 상담사에게 넘겼고, 방문체험은 희망 일시만 받았습니다.
- **고칠 점:**
  - 한 번에 3~4문장으로 말할 때가 있습니다(지시는 한두 문장).
  - 마무리 요약이 한 문장으로 깁니다.
  - 통화 종료 도구가 없어 AI가 스스로 전화를 끊지 못합니다. 도구 단계에서 붙입니다.

### STT 제품명 인식 (Deepgram)

| 고객이 한 말 | STT 결과 |
|---|---|
| 에프투 울트라 | `F two 울트라` |
| 각인하려고요 | `가긴 하려고요` |
| 메탈팹 | `메탈 백`, `메탈팩` |

- 프롬프트로 "바로잡아 이해하라"고 해도 LLM이 틀린 이름을 맞장구로 따라 말했습니다(3/3회).
- 그래서 **LLM에 넘기기 전에 코드로 고칩니다** (`src/transcript.ts`, 표는 `src/glossary.ts`의 `MISHEARD_TERMS`). 음성 경로에서 "메탈팩" → "메탈팹" 보정을 확인했습니다.
- 텍스트 디버거와 텍스트 시뮬레이션은 STT를 거치지 않아 이 보정도 타지 않습니다. 단위 테스트로 확인합니다.
- **Soniox(`stt-rt-v5` + context.terms)와 같은 문장으로 비교해야 합니다.** STT 선택의 핵심 지표입니다.

### 턴 감지

- 고객이 두 문장을 말하며 사이에 쉬면, 첫 문장("…하려고요.")에서 턴이 끝났다고 보고 AI가 답을 시작했다가 끊기는 경우가 있었습니다.
- 문법적으로 끝난 문장이라 턴 감지 판단 자체는 이상하지 않습니다. 실제 마이크 통화(`lk agent console`)에서 자주 나오면 `turnHandling.endpointing.minDelay`(기본 0.5초)를 늘려 봅니다.
- 로그에 `VAD inference is slower than realtime` 경고가 두 번 나왔습니다. 맥에서 디버거 TTS와 같이 돌 때 생긴 것으로 보이며, 서버에서 다시 확인합니다.

## 2026-11-03 STT 비교 1차 (같은 문장 5개, `lk agent debugger --audio`)

문장은 디버거가 LiveKit Inference TTS로 읽어 에이전트 마이크에 넣습니다. 사람 목소리·전화 음질(8kHz)은 아니므로 실제 녹음 비교는 따로 해야 합니다.

| 말한 문장 | Deepgram `nova-3` 원문 | Soniox `stt-rt-v5` |
|---|---|---|
| 에프투 울트라로 가죽 지갑에 각인하려고요. | F two 울트라로 가죽 지갑에 각인하려고요. | F2 울트라로 가죽 지갑에 각인하려고요. |
| 메탈팹이랑 피쓰리도 같이 보고 있어요. | 메탈 팩이랑 P 3도 / Mecharpack이랑 P 3 | 메탈팹이랑 P3도 같이 보고 있어요. |
| 엑스툴 제품 중에 엠투나 오원도 괜찮나요? | 제품 중에 M two나 O one도 (엑스툴 빠짐) | 엑스툴 제품 중에 M2나 O1도 괜찮나요? |
| 예산은 이백구십만 원 정도고, 할부로 하고 싶어요. | 예산은 이 백 구 십 만 원 정도고 로 하고 싶어요. (**할부 빠짐**) | 예산은 2,900,000원 정도고, 할부로 하고 싶어요. |
| 다음 주 토요일 오후 세 시쯤 방문할게요. | 정확 | 다음 주 토요일 오후 3시쯤 방문할게요. |

- Deepgram 지연: 말 끝 판단 0.38~0.41초(첫 턴 1.13초). LLM 첫 토큰 0.86~1.86초.
- 보정표(`MISHEARD_TERMS`)에 P3·M2·O1의 영문 표기를 추가했습니다. "할부"처럼 **통째로 빠진 단어는 보정으로 살릴 수 없어** STT 선택으로 해결해야 합니다.
- 고친 버그: Soniox 플러그인도 import 시점에 `SONIOX_API_KEY`를 읽어 두어 키를 못 찾았습니다. 생성할 때 직접 넘기도록 고쳤습니다(`src/models/index.ts`).

- **Soniox는 5문장 모두 정확**했습니다. 제품명은 보정 전 원문부터 맞았습니다(`context.terms` 효과로 보임). 숫자는 아라비아 숫자로 적습니다.
- 대신 Soniox의 말 끝 판단이 더 느립니다: 0.57~1.42초 (Deepgram 0.38~0.41초). LLM 첫 토큰은 0.76~1.63초.
- **판단: 기본 STT는 Soniox로 유지.** 다음 과제는 Soniox 끝점 설정(`maxEndpointDelayMs`, `endpointLatencyAdjustmentLevel`) 조정으로 말 끝 판단을 0.5초 안팎으로 줄이는 것입니다.

## 2026-11-03 Soniox 말 끝 판단 줄이기

| 단계 | 말 끝 판단 (5턴) | 비고 |
|---|---|---|
| 기본 설정 | 0.57~1.42초 | |
| + `endpointLatencyAdjustmentLevel: 3`, 언어 자동 감지 끔 | 0.40초 ×3, 1.26·1.29초 ×2 | 느린 턴은 Soniox가 최종 결과를 늦게 보낸 것 (받아쓰기 확정 지연 1.26초) |
| **+ 말이 끝나면 수동 확정(`finalize`)** | **0.38~0.54초 (10턴 모두)** | 1초 넘는 턴이 사라짐 |

- 원인: LiveKit 코어는 VAD가 말 끝을 감지해도 STT에 알리지 않고, Soniox 플러그인은 flush 신호를 무시합니다.
- 해결:
  - 고객 상태가 speaking → listening으로 바뀌면 STT 스트림에 flush를 보냅니다 (`src/models/soniox.ts`, `src/main.ts`).
  - 플러그인 패치로 flush를 Soniox `{"type":"finalize"}` 요청으로 바꿉니다 (`patches/@livekit__agents-plugin-soniox@1.9.5.patch`).
- 정확도는 그대로였습니다. 10턴 중 1번 "피쓰리"를 `F3`로 적은 경우가 있어 지켜봅니다.
- **이제 병목은 LLM 첫 토큰입니다** (같은 측정에서 0.99~1.69초). 다음 과제입니다.
